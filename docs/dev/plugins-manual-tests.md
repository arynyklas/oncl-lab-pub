# Порты плагинов в окне ручных инструментов: сборка wasm и тесты

Тесты `crates/oncl-core/tests/plugin_ports_manual.rs` прогоняют настоящие wasm-модули портов (`plugins/<порт>`) через тот же путь ручного вызова `oncl-core`, что и окно инструментов, с синтетическим ключом. Устройство описано в [manual-plugins.md](../design/manual-plugins.md), список плагинов в [manual-plugins-inventory.md](../design/manual-plugins-inventory.md). Для каждой операции из `[[operations]]` тест проверяет, что вызов завершился `Applied`, что ответ порта разбирается в документированном виде и что подпись проходит независимую проверку. Если объявление расходится с тем, что модуль на самом деле передаёт в ключевой импорт, Core отвергает вызов (`options-mismatch`, до применения ключа). Поэтому успешный прогон подтверждает и само объявление.

## Одна команда

```text
cargo xtask plugin-ports-manual [--wasm-dir <каталог>] [--no-build] [фильтр…]
```

Команда выполняет три шага:
1. `cargo build --release --locked --target wasm32-unknown-unknown --workspace` в `plugins/` (результат в `target/plugin-build`). Сеть не нужна, если зависимости из `Cargo.lock` уже в кэше cargo. Сборка занимает около 35 с.
2. `plugin-ops-check --require-wasm`: импорты каждой операции сверяются с импортами модуля.
3. `cargo test -p oncl-core --features plugins --test plugin_ports_manual -- --ignored [фильтр…]` с `ONCL_PLUGIN_WASM_DIR`. Фильтр задаёт часть имени теста (`rating1c`, `network`).

Тесты помечены `#[ignore = "needs the built port wasm…"]`: без модулей они бессмысленны, а обычный `cargo test` не должен собирать 34 модуля. В CI они выполняются: задания `test` в `ci.yml` запускают все тесты с `--run-ignored all`, и если `ONCL_PLUGIN_WASM_DIR` не задан, тесты сами собирают `plugins/` в `target/plugin-ports` (как `oncl-port-tests`; профиль задаёт `ONCL_PORTS_PROFILE`, по умолчанию `plugin-test`). Импорты модулей проверяет `plugin-ops-check --require-wasm` в заданиях `linux-checks` (модули `plugin-test`) и `plugins-release` (модули `release`). Если модулей нет, тест падает с сообщением.

## Окружение

| Переменная | Что |
|---|---|
| `ONCL_PLUGIN_WASM_DIR` | Каталог с `oncl_port_<порт>.wasm` (`-` → `_`). Если не задана, тесты собирают `plugins/` сами (`oncl_testkit::plugin::ports_built`). |
| `ONCL_OPENSSL` | OpenSSL 3 с `cms` (иначе `openssl` в `PATH`, на Windows ещё Git for Windows). Независимая проверка CMS и сырой подписи. |
| `ONCL_PYHANKO_PYTHON` | Python с `lxml` и `cryptography` (иначе `python3`/`python`). Независимая проверка XML-DSig (`tests/support/oracle/xmldsig_verify.py`). Без нужного окружения тест падает. |

## Как проверяется подпись

* CMS: `oncl_pki::cms::verify` над одобренным документом (и отказ над другим документом), а также `openssl cms -verify -binary -noverify` над ним же (и отказ над другим). Сертификат подписанта в CMS должен быть сертификатом ключа, вложенное содержимое (attached) побайтно равно документу, метка времени проверяется по наличию `signatureTimeStampToken` в отчёте.
* raw: RSA PKCS#1 v1.5 SHA-256 проверяется открытым ключом сертификата кодом репозитория и командой `openssl pkeyutl -verify -rawin -digest sha256`.
* XML: `oncl_xml::verify` и `xmldsig_verify.py`. Скрипт на lxml выполняет каноникализацию, проверяет дайджест каждого `Reference` после его преобразований, подпись `SignedInfo` RSA-ключом сертификата и то, что сертификат в `KeyInfo` принадлежит ключу. Проверяется и структура: какой элемент подписан, куда вставлена подпись, совпадает ли документ без подписи с исходным. Изменённый документ скрипт обязан отвергнуть. ГОСТ-подписи скрипт не проверяет (`unsupported`), их проверяют только верификаторы репозитория.

## Общий код тестов (`tests/support/ports.rs`)

Подключается так: `#[path = "support/ports.rs"] mod ports;`.

```rust
run_port_operation(port, operation, params, &RunOptions) -> PortRun
try_run_port_operation(…) -> Result<PortRun, PluginPrepareError>
RunOptions { tamper: Option<Box<dyn Fn(&str) -> String>>, key: Option<&'static str> }   // RunOptions::tampered(op, from, to)
PortRun { call: ApprovedCall, summary: ConsentSummary, request: String, cert, applications, http_log }
assert_applied(&run) / assert_refused_before_the_key(&run) / reply_json(&run) / from_base64(..)
oracle::verify_cms(cms, content, &cert, attached) -> CmsFacts
oracle::verify_raw_rsa(&cert, data, signature)
oracle::verify_xml(signed, &cert, n) -> XmlFacts;  oracle::assert_xml_rejected(doc, &cert)
```

`run_port_operation` делает следующее:
1. Читает `plugins/<порт>/plugin.toml` и модуль и ставит их в `PluginRegistry` (`PackageHash::Loose` через `loose_package_hash`) с `ManualLimits::desktop()`, тем же определением, что использует рабочий стол (`oncl_core::plugins::ManualLimits`, см. ниже). `RunOptions.limits` подставляет другие лимиты.
2. Регистрирует политику объявленных операций `allow_declared_with_pki` с эндпоинтами `oncl_plugin::NCA_PKI_ENDPOINTS`. Эту же константу использует рабочий стол: GET и POST для OCSP и TSA (`DEFAULT_OCSP`, `DEFAULT_TSA`).
3. Готовит ключ: фикстура `user-rsa-sign`, сертификат перевыпущен временным корнем, в AIA указан OCSP-ответчик по умолчанию, ответчики OCSP и TSA заменены моками под тем же корнем, часы установлены на `NOW` фикстур.
4. Вызывает `plugin_prepare`, получает `ConsentSummary`, создаёт подтверждение через `UserConfirmation::after_user_confirmed` (публичный конструктор, которым пользуется и окно), затем `approve` и `plugin_call_approved`.

Со стороны плагина ничего не подменяется.

Негативный тест для каждого порта: `RunOptions::tampered(операция, "поле = значение", "поле = другое")` правит манифест, и вызов должен быть отвергнут с `options-mismatch` (`TicketRefusal::Options`), результатом `NotApplied` и неприменённым ключом.

## Как добавить порт

1. В `plugins/<порт>/plugin.toml` добавьте `[[operations]]` (формат описан в [plugins.md](../design/plugins.md)), `min_core` не ниже `operations_min_core()`, поднимите версию плагина в манифесте, `Cargo.toml` и `plugins/Cargo.lock`. Хеши в `plugins/workspace/registry.toml` не трогайте, их обновляют при выпуске.
2. Запрос в шаблоне должен точно совпадать с тем, что отправляет страница (см. инвентаризацию), а профиль с тем, что порт передаёт в ключевой импорт. В `imports` указывайте только реально вызываемые импорты: лишний отвергнет `plugin-ops-check`, а недостающий даст `Denied` при вызове. У любой операции с ключом должно быть `network = "pki"`.
3. Создайте файл `tests/plugin_ports_manual/<порт>.rs` и добавьте `mod` в `plugin_ports_manual.rs`: по положительному тесту с независимой проверкой на каждую операцию и негативный тест с `tampered`.
4. Запустите `cargo xtask plugin-ports-manual <порт>`.

## Лимиты рабочего стола (`ManualLimits::desktop()`)

Одно определение `oncl_core::plugins::ManualLimits` используют и рабочий стол (`crates/openncalayer/src/plugins/manual.rs`: `ManualLimits::desktop().instance` при установке каждого плагина), и тесты. Умолчания SDK остаются консервативными и не совпадают с этими значениями.

Замеры на реальных портах (отладочная сборка, лимиты с запасом, пики сняты временной инструментацией):

| операция | метаданные сверх `max_transfer` | линейная память гостя | ответ |
|---|---|---|---|
| `sign-xml`, `sign-xml-element` (1 КиБ…64 КиБ) | ≈ 65,0 МБ, от документа не зависит (XML ex и XAdES B/T/LT так же) | 1,2–1,7 МБ | 3,5–67 КБ |
| CMS и raw: 1 КиБ | 2,4 МБ | 1,2 МБ | 2,2–5,7 КБ |
| CMS и raw: 1 МиБ | 135 МБ | отделённая 9–11 МБ, с вложением 14,5 МБ | вложенная CMS 1,33 × документ |
| CMS и raw: 4 МиБ | 539 МБ | 32–40 МБ, с вложением 53 МБ | |
| CMS и raw: 12 МиБ | 1,61 ГБ | 98–123 МБ, с вложением 153 МБ | 16,0 МиБ |

* Метаданные CMS и raw равны `max_transfer` + 128 × документ + 2,2 МБ: каждый ключевой импорт допускает 128 байт метаданных на байт своих аргументов (`host_call_metadata`). У XML около 65 МБ уходит на проверку подписанного документа после подписи (`oncl_xml::verification_metadata_bound`), и от размера документа это не зависит.
* Память гостя не превышает 12,1 байта на байт документа (вложенная CMS) плюс 3 МиБ. Передаётся документ в base64 в запросе и 4/3 документа в ответе, поэтому 16 МиБ передачи не хватает на документ в 12 МиБ (ответ 16,0 МиБ).
* Кроме того, вызов резервирует `8 × max_transfer + max_memory` памяти и `max_transfer` метаданных (`call_scratch`). Метаданные учитываются и как память.

`manual_call_budget(лимиты, вид, длина, длина_текстовых_параметров)` суммирует всё это с запасом. Аргументы считаются как документ плюс все текстовые параметры вызова плюс 4 КиБ: опция `param:` может взять значение из любого из них, включая сам подписываемый XML-текст, поэтому он учитывается и как документ, и как текстовый параметр. К CMS и raw добавляется 4 МиБ, к XML граница `verification_metadata_bound` и 8 МиБ памяти. `Engine::plugin_prepare` и `plugin_call_approved` берут эти резервы из бюджета контекста и сразу отдают обратно, а при нехватке отказывают до применения ключа и до согласия с подкодом `resource-budget` (если для XML нет временного хранилища, подкод `no-temporary-store`).

### Выбор `max_document`

Бюджеты задают потолки учёта, а не выделенную память. Платформа обещает ограниченный объём ОЗУ, контрольный процесс укладывается в 1 ГиБ. Ниже измеренный пик рабочего набора процесса теста (psutil, отладочная сборка, весь тест с фикстурами и самим документом) при вложенной CMS документа максимального размера (`limits::the_attached_cms_of_the_largest_document_signs` с `ONCL_PORT_MAX_DOC_MIB`). Базовая линия на малом документе 20 МиБ.

| `max_document` (размер, под который считаются лимиты) | передача | линейная память | бюджет метаданных | бюджет памяти | резерв по модели вложенной CMS, `CmsEx` (память / метаданные; бюджеты считаются по самому большому вызову, `XmlEx`, поэтому метаданных в них больше) | пик рабочего набора | запас до 1 ГиБ по бюджету памяти |
|---|---|---|---|---|---|---|---|
| 2 МиБ | 5 МиБ | 60 МиБ | 384 МиБ | 512 МиБ | 374 / 266 МиБ | 62 МиБ | 2,0× |
| **4 МиБ** | 9 МиБ | 112 МиБ | **704 МиБ** | **896 МиБ** | 718 / 526 МиБ | 104 МиБ | 1,14× |
| 8 МиБ | 17 МиБ | 216 МиБ | 1280 МиБ | 1664 МиБ | 1406 / 1046 МиБ | 247 МиБ | бюджет 1,6 ГиБ > 1 ГиБ |
| 16 МиБ | 33 МиБ | 424 МиБ | 2368 МиБ | 3136 МиБ | 2782 / 2086 МиБ | 458 МиБ | бюджет 3,1 ГиБ, втрое выше |

На 64-битных системах выбрано 4 МиБ. Реальный рабочий набор укладывается в 1 ГиБ и при 16 МиБ (458 МиБ), но потолки учёта при 8 и 16 МиБ (1,6 и 3,1 ГиБ) больше бюджета машины, а модель «128 байт метаданных на байт» задана не нами. Поэтому выбран меньший предел документа с понятным отказом (`resource-budget` или `RequestTooLarge` у самого шаблона, до согласия). Форма операции принимает документ до объявленного в манифесте `max_bytes` (по умолчанию 16 МиБ), а рабочий стол отказывает выше своего предела. На 32-битных системах предел 512 КиБ: `oncl_plugin::MAX_MEMORY` там 16 МиБ (память гостя 12,1 × 0,5 МиБ + 3 МиБ ≈ 9 МиБ), передача 2 МиБ, бюджеты метаданных и памяти по 192 МиБ.

`max_document` не жёсткий предел, а размер, под который считаются лимиты. Принимает ли вызов документ, решает проверка по бюджету перед применением ключа. При 4 МиБ проходят документы примерно до 5,3 МиБ (вложенная CMS на 5 МиБ действительно подписывается). Форма на странице «Плагины» сужает объявленный в манифесте `max_bytes` до `ManualLimits::desktop().max_document`, чтобы отказ был виден ещё до выбора файла, а подпись под полем показывает действующий предел. Отказ по размеру документа возвращается как `InputLimit` (подкод `resource-budget`). Если бюджеты не вмещают даже модуль с пустым документом (движок настроен неверно), возвращается `MemoryLimit` с тем же подкодом.

Бюджеты 704 и 896 МиБ относятся к учёту одного движка и не выделяются: измеренный пик рабочего набора при 4 МиБ около 104 МиБ. У движка документов свой бюджет в 1 ГиБ. Сумма потолков двух движков больше 1 ГиБ, но реальной памяти сверх измеренной это не добавляет.

Движок окна плагинов должен брать `ManualLimits::desktop().resources` (со своим `operation_timeout`). С умолчаниями SDK любая XML-операция и любой CMS-документ крупнее примерно 0,4 МиБ отказываются с `resource-budget`. Страница плагинов (`oncl_ui::plugin_offer`, `engine_limits()`) так и делает. Движок документов (`main.rs`, `desktop_limits()`: 24 часа и умолчания бюджетов) плагинов не держит, и эти лимиты ему не нужны. Проверка бюджета не удерживает резерв после себя. Занять место между ней и применением ключа никто не может, потому что `max_in_flight = 1`. В сумму `manual_call_budget` входит и ответ модуля (`max_transfer` памяти), поэтому вызов с большой передачей и малым документом тоже учитывается.

Итоговые значения `ManualLimits::desktop()` на 64-битных системах: `max_document` 4 МиБ, `max_transfer` 9 МиБ, `max_memory` 112 МиБ, `metadata_bytes` 704 МиБ, `memory_bytes` 896 МиБ. Остальное берётся из умолчаний `ResourceLimits`. `operation_timeout` равен 5 минутам, а хост, который ждёт пользователя внутри операции, сам его удлиняет: `ResourceLimits { operation_timeout, ..ManualLimits::desktop().resources }`. `fuel` по умолчанию SDK. `ManualLimits::for_max_document` выводит всё из размера документа: передача = (4/3 документа + 16 КиБ) × 1,5, память = 2 × (13 × документ + 4 МиБ), но не выше `MAX_MEMORY`, бюджеты = `manual_call_budget` самого большого XML-вызова × 1,1, с округлением вверх.

Тесты лимитов:
- `limits::every_cms_and_raw_operation_signs_a_document_at_the_limit`: все четыре операции CMS и raw на документе в 4 МиБ, проверка через openssl и код репозитория;
- `the_estimate_signs_and_one_byte_less_is_refused_before_the_key`: все 7 операций подписывают ровно по модели, а на байт меньше метаданных или памяти дают `resource-budget` до ключа;
- `the_default_metadata_budget_refuses_an_xml_signature_before_the_key`;
- `a_document_over_the_limit_is_refused_before_the_key`;
- `an_engine_without_a_temporary_store_refuses_xml_before_the_key`.

Другие настройки, которые нужны для работы портов:

* `EngineServices::with_temporary_store` (для XML; без него `no-temporary-store` до ключа), `with_validation` (онлайн-проверка подписанта), `with_plugin_keys`. Временное хранилище окна создаётся как `TemporaryStore::new(spool)` в том же каталоге `data/spool`, что и у движка документов (`desktop_engine`: замок владельца и очистка устаревших файлов при старте).
* Эндпоинты `network = "pki"`: GET и POST для OCSP и TSA (`oncl_plugin::NCA_PKI_ENDPOINTS`). Подписанта проверяют GET-запросом к OCSP из сертификата, метку времени Kalkan тоже берут GET-запросом.
* Операция с `uses.key` без `network = "pki"` никогда не подписывает (`network.rs`).
* `StoreLimits` с `trap_on_grow_failure` не должен считать `MemoryLimit` случай, когда `memory.grow` не хватило топлива на конце отрезка: это возобновляемая ситуация. Иначе вызов портов падал бы в зависимости от длины документа (на 350 КБ падает, на 400 КБ нет, при любом `max_memory`). `GuestLimits` не считает `OutOfFuel` отказом роста, это проверяет тест `memory_growth_crossing_a_fuel_slice_is_resumed_not_a_memory_limit`.

Покрытые порты и операции:
- `rating1c`: 7 операций;
- `fhs`: `sign-xml`, `sign-text` (`args` передаётся объектом);
- `esf-osdkz`: `sign-plain-data` (корневой запрос, `raw` над текстом; Core отказывает на управляющих, bidi и невидимых символах);
- `energy`: 4 операции `sign-cms-*`;
- `eproc`: 2 операции;
- `efactoring`: 6 операций (`sign-text-*` ×4, `sign-xml`, `sign-xml-element`);
- `market`: 5 операций (`sign-text-*` ×4, `sign-xml`);
- `dogovor24`: `sign-cms`;
- `qiwi`: 2 операции, `sign-xml-rsa` и `sign-xml-gost2004`, по одной на алгоритм ключа. Подпись ГОСТ 2004 проверяет только `oncl_xml::verify`, скрипт на lxml знает только RSA.

Профили с `transforms` описаны в инвентаризации, тесты для них лежат в `qiwi.rs` и `efactoring.rs`. Общие таблицы негативных тестов (подмена профиля, удаление импорта) находятся в `plugin_ports_manual/wave3_kit.rs`.

## Чего эти проверки не доказывают

* Метка времени: проверяется наличие `signatureTimeStampToken` в CMS (отчёт `oncl_pki::cms::report`), но сам токен независимым инструментом не проверяется.
* ГОСТ: ключи ГОСТ проверяют только верификаторы репозитория, а `openssl` и `xmldsig_verify.py` работают только с RSA. Объявленные профили не фиксируют алгоритм (Core выбирает его по ключу), поэтому ключи ГОСТ не отсекаются. При ручной проверке операции с ними подписывали, но автоматического положительного теста с ГОСТ-ключом нет, и ГОСТ-подписи независимым инструментом не проверяются.
* `create-raw-sign` проверяется для RSA PKCS#1 v1.5 SHA-256.
* Независимая проверка XML отвергает неизвестные преобразования, неоднозначный `Id` (два элемента с одним `Id`) и подпись без ссылок (`the_xml_oracle_rejects_wrapping_shapes`).
* `sign-xml-element`: оба XPath (`tbs`, `parent`) абсолютные и вводятся текстом, у подписываемого элемента должен быть атрибут `Id`. Вариант оригинала «tbs с пустым parent» не покрыт: родитель обязателен (профиль `placement = parent` задаётся тогда и только тогда, когда задан `parent`). То же относится к `eproc.sign-xml-element` и к `rating1c` для `xml_ex`: сам порт принимает пустой родитель, а окно нет. У `eproc` тип ключа зафиксирован шаблоном (`keyType = SIGNATURE`), поэтому привязанный ключ типа AUTHENTICATION приведёт к ответу порта «action.canceled».

* `PluginRegistry::install` не ограничивает размер wasm (`MAX_WASM` = 16 МиБ проверяет только `Package::read`). Хост, который ставит модуль не из пакета, должен проверить размер сам.
