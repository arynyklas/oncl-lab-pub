# Наблюдатель за оригиналом

Наблюдатель следит за оригинальным NCALayer: версией и полями манифеста `ncalayer.der`, его подписантом, дистрибутивами, составом и содержимым бандлов ядра и плагинов, сертификатами в keystore и API байткода. Любое изменение не позже чем через 6 часов превращается в коммит фактов в ветке `upstream` этого репозитория и в issue с меткой `upstream`, `upstream-plugin` или `upstream-alert`.

## 1. Что публикуется и что нет

Публикуются только факты:

- поля манифеста НУЦ (`version`, `info`, `updurl`, `syspkgs`, `disturls`, бандлы со всеми полями, включая неизвестные новые), его sha256, размер, время подписи и подписант (sha256, серийный номер, субъект, издатель, срок);
- для каждого дистрибутива и бандла: URL (без одноразового ключа страницы загрузок), имя файла, размер, sha256, опубликованный на странице SHA-1, формат, состав файлов (путь, размер, sha256, вид), сведения о JRE (версия, поставщик, архитектура, число файлов, хеш дерева), метаданные установщиков (ключи `[Setup]` из разрешённого списка, значения реестра, файлы `[Run]`, `Info.plist`, смещение вложенного архива в `.sh`, версия Go и хеш вложенной программы лёгкого установщика, версии `tzdb.dat`);
- для каждого JAR: заголовки `MANIFEST.MF` из разрешённого списка, подписанты блоков подписи, хеш содержимого без файлов подписи, публичные и защищённые классы, методы и поля с дескрипторами, методы с аннотацией `NCALayerMethod`, имена модулей, строковые константы (коды ошибок и URL), номера портов, счётчики классов сторонних библиотек, нативные файлы, алиасы и сертификаты keystore, сведения о вложенных манифестах.

Никогда не публикуются файлы оригинала и их части (бинарники, извлечённые файлы, декомпилированный код, дословные фрагменты кода, тексты скриптов установщиков, тексты страниц сайтов НУЦ), закрытые ключи и зашифрованные блоки ключей keystore, пароли.

## 2. Как устроено

Код находится в `xtask/src/upstream/` и запускается как `cargo xtask upstream`. Workflow [`upstream.yml`](../../.github/workflows/upstream.yml) работает по расписанию каждые 6 часов и вручную, с `concurrency: upstream`, так что запуски не пересекаются. Он использует только `GITHUB_TOKEN`, других секретов нет.

Задание `collect` (windows-2025, только `contents: read`) запускает `cargo xtask upstream tools`, которая закрепляет внешние распаковщики, и `cargo xtask upstream run --dry-run`. Та опрашивает источники, скачивает изменившееся в `$RUNNER_TEMP`, распаковывает, собирает факты и пишет каталог emit, в котором допустимы только файлы `*.json`. Это проверяет и сам `run`, и отдельный шаг. Каталог уходит артефактом `upstream-facts` на 3 дня, а оригиналы удаляются вместе с временным каталогом.

Задание `publish` (ubuntu-24.04, `contents: write`, `issues: write`, без кэшей) запускает `cargo xtask upstream publish --from out`. Команда заново и строго проверяет артефакт: только ожидаемые пути, только JSON размером до 64 MiB, схемы с отказом на неизвестные поля, история совпадает с `latest/facts.json`, `key8` сходится. Затем она сама формирует тексты issues из `diff.json`, коммитит в ветку `upstream`, пушит без force и отправляет `repository_dispatch` с типом `upstream`. Если упал `collect`, открывается issue `upstream-alert` с видом `collect_failed`.

### Опрос

Манифест скачивается и проверяется на каждом запуске: подпись CMS, ровно один подписант `CN=NCALayer`, сертификат подписанта выдан корнем НУЦ (`oncl_pki::roots::nca_production`). Для дистрибутивов и фиксированных файлов опрос смотрит HEAD (размер, `ETag`, `Last-Modified`) и `hash` из манифеста. Ссылки страницы загрузок сравниваются по SHA-1, который опубликован рядом с ними; одноразовый ключ `download.php?key=` в идентичность источника не входит. Бандлы сравниваются по `hash` из манифеста, без запросов.

Источник считается исчезнувшим только после 3 неудачных опросов подряд, успешный опрос сбрасывает счётчик. HTML-страница вместо файла или манифеста (ошибка или капча со статусом 200) считается сбоем опроса, а не новой версией и не `bad_signature`. Если не загрузилась сама страница загрузок, её ссылки остаются в фактах и тоже накапливают неудачи.

Ключ `download.php?key=` обслуживает ровно один запрос (HEAD тоже; следующий получает 302 на HTML-страницу `404.php`) и только с cookie сессии страницы и `Referer`. Поэтому опрос ссылки страницы не запрашивает. Перед каждой загрузкой такой ссылки `run` заново читает страницу в новой сессии и берёт ссылку с тем же slug и свежим ключом. Статус ссылки меняют только эти загрузки: новая или вернувшаяся ссылка начинает со статуса `ok`, а ссылка со статусом `failing` или `refused` скачивается каждым запуском, пока загрузка не удастся. Счётчик неудач ссылки считает только опросы подряд, в которых её не нашли (страница не загрузилась или ссылки на ней нет), и только он убирает ссылку после 3 таких опросов. Опрос, нашедший ссылку, обнуляет счётчик, неудачные загрузки его не меняют.

Если изменение замечено, а файл скачать не удалось, опрос его не запоминает: следующий запуск снова увидит изменение и повторит загрузку. Исключение составляет ссылка страницы со статусом `refused`: следующий опрос об изменении не сообщает, но запуск всё равно скачивает её снова и сверяет с опубликованным SHA-1. Файл, который оставлен с пометкой «содержимое не изменилось», тоже сверяется с `hash` манифеста и опубликованным SHA-1.

### Распаковка

Оригиналы никогда не запускаются. ZIP, JAR, `.sh` (заголовок и вложенный ZIP) и лёгкий установщик Windows (программа на Go с gzip-потоком настоящего установщика) разбирает наш код; записи ZIP читаются в памяти и на диск не пишутся. Установщики Inno Setup распаковывает innounp 2.71.2: он скачивается с закреплённого коммита репозитория InnoUnpacker, sha256 архива и программы сверяются. MSI с кабинетами и DMG распаковывает 7-Zip из образа раннера, только версии 25.01 и новее, потому что они по умолчанию не создают символические ссылки за пределами каталога распаковки. Со старыми версиями такие дистрибутивы получают `skipped`. Вывод инструментов пишется в файл в рабочем каталоге, в журнал попадает только код выхода. Обход каталога после работы инструмента пропускает символические ссылки и reparse point.

Лимиты: манифест 1 MiB, страница 2 MiB, бандл 256 MiB, дистрибутив 1 GiB. При распаковке: 4 GiB всего, 200 000 файлов, 512 MiB на файл, вложенность архивов до 4. Превышение лимита даёт ошибку, данные не обрезаются. Перенаправления обрабатываются вручную, не больше 5, каждый адрес проверяется.

### Срок запуска

`collect` останавливается через 120 минут, поэтому у `run` свой срок: 90 минут от старта (`--deadline-minutes`, по умолчанию `RUN_DEADLINE`; `0` отключает срок). Когда он истекает, ещё не начатые загрузки пропускаются, а идущая прерывается: запросу не дают больше оставшегося времени. В журнал пишется строка `fetch: <id> skipped: run deadline passed, left for the next run`, и источник возвращается в состояние до запуска (источник, которого там не было, следующий опрос снова назовёт новым). Сбой при этом не засчитывается, запуск завершается обычным образом, и факты и записи того, что успело скачаться, публикуются.

### Сеть

Соединения разрешены только с публичными адресами. Loopback, частные сети, link-local, CGNAT 100.64/10, ULA, multicast, unspecified, адреса документации и такие же адреса в виде IPv4-mapped отвергаются до соединения. У бандлов НУЦ есть URL на частные адреса, они получают статус `refused`. Имя разрешается один раз на запрос, проверяются все его адреса, и соединение идёт только на них, без повторного разрешения и без прокси из окружения. Поэтому смена ответа DNS (DNS rebinding) не уведёт соединение на другой адрес.

Запрос без сессии может пойти на любой проверенный адрес; если один не отвечает, берётся следующий. Сессия соответствует одной загрузке ссылки страницы: чтение страницы и запрос ссылки идут на тот адрес, куда сессия попала первой. Пока адрес не закреплён, следующий пробуется, только если к предыдущему не удалось подключиться. У `ncl.pki.gov.kz` несколько записей A, а PHP-сессия живёт на одном сервере, и ссылка, запрошенная у другого, отвечает `404.php`. Каждая ссылка получает свою сессию, поэтому сервер, который перестал принимать соединения или отказывает, стоит неудачи одной ссылки, а не всех. Сервер, который принимает соединение и зависает, задерживает каждую закреплённую за ним загрузку до тайм-аута запроса: 10 минут для ссылок страницы (`PAGE_DOWNLOAD_TIMEOUT`; ссылок пять, у каждой своя сессия) и 30 минут для остальных.

Сертификаты TLS сайтов `*.pki.gov.kz` выпущены публичным центром WebPKI, поэтому для всех хостов используются корни WebPKI. Таблица `TLS_ROOTS` в `xtask/src/upstream/http.rs` позволяет назначить хосту корни НУЦ.

## 3. Ветка `upstream`

Ветка без общей истории с `main` (orphan) и только с файлами JSON; это проверяется перед каждым коммитом:

```
state.json                         состояние опроса (внутреннее)
latest/facts.json                  последние факты
index.json                         история
history/<id>/facts.json            факты записи
history/<id>/diff.json             разница с предыдущей записью
history/<id>/changes.json          изменения источников по опросу
```

- `id` = `<YYYY-MM-DD>-<version>-<key8>`. В `version` всё, что не входит в `[A-Za-z0-9._-]`, заменено на `_`, `key8` состоит из первых 8 hex-цифр sha256 байтов `facts.json`. `id` соответствует `^[0-9]{4}-[0-9]{2}-[0-9]{2}-[A-Za-z0-9._-]+$`.
- Все файлы пишет `serde_json` с отступами и переводом строки в конце, коллекции отсортированы. В фактах нет времени запуска, `ETag` и `Last-Modified`, так что одинаковое состояние источников даёт одинаковые байты и одинаковый `key8`.
- Новая запись истории появляется только при изменении разобранных фактов. Пробелы, порядок ключей JSON и переводы строк после публикации или checkout изменением не считаются, в том числе на следующий день. Хеши файлов и подписи входят в сравнение, поэтому перепаковка и переподпись дают записи `repack`. Счётчики неудач источников в `state.json` обновляются независимо от истории.
- `latest/facts.json`: `{schema: 1, manifest, bundles{symname: {name, version, required, …, fetch, jar, signer_matches}}, distributions{source id: {url, page, label, filename, size, sha256, published_sha1, format, status, unpack, files, jre, jars, embedded_manifests, meta}}, jars{sha256: {…, content_sha256, manifest_mf, signers, api, libraries, natives, keystores, embedded_manifests}}}`. Значения `fetch` и `status`: `ok`, `pending`, `unreachable`, `refused`, `hash_mismatch`.
- `signers[путь блока]` содержит сертификат, который первый `SignerInfo` блока называет по издателю и серийному номеру. Записи нет, если `SignerInfo` ссылается на `subjectKeyIdentifier` или его сертификата нет в блоке.
- `index.json`: `{schema: 1, entries: [{id, date, observed, version, key8, path, kind, summary{core[], plugins[{symname, from, to, change}], distributions[], notes[]}, issues[{key, number, label}]}]}`, записи по возрастанию `observed`. Строки `summary` содержат простой текст.
- `kind`: `baseline` для первых фактов, `change` для изменения, `repack`, если изменились только байты (перепакованный или переподписанный JAR с тем же содержимым, API и заголовками, переподписанный манифест с тем же JSON).
- Идентификаторы источников: `manifest`, `dist:<type>` (`disturls` с непустым URL), `page:<slug подписи ссылки>`, `fixed:ncalayer.zip`, `fixed:tzdb.dat`, `bundle:<symname>`.

## 4. Issues

- `upstream` относится к ядру: изменились поля манифеста (кроме переподписи), бандл ядра (`required`, кроме перепаковки) или содержимое дистрибутива. Смена подписанта манифеста отмечается предупреждением в issue и сбоем не считается.
- `upstream-plugin` открывается по одному на каждый изменившийся плагин (кроме перепаковки) и содержит строку о порте из `plugins/<short>/registry.toml`.
- `upstream-alert` сообщает о сбое: `bad_signature`, `manifest_unreachable`, `collect_failed`. На каждый вид в день одно issue: его создаёт первый запуск дня, следующие не меняют.

Последняя строка тела имеет вид `<!-- upstream-key: <key> -->`, где ключ равен `core:<version>:<key8>`, `plugin:<symname>:<version>` (`plugin:<symname>:removed:<key8>`) или `alert:<kind>:<date>`. По ключу повторный запуск находит issue. Если тело то же, ничего не происходит. Если другое и issue открыто, тело заменяется и добавляется комментарий. Если issue закрыто, добавляется только комментарий, issue не переоткрывается. Номера issues записываются в `index.json` в том же коммите.

Первый запуск даёт запись `baseline` без issues. Перепаковка, смена доступности источника и первая успешная загрузка уже известного источника (дистрибутива, ссылки страницы или бандла, который до этого был `pending`) дают только строку в `summary.notes` («первая загрузка известного источника»). Источник, который опрос видит впервые (`added` в `changes.json`), и новый sha256 уже загружавшегося дистрибутива открывают issue.

## 5. Ручной запуск

```sh
gh workflow run upstream.yml -f mode=run           # сбор и публикация
gh workflow run upstream.yml -f mode=issues-only   # issues последней записи ветки
```

Локально, без публикации:

```sh
cargo xtask upstream run --dry-run --emit target/upstream/emit
```

Без `--dry-run` команда `run` сначала открывает ветку `upstream` (её worktree и служит состоянием, `--state` тогда запрещён), затем публикует каталог emit тем же кодом, что и `upstream publish`; нужны `GITHUB_TOKEN` и `GITHUB_REPOSITORY`. `publish` отказывается от каталога emit, в `index.json` которого не хватает какой-либо записи ветки: такой каталог собран не из её состояния и стёр бы историю. MSI и DMG распаковывает 7-Zip 25.01 или новее (путь задаёт `ONCL_7Z`). Пакет `7zip` в Ubuntu 24.04 старее, и с ним MSI и DMG получают `skipped`; без innounp `skipped` получают установщики Inno Setup. `cargo xtask upstream poll` печатает только изменения источников.

## 6. Разбор `upstream-alert`

- `bad_signature`: манифест не прошёл проверку (другая подпись, неизвестный издатель, CN не `NCALayer`). Факты не обновлены. Скачайте `ncalayer.der` вручную и сверьте подписанта с опубликованными сертификатами НУЦ. Если НУЦ сменил корень, обновите `oncl_pki::roots`.
- `manifest_unreachable`: манифест недоступен (сетевая ошибка, статус не 2xx, HTML или другой файл вместо DER) 3 опроса подряд или с первого запуска. Проверьте доступность сайтов НУЦ с раннеров по журналу `collect`. Если доступ заблокирован, используйте резервный путь ниже.
- `collect_failed`: упало задание `collect`, журнал прогона есть по ссылке в issue.

## 7. Резервный путь при недоступности сайтов НУЦ с runner'ов GitHub

1. Задайте переменную репозитория `UPSTREAM_SOURCE=lab`, тогда плановые запуски `collect` выключаются.
2. На машине с прямым доступом к сайтам (приватная лаборатория), в checkout `main`, выполните команды ниже. Наблюдатель соединяется только напрямую и переменные прокси (`HTTPS_PROXY`, `ALL_PROXY` и другие) не использует, потому что через прокси соединение ушло бы мимо проверенных адресов. Если такие переменные заданы, `run`, `poll` и `tools` пишут об этом строку.

   ```sh
   git fetch origin upstream
   git worktree add --detach ../upstream-state origin/upstream
   cargo xtask upstream run --dry-run --state ../upstream-state --emit <dir>
   cargo xtask upstream publish --from <dir> --branch-dir ../upstream-lab --no-push --no-issues
   git -C ../upstream-lab push origin HEAD:refs/heads/upstream-lab-<дата>
   ```

   С `--no-push --no-issues` команда `publish` не требует токена: она проверяет каталог emit, создаёт worktree ветки `upstream` в `../upstream-lab` и коммитит факты. Затем откройте PR из `upstream-lab-<дата>` в `upstream`.
3. После слияния выполните `gh workflow run upstream.yml -f mode=issues-only`.
4. Когда доступ вернётся, удалите переменную `UPSTREAM_SOURCE`.

## 8. Кто читает данные

- Реестр плагинов читает `index.json` и `latest/facts.json` (`manifest.version`, `bundles{symname: {version, required}}`) и пересобирает Pages по `repository_dispatch: upstream`. Для Pages `latest/facts.json` читается потоком через `BufReader` с тем же лимитом 64 MiB, что у `publish`: большие `distributions` и `jars` проверяются как JSON, но в памяти не хранятся. `index.json`, индексы каналов и список релизов ограничены 8 MiB каждый. Некорректный или слишком большой файл даёт ошибку, частичных данных не бывает.
- Приватная лаборатория читает ветку без токена (по sha коммита), скачивает изменившиеся оригиналы со сверкой sha256 из `latest/facts.json`, декомпилирует изменившиеся JAR в песочнице без сети и учётных данных и хранит всё у себя.

## 9. Известные ограничения

- Имена файлов MSI в фактах берутся из таблицы File в том виде, в каком их выдаёт 7-Zip, а не как имена после установки.
- Порты, заданные в байткоде инструкцией `sipush`, не попадают в пул констант и в `ports` не видны.
- Ссылки страницы загрузок без опубликованного SHA-1 скачиваются целиком на каждом опросе (сейчас SHA-1 публикуется для всех ссылок). Ссылка со статусом `failing` или `refused` скачивается на каждом запуске, пока загрузка не удастся.
- Бандл, JAR которого не скачался при первом появлении, получит сравнение API только при следующем изменении; появление JAR после сбоя отражается лишь строкой в `notes`.
