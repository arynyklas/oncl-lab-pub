# SDK: обзор возможностей

Здесь описаны встраивание `oncl-core`, подписи CAdES, сервис `oncl-server`, плагины в SDK, а также подпись и проверка PDF и XML. Контракты SDK, semver и миграция описаны в [`sdk.md`](sdk.md), журнал надёжного аудита в [`audit.md`](audit.md). Имена вида `P01`, `X03`, `C03`, `L01` в командах ниже являются именами случаев приёмочной пробы `sdk_probe` (аргумент `--case`).

## Встраивание (из git, не из crates.io)

`oncl-core` выполняет потоковые подпись, проверку, валидацию, инспекцию и метки времени. Доверие, ключи, часы, сеть, аудит и лимиты ресурсов задаёт приложение, в которое встроен SDK. Графическая сессия, демон, слушающий порт и самообновление ему не нужны.

SDK в crates.io не публикуется. Подключайте его по git с тегом выпуска (`Cargo.lock` закрепит коммит тега) или по path из рабочей копии на проверенном теге. Все сторонние зависимости SDK берутся из crates.io, `[patch.crates-io]` не нужен:

```toml
[dependencies]
oncl-core = { git = "https://github.com/arynyklas/OpenNCALayer", tag = "v0.1.3", features = ["full"] }
```

Без features получается минимальный SDK: CMS/CAdES, хеширование, PKI-валидация, файлы ключей и пакеты операций. Есть также `tokens`, `xml`, `pdf`, `jose`, `plugins` и `full` (всё сразу). Ни одна из них не тянет Slint, desktop, механизм обновления, сервер или асинхронный рантайм; это проверяет `cargo xtask sdk closure`.

Примеры выпускают одноразовую PKI и не обращаются к сети: `cargo run -p oncl-core --example sign_file`, `--example verify_file -- <каталог> <файл>` и `--example custom_transport` (собственный HTTP-транспорт приложения; без сети строгая подпись отклоняется до применения ключа).

Semver, контракты ошибок и лимитов, заметки о миграции и поставка описаны в [`docs/dev/sdk.md`](sdk.md). Цепочку упакованных исходников офлайн проверяет `cargo xtask sdk smoke`; в реестр SDK не загружается. Лицензии сторонних крейтов, от которых зависит SDK, собраны в [`crates/oncl-core/THIRD-PARTY.txt`](../../crates/oncl-core/THIRD-PARTY.txt).

## CAdES

SDK поддерживает уровни CAdES B, T, LT и LTA: `SignRequest::cades_create` / `cades_add`, `VerifyRequest::cades`, `Engine::extend` / `extend_staged`. Лимиты на доказательства задаются явно (`EvidenceLimits`), доверие и сеть задаёт только приложение.

Чтобы получать новые метки времени (уровни от T), нужна `CadesConfiguration`. Для проверки уже вложенных доказательств и для со-подписи уровня B она не требуется. Достройка подписи до более высокого уровня требует отдельного права `Action::Extend`, сохраняет подписанные поля и закрытый ключ не использует. Уровень контейнера равен наименьшему проверенному уровню среди всех подписантов.

Архивный профиль соответствует EN 319 122-1 V1.3.1 (`archiveTimestampV3` и `ATSHashIndexV3`), архивный хеш пока только SHA-256. Старый CAdES-A v2 не поддерживается. Прежние контракты WSS и CLI от этого не меняются.

Локальная проверка:

```
cargo run -p oncl-core --example sdk_probe -- --case C03 --out target/c03-public
```

Проба выпускает только публичные синтетические RSA-артефакты всех четырёх уровней, присоединённые и отсоединённые, с несколькими подписантами, а также изменённые архивы для сверки независимым инструментом. Прогон с документами 1 ГиБ, замер RSS и матрицу платформ desktop она не заменяет.

## Сервис `oncl-server`

`oncl-server` работает и как отдельный сервис, и как библиотека. У программы есть подкоманды `serve`, `token-create` и `install-file`. HTTP API по умолчанию выключен (`enabled = false`); включается в `server.toml` или флагом `--enable-api`. Доступ даётся по токенам с правами на отдельные действия. TLS и OTLP включает только оператор, OTLP только с явного согласия.

Подробнее:

- [`docs/user/server.md`](../user/server.md): настройка, токены, пределы;
- [`docs/user/http-api.md`](../user/http-api.md): маршруты и ошибки;
- [`docs/dev/platform-interop.md`](platform-interop.md): сверка с NCANode;
- [`docs/dev/platform-acceptance.md`](platform-acceptance.md): приёмка на платформах и её состояние;
- [`audit.md`](audit.md): журнал надёжного аудита при использовании сервера как библиотеки.

Шифрование и расшифрование CMS есть только в библиотеке `oncl-pki` (`oncl_pki::cms::envelope`, профили RSA-OAEP); в API SDK, CLI и HTTP их нет. Казахстанский ГОСТ-профиль шифрования не реализован (Kalkan его не поддерживает) и не заявляется. Пакета WinGet нет, программы устанавливаются из Releases.

## Плагины в SDK

С feature `plugins` `oncl-core` выполняет плагины WebAssembly в безголовом хосте с ограниченными правами. Установка плагина ещё не даёт права его вызывать. Приложение явно связывает вызывающего, операцию, вложенные методы ABI, ключи, замороженные источники, неопубликованные результаты и сетевые адреса; итоговые права равны пересечению этих связей с манифестом и политикой хоста.

Подписи Raw, CMS, XML и XAdES из плагина используют исходный `OperationContext` и охранник ключей. Если операция требует диалога, возвращается `InteractionRequired`, интерфейс при этом не блокируется. Пакеты, каталог и механизм обновления плагинов доступны только с отдельной feature `oncl-plugin/distribution`, которую включает desktop; настройки остаются в рантайме.

Права на PKI задаются HTTP-методом и точным базовым URL, включая внутреннюю проверку сертификата перед подписью. Производный GET разрешён, только если его построил штатный PKI-кодировщик от этого базового URL; подстановки по origin или префиксу и перенаправления права не расширяют. Цепочки сертификатов и результаты DER/Base64/PEM предсказуемого размера проверяются по исходным квотам до применения ключа; предварительная проверка не списывает выходные байты. Вызов `log` в безголовом режиме подтверждается без записи данных плагина.

`KeysSignXml`, `KeysSignXmlEx` и `KeysSignXades` вызывают настоящие охраняемые устаревшие (legacy) функции Core с исходными селекторами XPath, пространствами имён и раскладкой. Уровни T и LT требуют совпадающего TSA, настроенного приложением, и фактических доказательств. Публичная цепочка, пришедшая от плагина, не становится якорем доверия, а алгоритм по умолчанию из устаревшего API не может разойтись с реальным ключом. Размер сериализованного XML проверяется до применения закрытого ключа по исходной квоте и временному пределу ABI. Если после этого модуль аварийно завершается или TSA отвечает ошибкой, исход остаётся `Applied`, а частичный результат не публикуется.

Проверка с настоящим WASM и независимым OpenSSL:

```
cargo run -p oncl-core --features plugins,tokens --example sdk_probe -- --case L01 --out target/l01-smoke
```

Этот случай также запускает ограниченную независимую проверку через Python `lxml` (libxml2) и `cryptography`: подпись RSA, все ссылки (references) и отрицательный контроль с изменённым документом. Это проверка ABI в ограниченном объёме: она не заменяет прогон 1 ГиБ и RSS, проверку токенов НУЦ и матрицу desktop и не является сертификацией PKIX, ГОСТ или НУЦ.

## PDF и PAdES

### Проверка

`oncl-pdf` и feature `oncl-core/pdf` проверяют существующие подписи PDF (`VerifyRequest::pdf()`) и добавляют невидимую отсоединённую подпись CMS в новую инкрементальную ревизию PDF (`SignRequest::pdf(key, PdfSignProfile)`). Уровни PAdES B/T/LT/LTA доступны через отдельный явный профиль (ниже).

Операциям нужен явно настроенный `TemporaryStore`. Исходные байты один раз копируются в закрытый снимок, и уже из него с ограниченными буферами читаются xref, потоки объектов, цепочка инкрементальных обновлений `/Prev` и подписанные ByteRange. Снимок учитывает фактически прочитанный ввод, не доверяет заявленной длине и исключает подмену файла между разбором и хешированием.

Отчёт связывает каждого подписанта с защищённой ревизией, точным исключённым токеном `Contents` и фактом последующих изменений. Криптографическая корректность не заменяет полную политику доверия. Неподдерживаемый формат никогда не получает Valid.

Происхождение метаданных подтверждают только закрытые преобразования SDK `SnapshotEncoding::{Identity,PdfByteString}`, декодер вызывающей стороны для этого не годится. Повторный захват подлинного снимка Source той же операции не увеличивает `bytes_in`, а снимок чужой операции отклоняется до ввода-вывода. Каждая новая копия держит реальный резерв временного диска и памяти, освобождение (Drop) копии возвращает её дисковую ёмкость. Повторное чтение сохраняет исходные дедлайн и управление и читает ограниченные упорядоченные диапазоны, новой операции и нового лимита времени оно не получает.

```
cargo test -p oncl-pdf --test all verify::
cargo run -p oncl-core --features pdf --example sdk_probe -- --case P01 --out target/p01-smoke
```

Проба использует настоящий RSA-PDF, подписанный внешним pyHanko; изменение внутри подписанной ревизии и отдельное последующее обновление служат отрицательными контролями. Виртуальный тест xref за пределом 4 ГиБ проверяет только арифметику смещений и позиционирование. Работу с настоящими PDF размером 1 ГиБ и предел RSS 1 ГиБ проверяет платформенная приёмка.

### Подпись

Подпись сохраняет весь исходный байтовый префикс, страницы, поля формы и цепочку `/Prev`. Новые потоки xref используют 8-байтовые смещения, в том числе больше десяти десятичных цифр. Перед добавлением подписи проверяются все предыдущие подписи и то, что последняя ревизия ими покрыта: неподписанное последующее обновление нельзя узаконить новой подписью. Преобразования прав сертифицирующих подписей и блокировки полей, а также XFA отклоняются.

`PdfSignProfile::new(bytes)` задаёт размер места под CMS (по умолчанию 16 КиБ). До применения закрытого ключа тот же кодировщик ASN.1 вычисляет точный размер DER с фактическими сертификатом и атрибутами и фиксированной длиной подписи RSA или ГОСТ. Если места заведомо не хватает, операция отклоняется с NotApplied, охранник и ключ не вызываются. Если неожиданно большой ответ приходит от ключевого модуля уже после применения ключа, результат остаётся ошибкой с Applied, промежуточный вывод не публикуется, скрытого повтора нет.

Core требует обычного права `Action::Sign`, текущей строгой валидации и охранника; `SignDigest` и `allow_prehashed` права подписывать PDF не дают.

Для исторического завершения `%%EOF` без перевода строки или с одиночным CR поле `revision_end` остаётся точным концом подписанного ByteRange. Поля `parser_revision_end` и `PdfEndpointScope` показывают физически прочитанный конец строки и допустимую историческую границу. Последняя подпись по-прежнему обязана покрывать точный текущий конец файла; произвольные пробелы, `%%EOFX` и неполный EOF допустимыми концами подписанной области не становятся.

Закрытый `PdfSignatureOutput` работает только с пустым промежуточным выводом (OUTPUT) той же операции. Добавление учитывает вывод и временные данные один раз, ByteRange фиксируется до хеширования, после этого меняется только зарегистрированный шестнадцатеричный `Contents`. Он не открывает `File`, не даёт произвольного позиционирования и правки и не даёт записи в `FrozenInput`. `shared_view()` у `ResourceScope` даёт ещё один дескриптор той же операции с теми же общими счётчиками, дедлайном, управлением и арендой допуска; новой квоты для другого запроса он не создаёт.

```
cargo test -p oncl-pdf --features testing --test all sign::
cargo run -p oncl-core --features pdf --example sdk_probe -- --case P02 --out target/p02-smoke
```

Проба публикует только исходный PDF, PDF с одной и двумя подписями, публичные сертификаты и отчёт: четыре страницы, созданные внешним инструментом, содержательный RGB XObject больше 3 МиБ, два разных RSA-ключа, проверку обеих подписей и отрицательный контроль с изменением подписанной области. Независимые проверки pyHanko, OpenSSL и poppler и полный прогон 1 ГиБ/RSS на платформах выполняются отдельно.

### Уровни PAdES

`SignRequest::pades(key, profile, level, material, evidence_limits)`, `VerifyRequest::pades(required, evidence_limits)` и `ExtendRequest::pdf(level, pdf_limits).with_evidence_limits(evidence_limits)` используют настоящие `ETSI.CAdES.detached`, CMS SignatureTimeStamp, общие DSS/VRI и DocumentTimeStamp по RFC 3161. Профиль соответствует [EN 319 142-1 V1.2.1, 5.4.2/5.4.3 и 6.3 n), q), r)–y)](https://www.etsi.org/deliver/etsi_en/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf).

Новая подпись уровня T получает метку времени CMS над настоящим signatureValue. При достройке ранее выпущенной подписи B ставится документная метка времени над фактическими ByteRange, старый `Contents` и исходный байтовый префикс не меняются. LTA требует последующей проверенной метки времени, покрывающей DSS и предыдущие доказательства. Уровень документа равен наименьшему проверенному уровню всех подписантов; запрошенный уровень или наличие токена его не задают. Время подписания подтверждается только после проверки отпечатка (imprint), криптографии и EKU TSA, доверия приложения и актуального статуса цепочки TSA. Поле PDF `/M` доказательством существования не является.

Достройка требует отдельного права `Action::Extend`. В Core этот путь вообще не открывает KeyProvider, не запрашивает секретов и не применяет закрытый ключ. Новая подпись по-прежнему требует `Action::Sign`, строгой валидации и охранника. Новые метки времени запрашиваются через явно заданную приложением `CadesConfiguration`, общую для всех форматов AdES. Уровню B и проверке уже вложенных доказательств настройка TSA не нужна. Корни, часы, закрепления и сетевая политика из PDF не берутся.

После первой подписи разрешён только ограниченный набор изменений: DSS/VRI, сертификаты и статусы, добавление полей подписи и меток времени. Изменения страниц, содержимого, исходных объектов, прав или посторонних данных каталога и трейлера новой ревизией или меткой времени не узакониваются. Старые объекты, а с ними прежние доказательства и метки времени, остаются байт в байт. VRI проверяется только на уровне ключей: ключ VRI старой подписи удалить нельзя, но его содержимое может указывать на другие объекты. DSS можно переписать новыми объектами (например, со свежим OCSP), как это делает NCANode. Поле подписи или метки времени (`/FT /Sig` с настоящим `/V`) допускается и в виде невидимого виджета (`/F 132`) нулевой площади с пустым представлением, если страница меняется только добавлением этого виджета в `/Annots`.

Профиль `pdf` не считает DocTimeStamp подписантом и не отказывает из-за него. При этом пропущенный DocTimeStamp не проверяется на ByteRange и Contents: искажённый токен или токен, не покрывающий документ, в общем профиле молча игнорируется.

При проверке всех подписей PDF используется один набор общих доказательств DSS и меток времени, принадлежащий операции, и одна подготовленная проверка доказательств. Общие сертификаты и токены не декодируются заново для каждого подписанта. Каждая CMS при этом отдельно проверяет фактический дайджест, SID, ESS и граф включения; отпечаток, время, доверие и актуальный статус цепочки TSA проверяются для каждого доказательства. DSS поддерживается только с прямыми ссылками на потоки DER без фильтров; другие кодировки и неподдерживаемые преобразования прав отклоняются.

Обновление вывода выполняется только добавлением в новой транзакции, без старых мест для правки. Любая ошибка, включая отмену в момент возобновления или запечатанного снимка, навсегда запрещает публикацию, даже если приложение потом снимет флаг отмены. Чужие артефакты и артефакты исходных данных не портятся. Внутренние повторные чтения и проверки не списываются повторно со счётчиков ввода и вывода.

```
cargo test -p oncl-pdf --features testing --test ades
cargo run -p oncl-core --features pdf --example sdk_probe -- --case P03 --out target/p03-smoke
```

Проба выполняет настоящие операции RSA, ГОСТ-2004 и ГОСТ-2015-512 с локальными TSA, OCSP и CRL на loopback: все четыре уровня, обновление архива, переход B→T, несколько подписантов и отрицательные контроли DSS и токенов. Независимая проверка новых RSA-PDF, включая архивную валидацию и подмену, в окружении с pyHanko 0.38 и новее:

```
python crates/oncl-core/examples/sdk_probe/pades_oracle.py --out target/p03-smoke
```

Это не квалифицированная сертификация и не сертификация НУЦ, не независимая проверка ГОСТ и не замена прогона с содержательными PDF 1 ГиБ, замера RSS и платформенной приёмки. Границы 2 и 4 ГиБ проверяются только арифметическими пробами за пределом гарантии.

## XML, XAdES и WS-Security

### Подпись и проверка

Feature `oncl-core/xml` добавляет подпись, добавление подписи и проверку XML из Source в UTF-8, а также достройку доказательств без ключа: `SignRequest::xml/xades`, `VerifyRequest::xml/xades`, `ExtendRequest::xml`. Явный `VerifyRequest::xml_kalkan()` проверяет байты так же, как Kalkan. Приложение должно настроить `ValidationServices` и `TemporaryStore`; TSA задаётся общей `CadesConfiguration`, и запрос не может расширить корни или сетевую политику.

`oncl-xml::verify_source` проверяет каждый SignedInfo, сертификат, SignatureValue и Reference. Отчёт хранит факты по каждому подписанту, SHA-256 настоящего сертификата и точные диапазоны покрытых узлов. Один канонический писатель обслуживает и ограниченный DOM, и индексированные фрагменты исходного Source, так что большого DOM или буфера в памяти нет. Канонизированные References могут храниться в учтённом `TemporaryStore` до открытия ключа.

Поддерживаются:

- inclusive и exclusive C14N, с комментариями и без, InclusiveNamespaces;
- ссылки по ID и URI с процентным кодированием, однозначные пути XPointer;
- ограниченные Manifest;
- XPath-фильтр `not(ancestor-or-self::ds:Signature)` с привязкой пространства имён.

Преобразование Enveloped исключает текущую подпись. Исключение и последующих подписей включено только в режиме `KalkanLegacy`. Неоднозначные ID, KeyInfo и X509Data и неподдерживаемые преобразования отклоняются; изменение неподписанного узла подписи не приписывается.

### XAdES

Уровень XAdES B/T/LT/LTA определяется общей политикой доверия и проверкой доказательств времени, а не наличием элемента метки времени. SignatureTimeStamp 1.3.2 покрывает весь канонический SignatureValue. ArchiveTimeStamp 1.4.1 выбран в нераспределённой форме из ETSI EN 319 132-1 V1.2.1 §5.5.2.2: он покрывает все преобразованные References, SignedInfo, SignatureValue, KeyInfo, предыдущие неподписанные свойства и прочие Objects в установленном порядке. Достройка и обновление архива проверяют все старые и новые доказательства и не требуют KeyProvider или охранника подписи.

Наименьший проверенный уровень возвращается только при Valid. Поддерживаются один SignatureTimeStamp и несколько обновлений ArchiveTimeStamp, каждое доказательство проверяется. Повторные независимые SignatureTimeStamp, другие версии и распределённое покрытие архива отклоняются явно; уровень при этом не понижается молча до проверяемого.

Новые подписи baseline содержат подписанный DataObjectFormat/MimeType для каждой Reference на данные; ObjectReference ссылается на Reference@Id, а не на ID подписанных данных. Прежние ограниченные подписи XAdES по-прежнему проверяются математически, но без обязательных свойств baseline уровень baseline не получают. Достройка LTA без ключа обновляет устаревшие публичные статусы только после проверки всех прежних доказательств и до выпуска архивной метки, покрывающей все текущие доказательства; финальная проверка защищённого архивного префикса не ослаблена.

### Подпись из Source и устаревшие API

`oncl-xml::sign_spec_source` даёт ограниченный `XmlSignSpec` через DigestSigner и исходный ResourceScope. Прежние XPath, размещение, вывод, раскладка и лимиты сохранены, построитель и канонический писатель общие. Подпись из Source не строит DOM большого документа. Add сохраняет прежние подписи, но стандартная ссылка на весь документ может быть нарушена последующим Add. WS-Security использует тот же индекс и канонический писатель.

Внутренние повторные чтения для хеширования и доказательств не расходуют финальную квоту вывода; внешний `copy_entry` списывает каждую выдачу. Захваты, сделанные из OUTPUT, остаются OUTPUT. Отмена или ошибка закрытой транзакции вывода запрещает публикацию и после того, как сигнал отмены снят.

`SignRequest::xml_legacy` в Core сохраняет ограниченный контракт XmlSignSpec через исходный AuthorizedSigner. `SignRequest::xades_legacy` принимает ограниченный XadesSpec и создаёт полный B/T/LT общим механизмом доказательств, не раскрывая ключ; TSA должен совпадать с явной настройкой приложения. Селекторы и канонические References готовятся до открытия ключа. Выбранная цепочка LT из запроса и публичный материал приложения вместе проверяются по закодированному размеру и количеству до захвата и до применения ключа, без предварительного копирования и кодирования DER. Уровни B и T сохраняют совместимость и цепочку запроса не сериализуют.

### Учёт подписанного ввода

`capture_signed_input` сохраняет SHA-256 неизменяемых подписанных байт и закрытую роль читателя формата, чтобы одобрение и повторное чтение в той же операции работали с теми же данными. При приёме подписанного ввода фактический прогресс считается необратимо, а ограниченные накладные байты самой подписи учитываются отдельно. Прикладные Objects, поддельные метаданные, пробелы и инструкции обработки (PI) остаются байтами документа. Как байты формата засчитываются только распознанные парсером ограниченные объявление XML и BOM, а также раскрытие пустого родителя, содержащего одни подписи; это не утверждение о том, как документ был написан изначально. Обычные потребители исходного ввода и хеша не принимают читателей с ролью формата.

Раскладка подписи проверяется сразу по лимитам обрамления и работы. Ёмкость под сохраняемую геометрию резервируется до роста, лимита на число узлов документа нет.

При динамической проверке Core берёт доверенное время приложения после фактического ответа TSA, и финальная проверка XML использует один поздний момент для всех подписантов. Прямые API с фиксированным моментом проверки сохраняют прежнее поведение и монотонные дедлайны.

Независимая ограниченная проверка (lxml/libxml2 и cryptography; точные C14N, дайджесты и математика RSA, без ГОСТ и без доверия):

Это ограниченный профиль с прямым корнем, а не универсальный валидатор PKIX/XAdES и не независимое доказательство для ГОСТ, 1 ГиБ или RSS.

### WS-Security

`oncl_xml::wsse::{SourceWsseSignProfile, WsseVerifyProfile}` и в Core `SignRequest::wsse` / `VerifyRequest::wsse` поддерживают в том числе одобренные пакетные Create и Add. Используемый Body должен быть единственным прямым Body настоящего Envelope SOAP 1.1 или 1.2 с одним глобально уникальным WSU Id. Каждый подписант проверяется относительно этой области: математика по всему документу, перенесённый старый Body, неподписанная подмена, псевдонимы ID, неверное пространство имён и токен другого получателя утверждения о покрытии не дают.

Приложение выбирает actor/role для Security, обязательные прямые прикладные заголовки и политику подписанных Created/Expires в UTC. Timestamp здесь только подписанное утверждение о свежести; доказательством существования и защитой от повтора он не является. Поддерживаются полный сертификат в KeyIdentifier (вариант, который использует закреплённый образец NCANode) и стандартная локальная ссылка BinarySecurityToken/STR. Удалённые токены, поиск по SKI или issuer-serial, шифрование, SAML и неизвестные распознанные доказательства Security явно не поддерживаются. Новые подписи создаются алгоритмами RSA-SHA256, ГОСТ-2004 и ГОСТ-2015/512 с прежними строгими правилами приложения для PKI, алгоритмов и ключей.

Байтами формата считаются только ограниченное распознанное обрамление Security, типизированные токены и Timestamp и необходимая вставка WSU Id; обычные заголовки и Body остаются прикладными байтами. Остальные лексические байты сохраняются. `XmlVerificationFacts::wsse()` возвращает фактическое покрытие Body, заголовков и Timestamp по каждому подписанту, а `read_used_soap_body` читает только байты исходной области.

Приложение не может выбрать для обработки `role/none`. Прикладные Header, Body и Envelope в чужом пространстве имён контейнерами SOAP не считаются. Id в Unicode одинаково записываются и проверяются как однозначные голые фрагменты. Комментарии и PI внутри типизированных токенов и Timestamp и лишний текст в Timestamp отклоняются, бесплатными метаданными они не становятся. Проверяется фактическая длина Security и заголовка, содержащего только Security, вместе с суммарным обрамлением, а не нормализованный буфер лексера.

`wsse::sign_prepared` проверяет явно переданное время приложения до применения ключа. У упрощённого `wsse::sign_source` своего источника времени нет, поэтому ввод или профиль с Timestamp требуют подготовленного API с доверенным ValidationContext. Неподдержанное требование создать baseline EN и заведомо невыполнимые лимиты раскладки или ссылок отклоняются до обращения к поставщику ключа. Проверка уже вложенных доказательств XAdES сохранена; генератор WSSE свойства baseline EN себе не приписывает.

Предварительный размер считает тот же генератор подписи через проверяемый приёмник UTF-8 с потоковым экранированием атрибутов XML. References заимствуют уже принятые Id, поэтому полная экранированная подпись и копии строк Id ради подсчёта не создаются. Временные буферы дескрипторов и токенов проверяются до выделения памяти. Отказ по размеру, известный из профиля, происходит до приёма ввода в Core, до поставщика ключа и до применения закрытого ключа, без повышения лимитов метаданных; резерв метаданных уже учитывает живую память.

```
cargo run -p oncl-core --features xml --example sdk_probe -- --case X05 --out target/x05-smoke
```

Проба покрывает содержательный SOAP Body больше 64 МиБ, Add с RSA и ГОСТ, все три алгоритма на ограниченных случаях, настоящую закреплённую PKI на loopback и изменения и обёртывание документа. Независимая ограниченная проверка (жёсткий предел DOM 1 МиБ):

```
python crates/oncl-core/examples/sdk_probe/wsse_oracle.py target/x05-smoke
```

Перед запуском скопируйте `target/fixtures/ncanode/wsse-ncanode.xml` (появляется после `cargo xtask fetch-fixtures`) в каталог вывода под именем `pinned-ncanode.xml`. Скрипт независимо сверяет exclusive C14N libxml2, SHA-256 и математику RSA внешнего закреплённого образца и нового образца RSA. Каноническое разложение для ГОСТ не является независимой проверкой математики ГОСТ, а у просроченного внешнего образца проверяется только математика, доверенным Valid он не становится. Среды Java/Kalkan, промышленной сертификации, замера RSS и прогона 1 ГиБ здесь нет; это остаётся за платформенной приёмкой.
