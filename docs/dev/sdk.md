# Rust SDK: встраивание, возможности, стабильность, готовность к публикации

`oncl-core` является встраиваемым SDK OpenNCALayer. Он выполняет типизированные потоковые подпись, проверку, валидацию, инспекцию и метки времени над файлами и потоками байт. Доверие, ключи, часы, сеть, аудит и лимиты ресурсов задаёт приложение, в которое встроен SDK. Интерфейса, демона, слушающего порта, сборщика телеметрии, установщика и самообновления в нём нет, графическая сессия не нужна. CLI `oncl` и HTTP-сервис `oncl-server` используют тот же движок, но в зависимости SDK не входят.

Здесь описан контракт SDK в поставляемом виде. Устройство платформы описано в [`../design/platform.md`](../design/platform.md), краткое введение в README крейта: [`../../crates/oncl-core/README.md`](../../crates/oncl-core/README.md).

## 1. Подключение (релиза в реестре нет)

В crates.io ничего не опубликовано, поэтому `cargo add` с версией из реестра не сработает. Свободны ли имена крейтов `oncl-*` в crates.io, не проверялось. Зависеть нужно от проверенного тега или коммита по path или git.

Все сторонние зависимости SDK берутся из crates.io, `[patch.crates-io]` не нужен:

```toml
[dependencies]
oncl-core = { path = "OpenNCALayer/crates/oncl-core", features = ["full"] }
```

`cargo xtask sdk smoke` (раздел 7) собирает такого потребителя только из распакованных пакетов исходников, а не из workspace.

## 2. Features и зависимости

У `oncl-core` нет features по умолчанию (`--no-default-features` даёт минимальный SDK). Набор зависимостей считается как обычный граф без proc-macro; его печатает `cargo xtask sdk closure` (`cargo tree -p oncl-core --no-default-features [--features F] -e normal`, хост Windows):

| набор features | крейтов | крейты `oncl-*` в нём |
|---|---|---|
| minimal | 92 | oncl-core, oncl-gost, oncl-pki, oncl-registry |
| `tokens` | 99 | + oncl-token |
| `xml` | 95 | + oncl-xml |
| `pdf` | 95 | + oncl-pdf |
| `jose` | 97 | (новых `oncl-*` нет; добавляет base64, serde, serde_json) |
| `plugins` (включает `xml`) | 149 | + oncl-flows, oncl-pdk, oncl-plugin, oncl-protocol, oncl-token, oncl-xml |
| `full` | 150 | всё перечисленное, + oncl-pdf |

Ни один набор не содержит Slint, winit, tokio, axum, hyper, velopack, tray-icon, rfd, webbrowser, а также `oncl-ui`, `oncl-desktop`, `oncl-api`, `oncl-server`, `oncl-cli`, `openncalayer` и `oncl-nmhost`; если какой-то из них появится, `cargo xtask sdk closure` завершится ошибкой. `oncl-update` в `full` не входит. Он подключается только через собственную feature `distribution` крейта `oncl-plugin` (хранилище пакетов плагинов), которую потребитель включает отдельно; её тесты и место в цепочке публикации описаны ниже.

| feature | что добавляет |
|---|---|
| (minimal) | хеширование, CMS/CAdES B/T/LT/LTA, PKI-валидация, ключи из файлов / встроенных PKCS#12 / JKS / слотов, названных хостом, пакеты (batch), инспекция, отдельные штампы времени |
| `tokens` | аппаратные токены и ID-карты как источники ключей |
| `xml` | XMLDSig, XAdES, WS-Security: подпись / добавление / проверка |
| `pdf` | PAdES: подпись / проверка |
| `jose` | JWS и JWT: создание / добавление / проверка |
| `plugins` | безголовый хост WebAssembly-плагинов (только рантайм, права выдаёт оператор) |
| `full` | всё перечисленное |

Шифрования и расшифрования CMS в этом наборе нет. Для получателей с ключами RSA они есть только в библиотеке `oncl-pki` (`oncl_pki::cms::envelope`, см. [`platform-interop.md`](platform-interop.md)), в API SDK, CLI и HTTP они не выведены. Казахстанского ГОСТ-профиля шифрования нет: провайдер Kalkan не умеет ни согласования ключа, ни ГОСТ-шифра в CMS, а профиль без проверки на нём мы не придумываем. RSA его не заменяет.

При расшифровании открытый текст попадает в приёмник (`StagingSink`) частями до проверки тега GCM: тег стоит в конце сообщения, а держать 1 ГиБ в памяти нельзя. При любой ошибке вызывается `discard`, и результат считается успешным только после `Ok`. Всё, что выдано до `Ok`, предварительное. Гарантию «аутентифицированный профиль не выдаёт данные до проверки» соблюдает только настоящий промежуточный приёмник: временный файл в каталоге, доступном только владельцу, который после `Ok` переименовывается в итоговое имя, а в `discard` удаляется. Готового файлового приёмника в библиотеке пока нет, его должен предоставить вызывающий код; при подключении расшифрования к Engine он понадобится первым.

## 3. API встраивания

Приложение создаёт один `Engine` и открывает по одному контексту на операцию:

```text
EngineServices::hash_only(limits)            // host services, nothing global
    .with_keys(provider, guard)              // key sources + the audit guard
    .with_validation(ValidationServices)     // trust anchors, status transport, clock
    .with_temporary_store(store)             // only for operations that must stage bytes
    .with_cades(...) / .with_plugins(...)    // optional
Engine::new(services)?
engine.begin(ExecutionGrant, OperationPolicy, Arc<dyn OperationControl>)? -> OperationContext
engine.sign / verify / hash / inspect / extend / stamp / ... (request, Source, output, &mut ctx)
```

Всё, что нужно SDK, передаёт ему программа. Из сети, окон или настроек desktop он ничего не берёт:

| что | тип | примечания |
|---|---|---|
| разрешение | `ExecutionGrant` | действия и id ключей, только из доверенного кода хоста |
| ключи | `KeyProvider` (`keys::KeySources` для файлов/inline/named/токенов) | секреты берутся в заём, затираются (zeroize), не попадают в spool |
| аудит | `KeyUseGuard` | `before_use` обязан записать надёжно **до** применения закрытого ключа; отказ запрещает использование; `finish` записывает исход |
| доверие, статус | `ValidationServices` (якоря, промежуточные, `HttpTransport`, `NetworkPolicy`, часы) | строгие политики без статуса закрываются отказом |
| транспорт | `oncl_pki::http::HttpTransport` | CRL / OCSP / RFC 3161; `UreqTransport` — лишь значение по умолчанию; см. пример `custom_transport` |
| часы | `Arc<dyn Fn() -> OffsetDateTime>` | внедряются, чтобы вердикты воспроизводились |
| отмена, прогресс | `OperationControl` | контрольные точки; блокирующий ввод-вывод должен прерываться хостом |
| временное хранилище | `TemporaryStore` | ограниченное, приватное; никогда не хранит ключи и пароли |

Примеры запускаются командой `cargo run -p oncl-core --example <name>`. Они выпускают одноразовую RSA PKI при запуске, не используют сеть, и ключей в репозитории для них нет:

- `sign_file [WORKDIR [FILE]]` и `verify_file WORKDIR FILE` создают и проверяют отсоединённую подпись CMS при строгой валидации; для изменённого документа `verify_file` завершается с кодом 1.
- `custom_transport` подключает к валидации собственный `HttpTransport` приложения; когда сеть недоступна, строгая подпись отклоняется с `NotApplied`.

`tests/examples.rs` запускает их как настоящие процессы, так что примеры не устаревают незаметно.

## 4. Результаты и ошибки

### Вердикт

`Verdict::{Valid, Invalid, Indeterminate}` отвечает на вопрос о подписи и ошибкой выполнения не является. Отчёт отдельно сообщает о целостности подписи, цепочке до якоря, сроке действия, отзыве, доказательстве метки времени и заявленном времени подписания (`CheckStatus::{Passed, Failed, Unavailable, NotApplicable}`). Отсутствующие доказательства дают `Unavailable` или `Indeterminate`, но никогда `Valid`. Отмена, дедлайн и нехватка ресурсов являются ошибками, а не вердиктами.

### Нарушения профиля

Запрос профиля CAdES или PAdES (`cades-b`, `pades-t`, ...) требует больше, чем целостности. Если сама подпись верна, но в CMS не хватает требования baseline, у подписанта остаётся `signature = Passed` и добавляется `ValidationReason::Profile(ProfileViolation)`. Такие нарушения: нет signing-time в подписи CAdES; есть signing-time в подписи PAdES (EN 319 142-1, таблица 1; Kalkan его пишет); тип содержимого не id-data; нет атрибута signing-certificate. На этом профиле такой подписант получает `Invalid` и не заявляет `ades_level`. Ошибки дайджеста, ESS и значения подписи остаются отказами `Signature(..)` и сообщаются рядом с нарушением профиля. Общие профили `pdf` и `cms` baseline не требуют и оценивают те же байты только по целостности и доверию.

### AppliedState

Каждый отказ после момента, когда операция с закрытым ключом могла начаться, несёт `NotApplied`, `Applied` или `Unknown` (`OperationError::applied_state`). SDK не обещает отката, повтора или применения ровно один раз: уже выданная удалённо метка времени или подпись, вычисленная до отказа приёмника вывода, остаются как есть. Если охранник отказал в `finish` после применения ключа, сообщается `Applied`.

### Ошибки

`OperationError` (типизированная ошибка) и `ErrorCode` (`OperationError::code`, стабильные машиночитаемые категории, никогда не выводятся из текста сообщений) публичны. Пока версии ниже 1.0, приложения должны сопоставлять `ErrorCode` с веткой `_`. Ни это перечисление, ни `ValidationReason`, ни `ProfileViolation` сейчас не помечены `#[non_exhaustive]`, поэтому новый вариант (как `ValidationReason::Profile`) ломает сборку потребителей и указывается в заметках о миграции того выпуска, где он появился. Пометить эти перечисления `#[non_exhaustive]` планируется в первом выпуске, которому понадобится новый код; сейчас этого не сделано, так как изменение затрагивает сопоставления во всех потребителях внутри workspace. Текст `Display` предназначен для логов, по нему нельзя ветвить логику.

### Резервы, которые держат отчёты

Результаты, которые удерживает приложение (`ScopedSigners`, промежуточный вывод, результаты пакетов), сохраняют резервы памяти и метаданных и исходную область операции. При бюджете в одну операцию (по умолчанию) освобождайте их до допуска следующей операции, как это делают примеры.

## 5. Лимиты

`ResourceLimits::default()` (профиль движка по умолчанию; хост может его менять):

| лимит | по умолчанию |
|---|---|
| операций одновременно | 1 |
| входной документ | 1_073_741_824 байт (1 ГиБ) |
| контейнер (структура CMS/XML/PDF) | 1_073_741_824 |
| обрамление (framing) | 67_108_864 |
| вывод | 2_214_592_512 (input + container + framing) |
| учитываемая живая память | 1_073_741_824 (1 ГиБ) |
| scratch (временное хранилище) | 8_589_934_592 |
| метаданные | 67_108_864 |
| дедлайн операции | 300 с от допуска, не перезапускается |

Документ больше 1 ГиБ отклоняется типизированной ошибкой `InputLimit`. Приложение может поднять `input_bytes`, но гарантирован только 1 ГиБ. Это лимиты учёта, а не измерение RSS процесса. Приёмочный прогон «1 ГиБ / 1 ГиБ» (`cargo xtask platform-proof`) пройден, 70 из 70 случаев; см. [`platform-acceptance.md`](platform-acceptance.md). Лимиты отдельных форматов (пакет до 1024 элементов, 8 подписей на токен JOSE, 10_000 итераций KDF при инспекции и другие) описаны в соответствующих модулях. Унаследованные интерфейсы плагинов NCALayer сохраняют свои контрактные лимиты на строки и Base64, лимиты SDK на них автоматически не распространяются.

### Подписанные результаты и `container_bytes`

`input_bytes` ограничивает документ, а не подпись. Подписанный результат для документа размером ровно `input_bytes` может превысить этот лимит только на классифицированные байты контейнера, в пределах `container_bytes` и собственного предела формата, и SDK снова читает такой результат из любого `Source` (файл, сокет, HTTP-загрузка).

Приложение, которое обязано принять загрузку целиком до начала работы (`oncl-server`), складывает такой ввод во временное хранилище через `FrozenInput::capture_wire`. Этот вызов не списывает ни один из двух лимитов: он держит не больше оставшегося лимита документа плюс оставшегося `container_bytes`, а необязательный максимум сужает это значение. Затем движку передаётся `FrozenInput::wire_reader`, внешний источник известной длины с произвольным доступом. Движок списывает и классифицирует эти байты так же, как файл, поэтому учёт совпадает с SDK и CLI. Допущенный снимок таких байт движку не передаётся: `FrozenInput::reader` их отклоняет, а `wire_inspection_reader` служит для повторного чтения в той же операции, когда приложению нужны собственные проверки. Данные, которые вообще не являются документом (например, доказательства для валидации со своими границами), можно сохранять тем же способом с указанием максимума.

Ключ сервера `container_bytes` (по умолчанию 1 ГиБ) соответствует `ResourceLimits::container_bytes` движка. Предел размера запроса с подписанным `input` равен `input_bytes + container_bytes + framing_bytes + 64 КиБ` (см. `docs/user/http-api.md`).

### Приём ввода без занятия слота

Пока приложение ждёт медленного клиента, принимая байты запроса, оно не должно занимать на это ожидание слот `max_in_flight` движка или поток. `Engine::admit_intake` работает как `Engine::admit`, но без слота: память, временный диск, метаданные, лимиты документа, контейнера и обрамления, дедлайн и управление списываются так же, как при обычном допуске. Слот занимает `OperationAdmission::occupy_slot` (или, не позднее, `Engine::begin_admitted`), когда ввод получен; если все слоты заняты, возвращается тот же `CapacityExceeded`, ничего не меняется, и вызов можно повторить. Число таких операций приложение ограничивает само.

Две формы API принимают байты частями вместо одного вызова: `oncl_pki::io::InputSpool` (`document` для `FrozenInput::capture`, `wire` для `FrozenInput::capture_wire`; `push` на каждую часть, `finish` возвращает `FrozenInput`) и `oncl_pki::digest::HashStream` (для `hash_source`). Каждая часть учитывается, проверяется по лимиту (на пределе пробуется байт N+1, при превышении `InputLimit`) и сверяется с управлением и дедлайном операции так же, как в форме с одним вызовом. Отличие одно, по памяти: `HashStream` списывает с операции свой буфер в 256 КиБ, а `InputSpool` буфера не держит и памяти не списывает (часть пишется сразу, не больше `IO_CHUNK_BYTES` за одну запись). Если приложение накапливает части перед `push`, этот буфер принадлежит ему и списывается им самим. `oncl-server` один раз на запрос резервирует `IO_CHUNK_BYTES` через `ResourceScope::reserve_memory` и передаёт данные частями по 256 КиБ; перед ожиданием клиента он сбрасывает накопленное, чтобы правила темпа загрузки не относили время записи на диск на счёт клиента. На этапе загрузки `oncl-server` использует все три механизма (см. `docs/user/server.md`).

### Учёт CAdES

Проверка, достройка и со-подпись в `cms::ades` (и простая со-подпись CMS) читают байты подписи один раз классифицирующим парсером CMS, одновременно складывая их во временное хранилище. Структура SignedData (заголовки, сертификаты, значения отзыва, signer infos и их токены меток времени) считается контейнером и ограничена `container_bytes`; документом считается только содержимое. Отсоединённое содержимое читается отдельно и списывается с `input_bytes`. Отсоединённый документ, уже допущенный приложением (читатель `FrozenInput`, как у временного хранилища в `oncl-server`), читается повторно и второй раз не списывается; это одинаково для verify, extend и co-sign.

Присоединённый результат CAdES состоит из документа и подписи. Документ размером ровно `input_bytes` можно снова проверить, достроить и со-подписать; документ на один байт больше даёт `InputLimit`. Структура подписи, которая не помещается в лимит контейнера, даёт `ContainerLimit` (или `InputLimit`, если весь присоединённый ввод уже при приёме больше `input_bytes + container_bytes`), и всё это происходит до применения ключа.

Доказательства, которые движок копирует из ввода (сертификаты, статусы, токены меток времени), снова списываются с `container_bytes`, а extend и co-sign списывают и записываемую структуру. Замер: verify 7081 байт контейнера, extend до LT 17429. Поэтому лимит контейнера должен вмещать исходную структуру, эти доказательства и выходную структуру; доказательства дополнительно ограничены `EvidenceLimits`. Временное хранилище (`TempLimit`) занимает до `input_bytes + container_bytes` плюс одна часть. Простой профиль `cms` (`cms::stream::verify`/`extract`) читает ввод так же.

### Надбавка контейнера для подписанных PDF

При обратном чтении PDF, который уже несёт подписи, объём может превысить лимит документа на ограниченную надбавку. Её предел:
`min(container_bytes, (max_revisions - 1) * 4 * max_object_bytes + PdfLimits::max_evidence_bytes)`
(`crates/oncl-pdf/src/verify.rs`, `lib.rs`). По умолчанию это около 188 МиБ (`max_revisions` = 16, `max_object_bytes` = 1 МиБ, `PdfLimits::max_evidence_bytes` = 128 МиБ). `max_evidence_bytes` является полем слоя PDF; ни одно поставляемое приложение (CLI, сервер, desktop) пока не выводит его из `EvidenceLimits.max_total_bytes`, поэтому везде действует значение по умолчанию 128 МиБ.

### Реестр плагинов и объявленные операции (`plugins`)

`PluginRegistry::install(manifest, package, wasm, limits, policy)` сохраняет вместе с плагином `PackageHash`. `PackageHash::File` равен SHA-256 всего файла пакета, прочитанного `oncl_plugin::Package::read`. `PackageHash::Loose` (`plugins::loose_package_hash(manifest_toml, wasm)`; его используют CLI и сервер, которые загружают манифест и модуль по отдельности) вычисляется по этим двум входам с разделением доменов. Значения разных видов никогда не совпадают и кодируются разными тегами (`PackageHash::canonical`). Хеш Loose не является хешем файла пакета, и ни один из них не сверяется с модулем: реестр принимает значение как есть. Приложение, которое загружает плагины через `oncl_plugin::Store` (feature `distribution`, этим крейтом не включается), обязано брать манифест, модуль и `File(package.sha256)` из одного и того же значения `Package`. `BuiltinInfo::sha256` (хеш только модуля) не относится ни к одному из видов. Для аудита плагин идентифицируется как `PluginIdentity { id, package, version }`, а не по имени из манифеста (`Engine::plugin_identity`).

Плагин без `[[operations]]` работает как раньше: его права и `PluginPermission::with_keys` жёстко задают ключ. Для плагина, который объявляет операции, `PluginRegistry::allow_declared` (и `allow_declared_with_pki`) добавляет политику реестра, построенную только из манифеста: объявленные импорты для одной тройки `(plugin, operation, caller)` и любой ключ. Конкретный ключ проверяется в разрешении на конкретный вызов (там же `PluginPermission::with_keys`), и это разрешение никогда не принимает объявленную политику за ключ.

Объявленная `network` соблюдается. `none` не разрешает ни одного адреса. `pki` разрешает только адреса на PKI-хостах, которые передаёт приложение (обычно `oncl_plugin::NCA_PKI_HOSTS`, включая поддомены). Операции с `network = [urls]` в этом выпуске в ручном окне не запускаются и в списке не показываются (`PluginRequestError::NetworkUnsupported`). Может ли вызывающий данного вида использовать вариант операции `manual` или `server`, проверяет приложение, которое связывает всё вместе.

`Engine::plugin_operations` перечисляет `Manifest::manual_operations` (без сетевых URL). `Engine::plugin_request` собирает точный текст запроса для модуля из разобранного JSON-шаблона и типизированных значений `PluginParam`, без вставки текста. Шаблоном может быть любой JSON-объект; на любой глубине целиком заменяется каждое строковое значение-плейсхолдер, но никогда не ключ и не часть строки. Итоговая длина вычисляется заранее: если она больше `max_transfer` плагина, запрос отклоняется с `ErrorCode::InputLimit` до подстановки; иначе текст пишется один раз в буфер этого размера.

Документы передаются в стандартном base64 и не могут быть пустыми. Текст считается в символах, как и его объявленный лимит, а если профиль ключа читает его как XPath, он проверяется `Source::check_value`. Текст, который сам подписывается, не может содержать управляющих символов, кроме `\n` и `\t`, а также двунаправленных и невидимых символов (`InvalidValue`; окно передаёт ту же строку `&str`, которую показывает). Операция с ключом обязана объявлять `network = "pki"`, а текстовый параметр может быть подписываемым содержимым ключа любого вида (его байты UTF-8). Текст не нормализуется.

Вывод представляет собой компактный JSON с отсортированными ключами объектов (порядок ключей шаблона не сохраняется); целые числа выводятся как записаны, а число шаблона, не являющееся `i64`/`u64`, отклоняется (`InvalidTemplate`) и заново не печатается. Необъявленные операции, операции не manual, операции `derived`, операции с сетевыми URL и неверные параметры отклоняются `PluginRequestError`, всегда с `NotApplied`, до использования какого-либо ключа. Согласия пользователя этот API не касается; билет использования ключа, его охранник и одобренный ручной вызов описаны ниже.

#### Билет использования ключа и `PluginConsentGuard` (`plugins`)

Плагин, в манифесте которого объявлены какие-либо `[[operations]]`, вызывается через `plugin_call` только под объявленным именем операции, независимо от того, кто выбрал метку (ручное окно, grant сервера, флаг CLI). Любая другая метка отклоняется до запуска модуля (`PermissionDenied`, `NotApplied`, `OperationContext::plugin_refusal() == Some(TicketRefusal::UndeclaredOperation)`). Сервер пропускает grant с необъявленной операцией такого плагина и пишет об этом ошибку в лог, CLI отклоняет вызов. Плагины без объявлений работают как раньше.

Вызов под объявленным именем получает билет. Для каждого из `keys_sign_raw/cms/cms_ex/xml/xml_ex/xades` Core один раз декодирует аргументы, строит из этого же декодированного значения `plugins::PluginUse` и кладёт его в контекст операции. `AuthorizedSigner::sign_digest` переносит билет в `KeyUseEvent` (`KeyUseEvent::plugin()`; `None` для любого использования документом и для операций плагина без объявлений).

Билет содержит идентичность плагина (`id`, `PackageHash`, версия), объявленную операцию, вызывающего, вид подписи, handle и `KeyId` единственного привязанного ключа, `ContentBinding` (SHA-256 и длина подписываемых байт; `prehashed` для входа CMS `Digest`) и `options_sha256`. Хеш опций равен SHA-256 от `oncl_plugin::operations::Profile::encode` для профиля, построенного из фактических аргументов, тем же кодировщиком, которым `KeyUse::options_sha256` кодирует объявленный профиль.

Аргументы, которые нельзя выразить профилем, отклоняются до открытия ключа: CMS с co-sign, `attrs.extra`, `econtent_type`, выбор `digest`, сертификаты `Extra`, собственный TSA, signingTime не по умолчанию, XML `signature_id` или объект signing-time, XML `transforms` не в виде проверяемого списка, цепочка XAdES. XML `transforms` принимаются только как проверяемый список: сначала `enveloped`, затем не больше одной канонизации (пустой список и любой другой порядок отклоняются); список входит в хеш опций. `cosign = Auto` принудительно превращается в `Never`, поэтому содержимое билета совпадает с тем, что реально подписывается. Импорт, вид которого операция не объявляет или чьё объявленное содержимое `derived`, отклоняется.

Объявленная операция привязывает не больше одного ключа. Каждый импорт, принимающий ключ (`keys_describe`, `keys_chain`, `keys_release`, импорты подписи), на любой другой handle отвечает одним и тем же `PermissionDenied`, а `keys_release` для привязанного handle идемпотентен. Билет допускает ровно одно использование (`max_uses = 1`).

`KeyUseEvent::plugin()` есть только с feature `plugins` крейта `oncl-core`. Доступный без неё `KeyUseEvent::is_plugin()` сообщает, несёт ли событие билет (без feature всегда `false`). `KeyUseGuard` приложения, которое регистрирует плагины с объявленными операциями, ОБЯЗАН отклонять любое событие с `is_plugin()`, если сам он не является охранником плагинов: охранник документов, который игнорирует билет, авторизовал бы использование по билету как использование документом. `oncl-server`, `oncl-cli` и `ConsentGuard` из `oncl-ui` так и делают.

`PluginConsentGuard` (`KeyUseGuard`) является охранником движка плагинов. `before_use` отклоняет событие (`PermissionDenied`, ключ не применён), если только событие не несёт билет и охранник не держит непросроченный `PluginApproval` для того же вызова, идентичности плагина, операции, вызывающего, ключа и handle, с одним неизрасходованным `ApprovedUse`, у которого вид, содержимое и хеш опций равны билету; тогда это использование расходуется. Причина отказа записывается по `OperationId` в ограниченный лог на `REFUSAL_LOG` (64) записей: `refusals(id)`, `take_refusals(id)`, `refusal_log()`. Без одобрения охранник отклоняет всё, в том числе использование ключа документом без билета, поэтому для документов нужен отдельный движок. `PluginApproval` (не `Clone`, не `Deserialize`, публичного конструктора нет) выдаёт Core (ниже), и его nonce принимается один раз. Охранники сервера (`DurableAuditGuard`) и CLI (`Authority`) отклоняют каждое использование по билету, пока у них нет собственных grants для плагинов (`plugin_bytes`); плагины без объявлений работают как раньше.

#### Manual window (ручное окно): сводка согласия, одобрение, одобренный вызов (`plugins`)

Core выполняет три шага в указанном порядке (`docs/design/manual-plugins.md`, 4.2, 4.3, 4.8). `plugin_prepare` и `plugin_call_approved` принимают один и тот же `ManualCall { plugin_id, operation, params, key: &PluginKeyBinding, caller: &CallerContext }`.

1. `Engine::plugin_prepare(&ManualCall, &mut OperationContext)` возвращает `PluginPrepared` или `PluginPrepareError` (всегда `NotApplied`).

   Он один раз открывает ключ: вход в токен или расшифровка хранилища ключей происходят здесь и ещё раз при вызове. Поэтому приложение запрашивает секрет до показа согласия и кладёт его в запрос ключа в привязке. Неудачное открытие возвращается как `KeyUnavailable` без указания причины.

   Параметры проверяются так же, как в `plugin_request`. Затем фиксируется, что именно подписывается: байты привязанного параметра, их SHA-256 и длина. Для профиля `cms_ex` с `content_form` = `digest` дайджест считает сам Core хеш-алгоритмом, который соответствует алгоритму подписи привязанного ключа, той же функцией, которую затем использует подписант: ГОСТ 34.311, Стрибог или SHA-2 по сертификату и политике контекста. Дайджест, названный плагином, никогда не используется. Фиксируются и опции (`KeyUse::options_sha256`, где источники `param:` профиля заполнены из типизированных текстовых параметров тем же кодировщиком, что и в билете).

   `caller` обязан быть `CallerContext::LocalOperator` (у ручного окна нет origin), а привязка ключа должна нести публичные метаданные (`with_public_metadata`: alias и сертификат). Метаданные являются заявлением приложения о ключе, которым будет сделана подпись: Core показывает их и передаёт плагину (`BoundKey`, `keys_describe`), а `plugin_prepare` сверяет сертификат с тем, что хранилище держит для этого ключа (`CertificateMismatch`).

   `PluginPrepared::summary()` возвращает `ConsentSummary`, доверенное описание для показа пользователю: идентичность `{id, PackageHash, version}`, имя операции, вид, число использований, объявленный профиль с подставленным текстом пользователя, хеш опций, имя параметра с содержимым, длину, SHA-256 и дайджест для prehashed, alias ключа, серийный номер, CN субъекта, отпечаток SHA-256 и `not_after`, а также PKI-адреса, зарегистрированные приложением. Текста плагина в сводке нет (`name`, `description`, `label` остаются в собственном кадре плагина). `key.alias` и `key.subject_cn` являются строками приложения и сертификата, и отрисовщик обязан их экранировать.

2. `UserConfirmation::after_user_confirmed(&ConsentSummary)` является единственным способом получить токен, который принимает `PluginPrepared::approve(confirmation, ttl)`. Приложение обязано вызывать его только из обработчика собственного действия пользователя на элементе подтверждения, после того как отрисована именно эта сводка. Подтверждать автоматически, заранее или по сохранённому ответу нельзя (ничего не сохраняется). Токен содержит SHA-256 показанной сводки, поэтому подтверждение одной сводки не одобряет никакую другую. Токен не `Clone` и не `Copy`.

   `approve` возвращает `PluginApproval`, в котором записаны: вид, привязка содержимого и хеш опций из шага prepare; одно использование (`max_uses = 1`); вызов контекста, для которого он подготовлен; дедлайн `ttl` по монотонным часам от текущего момента (`None` означает `APPROVAL_TTL` = 120 с; больший запрос урезается до этого значения, ноль отклоняется); nonce из 16 байт CSPRNG операционной системы (при сбое генератора одобрение не выдаётся).

3. `Engine::plugin_call_approved(&ManualCall, PluginApproval, &ManualHost, &mut OperationContext) -> ApprovedCall` запускает модуль в ручном окне.

   Использование заново выводится из параметров, переданных при этом вызове, и одобрение, выданное не ровно для них (другой документ, текст, ключ или handle, вызывающий, операция, вызов; истёк срок), отклоняется до запуска модуля. Модуль никогда не видит документ, который пользователь не одобрил. Затем строится запрос (`plugin_request`), одобрение передаётся `PluginConsentGuard` движка и запускается `oncl_plugin::Compiled::call_manual` со свежим `BoundInteraction`. `BoundKey` строится из того же `PluginKeyBinding`, которым подписывает ключевой модуль; часы берутся из валидации и читаются в момент вызова; транспорт и `OcspCache` берутся у приложения из `ManualHost`; origin нет. Окончательную проверку при использовании ключа выполняет охранник. По окончании вызова одобрение отзывается (`Drop`, то есть и при trap, ошибке и панике).

   Движок должен быть построен через `EngineServices::with_plugin_keys(provider, Arc<PluginConsentGuard>)`, и это его единственный охранник ключей. `with_keys` его сбрасывает, и тогда одобренный вызов отклоняется с `TicketRefusal::NoGuard`. Одновременно выполняется только один одобренный вызов (`Busy`). Документы обрабатывайте на другом движке: `ConsentGuard` desktop отклоняет событие с билетом, а охранник плагинов отклоняет событие без билета.

Одобрение привязано к SHA-256 сертификата подписанта. Его несут `ApprovedUse` и `PluginUse`, показывает `ConsentSummary.key.fingerprint_sha256`. `plugin_prepare` один раз открывает ключ и отклоняет вызов (`CertificateMismatch`), если сертификат в хранилище не совпадает с метаданными привязки. В момент подписи `AuthorizedSigner` записывает в билет отпечаток сертификата, который держит аренда ключа, и охранник (а также быстрая проверка в `plugin_call_approved`) отклоняет другой сертификат с `TicketRefusal::CertificateChanged`; ключ при этом не применяется. Alias служит только для показа и не сверяется. Алгоритм prehash выбирается по тому же строгому правилу, что у подписанта.

Практические замечания. Давайте каждому движку собственный `PluginConsentGuard`: у него один слот одобрения. Вызов, отклонённый как `Busy`, расходует своё одобрение, и пользователю придётся подтвердить снова. Приложения ОБЯЗАНЫ задавать дедлайн в контексте, который передаётся в `plugin_call_approved`, потому что плагин держит слот операции, пока не истечёт дедлайн или топливо. Дедлайн одобрения отсчитывается монотонным `Instant`, который может стоять, пока система находится в спящем режиме.

`ApprovedCall` сообщает фактический исход: `result()`/`response()` (строка ответа модуля), `applied()` (`Applied`, в том числе когда модуль упал после использования ключа; `Unknown`, когда само приложение исход не сообщило; `NotApplied` для каждого отказа) и `refusals()` (типизированные `TicketRefusal` этого вызова от охранника или от проверок до запуска модуля, а также `NoGuard`, `Busy`, `Replayed`, `UndeclaredOperation`, `Caller`).

#### Подкоды отказов и факты аудита (`plugins`)

`ErrorCode` для плагинов не расширяется. Вместо этого у каждого отказа плагина есть `PluginRefusalCode` (стабильный, `#[non_exhaustive]`). `id()` возвращает строку в kebab-case (`content-mismatch`, `package-changed`, `approval-expired`, `not-declared`, `not-granted`, ...), которая никогда не переиспользуется и не перенумеровывается. `ALL` перечисляет все подкоды в порядке добавления, а тест фиксирует полный список id, так что любое изменение делается сознательно.

`error_code()` возвращает `ErrorCode`, с которым сообщается отказ, и он всегда совпадает с `OperationError::code`: `PermissionDenied` для отказов по билету, вызывающему и объявлению, `InputLimit`/`InvalidInput` для параметров, а также `UnsupportedAlgorithm`, `MissingKeyProvider`, `Io`. Подкод можно получить для каждой причины: `From<TicketRefusal>`, `From<&PluginRequestError>`, `From<&PluginPrepareError>`, `From<ApprovalIssueError>`, `From<ApprovalRejected>` и метод `subcode()` у каждой из них. `TicketRefusal::NotGranted` означает использование ключа сервером или CLI, которое не покрыто ни одним grant оператора. `TicketRefusal::AuditFactTooLong` означает, что версию или id grant нельзя записать в аудит (больше 255 байт); такое использование отклоняется до обращения к журналу. `DurableAuditGuard::with_plugin_policy` возвращает `io::Result<Self>` (ошибка, если охранник уже разделён).

Где приложение читает подкоды:

- `ApprovedCall::subcode()`: первый отказ охранника, иначе причина, по которой вызов не удалось подготовить; `None`, если ничего не отклонено, в том числе после ошибки, случившейся после применения ключа;
- `OperationContext::plugin_refusal_code()`: необъявленная метка, отклонённая в `plugin_call`;
- для сервера с `DurableAuditGuard`: `take_plugin_refusals(operation_id)`, преобразуемый через `PluginRefusalCode::from`.

Сам плагин подкода никогда не видит: он получает голый `PermissionDenied` без текста причины.

`PluginAuditRecord::from_ticket(&PluginUse, nonce, grant_id)` описывает использование для аудита: плагин `{id, вид пакета + sha256, version}`, операцию, `PluginUse::digest()` (дайджест билета), SHA-256 nonce одобрения с разделением доменов (сам nonce не записывается), SHA-256 и длину содержимого, признак того, что содержимое является prehashed-дайджестом, SHA-256 опций, вид вызывающего (не его имя), `declared` и `grant_id` оператора. Байтов документа, параметров и секретов в записи нет. Когда использование авторизовано, `PluginConsentGuard` выдаёт эту запись событием `tracing` с `target = "oncl::plugin_audit"`; отказ с подкодом и дайджестом билета выдаётся событием `warn`. Отказы, которые до охранника не доходят (ошибка запроса или prepare, одобрение, отклонённое при вызове), выдаются событиями `warn` того же target с подкодом. Долговременная форма аудита описана в `docs/user/server.md` (раздел об аудите).

`PluginApproval::new`, `ApprovedUse::new` и другие конструкторы не публичны. С feature `testing` крейта `oncl-core`, которая никогда не входит в выпуск, `PluginApproval::for_tests`, `ApprovedUse::for_tests`, `PluginUse::for_tests` и `KeyUseEvent::with_plugin_ticket_for_tests` создают то, что Core сам никогда бы не создал; они нужны для тестов охранников. Программы выпуска собираются с `-p`, но `cargo build --workspace --all-targets` и `cargo test` объединяют `testing` из dev-зависимостей в те же бинарники. Поэтому CI запускает `cargo xtask check-release-features`: он читает `cargo tree -p <openncalayer|oncl-cli|oncl-server|oncl-ui> -e normal -f "{p} [{f}]"` (features обычного дерева, без dev-зависимостей) и завершается ошибкой, если у какого-либо крейта включена `testing`.

## 6. Semver, версии и миграция

- Версия общая для всех крейтов SDK и приложений (`[workspace.package]`). У плагинов свои версии.
- До 1.0 (`0.1.0-alpha.N`) любая альфа может ломать публичный API любого крейта SDK. Каждая поломка требует повышения версии и заметки о миграции ниже. Внутренние модули не становятся стабильным контрактом только потому, что они `pub` внутри workspace.
- Версия SDK в момент изменения равна следующей невыпущенной версии; её берут из тегов и манифестов, а не угадывают. Версия `[workspace.package]` в этом дереве — `0.1.2-beta.1`; предыдущий
  выпущенный тег — `v0.1.1`.
  При повышении меняются вместе: `[workspace.package] version`, закрепления `=<версия>` цепочки SDK в `[workspace.dependencies]` (нужны для `cargo package`), четыре встроенных `plugin.toml` (`version`, `min_core`), lock-файлы (`Cargo.lock`, `plugins/Cargo.lock`, `crates/oncl-pdk/example/Cargo.lock`) и строка статуса в README, если в ней указан выпуск. Закрепление, расходящееся с версией workspace, делает весь workspace неразрешимым (`failed to select a version for the requirement oncl-gost = "=0.1.2-beta.1"`), так что забытое закрепление в выпуск не попадёт.

### Переход с 0.1.1 на 0.1.2

Сравнение с выпущенным `v0.1.1`. Публичный API меняется у `oncl-update` и у `oncl-plugin` с feature `distribution`. У `oncl-gost`, `oncl-registry`, `oncl-pki`, `oncl-pdf`, `oncl-protocol`, `oncl-pdk`, `oncl-xml`, `oncl-token`, `oncl-flows` и `oncl-core` он прежний.

Что перестанет собираться в `oncl-update` и как это исправить:

- `choose_plugin` и `offer` принимают `&Catalog` вместо `&Index`. Прежнее поведение даёт `Catalog::owner(index)`: каталог из одного индекса владельца, в котором все издатели недоступны.
- `PluginChoice` помечен `#[non_exhaustive]` и получил вариант `PublisherRevoked(&PublisherName)`: плагин отозванного издателя выключают так же, как при `Withdrawn`. В `match` нужна ветка `_`.
- У `PluginRelease` новые поля `publisher: Option<tuf::PublisherName>` и `capabilities: Option<DeclaredCapabilities>`. Из JSON они не читаются (`#[serde(skip)]`); в литерале структуры задайте оба равными `None`.
- У `tuf::TufError` новый вариант `Delegation { role: RoleName, error: DelegationError }`, исчерпывающему `match` нужна ветка для него.
- У `tuf::Limits` новые поля `delegated` (128 КиБ на файл роли), `max_delegations` (32 роли) и `max_role_targets` (256 целей в роли). В литерале задайте их или допишите `..Limits::default()`.
- У `tuf::TrustState` новое поле `delegated: BTreeMap<RoleName, RoleState>`; в литерале подойдёт `BTreeMap::new()` или `..TrustState::default()`. Файл состояния, в котором сохранены роли издателей, версия 0.1.1 не прочитает: `TrustState` объявлен с `deny_unknown_fields`.
- `tuf::Targets::from_signed(signed)` стал `from_signed(signed, profile)`. Поле `Targets::targets` теперь `BTreeMap<TargetPath, Target>` вместо `BTreeMap<String, Target>`. Поиск по `&str` работает как раньше (`TargetPath: Borrow<str>`), но ключи при обходе имеют тип `&TargetPath` (строку даёт `as_str()`).
- Функция `tuf::model::valid_target_path` удалена, её заменяет `TargetPath::parse(path).is_ok()`.
- `tuf::layout::target_file_path` принимает `&TargetPath` и возвращает `String` вместо `Option<String>`.

Что перестанет собираться в `oncl-plugin` (feature `distribution`) и как это исправить:

- `Store::install(package, bytes, source)` стал `install(package, bytes, source, publisher)`: `publisher: Option<&tuf::PublisherName>` — издатель выпуска каталога (`PluginRelease::publisher`), для порта из индекса владельца и для файла пользователя `None`.
- У `Installed` новое поле `publisher: Option<PublisherName>`, у `StoreState` — `declined_replacements: BTreeMap<String, String>`; в литерале задайте `None` и `BTreeMap::new()`. Файл состояния с ними версии 0.1.1 и 0.1.2-beta.1 читают: оба поля без значения не пишутся, а незнакомые поля они пропускают. Но, сохранив состояние заново (после отката на них проверкой здоровья или вручную), они оба поля теряют: издатель затем восстанавливается по префиксу, а отказы от замены порта забываются, и замену предложат снова. Имя издателя, которое новая версия не принимает, читается как `None` (журнал `warn`), остальное состояние не теряется.

Что меняется в поведении:

- `TufClient` по умолчанию читает репозиторий в профиле `Profile::Delegating`: член `delegations` верхнего `targets` принимается, а `refresh` его не читает. Клиент 0.1.1 отказывал в таком файле с `TufError::Unsupported`. Прежнее поведение включает `TufClient::with_profile(Profile::Legacy)`.
- С feature `testing` метод `tuf::testing::Repo::client` создаёт клиента в профиле `Delegating`, а у `Repo` появилось публичное поле `delegations`.

Что добавлено в `oncl-update`:

- модуль `catalog` (каталог плагинов: индекс владельца и выпуски сторонних издателей, `docs/design/publishers.md`). Из корня крейта реэкспортируются `Catalog`, `CatalogBuilder`, `CatalogError`, `DeclaredCapabilities`, `EntryRejected`, `EntryRejection`, `PublisherPolicy`, `PublisherRelease` и `PublisherState`. Остальное доступно как `catalog::…`: `PluginId`, `IdPrefix`, `ModuleName`, `BundleName`, `PROJECT_PREFIX`, `ActivePublisher`, `Publisher`, `PublisherDisplay`, `RevokedVersion`, `Standing`, `CapabilitiesError`, `PublisherTarget`, `MAX_URL`, `MIRROR_BASE`, `mirror_url`, `ReleaseSource`, `SourceError` и `SourceVcs`;
- метод `UpdateError::unreachable()`;
- в `tuf`: модули `delegation` (`Delegations`, `DelegatedRole`, `RefusedRole`) и `names` (`TargetPath`, `RoleName`, `PublisherName`, `PathPattern`, `NameError`, `NameKind`), типы `Profile`, `DelegationError`, `RoleState`, `Delegated` и `VerifiedRole`, методы `TufClient::with_profile`, `TufClient::profile`, `TufClient::delegated`, `TufClient::verify_cached_role` и `Targets::delegations`, функции `ed25519::verify_threshold` и `layout::delegated_path`; `PublisherName` (де)сериализуется строкой с проверкой грамматики;
- функция `choose_installed` (как `choose_plugin`, но с издателем, записанным при установке), методы `Catalog::publisher_state_of`, `Catalog::is_installed_revoked` и `CatalogBuilder::capabilities`, вариант `EntryRejection::CapabilitiesUnreadable`.

Что добавлено в `oncl-plugin` (feature `distribution`): `TryFrom<&DeclaredCapabilities> for Capabilities` (правила таблицы `[capabilities]` манифеста, без `builtin`); у `Store` методы `set_publisher`, `set_declined_replacement`, `replace` (порт заменяется плагином издателя одной записью состояния, файлы порта удаляются после неё; уже установленный плагин не заменяет порт, `AlreadyExists`), `prune_files` (удаляет пакеты и настройки, которых нет у установленных плагинов и которые не менялись дольше `Store::PRUNE_AFTER`, 10 минут; настройки встроенных модулей остаются), `save_publishers`, `load_publishers`, `save_role`, `load_role` и `prune_roles` (файлы `<data>/plugins/catalog/publishers.json` и `<data>/plugins/catalog/roles/pub-<имя>.json`). `Store::remove` порта забывает и отказ от его замены.

Сборка: `oncl-gost` и `oncl-pki` берут `streebog` и `hmac` из crates.io, поэтому раздел `[patch.crates-io]` с форками из заметки rc.2 → rc.3 потребителю SDK больше не нужен. Новая зависимость `oncl-gost`: `subtle` `=2.6.1`.

Поле `Targets.delegations` и вариант `TufError::DelegationsMissing` существовали только в `main` после `v0.1.1` и ни в один выпуск не попали.

## 7. Готовность к публикации

Цепочка SDK в порядке публикации (каждый крейт после тех, от которых он зависит):

`oncl-gost` → `oncl-registry` → `oncl-pki` → `oncl-pdf` → `oncl-protocol` → `oncl-pdk` →
`oncl-xml` → `oncl-token` → `oncl-flows` → `oncl-update` → `oncl-plugin` → `oncl-core`

Это все крейты, достижимые из `oncl-core` со всеми features и с feature `distribution` крейта `oncl-plugin` (она добавляет `oncl-update`). У них заполнены `description`, `license` (Apache-2.0), `repository`, `rust-version`, `keywords`, `categories`, список `include` и указано `publish = true`. В `include` входят исходники, данные, которые встраивает сборка, `LICENSE` и `NOTICE`; тестов, fixtures, корпусов, скриптов и скриптов независимой проверки там нет. `oncl-core` дополнительно поставляет `README.md`, три примера и `THIRD-PARTY.txt`. Все остальные крейты (`oncl-ui`, `oncl-desktop`, `oncl-api`, `oncl-server`, `oncl-cli`, `openncalayer`, `oncl-nmhost`, `oncl-tls`, `oncl-trust`, `oncl-ipc`, встроенные модули, их сборочные и тестовые крейты, прослойки для Windows 7, `oncl-testkit`, `oncl-port-tests`, плагины) остаются с `publish = false`, как задано по умолчанию в workspace.

`cargo xtask sdk smoke` проверяет цепочку без реестра и без загрузки:

1. `cargo package --offline` всей цепочки с верификацией: каждый крейт собирается из собственного упакованного tarball, а соседние крейты берутся из локального оверлея tarball'ов cargo. Сторонние пакеты должны лежать в кэше cargo (`cargo fetch --locked`), загрузок во время проверки нет.
2. Файлы `.crate` распаковываются, и проверяется, что внутри нет `tests/`, `fixtures/` и `target/`, а `LICENSE` и `NOTICE` есть.
3. Отдельный крейт (со своим `[workspace]` и lock-файлом) зависит от `oncl-core` (`full`) и `oncl-pki` по path на распакованные исходники, с `[patch.crates-io]` на остальные распакованные крейты. В его `cargo metadata` не должно быть локальных пакетов вне распакованных исходников, а в `cargo tree` не должно быть запрещённых крейтов интерфейса, desktop, обновления, сервера и рантайма. Затем он собирается и запускается: настоящие подпись и проверка CMS, изменённый документ отклоняется, подпись без сети отклоняется с `NotApplied`. В этом процессе нет ни дисплея, ни демона, ни сборщика телеметрии, ни слушающего порта.

Что не проверено и не заявляется:

- Загрузка в реестр не выполнялась, это отдельное решение. Форков в цепочке больше нет: `oncl-gost` и `oncl-pki` берут `streebog` и `hmac` из crates.io, а Streebog и HMAC для секретного ввода — код самого `oncl-gost` (`src/streebog_secret.rs`, `src/secret_hmac.rs`).
- Доступность и принадлежность имён крейтов в реестре не проверены.
- `cargo publish --dry-run` против настоящего реестра, загрузка и проверки после неё выполняются только при отдельно согласованной публикации.
- Проверка потребителя работает только на платформе, где запущена; матрица Linux/macOS/Win7 проверяется отдельно (приёмочный прогон «1 ГиБ / 1 ГиБ» пройден, см. раздел 5).

Команды: `cargo xtask sdk closure`, `cargo xtask sdk smoke [--keep]`, `cargo xtask sdk licenses [--check]`.

`cargo test -p xtask --test sdk_delivery` работает без сети и без сборки, только через `cargo metadata` и `cargo tree`. Он проверяет, что множество крейтов с `publish = true` равно `xtask::sdk_delivery::CHAIN` и цепочка идёт в порядке зависимостей; что ни один набор features `oncl-core` не содержит Slint, winit, tokio, axum, hyper, velopack или другого запрещённого крейта; что `THIRD-PARTY.txt` актуален (устаревшая копия обнаруживается); что крейт из зависимостей, отсутствующий в карте реестра, даёт ошибку с его именем, а не пропускается молча.

Долгая проверка запускается явно (владельцем выпуска или в CI; ни в один workflow она не подключена): из корня workspace на машине с заполненным кэшем реестра (`cargo fetch --locked`) выполните `cargo run -p xtask -- sdk smoke`. Успех означает код 0 и последнюю строку `SDK-CONSUMER-OK`; `--keep` оставляет `target/sdk-smoke` для разбора. Нужен `tar` в `PATH` (GNU или bsdtar). Сборка занимает минуты (генерация ключей RSA, `oncl-core` с `full`).

## 8. Лицензии и уведомления

Каждый крейт цепочки поставляет `LICENSE` (Apache-2.0) и `NOTICE`. `oncl-pki/roots/` встраивает рабочие сертификаты УЦ НУЦ: это публичные документы, права на них принадлежат эмитенту, и под Apache-2.0 они не лицензируются (`fixtures/README.md`). В `testing-data/` лежит синтетический ключ. `crates/oncl-core/THIRD-PARTY.txt` перечисляет сторонние крейты, от которых зависит SDK (из crates.io, для каждой поставляемой платформы, включая `distribution` плагинов), вместе с текстами их лицензий. Файл генерирует `cargo xtask sdk licenses`, а `--check` сверяет его с текущими зависимостями. Отдельную опись для программ строит `cargo xtask licenses`.

## Лимиты доказательств и большие встроенные CRL

У `oncl_pki::evidence::EvidenceLimits` три поля для CRL (код, создающий структуру литералом, нужно дополнить):

| Поле | Смысл |
|---|---|
| `max_crl_bytes` | суммарный допуск CRL-свидетельств в spool |
| `max_crl_item_bytes` | на один CRL, никогда выше `crl::MAX_CRL_LEN` (64 МиБ) |
| `max_total_bytes` | сумма по всем категориям свидетельств, включая CRL |

`EvidenceLimits::validate` отклоняет нулевые `max_crl_bytes`, `max_crl_item_bytes` и `max_total_bytes` с `EvidenceError::InvalidLimits`, как и нулевой `max_bytes`. Порядка между ними он не требует: при приёме берётся минимум из предела на элемент, суммы по CRL и общей суммы, а предел на элемент ограничивается `MAX_CRL_LEN`, так что больший предел просто не влияет. `EvidenceLimits::intersect` даёт поэлементный минимум двух наборов; им пользуются `oncl-core` и `oncl-xml`.

`max_bytes` и `max_item_bytes` относятся только к доказательствам, которые не являются CRL. Чтобы литерал допускал столько же, сколько до появления полей CRL, задайте `max_crl_bytes = max_total_bytes = max_bytes` и `max_crl_item_bytes = max_item_bytes`. Декодированные сертификаты, ответы OCSP и токены списываются с RAM и метаданных с повышающим коэффициентом. CRL больше `crl::MAX_BER_CRL_LEN` (1 МиБ) обязан быть в DER: он сканируется на месте через `crl::serial_status` и списывается один раз. Меньший CRL может быть в BER; он разбирается в дерево и списывается с тем же повышающим коэффициентом. `EvidenceStore::collect_base64` принимает элемент доказательства из текста base64 с квотами на декодированный размер; это нужно для XML.

Лимиты в приложениях:

- CLI при проверке принимает CRL до 32 МиБ (16 МиБ и 1 МиБ для прочих доказательств, 48 МиБ всего, `args.rs`), предел покрытия равен размеру документа (пределу вывода). При подписи файлы `--evidence-*` ограничены 256 КиБ каждый и 8 МиБ всего (`evidence.rs`), а для XAdES-LT/LTA предел ещё ниже (см. ниже).
- У `oncl-server` тот же предел покрытия: его `max_coverage_bytes` равен пределу вывода операции, а не `input_bytes`, потому что метка PAdES при переходе LT → LTA покрывает весь подписанный документ, который при полном допуске уже больше `input_bytes`. Часть запроса с доказательством ограничена 1 МиБ (`EVIDENCE_ITEM_BYTES`, проверяется раньше), а 2 МиБ на CRL составляют квоту движка для доказательств внутри проверяемого контейнера.
- У `oncl-ui` предел 1 МиБ.

Поэтому `oncl-server` и `oncl-ui` отклоняют sign и extend с полным CRL НУЦ (около 20 МБ), и эти лимиты сохраняются намеренно. Приложение, которому нужно другое, само задаёт поля `max_crl_*`.

Приложение, которое отдельно ограничивает доказательства в PDF, должно выводить этот предел из `EvidenceLimits.max_total_bytes` (поставляемые приложения пока так не делают; см. надбавку контейнера в разделе 5). Потоки доказательств DSS в PDF читаются по областям и ограничены не `PdfLimits::max_object_bytes`, а учётом контейнера и памяти в области и квотами доказательств.

Поддерживается офлайн-проверка CMS/CAdES и XAdES со встроенным полным CRL. Не поддерживаются: онлайн-загрузка CRL (`crl::fetch_for` по-прежнему декодирует CRL целиком с коэффициентом 128x), файлы CRL оператора (`--evidence-crl` ограничен 256 КиБ на файл), онлайн-загрузка для PAdES-LT и подпись XAdES с полным CRL (ниже). Структурные проверки PAdES (`/ID` в трейлере, свободный заголовок объекта 0) работают; проверка PAdES-LT настоящих файлов NCANode ограничена чтением областей DSS и пределом надбавки контейнера (раздел 5, «Лимиты»).

### XAdES с полным CRL: проверка

XAdES-LT от NCANode/Kalkan содержит полный CRL НУЦ (около 20 МБ, 27 МБ в base64 с `&#13;` в концах строк) в `xades:EncapsulatedCRLValue`. `XmlVerifyProfile::max_metadata_bytes` ограничивает только структурную разметку. Текст листьев `EncapsulatedX509Certificate/OCSPValue/CRLValue` сканер записывает как диапазоны исходных байт, вычитает из размера свойства, в котором они находятся, и потоком пропускает через `EvidenceStore::collect_base64` (ссылки на сущности и CDATA декодируются на лету, буферами по 16 КиБ). Декодированные байты списываются с `max_crl_item_bytes`/`max_crl_bytes`/`max_total_bytes` до сохранения. Ни `String`, ни DOM, ни `Vec` с base64 для листа не создаётся.

`validate_unsigned_layout` принимает решение по структуре, которую записал сканер. Представление для архивной метки времени берёт канонические текстовые фрагменты каждого листа у канонического рендерера (`canonical_stream::stage_with_leaves`), а не разбирает отрендеренные байты. Текст корректного листа ограничен только квотами доказательств на его декодированные байты; лист из одних пробелов декодируется в пустоту и ограничен лишь размером входа (он идёт потоком и в памяти не удерживается). XAdES внутри WSSE сохраняет прежний предел диапазона (`70 x max_metadata_bytes` на `Signature`), поэтому CRL больше примерно 17 МБ внутри SOAP-конверта отклоняется.

Что видит приложение:

- Заданные приложением `EvidenceLimits` не урезаются лимитом метаданных (`effective_limits`). Лимит метаданных только масштабирует значения по умолчанию у приложения, которое ничего не настраивало, и так же работает при sign и extend (`effective_limits` общая). Ненастроенное приложение по-прежнему отклоняет CRL больше 256 КиБ с `EvidenceError::Limit`.
- `VerifyRequest::xades_with_limits` является аналогом `cades`/`pades` для XAdES; CLI вызывает его со своей квотой CRL 32 МиБ.
- Повторное чтение отсканированного CRL (DER, больше 1 МиБ) списывается только как память, а не ещё и как метаданные (индекс XML допускается в пределах 56 МиБ из 64 МиБ бюджета метаданных по умолчанию).
- `oncl-server` и `oncl-ui` лимитов XAdES не передают и такие документы отклоняют.

### XAdES с полным CRL: подпись не поддерживается

`xades::source::material_xml`/`complete_signature`, `sign.rs`, `xades.rs` и `references/extension.rs` строят неподписанные свойства как `String`, ограниченную `max_metadata_bytes`. Фактический предел подписи и достройки XAdES-LT/LTA:

- если приложение не настроило `EvidenceLimits`, один CRL может быть не больше 256 КиБ (`max_metadata_bytes` по умолчанию 262144): CRL в 256 КиБ проходит предварительную проверку, на байт больше даёт `EvidenceError::Limit` до чтения документа (тест `default_signing_limits_refuse_a_crl_one_byte_over_the_markup_cap`);
- кроме того, сумма всех сертификатов, ответов OCSP и CRL (в исходном виде) и готовый текст свойств (base64, ×4/3) тоже не должны превышать `max_metadata_bytes`, иначе `MetadataLimit`; по этим проверкам CRL в подписи не превышает примерно 190 КиБ (256 КиБ × 3/4; значение вычислено из кода, а не измерено) и делит это место с сертификатами и ответами OCSP;
- `max_metadata_bytes` не может быть больше 1 МиБ (профили отклоняют большее значение), поэтому даже при максимальной настройке предел составляет около 768 КиБ на все доказательства.

Поэтому полный CRL НУЦ (около 20 МБ) при подписи и достройке XAdES-LT/LTA не поддерживается ни в одном приложении; лимиты оставлены как есть и задокументированы. Если поддержка понадобится, сгенерированные свойства можно писать в промежуточный артефакт и собирать подпись из начала, промежуточных неподписанных свойств и конца. Каноническая форма этих свойств при exclusive C14N совпадает с текстом, которым они генерируются, так что покрытие архива и фрагменты листьев не потребуют разбора; это нужно подтвердить дифференциальным тестом против `canonical_stream`.

## Встроенный статус LT/LTA оценивается на момент доказательства

Статус отзыва, который несёт подпись (ответы OCSP и CRL в CAdES/PAdES/XAdES уровней `LT` и `LTA`), служит доказательством для проверки спустя долгое время после выпуска подписи. Если оценивать его по часам проверяющего (`nextUpdate`, `ALLOWED_PERIOD`, срок действия сертификата ответчика на `now`), документ, который при подписании был `Valid`, через несколько минут становится `Indeterminate`. Поэтому правило другое; оно находится в одном месте, в `oncl-pki` (`ocsp::check_embedded_at_proof`, `crl::serial_status_at_proof`, выбор через `validation::offline_revocation`, переключатель `pkix::Currency`), и его используют CAdES, XAdES и PAdES.

### Правило

Если проверено время доказательства `P`, встроенный ответ OCSP или CRL о сертификате пути принимается, когда проходят все обычные проверки (CertID, привязка к эмитенту, подпись, цепочка ответчика и OCSPSigning/no-check, `unknown` отклоняется, CRL является полным CRL эмитента) и при этом:

* ответ свеж на момент `P` (EN 319 102-1 5.2.5.4: максимальная свежесть равна `nextUpdate - thisUpdate`, если ограничение не задаёт иное). Если есть `nextUpdate` (он есть у каждого CRL и у некоторых ответов OCSP), ответ свеж тогда и только тогда, когда `P < nextUpdate`; поэтому подходит 35-дневный CRL УЦ, выпущенный за несколько часов до доказательства. Если `nextUpdate` нет (OCSP НУЦ), ответ свеж тогда и только тогда, когда `P - CLOCK_SKEW < thisUpdate` (300 с, строгое неравенство);
* `thisUpdate <= now + CLOCK_SKEW` (для CRL `thisUpdate <= now`), то есть ответ не из будущего относительно проверяющего;
* сертификат ответчика строит цепочку на момент `thisUpdate`, а не `now`;
* `nextUpdate` и `ALLOWED_PERIOD` с `now` не сравниваются.

`P` равно genTime метки времени подписи (уровни `T` и `LT`; для документной метки PAdES это первое доказательство). Для `LTA` используется та же метка времени подписи: архивные метки защищают доказательства, но `P` не сдвигают, поэтому статус, встроенный после метки подписи и до архивной метки, должен оставаться приемлемым. Встроенный статус сертификата самой службы меток времени оценивается так же, с genTime этого токена в роли `P`. Без времени доказательства (уровень `B`, отсутствующая или недействительная метка) `at` равно `now` и действует обычное правило; статус, полученный онлайн, всегда оценивается как актуальный на `now`.

Сертификаты подписанта и цепочки оцениваются на момент `P` (`certificate_facts` и путь до якоря используют `P`). Отозван в `P` или раньше означает `Invalid`. Отозван после `P` означает, что подпись остаётся действительной, и это сообщается как `RevokedAfterProvenTime`.

### Учитываются все приемлемые статусы

Для одного сертификата оценивается каждый встроенный ответ OCSP и CRL, прошедший проверки выше, в произвольном порядке (их число ограничено лимитами хранилища доказательств). Любой приемлемый `revoked` отзывает сертификат, и сообщается самое раннее время отзыва среди них (в `P` или раньше: `Invalid`/`Revoked`; после `P`: `RevokedAfterProvenTime`). Для `Good` нужен хотя бы один приемлемый `good` и ни одного `revoked`, иначе статус остаётся `Unavailable`. Неприемлемый статус (устарел, не тот эмитент или ответчик, другой сертификат, `unknown`) игнорируется и никогда не превращает `Unavailable` в `Good`. Ответ `good`, стоящий первым, не скрывает последующий `revoked`.

Для статуса, полученного онлайн (`check_path_revocation`), используется ОДИН источник на сертификат: CRL загружается, только если OCSP не дал ни `good`, ни `revoked`. Это остаточная слабость: `good` от ответчика OCSP принимается без обращения к CRL, который мог бы сказать `revoked`. EN 319 102-1 требует приемлемой информации о статусе, а не всех доступных источников, так что это вопрос политики, и он остаётся открытым. Кроме того, у `offline_revocation` нет проверки дедлайна и управления внутри цикла по статусам; его ограничивают только лимиты хранилища доказательств, и худший случай равен случаю без приемлемого статуса.

### Основание в стандарте

ETSI EN 319 102-1 V1.3.1, по опубликованному тексту:

- 5.2.5.4 (проверка свежести отзыва): статус свеж, когда `issuance time > validation time - maximum accepted freshness`;
- 5.5.4, шаг 6: проверка повторяется со *временем лучшей подписи*, если статус не был свеж относительно текущего времени;
- 5.5.4, шаг 4a: время отзыва после времени лучшей подписи подпись не делает недействительной, в этот момент или раньше даёт `INDETERMINATE/REVOKED_NO_POE`;
- 5.2.6.4 (валидация сертификата X.509) запускает проверку со временем валидации и не сверяет с ним сертификат, которым подписан CRL эмитента.

Умолчание `nextUpdate - thisUpdate` из шага 1 5.2.5.4 применяется к ответам с `nextUpdate`. Для ответов OCSP НУЦ, в которых его нет, свежесть задаётся ограничением `CLOCK_SKEW` (стандарт без nextUpdate говорит FAILED, пока ограничение не задано).

### Окно повтора

Атакующий, у которого есть ответ «good», полученный до отзыва, может использовать его в течение срока действия самого ответа, `nextUpdate - thisUpdate`: до 35 дней для CRL НУЦ и 300 с для ответа без `nextUpdate`. Архивная метка времени или доказательство существования `LTA` это окно не сужает, потому что `P` равно genTime метки подписи, а архивные метки только защищают встроенные данные. Это умолчание стандарта, и такое же окно было бы при проверке на момент подписания.

### Что не проверено и чем правило отличается от стандарта

0. Подтверждения на настоящей PKI нет. Закреплённые образцы LT от NCANode здесь никогда не доходят до времени доказательства, поэтому частота выпуска CRL НУЦ (35-дневный CRL корня, выпущенный за часы до метки времени) проверена записанным рабочим CRL (`crates/oncl-pki/tests/all/crl.rs`) и синтетическим 35-дневным CRL, а не документом с Valid на настоящей PKI. Путь простого CMS офлайн покрыт тестом `oncl-core` `offline_cms_status_is_judged_at_the_proof_time_not_the_host_clock`. В качестве `P` берётся ПОСЛЕДНЯЯ прошедшая проверку метка времени подписи, а стандарт (5.5.4, шаг 3b) берёт самую раннюю; это консервативнее.
1. 5.6.2.2.4, шаг 2a, также требует доказательства существования информации об отзыве не позже контрольного времени. Для `LTA` это архивная метка, связывающая доказательства, и её проверяет граф доказательств; для `LT` такое доказательство не запрашивается (кроме метки подписи там ничего нет), как и в 5.5.4.
2. Строгое `>` и свежесть 300 с выбраны в пределах ограничения, которое стандарт оставляет политике валидации; сам стандарт этих значений не предписывает.
3. Отзыв в `P` или раньше здесь даёт `Invalid`, а стандарт говорит `INDETERMINATE/REVOKED_NO_POE`; наш вариант строже.
4. Правило модели цепочки из стандарта о компрометации ключа при отзыве УЦ после `P` не моделируется.

## Плотные PDF: бюджет перекрёстных ссылок

`PdfLimits::max_objects` (по умолчанию 4096) ограничивает только обходы ГРАФА объектов: число полей AcroForm, элементы доказательств DSS, члены одного потока объектов, обход представления подписи. Размер документа он не ограничивает. Размер документа в объектах ограничен `PdfLimits::max_xref_entries` (по умолчанию 4 Mi записей по ВСЕМ ревизиям), и каждая запись стоит:

| Что | Стоимость |
|---|---|
| строка перекрёстных ссылок (любой ревизии) | 16 байт памяти операции, резервируется по мере чтения строки (шагами не более 65 536 строк), а не заранее |
| серия последовательных номеров объектов | 32 байта (в худшем случае по одной на запись) |
| классическая таблица xref / поток xref | читается чанками по 64 КиБ / инкрементально разжимается (включая предиктор PNG) прямо в строки; декодированная таблица не удерживается, `max_object_bytes` и `max_decoded_bytes` на неё больше не действуют, размер после разжатия ограничен объявленными строками и `max_decode_work` |

До выделения памяти под строки отклоняются объявленное число, превышающее остаток бюджета, и число, которое не может поместиться в оставшуюся часть файла (для классической таблицы). Лишние или недостающие данные потока xref обнаруживаются только после того, как имеющиеся строки прочитаны и списаны; такой документ некорректен и всё равно отклоняется до использования ключа. При превышении бюджета возвращается `PdfError::Limit("xref entries")` (ровно на limit+1, по всем ревизиям), а если строки не помещаются в квоту памяти, `MemoryLimit`. Оба отказа происходят при чтении, до любого использования закрытого ключа (`NotApplied`).

Классическая таблица принимается независимо от того, где проходят границы чанков по 64 КиБ. Заголовок подраздела или запись, разрезанные концом чанка, перечитываются из нового чанка (в том числе когда последний токен упирается в конец чанка и число может оказаться разрезанным), так что приём обычных записей от выравнивания не зависит. Единица, начинающаяся в начале чанка, принимается, если заканчивается внутри этого чанка, и отклоняется в противном случае. Заголовок подраздела, окружённый пробелами длиннее чанка, в зависимости от выравнивания может быть отклонён (отказ безопасен; в реальных документах так не бывает).

Не списываются ограниченные временные буферы: чанк чтения 64 КиБ, буферы строк разжатия и предиктора (`RowReader`, одна строка предиктора не больше `max_object_bytes`) и копия при росте вектора строк (не больше одного шага, 1 МиБ, сверх списанной ёмкости).

Приложения, которые заранее проверяют обновление PAdES, добавляют строки через `budget::PriorSignatures::xref_entries` → `budget::PlanInputs::xref_entries` (`budget::xref_memory` даёт верхнюю оценку для `plan_memory`); сервер так и делает. `budget::reader` от `max_revisions` не зависит.

Замеры (отладочная сборка, настоящий процесс `oncl`, `scripts/pdf-dense/gen_dense_pdf.py`, три ревизии, результат перепроверен pyHanko, подпись выходного файла цела на всём файле):

| документ | размер | время подписи | пик рабочего набора |
|---|---|---|---|
| 1 M объектов, классический xref | 123 МБ | 3,2 с | 43 МБ |
| 1 M объектов, потоки объектов и потоки xref Flate/PNG | 58 МБ | 1,9 с | 44 МБ |
| 4 M объектов (предел по умолчанию) | не указан | 13,5 с | 135 МБ |
