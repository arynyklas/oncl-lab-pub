# Выпуск версии и публикация индекса обновлений

Инструкция для мейнтейнера: от ключей TUF до опубликованного обновления. Формат индекса, правила проверки и поведение клиента описаны в [`../design/update-index.md`](../design/update-index.md).

Кратко процесс выглядит так. Тег `v<версия>` собирает релиз и открывает PR с индексами каналов этой версии (для релиза это `stable` и `beta`). Мейнтейнер при необходимости уменьшает раскатку, подписывает метаданные TUF в `tuf/v1` (`cargo xtask tuf update`, раздел 10) и пушит их в тот же PR. После слияния индексы и репозиторий TUF публикуются на GitHub Pages, и клиенты видят новую версию. Метаданные `timestamp` в день публикации подписывает CI. Это его единственный секрет: онлайн-ключ `timestamp` позволяет только перевыпустить отметку свежести для снимка, который уже подписал мейнтейнер. Остальные ключи в CI не попадают.

Репозиторий проекта называется `arynyklas/OpenNCALayer`, сайт находится по адресу `https://arynyklas.github.io/OpenNCALayer/`. Сборки, выпущенные до переименования репозитория, обращаются к прежнему адресу Pages, и перенаправление GitHub этого не исправляет; чтобы перейти на новый адрес, нужна новая сборка. Ассеты существующих релизов и их аттестации не пересоздаются. Имя команды `openncalayer`, идентификаторы пакетов и расширений и каталоги пользовательских данных остались прежними.

## 1. Настройки репозитория (один раз)

Эти настройки меняет только мейнтейнер, workflow сделать этого не может.

- Settings → Pages → Source: **GitHub Actions**. Без этого `pages.yml` не опубликует ни индекс, ни сайт: сайт соберётся и пройдёт проверки, но деплоя не будет, а в журнале появится `::notice::Pages is not enabled`.
- Settings → Actions → General → **Allow GitHub Actions to create and approve pull requests**. Без этого задание `index` не откроет PR с индексом.
- Settings → General → Releases → **Enable release immutability**. Когда черновик публикуется, GitHub замораживает его ассеты и тег: файл уже нельзя добавить, заменить или удалить, тег нельзя сдвинуть или удалить. Менять можно только заголовок, описание и флаги pre-release и Latest. Поэтому все файлы прикладываются к черновику до `gh release edit v<версия> --draft=false`, и до этого же момента должны пройти проверки `builtins`, `vm-smoke` и `mac-smoke.yml` (раздел 2, шаг 3). Настройка действует только на релизы, опубликованные после её включения; прежние релизы остаются изменяемыми.
- Settings → Rules (или Branches) → правило для `main` с обязательной проверкой **check**. Это последнее задание `ci.yml`: оно зелёное, только если прошли все задания, которые нужны этому запуску, в том числе `index` (вызывает `index-check.yml`) и `privacy` (вызывает `privacy.yml`). `index` запускается на каждый PR и пуш в `main` и всегда отчитывается. Если не менялись ни `updates/`, ни `tuf/`, ни `crates/oncl-update/keys/`, шаг cargo пропускается и задание проходит, так что обычным PR оно не мешает. Обязательная проверка должна пройти на коммите до того, как сдвинется `main`, а запуск на пуш в `main` отчитывается уже после пуша. Поэтому с этим правилом изменения попадают в `main` только через PR, а прямой пуш проходит, только если мейнтейнер внесён в список обхода (bypass list) правила; при классической защите ветки администраторы по умолчанию освобождены. Workflow сам включить правило не может. Без него можно слить PR с индексом, который не прошёл проверку. Pages такой индекс не опубликует, но и все следующие публикации остановятся, пока его не исправят.
- Окружение `tuf-timestamp` с секретом `TUF_TIMESTAMP_KEY` (настраивается после церемонии, раздел 10): **Deployment branches and tags = Selected branches**, только `main`. Секрет должен быть секретом окружения, а не репозитория, иначе его смог бы прочитать любой workflow, в том числе из ветки PR этого же репозитория.

Секреты подписи кода необязательны. Без них шаги подписи пропускаются с уведомлением в журнале сборки, и релиз выходит неподписанным.

- Authenticode через SignPath: секрет `SIGNPATH_API_TOKEN`, переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`.
- Apple: секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD` нужны для подписи и нотаризации `.app` (пакет обновления, `.zip`, содержимое `.pkg`). Сам `.pkg` подписывается и нотаризуется, только если задан ещё `APPLE_INSTALL_IDENTITY`, идентичность «Developer ID Installer» из того же `APPLE_CERTIFICATE_P12`.
- Mozilla AMO (unlisted): секреты `AMO_JWT_ISSUER` и `AMO_JWT_SECRET` (ключи API со страницы addons.mozilla.org/developers/addon/api/key/). С ними job `extension` подписывает `.xpi` обычного релиза (тег без суффикса), и подписанный файл идёт в релиз, `SHA256SUMS`, аттестацию и индекс под прежним именем. `.xpi` предварительной версии остаётся неподписанным. `web-ext` ставится из `extension/sign/package-lock.json` командой `npm ci --ignore-scripts` в шаге без секретов; версию меняют там же (`npm install --package-lock-only --ignore-scripts`) вместе с `package.json`. AMO подписывает версию один раз: если после успешной подписи упал другой job, запускайте «Re-run failed jobs», а не «Re-run all jobs», иначе понадобится новый тег.

Также необязателен секрет `PRIVACY_DENYLIST` для шага denylist в `privacy.yml` (раздел 12).

## 2. Выпуск версии

1. Поднять версию в `[workspace.package]` файла `Cargo.toml`. Вместе с ней поднимаются одиннадцать пинов `version = "=<версия>"` у крейтов SDK в `[workspace.dependencies]` (`oncl-flows`, `oncl-gost`, `oncl-pki`, `oncl-pdf`, `oncl-pdk`, `oncl-plugin`, `oncl-protocol`, `oncl-registry`, `oncl-token`, `oncl-update`, `oncl-xml`; без этого workspace не разрешается), четыре `plugin.toml` встроенных модулей и lock-файлы (подробно в [`sdk.md`](sdk.md), раздел 6). Затем обновить `Cargo.lock` (`cargo check --workspace`), прогнать проверки из раздела «Перед отправкой изменений» в [`development.md`](development.md) и закоммитить.

   В том же коммите записи раздела «Unreleased» в `CHANGELOG.md` переносятся в новый раздел `## <версия> — <дата>`. Они же служат основой описания релиза.
2. Поставить подписанный тег, проверить подпись и запушить:

   ```sh
   git tag -s v<версия> -m "OpenNCALayer <версия>"
   git tag -v v<версия>
   git push origin v<версия>
   ```

   Тег аннотированный и подписан ключом мейнтейнера (`user.signingkey`, тем же, которым подписываются коммиты). `git tag -v` должен сообщить о верной подписи. Если подписи нет или она не сходится, удалите тег (`git tag -d v<версия>`), пока он не отправлен, и поставьте заново.

   Первым делом задание `version` сверяет тег с версией в `Cargo.toml` и при расхождении останавливает сборку. Версия с суффиксом (`0.1.0-alpha.1`) выходит как pre-release и попадает только в канал `beta`. Версия без суффикса выходит обычным релизом и попадает в оба канала, `stable` и `beta`.
3. `release.yml` собирает по вариантам сборки (`win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64`, `osx`) архивы, установщики и пакеты Velopack с дельтами (`cargo xtask package windows|macos|linux`; Linux собирается в контейнере с glibc 2.28 через `cargo xtask package linux-build`), а также расширение, SBOM и `SHA256SUMS`. На каждый файл выпускается аттестация происхождения, после чего создаётся релиз. Установщики: `openncalayer-<версия>-<вариант>-setup.exe` для четырёх вариантов Windows, `openncalayer-<версия>-osx.pkg` и `openncalayer-<версия>-osx.zip`, `openncalayer-<версия>-linux-x64.AppImage`. Для `win-x64` и `win-x86` рядом публикуется `openncalayer-<версия>-<вариант>-winget-setup.exe`, установщик для WinGet ([`winget-installer.md`](winget-installer.md)). Манифест WinGet собирает `cargo xtask winget manifest` из этих файлов и `SHA256SUMS` релиза, только для релиза без суффикса; как его подать, описано в [`winget.md`](winget.md). Варианты `win7-*` собирает `cargo xtask win7`. Содержимое их пакетов вместе с `Squirrel.exe` и заглушкой Velopack, а также их `Setup.exe` проходят проверку импортов Windows 7.

   Для Arch Linux задание `arch` делает из архива `linux-x64` этого же прогона пакет `openncalayer-bin-<pkgver>-1-x86_64.pkg.tar.zst` (`cargo xtask package arch`; `pkgver` равен версии без `-`, например `0.1.0-rc.4` превращается в `0.1.0rc.4`). В закреплённом контейнере Arch Linux пакет собирается `makepkg`, устанавливается, запускается `openncalayer --version`, после чего пакет удаляется. Пакет выкладывается артефактом `release-arch` и, как остальные файлы, попадает в релиз, в `SHA256SUMS` и в аттестацию. Он собирается и для pre-release.

   Встроенные модули (WebAssembly) собирает один раз задание `builtins` (`cargo xtask builtins build`, каталог `target/builtins` с `SHA256SUMS`) и выкладывает артефактом. Каждый вариант скачивает его и задаёт `ONCL_BUILTINS_DIR`, так что все шесть вариантов вшивают одинаковые байты (`cargo xtask win7` и `cargo xtask package linux-build` берут модули из этой переменной, а без неё собирают сами). После сборки `cargo xtask builtins check --bin <программа>` сверяет вывод `openncalayer builtins` с `SHA256SUMS`. Контрольные суммы модулей публикуются ассетом `builtins-SHA256SUMS`.

   Перед публикацией черновика мейнтейнер ещё раз сверяет встроенные модули хотя бы для одного варианта Windows и для `linux-x64`. Для этого ассет `builtins-SHA256SUMS` кладётся в пустой каталог под именем `SHA256SUMS`, программа нужного варианта распаковывается, и запускается `cargo xtask builtins check --bin <программа> --dir <каталог>`. Команда должна сообщить, что вшиты все четыре модуля в том виде, в каком их собрало задание `builtins`. Если она нашла расхождение, черновик не публикуется.

   Каждый релиз создаётся черновиком; флаг `--prerelease` получает только версия с суффиксом. Все файлы релиза прикладывает к черновику задание `publish`, после публикации к релизу ничего не добавляется. Лаборатория проекта ставит установщики этого прогона на чистые Windows 7, Windows 11 и Linux и пишет статус коммита `vm-smoke`, а workflow `mac-smoke.yml` проверяет `.pkg` на Mac (раздел 11). Когда `vm-smoke` и `mac-smoke.yml` зелёные, мейнтейнер дописывает описание и публикует черновик (`gh release edit v<версия> --draft=false`). Если хотя бы одна из этих проверок красная, черновик не публикуется. PR индекса для черновика пройдёт `index check` только после публикации, потому что ссылки на ассеты черновика не открываются.

   Если задание `publish` упало посреди загрузки файлов, на теге остаётся неполный черновик, а повторный запуск создал бы рядом второй. Перед «Re-run failed jobs» удалите неполный черновик командой `gh release delete v<версия> --yes`. Флаг `--cleanup-tag` не нужен: тег понадобится повторному запуску.

   После `vm-smoke` агент лаборатории сверяет сборку того же тега с оригиналом (артефакт `conformance-<вариант>`, раздел 7) и пишет на коммит тега второй статус, `conformance`. Без зелёного `conformance` новая версия не попадёт в `stable`: его требует проверка PR индекса (раздел 3, шаг 3). Предварительной версии, которая идёт только в `beta`, этот статус не нужен.
4. Задание `index` скачивает ассеты релиза, выполняет `cargo xtask index add --channel <канал> --tag v<версия>` для каждого канала версии (для pre-release это `beta`, для релиза `stable` и `beta`; у каждого индекса свой следующий `seq`, прежние записи сохраняются) и открывает PR «chore(updates): add …» из ветки `updates/v<версия>`. Вариант `osx` попадает в индексы вместе с остальными; универсальную сборку проверяет `mac-smoke.yml` на Mac с Apple Silicon и с Intel (раздел 11). Метаданные TUF в этом PR ещё не обновлены, их подписывает мейнтейнер (раздел 3). Пока цели TUF расходятся с индексами, `tuf check` PR не пропустит.

## 3. Метаданные TUF в PR

На ветке PR, у себя на машине:

```sh
git fetch origin
git switch updates/v<версия>
```

1. При необходимости уменьшить `rollout` новой версии в индексах PR, `updates/v1/<канал>.json` (0–100). Руками в индексе меняются только значения полей. Переформатировать файл нельзя: он публикуется байт в байт, и `.gitattributes` запрещает git менять в нём концы строк.
2. Если репозиторий TUF уже создан (в дереве есть `tuf/v1`, раздел 10), подписать метаданные TUF для индексов PR. Цель TUF состоит из тех же байтов, что и индекс, поэтому после этого шага индексы не правятся:

   ```sh
   cargo xtask tuf update --keys <каталог ключей TUF>
   cargo xtask tuf check --no-timestamp --base origin/main
   ```

   Пароль ключей (один для root, targets и snapshot) вводится без эха и запрашивается, только если есть что подписывать. Команда копирует индексы в `tuf/v1/targets/indexes/<sha256>.<канал>.json`, пишет `tuf/v1/metadata/<N+1>.targets.json` и `<N+1>.snapshot.json` (версии ровно на 1 выше, срок 30 дней) и проверяет результат клиентским кодом. Если индексы не менялись, она пишет «up to date» и ничего не трогает. `timestamp.json` команда не меняет. Пока церемонии не было (нет `tuf/v1`), этот шаг пропускается.

3. Проверить так же, как это сделает CI (нужен свежий `origin/main`):

   ```sh
   cargo xtask index check updates/v1 --base origin/main --vm-smoke --conformance
   ```

   Проверяются формат и срок индекса, правило URL, рост `seq` относительно базовой ветки и ответ `HEAD` 200 на каждый URL пакета и расширения. Кроме того, проверяются статусы коммита на теге каждой новой версии ядра: `vm-smoke = success` у каждой и `conformance = success` у новой версии в `stable` (для `beta` не нужен). Без сети используйте `--offline` без `--vm-smoke` и `--conformance`; тогда не проверяются ни `HEAD`, ни статусы.

   Если лаборатория ещё не поставила статус, проверка PR падает с сообщением «v<версия> has no successful … status». Когда статус станет зелёным, проверку перезапускают (Actions → CI → Re-run failed jobs: перезапустятся `index / indexes` и `check`). Красный статус означает, что версия в этот канал не выходит.
4. Закоммитить индексы и файлы `tuf/v1` и запушить. PR, который открыл workflow, сам проверок не запускает, поэтому `ci.yml` (задание `index`, оно вызывает `index-check.yml`) срабатывает именно на этот пуш. Без файлов `tuf/v1` `tuf check` отказывает с сообщением «index-mismatch: run `cargo xtask tuf update`».
5. Слить PR. После слияния `pages.yml` ещё раз проверяет индексы относительно коммита до пуша (`--base <github.event.before>`; на первом пуше `--no-base`, тогда проверяются формат, срок и URL) и публикует каталог `updates/` на GitHub Pages вместе с сайтом проекта (раздел 9). Клиенты читают индексы через TUF: репозиторий `tuf/v1` публикуется в `/tuf/v1/` вместе с `timestamp.json`, подписанным в тот же день (раздел 10).

Если до слияния этого PR вышла ещё одна версия, у второго PR будет тот же следующий `seq` в тех же файлах, и после слияния первого возникнет конфликт. Не разрешайте его вручную и не берите файлы своей ветки: `index check` сравнивает `seq` и пропавшие файлы, но не пропавшие версии, и такая правка незаметно потеряет версию из первого PR. Когда первый PR уже в `main`, перезапустите задание `index` релиза второй версии (Actions → Release → Re-run job `index`). Оно соберёт индексы заново от свежего `main`, с обеими версиями и следующим `seq`. Затем подпишите метаданные TUF, как описано выше.

Клиенты увидят новую версию при очередной проверке: первая проходит через 2–10 минут после запуска, следующие раз в 6–24 часа.

Чтобы позже расширить раскатку (вплоть до 100), поднимите `rollout` версии в `updates/v1/<канал>.json`, выполните `cargo xtask index refresh --channel <канал>` (изменённому индексу нужен новый `seq`, иначе проверка откажет), подпишите метаданные TUF (`cargo xtask tuf update`), откройте PR в `main` и слейте его, как в разделах 4 и 5. Для релиза это делается в обоих каналах.

## 4. Продление индекса

`index check` отвергает индекс, если с `generated` прошло больше 30 дней, даже когда в `expires` стоит более поздняя дата. Срок у каждого канала свой: индекс, который не менялся 30 дней, нужно продлить и заново подписать метаданные TUF. Предварительные версии меняют только `beta.json`, поэтому опубликованный `stable.json` нужно продлевать и тогда, когда выходят одни пререлизы:

```sh
cargo xtask index refresh --channel <канал>
cargo xtask tuf update --keys <каталог ключей TUF>
```

`refresh` меняет только `seq` (+1), `generated` и `expires`, список версий остаётся прежним. Дальше нужны PR в `main`, проверка и слияние, как в разделе 3.

## 5. Отзыв версии

Сломанную версию отзывают правкой индекса: в её записи ставится `"revoked": true`. Клиент читает только индекс своего канала, а релиз без суффикса записан и в `stable.json`, и в `beta.json`, поэтому отзывать его нужно в каждом индексе, где он есть, одним PR. Если отозвать только в одном, установки из другого канала останутся на этой версии и продолжат её получать. Версия, отозванная во всех своих индексах, больше не предлагается. Установки, которые уже на ней, получают самую новую неотозванную версию своего канала, даже если та старше.

Порядок для релиза (для пререлиза только `beta`):

```sh
# в updates/v1/stable.json и updates/v1/beta.json: "revoked": true у версии
cargo xtask index refresh --channel stable
cargo xtask index refresh --channel beta
cargo xtask tuf update --keys <каталог ключей TUF>
cargo xtask index check updates/v1 --base origin/main
```

`refresh` нужен ради нового `seq`, иначе проверка откажет. Затем откройте PR и слейте его. Если исправленная версия уже выпущена, достаточно отозвать сломанную, и клиенты перейдут на исправленную как на обычное обновление.

Опубликованный релиз не удаляют. GitHub больше не позволит создать релиз с тем же тегом, а ссылки на его файлы в индексах, в `firefox/updates.json` и в манифесте WinGet начнут отдавать 404. Сломанную версию выводят из обращения только отзывом в индексе.

## 6. Выпуск плагинов

Плагины выходят отдельно от ядра, пачками: релиз с тегом `plugins-ГГГГММДД` (второй за день `plugins-ГГГГММДД.1` и так далее). Это pre-release без флага Latest, чтобы последним релизом оставалось ядро. Выпускает плагины workflow `.github/workflows/plugins.yml`.

1. Поднять версию порта в его `Cargo.toml` и `plugin.toml` (они должны совпадать) и слить в `main`. Какие порты выйдут, можно узнать заранее:

   ```sh
   cargo xtask plugin pending --channel beta
   ```

   Команда печатает каталоги `plugins/<порт>`, чьей пары `(id, version)` ещё нет в индексе `beta`. Пустой вывод означает, что выпускать нечего.
2. Поставить тег на `main` и отправить его: `git tag plugins-ГГГГММДД && git push origin plugins-ГГГГММДД`. Workflow проверяет имя тега, собирает каждый порт из `pending` дважды (`cargo xtask plugin pack`) и сравнивает пакеты байт в байт; пакеты детерминированы, и пути машины сборки в модуль не попадают. Затем он проверяет, что `plugins/THIRD-PARTY.txt` актуален (`cargo xtask licenses --plugins --check`), и кладёт его рядом с пакетами. В этом файле перечислены лицензии крейтов портов и шрифтов, которые порты встраивают в модуль (`plugins/<порт>/fonts/`: файл шрифта, источник из `fonts/README.md` и текст `OFL.txt`). Последними создаются `SHA256SUMS`, аттестация происхождения всех файлов и релиз. Если выпускать нечего, workflow завершается с notice и без релиза. Новый шрифт добавляется в порт вместе с `OFL.txt` и `README.md` со строкой `Источник: <URL>`, иначе `cargo xtask licenses --plugins` откажет.

   Релиз плагинов workflow создаёт без `--draft`, поэтому он публикуется сразу после загрузки файлов и сразу становится неизменяемым; окна для проверки, как у черновика ядра, нет. Ошибку в выпущенных пакетах исправляют только новым тегом `plugins-ГГГГММДД.N`. Сломанный пакет попадёт в индекс, только если слить его PR (шаг 3), поэтому такой PR закрывают без слияния.
3. Затем workflow открывает PR `updates/<тег>`, который добавляет пакеты в индекс `beta` (`cargo xtask index add-plugin --channel beta`). На ветке PR выполните:

   ```sh
   cargo xtask tuf update --keys <каталог ключей TUF>
   cargo xtask index check updates/v1 --base origin/main
   ```

   Закоммитьте индекс и `tuf/v1`, отправьте, дождитесь зелёной проверки `check` (в неё входит `index`, то есть `index-check.yml`) и слейте. Клиенты получат плагин при следующей проверке индекса и перезагрузят его без перезапуска ядра. Ключи TUF, кроме `timestamp`, в CI не попадают.
4. В `stable` workflow не пишет. Готовую версию плагина без суффикса, проверенную в `beta`, мейнтейнер добавляет вручную в том же порядке: `cargo xtask index add-plugin --channel stable --tag <тег релиза> --package <пакет из релиза>`, затем метаданные TUF, проверка и PR. Предварительную версию (`1.0.0-beta.1`) команда в `stable` не добавит.

   В `stable` выходит только порт с `conformance = "confirmed"` в `plugins/<порт>/registry.toml`. Это значит, что поведение порта сверено с работающим оригиналом, а принятые отличия записаны в `[[differences]]`. Порт с `computed` команда отвергает («`<id>`: conformance with the original is not confirmed (conformance = computed)»), как и пакет, `id` которого нет ни у одного порта. Порты команда читает из `--plugins <каталог>` (по умолчанию `plugins/` рабочего дерева), поэтому запускать её нужно на коммите, где в `registry.toml` порта уже стоит `confirmed`. Для `beta` порты не читаются.

Собрать пакет локально: `cargo xtask plugin pack <каталог крейта плагина>`, результат появится в `target/plugins/<id>-<версия>.onclp`.

Проверить `[[operations]]` (окно ручной подписи) во всех `plugins/*/plugin.toml` и в указанных путях: `cargo xtask plugin-ops-check [путь…] [--wasm-dir <каталог>] [--require-wasm] [--json]`. Правила схемы проверяет тот же разбор манифеста, что и в ядре: имена, плейсхолдеры, подписи, профили, `max_uses = 1`, флаги `manual` и `server`. Команда дополнительно сверяет объявленные в операции `imports` с импортами собранного модуля (`target/plugin-build/wasm32-unknown-unknown/release/<крейт>.wasm`, появляется после `plugin pack`) и печатает сводную таблицу: плагин, операции, запускаемые, derived, статус. Операции с `content = "derived"` получают статус `blocked until MP3b` и код 0: окно такие операции не запускает, и среди поставляемых операций с `derived` нет. Код выхода 1 означает ошибки. Если модуля нет, это предупреждение и строка NOTICE (правило импортов пропускается), а с `--require-wasm` ошибка. Команда работает офлайн и быстро, поэтому выполняется в CI (в задании с `sdk closure`).

Отзыв версии плагина устроен как у ядра (раздел 5): `"revoked": true` у записи в каждом индексе, где она есть, затем `refresh`, метаданные TUF, проверка и PR. Установки на отозванной версии переходят на самую новую неотозванную, а если такой нет, плагин выключается.

## 7. Сборка для проверки совместимости

Тег версии запускает ещё и задание `conformance` в `release.yml`. Оно собирает ядро с тестовыми возможностями (`--features e2e-prompter`) для `linux-x64` и `win-x64` и пакеты всех портов (`dist/plugins/*.onclp`) с `SHA256SUMS`. Результат хранится 30 дней как артефакт workflow `conformance-<вариант>` и никогда не публикуется: `publish` берёт только артефакты `release-*`. С этой сборкой сверяют поведение с оригиналом в изолированной лаборатории. Только в ней есть подкоманда `openncalayer e2e install-plugin <пакет>` (ставит пакет как локальный плагин, сразу включённым, и печатает `<id> <версия>`) и переменная `ONCL_E2E_EXTRA_CA=<pem>`, с которой исходящий HTTPS ядра и плагинов доверяет этому CA вдобавок к корням webpki. В релизной сборке подкоманды нет и переменная ни на что не влияет; CI это проверяет.

## 8. Пакеты `oncl` и `oncl-server`

Тег версии запускает ещё и задания `platform` (по вариантам `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64`, `osx`) и `platform-sbom` в `release.yml`. Они собирают самостоятельные программы SDK отдельными архивами `oncl-<версия>-<вариант>` и `oncl-server-<версия>-<вариант>` (`.zip` для Windows, `.tar.gz` для остальных; без Velopack и без файлов настольной программы), `SHA256SUMS` и CycloneDX SBOM каждой программы.

Архивы делает `cargo xtask package platform --flavor <…> --bin <каталог> --version <версия> --dist <каталог>` (шаги описаны в `--help`). Сначала идут проверки варианта: статический CRT, отсутствие импортов, которых нет в Windows 7, glibc 2.28, оба среза macOS. Затем проверяется состав архива: только ожидаемые файлы, ни ключей, ни токенов, ни фикстур. В конце, если хост может их запустить, распакованные архивы проверяются запуском: hash и verify, `oncl-server` с примером конфигурации без слушающего сокета, подпись через сервер, явно включённый на loopback, чистая остановка. Сборки для Windows 7 и Linux делает `cargo xtask package platform-build` (`-Zbuild-std` на закреплённом nightly, контейнер с glibc 2.28), остальные собирает обычный `cargo build`.

Результаты хранятся 30 дней как артефакты workflow `platform-<вариант>` и `platform-sbom`. Это не `release-*`, `publish` их не берёт, они не подписываются и не отправляются ни в реестры, ни в магазины браузеров. К релизу они не прикладываются.

## 9. Сайт проекта на Pages

`pages.yml` публикует одним артефактом сайт проекта (`site/`, `cargo xtask registry build`: каталог портов, загрузка, история оригинала) и рядом с ним каталог `updates/`. Индексы копируются в артефакт после сборки сайта байт в байт. У сайта нет своего пути `updates`: workflow проверяет это и сверяет копию командой `diff -r updates _site/updates`.

Там же `pages.yml` кладёт `firefox/updates.json`, файл обновлений Firefox (`update_url` в манифесте расширения). Шаг «Firefox update manifest» берёт опубликованные релизы от `0.1.1` и выше, скачивает их `.xpi` и `SHA256SUMS` и включает версию, только если в `.xpi` есть подпись AMO (`META-INF/mozilla.rsa`); `update_hash` берётся из `SHA256SUMS` и сверяется с файлом (`cargo xtask ext updates`). Предварительные версии, черновики и неподписанные `.xpi` в файл не попадают, а релиз с битыми файлами пропускается с предупреждением. Без подписанных версий список пуст, и это допустимый файл. Файл обновляется при ближайшем запуске Pages после публикации релиза.

Workflow запускается:

- при пуше в `main`, который меняет индексы, ключи, `tuf/`, `site/`, `plugins/*/plugin.toml` или `registry.toml`, `xtask/`, тексты возможностей плагинов, бандлы ядра или фикстуры сайта;
- раз в сутки, чтобы подхватить новые релизы и факты из ветки `upstream`. GitHub отключает расписание после 60 дней без активности в репозитории; тогда его нужно снова включить в Actions;
- после того как наблюдатель за оригиналом опубликовал факты (`repository_dispatch` с типом `upstream`);
- после каждого запуска workflow Release (`workflow_run`). Релиз создаёт задание `publish` с токеном `GITHUB_TOKEN`, а события от этого токена другие workflow не запускают, поэтому событие `release` на такой релиз не приходит;
- когда мейнтейнер публикует черновик, правит или удаляет релиз (событие `release`). Само это событие не деплоит, потому что окружение `github-pages` пропускает только ветку по умолчанию, а перезапускает `pages.yml` на `main`. Пока релиз остаётся черновиком, список релизов на сайте его не показывает;
- вручную: Actions → Pages → Run workflow.

Вне пуша базой для проверки индексов служит коммит, который сейчас развёрнут на Pages (последний успешный деплой окружения `github-pages`). Так запуск по расписанию, после релиза или вручную не опубликует индекс, который не прошёл бы проверку при пуше. Если деплоев ещё не было, проверка идёт с `--no-base`. Без каталога `updates/v1` сайт публикуется, только если этого каталога нет ни в базе, ни в коммите, развёрнутом на Pages (развёрнутый коммит workflow ищет при любом событии, в том числе при пуше). Если индексы есть хотя бы в одном из них, workflow падает, а не убирает их с Pages.

Список релизов и ветка `upstream` считаются внешними данными. Если их нет или они повреждены, в журнале появляется предупреждение, на сайте пишется «данных пока нет», и сборка продолжается. Повреждённый `registry.toml` или индекс останавливает сборку.

## 10. TUF: ключи, церемония, повседневная работа

Схема, роли, сроки и поведение клиента описаны в [`../design/tuf.md`](../design/tuf.md), здесь собраны действия владельца. Инструменты вызываются как `cargo xtask tuf …` (справка: `cargo xtask tuf <команда> --help`). Они используют тот же код `oncl_update::tuf`, что и клиент, и перед завершением проверяют каждый свой результат клиентским кодом.

### Порядок выпуска

- Индекс и метаданные TUF меняются одним PR. Сначала выполняется `cargo xtask index add` или `refresh`, затем `cargo xtask tuf update` (раздел 3, шаг 2). Цель TUF состоит из тех же байтов, что и индекс, поэтому после `tuf update` индекс менять нельзя. Индексы и `tuf/v1` коммитятся вместе; `index-check.yml` и `pages.yml` отвергают индекс, которого нет в `tuf/v1`.
- Сборку нельзя выпускать, пока не выполнены два условия. Во-первых, пройдена церемония: выполнен `tuf init`, в дереве есть `crates/oncl-update/keys/root.json`, созданы окружение `tuf-timestamp` и секрет `TUF_TIMESTAMP_KEY`. Во-вторых, `tuf/v1` опубликован на Pages и `cargo xtask tuf verify-published --url https://arynyklas.github.io/OpenNCALayer/tuf/v1/` проходит (так же, как задание `verify`). Сборка без `keys/root.json` обновляться не умеет и в индексы не попадает: признак `keyed` в `release.yml` определяется по `root.json`.

### Что где лежит

| Файл | Что | Где хранить |
|---|---|---|
| `<ключи>/root.key`, `targets.key`, `snapshot.key` | секретные ключи Ed25519, зашифрованы паролем (формат секретного ключа minisign: scrypt и контрольная сумма; неверный пароль отвергается) | офлайн, на зашифрованном носителе; не в git |
| `<ключи>/timestamp.key` | ключ timestamp, **не зашифрован**, одна строка `oncl-tuf-ed25519-seed-v1:<64 hex>` | только как секрет GitHub; после установки секрета файл удалить (при потере ключа нужна ротация, `tuf root --rotate-timestamp`) |
| `tuf/v1/metadata/<N>.root.json`, `<N>.targets.json`, `<N>.snapshot.json` | метаданные, **хранятся все версии** | git |
| `tuf/v1/targets/indexes/<sha256>.<канал>.json` | копия индекса под своим хешем | git |
| `crates/oncl-update/keys/root.json` | корень доверия клиента: копия `metadata/1.root.json` байт в байт (клиент встраивает его при сборке) | git |
| `metadata/timestamp.json` | подписывает CI при публикации Pages | **не в git**, только в артефакте Pages |

Каталог ключей не должен находиться там, где git может его закоммитить; `tuf init` это проверяет и не перезаписывает существующие файлы. В macOS и Linux файлы ключей получают права `0600`. В Windows права владельца не выставляются, и файлы наследуют права каталога (`tuf init` об этом предупреждает). Поэтому каталог ключей держат в папке, доступной только вам, на зашифрованном томе. Ключи шифруются scrypt с параметрами minisign (32 МиБ памяти), так что защита зависит от длины пароля: используйте длинную фразу.

### Церемония (один раз)

1. Создать ключи, корень версии 1 и якорь доверия:

   ```sh
   cargo xtask tuf init --keys <каталог вне репозитория>
   ```

   Пароль не короче 12 символов вводится дважды, без эха. Он один для всех трёх зашифрованных ключей: команды открывают root, targets и snapshot одним паролем, и ключи с разными паролями они не откроют. Команда печатает идентификаторы ключей, пишет четыре файла ключей, `tuf/v1/metadata/1.root.json` (подписан ключом root, срок 365 дней, `consistent_snapshot: true`, четыре различных ключа, пороги 1) и его копию `crates/oncl-update/keys/root.json`. Существующие файлы она не перезаписывает.

2. Создать окружение GitHub и секрет. Через веб-интерфейс: Settings → Environments → New environment `tuf-timestamp` → Deployment branches and tags → Selected branches and tags → Add `main`. Или командами:

   ```sh
   gh api -X PUT repos/arynyklas/OpenNCALayer/environments/tuf-timestamp \
     -F 'deployment_branch_policy[protected_branches]=false' \
     -F 'deployment_branch_policy[custom_branch_policies]=true'
   gh api -X POST repos/arynyklas/OpenNCALayer/environments/tuf-timestamp/deployment-branch-policies \
     -f name=main -f type=branch
   gh secret set TUF_TIMESTAMP_KEY --env tuf-timestamp < <каталог>/timestamp.key
   ```

   В PowerShell перенаправление `<` не работает, там используется `Get-Content -Raw <каталог>\timestamp.key | gh secret set --env tuf-timestamp TUF_TIMESTAMP_KEY`. Сразу после этого удалите `timestamp.key` (`rm <каталог>/timestamp.key`, в PowerShell `Remove-Item`). Другой копии ключа быть не должно; если секрет потерян, его заменяют ротацией (`tuf root --rotate-timestamp`).

   Окружение `tuf-timestamp` пропускает только `main`, и секрет `TUF_TIMESTAMP_KEY` существует только в нём. `gh secret list` без `--env` его не показывает; если такой секрет нашёлся среди секретов репозитория, его удаляют командой `gh secret delete TUF_TIMESTAMP_KEY`. Требований к проверяющим у окружения нет, потому что задание подписывает по расписанию без участия человека.

3. Закоммитить `tuf/v1/metadata/1.root.json` и `crates/oncl-update/keys/root.json` вместе с первым `cargo xtask tuf update` (раздел 3, шаг 2) в ближайший PR индекса и слить его до тега первой версии, которая должна обновляться через TUF. Сборка тега встраивает якорь из своего дерева, и без него версия обновляться не сможет. Первая публикация Pages подпишет timestamp, дальше это повторяется ежедневно.
4. Проверить, что после деплоя задание `verify` workflow Pages зелёное, а `https://arynyklas.github.io/OpenNCALayer/tuf/v1/metadata/timestamp.json` отдаёт файл.

До церемонии (нет ни `tuf/v1`, ни якоря) `tuf check` пишет «no TUF repository yet» и проходит, Pages не публикует `/tuf/`, а задание `timestamp` ничего не делает. После церемонии пустой или отсутствующий секрет считается ошибкой: запуск Pages красный и ничего не деплоится, а прежний сайт с ещё действующим timestamp отдаётся до 7 дней. Публикация без timestamp допустима, только пока нет `tuf/v1`, и в форках, где задание `timestamp` не запускается (`github.repository` должен быть `arynyklas/OpenNCALayer`).

### Повседневно и по расписанию

- При каждом выпуске индекса: раздел 3, шаг 2.
- Раз в месяц, не реже чем каждые 30 дней, даже без выпусков: `cargo xtask tuf update --keys <каталог> --refresh`. Команда выпускает новые версии `targets` и `snapshot` с теми же целями и новым сроком; дальше PR, `index-check.yml`, слияние. Раз в неделю `tuf-expiry.yml` проверяет `main` и падает (GitHub присылает письмо о сбое запуска по расписанию), если до конца срока targets или snapshot осталось меньше 10 дней или до конца срока root меньше 45.
- Раз в год: `cargo xtask tuf root --keys <каталог>` продлевает root (версия N+1, 365 дней, те же ключи, подпись ключом root). Просроченный root клиент не принимает, а `tuf update` и `tuf timestamp` с ним отказывают.
- Старые версии метаданных не удаляются: `tuf check --base` отвергает удаление и правку опубликованных файлов.

### Что делает CI каждый день

`pages.yml` запускается раз в сутки и при каждом слиянии, которое меняет `tuf/` или индексы.

1. Задание `timestamp` работает в окружении `tuf-timestamp`, только на `main` и только в репозитории `arynyklas/OpenNCALayer`, только на событиях `push`, `schedule`, `workflow_run`, `workflow_dispatch` и `repository_dispatch`, с правами `contents: read`; все действия закреплены по SHA коммита. Оно собирает xtask до того, как секрет попадает в окружение, и последним шагом, где секрет есть только в `env` этого шага, выполняет `cargo xtask tuf timestamp` над копией `tuf/v1`. Команда сначала проверяет репозиторий клиентским кодом без timestamp: цепочку root от встроенного якоря `crates/oncl-update/keys/root.json`, подписи, версии, хеши всех файлов, совпадение целей с `updates/v1/*.json` и запас не меньше суток до конца срока root, targets и snapshot. При любой ошибке файл не создаётся, код выхода ненулевой, а сообщение не содержит ключа. Подписанный файл секретом не является и передаётся в `build` через выход задания; после шага с секретом нет ни артефактов, ни других действий. Пустой секрет при существующем `tuf/v1` считается ошибкой.
2. Задание `build` всегда проверяет закоммиченное дерево командой `cargo xtask tuf check --no-timestamp --base …`: якорь без `tuf/v1` или `tuf/v1` без якоря дают ошибку, отсутствие обоих проходит. Затем оно кладёт `tuf/v1` и `metadata/timestamp.json` в `/tuf/v1/` артефакта Pages (в git файл не попадает) и проверяет копию командой `cargo xtask tuf check --fail-on-expiring --min-days 3 --min-root-days 3`.
3. Задание `oracle` (без секретов и без права записи) читает собранный артефакт с помощью python-tuf (`xtask/assets/tuf-oracle/verify_repo.py`, зависимости закреплены хешами в `requirements.txt`, установка через `pip install --require-hashes`). Независимая реализация должна принять репозиторий в том виде, в каком он будет отдаваться. Её согласие необходимо, но недостаточно: python-tuf принимает кое-что из того, что отвергает клиент на Rust, и решающей остаётся проверка на Rust. `deploy` ждёт заданий `build` и `oracle`.
4. После деплоя задание `verify` запускает настоящий клиент по HTTPS против опубликованного сайта (`cargo xtask tuf verify-published --url …/tuf/v1/`, до четырёх попыток, потому что Pages кэширует файлы на 10 минут).

Любая из этих ошибок делает запуск красным, и GitHub присылает письмо о сбое запуска по расписанию. Если падает задание `timestamp` (репозиторий не проходит проверку, snapshot истёк, секрета нет), сайт не деплоится вообще. Сайт без `metadata/timestamp.json` дал бы каждому клиенту 404, то есть ошибку проверки, а прежний сайт ещё отдаёт timestamp, который действует до 7 дней. Из-за этого, пока TUF красный, не публикуются ни индексы, ни остальной сайт, и чинить нужно сразу (см. следующий раздел). Ручной запуск Pages (`workflow_dispatch`) с ветки, отличной от `main`, при существующем `tuf/v1` всегда красный: на такой ветке задание `timestamp` не запускается, а без timestamp `build` останавливается с ошибкой. Запускайте Pages только с `main`: `gh workflow run pages.yml --ref main`.

### Если timestamp истёк (запуск красный, клиенты не обновляются)

1. Откройте красный запуск Pages и прочитайте сообщение.
   - `expired` или `expiring` у `snapshot` или `targets`: продлите их командой `cargo xtask tuf update --keys <каталог> --refresh`, откройте PR и слейте; после слияния Pages подпишет timestamp.
   - `expired` у `root`: выполните `cargo xtask tuf root --keys <каталог>`.
   - `no TUF repository` или `does not verify`: исправьте репозиторий по коду ошибки из таблицы ниже.
   - «the environment variable TUF_TIMESTAMP_KEY is not set»: секрет пропал. Восстановите его через `gh secret set` из `timestamp.key` или выполните ротацию.
2. Пока запуск красный, Pages отдаёт прежний сайт. Его timestamp действует до 7 дней, после чего клиенты перестают принимать обновления (`docs/design/tuf.md`, «Сбои»). Установленные версии продолжают работать, ничего не откатывается, и клиенты снова получают обновления, как только Pages опубликует свежий timestamp.
3. Если Pages не публикуется потому, что GitHub отключил расписание после 60 дней без активности, включите его в Actions заново.

### Ротация (команды)

| Что | Команда | Потом |
|---|---|---|
| timestamp | `cargo xtask tuf root --keys <каталог> --rotate-timestamp` | порядок: (1) слить PR с новым root; (2) **после** слияния положить `<каталог>/timestamp.v<N>.key` в секрет (`gh secret set TUF_TIMESTAMP_KEY --env tuf-timestamp < <файл>`) и удалить файл; (3) запустить Pages вручную: `gh workflow run pages.yml --ref main`. Между (1) и (3) запуск Pages красный: новый root называет новый ключ, а в секрете ещё старый (до слияния наоборот: старый root не знает нового ключа), поэтому `tuf timestamp` отказывает и сайт не деплоится. Клиенты всё это время получают прежний сайт с ещё действующим timestamp (до 7 дней), и в этот срок нужно уложиться |
| snapshot / targets | `… --rotate-snapshot` / `… --rotate-targets` | `cargo xtask tuf update --keys <каталог>`: targets и snapshot, подписанные старыми ключами, больше не действуют, и команда сама подпишет новые версии; новый `root` и новые метаданные коммитятся одним PR |
| root | `… --rotate-root` | новый корень подписан и старым, и новым ключом root; новый файл `root.v<N>.key` хранить как root, старый удалить после публикации |
| продление root | `… ` (без флагов) | раз в год |

Новые зашифрованные ключи получают тот же пароль, которым открыты старые (не короче 12 символов). Новые ключи пишутся рядом со старыми с суффиксом `.v<N>.key`, где N равно версии нового root, а старые файлы остаются на месте. Ключ root один, порог 1, резерва нет, поэтому его потеря или утечка означает переустановку у всех пользователей (`docs/design/tuf.md`, «Ротация и компрометация»). Храните его так, чтобы не потерять и никому не отдать. Для ротации выпуск клиента не нужен.

### Что проверяет `cargo xtask tuf check`

`cargo xtask tuf check [--dir tuf/v1] [--index updates/v1] [--anchor crates/oncl-update/keys/root.json] [--base <ref>] [--no-timestamp] [--fail-on-expiring] [--min-days 10] [--min-root-days 45] [--now <время>]`. Если нет ни каталога, ни якоря, команда пишет `tuf check: no TUF repository yet` и завершается с кодом 0 (состояние до церемонии). Без `--no-timestamp` timestamp обязателен и проверяется (так проверяется репозиторий перед публикацией); с этим флагом timestamp в дереве, наоборот, запрещён.

С `--repo both` (по умолчанию) рядом с `tuf/v1` проверяется и `tuf/v2` (`docs/design/publishers.md`), если он есть: каталог `--v2-dir` (по умолчанию `v2` рядом с `--dir`), якорь `--v2-anchor` (по умолчанию его собственный `metadata/1.root.json`), реестр издателей `--publishers` (по умолчанию `publishers/`). Находки `tuf/v2` начинаются с `tuf/v2: `, сверки двух репозиториев — с `tuf/v1 and tuf/v2: `. `--repo v1` и `--repo v2` проверяют один. С `--no-timestamp` в `tuf/v2` нет ни timestamp, ни snapshot (снимок `tuf/v2` подписывает CI); без него обязательны оба.

Коды выхода: **0** означает, что всё проверено (предупреждения на код не влияют) или репозитория ещё нет; **1** означает найденные проблемы или невозможность выполнить проверку; **2** означает ошибку в командной строке. Каждая находка печатается строкой `tuf check: error[<код>]: <сообщение>` в stderr или `tuf check: warning[<код>]: <сообщение>` в stdout, в конце выводится `tuf check: ok` или `tuf check: failed with N problem(s)`. Часы для проверки подписей удерживаются внутри срока действия файлов, поэтому подписи и цепочка проверяются и у просроченного репозитория, а сроки дают отдельную находку.

| Код | Значение |
|---|---|
| `stray-file` | файл вне раскладки или файл цели, на который не ссылается ни один targets |
| `timestamp-committed` | `metadata/timestamp.json` лежит в дереве (с `--no-timestamp`) |
| `no-timestamp` | timestamp обязателен, но его нет |
| `no-root`, `root-gap`, `no-snapshot`, `no-targets` | нет `<N>.root.json`, пропущена версия root, нет snapshot или targets |
| `anchor-missing`, `anchor-mismatch`, `anchor` | нет якоря при существующем репозитории; якорь не равен `metadata/<его версия>.root.json` байт в байт; якорь не читается как root |
| `repository-missing`, `repository-removed` | якорь есть, каталога нет; репозиторий был в `--base` и пропал |
| `client` | клиент отвергает репозиторий (текст ошибки клиента в сообщении): цепочка root, подписи, версии |
| `signature`, `malformed`, `unreadable` | подписей меньше порога; файл не разбирается; файл не читается |
| `stale-snapshot`, `stale-targets`, `version-mismatch` | timestamp или snapshot указывают не на самую новую версию; версия в файле не равна версии в имени |
| `missing-file`, `hash-mismatch` | файл, на который ссылаются метаданные, отсутствует или не совпадает по длине или хешу |
| `index-mismatch`, `index-not-listed`, `index-missing`, `unexpected-target` | цель не равна байтам `updates/v1/<канал>.json` (нужен `cargo xtask tuf update`); индекс не перечислен в targets; targets перечисляют индекс, которого нет; цель не является индексом |
| `file-modified`, `file-removed`, `version-rollback`, `no-version-bump` | относительно `--base`: опубликованный файл изменён или удалён, версия уменьшилась, файлы добавлены без роста версии |
| `expired`, `expiring` | срок истёк или осталось меньше `--min-days` (targets, snapshot) или `--min-root-days` (root) дней; с `--fail-on-expiring` это ошибка, иначе предупреждение |
| `snapshot-committed`, `unexpected-timestamp` | `tuf/v2`: snapshot лежит в дереве; timestamp есть до проверки снимка |
| `delegation-refused`, `key-reused`, `delegations-missing` | `tuf/v2`: делегирование нарушает профиль; ключ роли издателя совпадает с ключом root; в targets нет поля `delegations` (клиент `0.1.2` его не требует, а `tuf/v2` без него не собирается) |
| `role` | `tuf/v2`: клиент не принимает последнюю версию роли делегированного издателя (подпись, версия, вложенные делегирования, цель вне путей) |
| `role-gap`, `role-not-delegated`, `too-large` | `tuf/v2`: пропущена версия роли; файлы роли есть, а делегирования ей не было ни в одном targets; файл роли больше, чем клиент читает (128 КиБ) |
| `snapshot-role-missing`, `snapshot-role-stale`, `snapshot-meta-incomplete`, `snapshot-rollback` | `tuf/v2`, страж онлайн-снимка: снимок не перечисляет роль, у которой есть файлы (и отозванного издателя); перечисляет не последнюю версию; запись без длины и sha256; более старый снимок рядом перечислял файл, который новый выкинул, или версию выше |
| `publishers-invalid`, `publishers-mismatch`, `publishers-not-listed`, `delegations-mismatch` | `tuf/v2`: `publishers/` нарушает правила; `publishers.json` или `delegations` в targets не то, что собрал бы `cargo xtask tuf update` |
| `shared-key`, `index-diverged` | цепочки корней двух репозиториев (все версии, не только действующие) делят ключ иначе, чем общий ключ targets, бывший только ключом targets в обеих (или ключ издателя — ключ какого-либо корня); targets двух репозиториев перечисляют разные индексы |
| `targets-key-differs` (предупреждение) | ключи targets двух корней разные: `cargo xtask tuf root --repo v2` после ротации targets в `tuf/v1` |
| `role-expired`, `role-expiring` (предупреждения) | `tuf/v2`: срок роли издателя истёк или подходит; публикацию не останавливает |

Остальные команды: `tuf init`, `tuf update [--refresh]`, `tuf timestamp --out <каталог> [--key-env ИМЯ | --key-file ФАЙЛ] [--anchor] [--index]`, `tuf root [--rotate-timestamp] [--rotate-snapshot] [--rotate-targets] [--rotate-root]`, `tuf verify-published --url <база> [--anchor] [--allow-missing]` (с `--allow-missing` ещё не опубликованный репозиторий не считается ошибкой). Для автоматизации и тестов пароль можно читать из файла (`--passphrase-file`), а время подписи задаётся `--now`.

`tuf/v2` (`docs/design/publishers.md`, «xtask»): `tuf init --repo v2 [--v1 tuf/v1] [--anchor]` — свой ключ root (зашифрован), онлайн-ключи `v2-snapshot.key` и `v2-timestamp.key` (секреты `TUF_V2_SNAPSHOT_KEY` и `TUF_V2_TIMESTAMP_KEY`), ключ targets из действующего корня `tuf/v1`; `tuf root --repo v2 [--rotate-root] [--rotate-snapshot] [--rotate-timestamp]` — ключ targets всегда берётся из `tuf/v1` (ротация targets делается в `tuf/v1`, затем `tuf root --repo v2`); `tuf update [--repo v1|v2|both]` — по умолчанию `both`: `tuf/v1` всегда, `tuf/v2` только если есть `tuf/v2/metadata/1.root.json`; когда он есть, сначала проверяется всё, из чего собирается `tuf/v2` (реестр издателей, их ключи против всех корней обеих цепочек, индексы), затем `tuf/v1` как раньше, затем верхний targets `tuf/v2` над теми же индексами, `publishers.json` и делегированиями из `publishers/` (снимок не пишет), при отказе любого ничего не остаётся записанным; `tuf snapshot --out <копия tuf/v2> (--previous https://…/tuf/v2/ | --first-publication) [--key-env ИМЯ | --key-file ФАЙЛ]` — онлайн-снимок над проверенной копией, продолжающий опубликованный (тот кладётся рядом); без timestamp на `--previous` команда отказывает, снимок «с нуля» подписывается только с `--first-publication`; `tuf timestamp --repo v2`, `tuf verify-published --repo v2` (ещё `publishers.json` и каждая делегированная роль). Пока `tuf/v2` нет, `tuf update` и `tuf check` пишут и проверяют `tuf/v1` побайтно так же, как раньше, и добавляют одну строку о том, что `tuf/v2` ещё нет.

## 11. После выпуска

- Проверить происхождение файлов релиза: `gh attestation verify <файл> --repo arynyklas/OpenNCALayer`.
- Проверить аттестацию, которую GitHub выпускает при публикации неизменяемого релиза: `gh release verify v<версия> --repo arynyklas/OpenNCALayer` для релиза целиком и `gh release verify-asset v<версия> <файл> --repo arynyklas/OpenNCALayer` для скачанного файла.
- Проверка установки на macOS. Workflow `mac-smoke.yml` запускается после каждого Release для тега (`workflow_run`) и вручную (Actions → Mac smoke → Run workflow, вход `tag`; для запуска через `workflow_dispatch` файл должен лежать в ветке по умолчанию). Он ставит `.pkg` тега командой `installer -pkg … -target CurrentUserHomeDirectory` на `macos-15` (Apple Silicon) и `macos-15-intel` (Intel) и печатает результат каждой проверки строкой `PASS|FAIL <имя> <подробности>`. Любой `FAIL` роняет задание, журнал каждого Mac сохраняется артефактом `mac-smoke-<runner>-<тег>`. Задание `index` его не ждёт, но PR с индексами (раздел 3) нельзя сливать, пока оба прогона не зелёные, потому что в индексах уже есть вариант `osx`. Список проверок находится в самом workflow, сводка в [`docs/user/install.md`](../user/install.md#установка). Черновик pre-release workflow с токеном только на чтение не видит. В этом случае `.pkg` берётся из артефакта `release-packages-osx` запуска Release, а вместо `SHA256SUMS` проверяется аттестация происхождения. После Release это происходит автоматически. При ручном запуске для черновика укажите ещё вход `run_id`, номер запуска Release для этого тега (его видно в адресе запуска в Actions → Release); для опубликованного релиза `run_id` не нужен. Метки раннеров соответствуют [списку образов GitHub](https://github.com/actions/runner-images#available-images). Раннеры на Intel GitHub поддерживает до вывода из эксплуатации образа macOS 15 осенью 2027 года ([объявление](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down)), после этого матрицу нужно сократить. Gatekeeper, самообновление, браузеры и значок в строке меню этот workflow не проверяет (демон запускается с `--no-tray`).
- Самообновление на macOS. Workflow `mac-selfupdate.yml` запускается только вручную (Actions → Mac self-update → Run workflow, входы `from` и `to`, по умолчанию `v0.1.0-rc.4` и `v0.1.0`). Он ставит опубликованный `.pkg` версии `from`, запускает демон и до 60 минут ждёт, пока тот сам обновится до `to` по опубликованному индексу. После этого проверяются строка `the update is healthy` в журнале и порт `127.0.0.1:13579`. Версия `from` должна быть опубликована (не черновик), а индекс `beta` на Pages уже должен перечислять `to`. Запуск идёт на `macos-15` и `macos-15-intel`, каждая проверка печатается строкой `PASS|FAIL <имя> <подробности>`, журналы сохраняются артефактом `mac-selfupdate-<runner>-<from>-to-<to>`.
- Убедиться, что индекс опубликован: `curl -fsS https://arynyklas.github.io/OpenNCALayer/tuf/v1/metadata/timestamp.json`.
- Сам себя обновляет только экземпляр, поставленный установщиком (`Setup.exe`, `.pkg`, `.zip`, AppImage). Программа из архива работает, но обновления у неё выключены. Пакет `openncalayer-bin` для pacman пользователь обновляет вручную, самообновление в нём тоже выключено.
- Пакет для Arch Linux отдельно не публикуется: чтобы исправить сам пакет, выпускают новую версию программы.

## 12. Приватность

Оригинальный NCALayer запускается только в приватной лаборатории, и то, что видно только там, в публичный репозиторий не попадает: записи обмена с оригиналом, серийные номера и имена тестовых сертификатов НУЦ, пути на машинах, имена приватных хостов, сетей и репозиториев. Ожидаемые значения в публичных тестах выводятся из правил на синтетических фикстурах, а не копируются из записей. Соблюдение этого проверяет `cargo xtask privacy`, в CI это делает `privacy.yml`: его вызывает `ci.yml` (задание `privacy`) в каждом своём запуске, то есть на каждый PR, каждый пуш в `main`, ночью и вручную.

Структура проверяется всегда:

- нет файлов `*.jsonl` и `*.jsonl.zst` вне `target/`. Фикстуры с таким расширением, которые не являются записями, перечислены в `TRANSCRIPT_FILE_EXCEPTIONS` в `xtask/src/privacy.rs`;
- нет текста с заголовком записи рекордера (`"recorded_at"` вместе с именем инструмента записи или кадром сервера `"dir":"s2c"`), в том числе с экранированными кавычками внутри строкового литерала;
- нет путей с буквой диска (`[A-Z]:\`, `[A-Z]:/`) ни в коде, ни в документах. Тестовые литералы, которые нужны коду (пути установки под Windows и подобные), перечислены по файлам в `MACHINE_PATH_EXCEPTIONS`: файл, буква диска и начало остатка пути. Новый литерал добавляется туда в том же PR;
- нет сертификатов, выпущенных тестовым УЦ НУЦ, ни в DER, ни в base64 (PEM, строки JSON и литералы, разбитые на несколько строк). Издатель определяется по имени: это субъекты сертификатов из `fixtures/nca/test/`. Сами эти сертификаты УЦ, синтетические фикстуры, публичные сертификаты НУЦ и фикстуры OpenSSL проходят. Записанный ответ публичного тестового OCSP НУЦ (`fixtures/nca-ocsp/`) разрешён по хешу содержимого (`TEST_CA_EXCEPTIONS`).

Проверяются отслеживаемые файлы рабочего дерева (`git ls-files`) целиком. С `--range <base>..<head>` дополнительно проверяется то, что добавляет каждый коммит диапазона относительно своего родителя (у слияния относительно первого), и сообщения этих коммитов. В текстовом файле проверяются только строки, добавленные коммитом (`+` в диффе; номер строки берётся из версии файла после коммита). Поэтому текст, который уже был в базе или в предыдущем коммите диапазона, не срабатывает повторно, когда коммит лишь правит файл рядом, сдвигает или переставляет эту строку; строка, которую дифф и удаляет, и добавляет, добавленной не считается. Бинарный файл (поиск сертификатов) проверяется целиком, но только когда коммит его добавляет или меняет, а путь файла проверяется, когда коммит его создаёт. Версия файла, совпадающая с версией в рабочем дереве, уже проверена целиком и отдельно не повторяется. Строка, добавленная и затем удалённая внутри диапазона, всё равно находится в коммите, который её добавил. Если вместо базы указать пустое дерево `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, проверяется вся история. Workflow берёт диапазон PR (`base..head`), пуша (`before..sha`) или новой ветки (от общего предка с веткой по умолчанию).

Denylist представляет собой приватный список того, что нельзя публиковать. В репозиторий он не попадает.

- `cargo xtask privacy --denylist <файл>`: по одной записи на строку, это подстрока без учёта регистра или `re:<выражение>` (синтаксис крейта `regex`). Пробелы по краям отбрасываются, пустые строки и строки, начинающиеся с `#`, пропускаются.
- Проверяются строки файлов (бинарный файл целиком, без номера строки), пути файлов и строки сообщений коммитов.
- Находка печатается как `файл:строка: denylist entry`, для сообщения коммита как `commit <id>:строка`, для версии файла из истории как `файл@<blob>:строка`. Ни сама запись, ни совпавший текст не печатаются, а ошибка в записи сообщает только номер строки списка.
- В CI список хранится в секрете `PRIVACY_DENYLIST` как base64 файла (`base64 -w0 <файл>` → Settings → Secrets and variables → Actions). Шаг denylist раскодирует его во временный файл и запускает уже собранный xtask. Без секрета (форк, PR из форка) шаг оставляет `::notice::` и проходит, а структура проверяется и там.
- У мейнтейнера тот же список перед каждым пушем проверяет хук `pre-push` в публичном checkout. Хук и список хранятся вне репозитория.

Найденное исправляют до пуша (`git commit --amend`, `git rebase -i`). Пушить коммит, на котором сработала проверка, нельзя, даже если следующий коммит это убирает: с `--range` проверка видит и его.
