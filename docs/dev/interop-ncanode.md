# Interop с NCANode (Kalkan)

`cargo xtask interop-ncanode` проверяет наши подписи XMLDSig и CMS и наши файлы ключей в [NCANode](https://github.com/ncanode-kz/NCANode). Сервер проверяет их через Kalkan, как это делают сервисы, принимающие подписи NCALayer. Команда работает только в Linux. В Windows она печатает «interop с NCANode запускается в Linux» и завершается с кодом 0.

## Образ

| | |
|---|---|
| Образ | `malikzh/ncanode@sha256:052222f30ac73d9f0060a5c80c572723d25dd84e21073435795a10db254c02b8` |
| Версия | NCANode 3.5.1 (тег Docker Hub `3.5.1`, релиз GitHub `3.5.1`), KalkanCrypt 0.7.5 |
| Ревизия | `0adab29a7d30c181d70e8cc6b4f243122f50c3b8`; с неё же `cargo xtask fetch-fixtures` берёт тестовые файлы |

Digest закреплён в `xtask/src/ncanode/container.rs` (`IMAGE`). Чтобы обновить образ, поменяйте digest там и в этой таблице, а также `NCANODE_COMMIT` в `xtask/src/fetch.rs`. После обновления проверьте, что контрольные случаи (см. ниже) по-прежнему получают `SIG_CRYPTO_FAILURE`, а хорошие подписи получают ожидаемую оценку сертификата. Правило прохождения опирается на порядок проверок в `AdesVerificationService.grade()`: сначала значение подписи, потом сертификат.

NCANode запускается с настройками по умолчанию: промышленные корни, CRL и OCSP НУЦ. При старте он скачивает сертификаты и CRL с `pki.gov.kz`, `root.gov.kz` и `crl.pki.gov.kz`/`crl.root.gov.kz`, так что нужна сеть. Если скачать сертификат НУЦ не удалось (`Cannot download file`, случается то с одним, то с другим сертификатом), NCANode завершается. Тогда xtask печатает журнал контейнера и запускает его заново, всего до пяти попыток.

Кэш NCANode (`/app/cache`) хранится в томе Docker `oncl-ncanode-cache` и переживает запуски. Уже скачанные сертификаты НУЦ NCANode берёт из кэша (`CaService`), поэтому следующая попытка или следующий запуск скачивает меньше. Исключение: `nca_gost.crt` просрочен (`notAfter` 2025-06-25), и NCANode скачивает его заново при каждом старте.

### Образ и том вне `target/`

Образ (около 700 МБ) и том `oncl-ncanode-cache` лежат вне `target/`, в хранилище Docker:
- образ объявляет `VOLUME /app/cache`, так что без именованного тома каждый запуск оставлял бы анонимный том;
- NCANode работает в контейнере от root, поэтому bind mount в `target/` оставил бы там файлы root, которые `cargo clean` не удалит.

Где они лежат, зависит от движка Docker: с `docker.io` внутри дистрибутива в `/var/lib/docker`, с Docker Desktop в его хранилище. Удалить их можно так:

```sh
docker volume rm oncl-ncanode-cache
docker image rm malikzh/ncanode@sha256:052222f30ac73d9f0060a5c80c572723d25dd84e21073435795a10db254c02b8
```

## Запуск

Нужен Docker. В Debian или Ubuntu (в том числе в WSL) он ставится и запускается от root:

```sh
apt-get install -y docker.io
service docker start
```

Пользователь должен входить в группу `docker`. В CI на раннере `ubuntu-24.04` Docker уже есть. Затем:

```sh
cargo xtask fetch-fixtures     # тестовые ключи NCANode → target/fixtures/ncanode/
cargo xtask interop-ncanode
```

Контейнер называется `oncl-ncanode-interop` (`ONCL_NCANODE_CONTAINER` меняет имя, `ONCL_NCANODE_CACHE_VOLUME` меняет том кэша) и слушает случайный порт на `127.0.0.1`. После проверки контейнер удаляется, а том с кэшем и образ остаются (как их удалить, написано выше). Контейнер с тем же именем, оставшийся от прерванного запуска, удаляется перед стартом.

Если `docker pull` падает с `docker-credential-desktop.exe: executable file not found` (в WSL остался `~/.docker/config.json` от Docker Desktop), образ можно скачать с пустым конфигом: `DOCKER_CONFIG=<пустой каталог> docker pull <образ>`. После этого команда скачивать образ уже не будет.

В CI команда запускается только в job `live` (по расписанию и вручную), а не на каждый push. Все 47 проверок проходят.

Полная независимая матрица семейств из OpenAPI NCANode (CMS/CAdES, XML/XAdES, PDF/PAdES и другие) запускается командой `cargo xtask platform-interop`, см. [platform-interop.md](platform-interop.md). Эта же команда проверяет только наши файлы ключей и XMLDSig и CMS через Kalkan. В platform-interop описан и локальный проверяющий на самом провайдере Kalkan (небольшая Java-программа; jar-файлы даёт оператор, в репозитории их нет). Он проверяет ГОСТ-подписи, которые NCANode через свой API проверить не может: WS-Security, сырую подпись, JWS `ECGOST3410-2015-512`.

## Что проверяется

Ключи:
- синтетические `fixtures/synthetic/user-{gost2015,gost2004,rsa}-sign.p12`;
- тестовые ключи NCANode (из `WithTestData.groovy`, скачиваются `cargo xtask fetch-fixtures`):
  - `individual_valid_2015.p12`: ГОСТ 2015-512, пароль `Aa123456`, истёк 2023-07-28;
  - `ceo_sign_revoked_2004.p12` (`KEY_CEO_SIGN_REVOKED_2004`): ГОСТ 34.310-2004, издатель `ҰКО 3.0 (GOST TEST)`, пароль `Qwerty12`, истёк 2023-01-18;
  - `individual_valid_sign_2004.p12` (`KEY_INDIVIDUAL_VALID_SIGN_2004`): несмотря на имя, это RSA-2048 / sha256WithRSA, издатель `ҰКО 3.0 (RSA TEST)`, пароль `Qwerty12`, истёк 2022-01-18. В выводе он называется «NCANode RSA».

Подпись создаётся в процессе (`oncl_xml`, `oncl_pki::cms`), а результат отправляется в HTTP API NCANode.

| Проверка | Как |
|---|---|
| XML, весь документ | `sign_enveloped` → `/xml/verify`. Документ на входе неудобный: BOM, декларация, комментарии, CRLF, пространство имён по умолчанию, `xml:lang`, атрибуты не по порядку, пустой элемент, кириллица. Подписанный документ в форме Kalkan, без BOM и декларации |
| XML, элемент `#payload` | `sign_element("//data")` → `/xml/verify` (с DTD, см. ниже) |
| CMS присоединённая и отсоединённая | `cms::sign` → `/cms/verify` (для отсоединённой подписи вместе с `data`) |
| XML, две подписи | синтетические ГОСТ 2015, затем RSA → `/xml/verify`. Проверяется число подписантов (2) и оценка первой подписи: вторую NCANode не оценивает (см. ниже) |
| CMS, соподпись | синтетические ГОСТ 2015, затем RSA → `/cms/verify`, 2 подписанта, оценка каждого |
| Контрольные случаи | NCANode обязан ответить `INVALID/SIG_CRYPTO_FAILURE` на изменённый документ (ГОСТ 2015, синтетический ключ); изменённый элемент `#payload` с DTD (ГОСТ 2015, синтетический ключ); изменённый элемент `#e1` с DTD (ключ NCANode ГОСТ 2015); испорченный `DigestValue` (ключ NCANode ГОСТ 2004); изменённое значение подписи CMS (синтетический ГОСТ 2015 и ключ NCANode ГОСТ 2004) |
| Digest против Kalkan | Kalkan подписывает тот же вход тем же ключом (`/xml/sign`), и `DigestValue` новой ссылки должен совпасть с нашим. Входы: неудобный документ целиком (все три ключа NCANode); тот же документ с нашей подписью (вторая подпись покрывает первую); элемент `#e1` под двумя разными `xml:lang`. Затем наш `verify` должен принять документ, подписанный Kalkan |
| `#e1` под двумя `xml:lang` | наша подпись элемента → `/xml/verify` |
| Наш файл ключа без сертификата | генерируем ключ (ГОСТ 2015, ГОСТ 2004, RSA; `oncl_pki::keygen`), строим на него CSR (`oncl_pki::csr`) и пишем ключ в `<PREFIX><keyId>.p12` (`keystore::create_key_file`, пароль `Default1`) → `/pkcs12/aliases`: Kalkan открывает файл и видит ровно один alias, равный keyId |
| Наш файл ключа с установленным сертификатом | синтетический ключ того же алгоритма выпускает сертификат по CSR (субъект, ключ и расширения из запроса, SKI = keyId); `keystore::install_certificate`, затем `keystore::change_password` на `Interop12`, как в `importCertificate` → `/pkcs12/info`: Kalkan находит в файле сертификат с нашим серийным номером |
| Kalkan подписывает CMS нашим файлом ключа | `/cms/sign` с этим файлом → `/cms/verify`: подпись Kalkan нашим ключом проверяется, 1 подписант, `INDETERMINATE/CHAIN_INCOMPLETE` |

Подпись CSR в NCANode проверить нельзя: метода для PKCS#10 у него нет, а `/x509/verify` принимает подписанные данные строкой UTF-8, которой `CertificationRequestInfo` не является. Подпись CSR проверяет сам xtask (нашим кодом, открытым ключом из запроса) перед выпуском сертификата. То, что Kalkan читает сгенерированный ключ, показывает проверка «Kalkan подписывает CMS». То, что Kalkan принимает подписи, созданные `PrivateKey::sign` (им же подписывается CSR), показывают проверки синтетическими ключами.

### Как читать результат

NCANode оценивает подпись по шагам (`AdesVerificationService.grade()`). Сначала проверяются значение подписи и дайджесты ссылок; при неудаче ответ `INVALID/SIG_CRYPTO_FAILURE`. Потом проверяется сертификат: срок, доверенный издатель, отзыв. Ни один ключ здесь не строит цепочку до действующего корня НУЦ: у синтетических ключей свои корни, тестовые сертификаты NCANode просрочены. Поэтому `valid` всегда `false`.

Проверка пройдена, только если NCANode вернул ровно ожидаемую оценку и ожидаемое число подписантов:
- хорошая подпись синтетическим ключом: `INDETERMINATE/CHAIN_INCOMPLETE`;
- хорошая подпись ключом NCANode: `INDETERMINATE/OUT_OF_BOUNDS_NO_POE` (срок истёк; для отозванного ГОСТ 2004 срок проверяется раньше отзыва);
- контрольный случай: `INVALID/SIG_CRYPTO_FAILURE`.

До оценки сертификата NCANode доходит, только если значение подписи сошлось, поэтому `OK` в колонке `signature` означает, что Kalkan принял подпись. Контрольные случаи показывают обратное на тех же путях: с DTD для элементов, на просроченных ключах NCANode, для XML и CMS. Значения колонки `signature`: `OK` для хорошей подписи с ожидаемой оценкой; `rejected, expected` для контрольного случая, отвергнутого как положено; `UNEXPECTED` для любой другой оценки (в колонке оценки тогда дописано, какая ожидалась); `ERROR`, если запрос не удался.

Особенности NCANode, которые учитывает команда:
- `/xml/verify` не регистрирует атрибуты `Id`, поэтому не находит `URI="#id"` и отвечает `SIG_CRYPTO_FAILURE` даже на подпись элемента, которую сделал сам Kalkan через `/xml/sign` с `referenceUri`. Поэтому в начало подписанного документа, который уходит в `/xml/verify`, xtask вставляет внутреннее подмножество DTD `<!DOCTYPE root [<!ATTLIST data Id ID #IMPLIED>]>`. Каноническую форму оно не меняет. С таким DTD подпись Kalkan проверяется (`OUT_OF_BOUNDS_NO_POE`), наша тоже, а изменённый элемент отвергается.
- В `/xml/verify` подпись ищется как `ds:Signature` среди детей корня и снимается через `root.removeChild`. Поэтому NCANode проверяет только подписи с префиксом `ds:`, вставленные в корень. Наши подписи именно такие.
- Для XML с несколькими подписями NCANode возвращает оценку только первой по документу подписи (проверяет он с последней), а `valid` вычисляет по всем. Поэтому проверка «XML 2 signatures: count, 1st graded» сверяет число подписантов и оценку первой подписи, но не второй. Вторую подпись покрывают проверка «XML document» с синтетическим RSA (Kalkan принимает нашу RSA-подпись) и «Kalkan digest: over our signature» (наш digest документа, уже несущего подпись, совпадает с дайджестом Kalkan).

Правило Kalkan для `xml:*` в Canonical XML: при наследовании от опущенных предков побеждает внешнее значение (`crates/oncl-xml/src/c14n.rs`). Это видно по проверкам «#e1 under 2 xml:lang»: digest элемента `<e Id="e1">` под `<r xml:lang="ru">` → `<m xml:lang="kk">` совпадает с дайджестом Kalkan, и NCANode принимает нашу подпись этого элемента.

Проверки «our key file»: `opened` в колонке `signature` значит, что ответ NCANode совпал с ожидаемым (для «key alone» это список alias из одного keyId, для «certificate installed» серийный номер выпущенного сертификата в том виде, как его печатает NCANode: `BigInteger.toString(16)`); `UNEXPECTED` значит, что не совпал (ожидаемое значение дописано в последнюю колонку). Проверка «Kalkan signs CMS» читается так же, как остальные проверки CMS. Ключи генерируются заново при каждом запуске, поэтому keyId и серийные номера в выводе каждый раз другие.
