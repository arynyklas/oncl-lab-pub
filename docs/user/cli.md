# Командная строка `oncl`

`oncl` работает поверх SDK и по умолчанию всё делает локально: он не запускает настольную программу, HTTP-сервер, демон или браузер. Если указать `--endpoint`, `oncl` становится потоковым клиентом HTTP-контракта `oncl-server` (раздел [«Удалённый режим»](#удалённый-режим---endpoint)). Режим выбирается только этим флагом, автоматического переключения нет.

Из исходников команду запускают так: `cargo run -p oncl-cli -- …`.

Команд шифрования и расшифрования (`encrypt`/`decrypt`) нет, в том числе в варианте «только RSA». Остальные ограничения перечислены в разделе [«Известные ограничения»](#известные-ограничения).

## Архив

`oncl` поставляется отдельным архивом без установщика:

- `oncl-<version>-<flavor>.zip` для Windows: `win-x64`, `win-x86`, для Windows 7 SP1 `win7-x64` и `win7-x86`;
- `oncl-<version>-<flavor>.tar.gz`: `linux-x64` (собран под glibc 2.28) и `osx` (универсальный).

В настольный пакет OpenNCALayer он не входит. У него нет установщика, канала обновлений и автозапуска, и он ничего не пишет вне путей, которые вы указали. В архиве лежат программа, `README.md`, `docs/cli.md`, `LICENSE`, `NOTICE` и `THIRD-PARTY.txt` с лицензиями стороннего кода, вошедшего в эту сборку (AWS-LC есть только в сборках для Linux и macOS). Сертификатов, ключей, токенов и тестовых файлов в архиве нет. Чтобы обновиться, распакуйте архив новой версии.

Архивы `oncl` и `oncl-server` к релизам на GitHub не прикладываются. Workflow выпуска сохраняет их как артефакты запуска (`platform-*`) на 30 дней; их можно скачать оттуда или собрать программу из исходников по руководству разработчика.

```sh
tar -xzf oncl-<version>-linux-x64.tar.gz
./oncl-<version>-linux-x64/oncl --version
printf abc | ./oncl-<version>-linux-x64/oncl hash --algorithm sha256 --input -
```

В Windows распакуйте `.zip` проводником или командой `tar -xf oncl-<version>-win-x64.zip` и запускайте `oncl.exe` из этой папки. Распространяемый пакет Visual C++ не нужен. Мейнтейнеры собирают и проверяют архивы командой `cargo xtask package platform` (справка: `cargo xtask package platform --help`).

## Команды

| Команда | Что делает |
|---|---|
| `hash --algorithm sha256\|gost2004\|gost2015-512 --input -` | Потоковый дайджест файла или stdin |
| `sign --profile …` | Подпись закрытым ключом, привязанная к источнику (см. ниже) |
| `verify --profile …` | Проверка с доверием, которое задаёт оператор; отсоединённая подпись через `--detached` |
| `extract` | Содержимое CMS как есть, без проверки |
| `inspect --profile certificate\|container\|cms\|named-key` | Только открытые метаданные |
| `extend --profile cms\|xml\|pdf --level b\|t\|lt\|lta` | Добавление доказательств к подписи без ключа |
| `timestamp acquire\|verify` | Отдельный токен штампа времени RFC 3161 |
| `jws sign\|verify`, `jwt encode\|verify\|decode` | JOSE: RS256 и ECGOST3410-2015-512 |
| `plugin call` | Вызов плагина WASM с правами, которые выдаёт оператор ([«Плагины»](#плагины-oncl-plugin)) |
| `plugin operations` | Список операций из манифеста плагина, по которому пишут права; по желанию проверка модуля |
| `batch run` | Упорядоченный смешанный пакет из JSON-манифеста |

Профили подписи: `cms`, `raw`, `digest-sha256|gost2004|gost2015-512`, `xml`, `wsse`, `pdf`, а также `cades-`, `xades-` и `pades-` с уровнями `b`, `t`, `lt`, `lta`. Профили проверки: `cms`, `xml`, `xml-kalkan`, `wsse`, `pdf` и те же семейства с уровнями. Профиль и алгоритм никогда не определяются по имени файла или по данным из недоверенного токена.

Пример (Git Bash):

```sh
printf abc | cargo run -p oncl-cli -- hash --algorithm sha256 --input -
```

Команда печатает `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`. `--input -` отдаёт stdin ровно одной роли; если stdin назначен двум ролям, команда отказывает ещё до чтения и записи.

## Подпись закрытым ключом, секреты и полномочия

```text
oncl sign --profile cms --detached --input document.bin --output signature.der \
  --key signer.p12 --secret-file secrets/signer.secret --authorize \
  --root operator-root.der --pki-endpoint https://pki.example.test
```

`--authorize` подтверждает использование ключа именно для этого источника, профиля, ключа и места назначения. Пароль сам по себе такого разрешения не даёт. Разблокированные ключи между запусками не кэшируются. Перед использованием закрытого ключа всегда выполняется строгая проверка сертификата и отзыва; `--offline` меняет только политику проверки, на подпись он не влияет.

Ключ задаётся одним из двух способов:

- `--key` с файлом PKCS#12 или JKS (`--alias`, если записей несколько);
- `--token-reader NAME --token-kind … --token-alias …` для PC/SC-токена. Если считывателя нет, команда отказывает и ничего не пишет.

Секреты в аргументах командной строки не передаются. Есть два варианта:

- `--secret-file` с файлом в существующем каталоге, доступ к которому есть только у владельца. SDK проверяет владельца и ACL каталога и файла, число жёстких ссылок и точки повторной обработки (reparse points) и ничего не исправляет сам. Файл может содержать не больше 4097 байт: пароль до 4096 байт и один завершающий LF или CRLF. Длинный файл не усекается, а отклоняется. Незащищённый каталог, слишком большой или отсутствующий файл и каталог вместо файла приводят к отказу до использования ключа.
- `--secret-interactive` для ввода с терминала. Пароль хранится в буферах фиксированного размера и затирается после использования. Если stdin занят документом или это не терминал, команда отказывает.

При интерактивном вводе Backspace удаляет один символ (скаляр Unicode), Ctrl-U очищает ввод, Ctrl-W удаляет слово, Ctrl-C отменяет. Режим терминала восстанавливается при обычном завершении, при ошибке и при раскрутке стека. При принудительном завершении процесса или зависшем системном чтении немедленная отмена и восстановление терминала не гарантируются.

## Доверие, сеть и время

Доверие задаёт только оператор:

- `--root` и `--intermediate`: корневые и промежуточные сертификаты;
- `--pki-endpoint`: точные адреса (origin) служб PKI. Для литерального IP адрес закрепляется сам; для DNS-имени нужен `--pki-pin 'http://host:port=IP:port'`, потому что системный DNS не используется;
- `--tsa-url` для получения штампов времени и `--tsa-policy OID` (для XAdES обязателен);
- `--as-of <Unix seconds>`: момент проверки. По умолчанию берутся часы хоста в UTC.

CAdES, PAdES и XAdES уровней T, LT и LTA с этими параметрами работают. Сертификаты, которые пришли внутри документа, якорями доверия не становятся.

Вся конфигурация читается в пределах одного бюджета памяти: не больше 1024 файлов сертификатов, 64 адресов и привязок, а закодированные сертификаты в сумме не больше `--configuration-bytes` (по умолчанию 16 МиБ). Дубликаты тоже засчитываются в бюджет.

Подпись CMS проверяет `oncl verify --profile cms --input <signature.p7s> --root <NCA root>`. Встроенного набора доверия нет, корни НУЦ, которым вы доверяете, передайте через `--root`. На вход принимается DER или BER. С флагом `--pem` (только для профиля CMS) принимается PEM: не больше 16 МиБ текста, ровно один блок `CMS` или `PKCS7` без текста вокруг; блок декодируется до разбора. Текстовое поле демо-страницы выдаёт PEM, а её файл `.p7s` содержит DER. Проверка всегда строгая. Политика совместимости с NCALayer (`OperationPolicy::ncalayer_compatibility()`) доступна только программе, которая встраивает SDK; в командной строке её не включить. Отчёт перечисляет отдельные проверки. Если время подписи ничем не доказано или данные об отзыве недоступны, вердикт `Indeterminate` (код выхода 3).

С `--profile cades-*` или `pades-*` подпись, которая проходит криптографическую проверку, но нарушает правила базового профиля, получает причину `Profile(SigningTimeForbidden|SigningTimeMissing|ContentTypeNotData|SigningCertificateMissing)`. Проверка подписи при этом `Passed`, вердикт `Invalid` (код выхода 2), а `ades_level` не указывается. PAdES, созданный Kalkan, содержит атрибут signing-time, который запрещает EN 319 142-1 (таблица 1), поэтому под `pades-*` он получает такую причину. `--profile pdf` проверяет те же байты только на целостность и доверие.

## Отчёты, коды выхода и вывод

| Код выхода | Значение |
|---:|---|
| 0 | Завершено или проверка `Valid` |
| 2 | Проверка `Invalid` |
| 3 | Проверка `Indeterminate` (например, `--offline` или статус недоступен) |
| 4 | Пакет не завершён: есть элементы с ошибкой или не запущенные |
| 1 | Сбой выполнения, ввода, ресурсов, прав или ошибка в аргументах |
| 130 | Отмена (Ctrl-C или Ctrl-Break) |

Если истёк срок `--timeout-seconds`, одиночная команда завершается кодом 1 (`DeadlineExceeded`), а пакет кодом 4 с частичным результатом. Поле `code` верхнего уровня в отчёте пакета принимает значения `Completed`, `Partial`, `Cancelled` или `DeadlineExceeded`. Если отчёт после остановки доставить не удалось, в stderr пишется `report_delivery_failed_after_stop`, а код 130 или 4 не меняется.

`--json` пишет отчёт в stdout, `--report <new path>` пишет его в новый файл. Двоичный `--output -` вместе с JSON в stdout отклоняется до чтения и записи. Сообщения об ошибках в аргументах не показывают их значения.

Результаты сначала пишутся во временный файл, а затем публикуются без перезаписи: существующий файл назначения и исходный файл никогда не заменяются. Квота, сериализация и синхронизация отчёта проверяются до публикации документа, но запись отчёта на диск после этого всё равно может завершиться сбоем, и об этом сообщается. Документ и отчёт не составляют одну атомарную транзакцию, а выполненная подпись не откатывается.

## JWS/JWT, WS-Security и пакеты

`jws sign|verify --serialization compact|flattened|general [--detached]`; `jwt encode|verify|decode`. `jwt verify` принимает `--issuer`, `--audience`, `--leeway-seconds` и сверяет время с часами хоста. `jwt decode` ничего не проверяет. Полезная нагрузка JWS не больше 256 КиБ, claims не больше 64 КиБ.

`sign|verify --profile wsse` принимают `--soap-version soap11|soap12`. Для проверки есть `--wsse-role`, `--wsse-required-header`, `--wsse-timestamp-required` и `--wsse-timestamp-max-lifetime`, для подписи `--wsse-token-reference ncanode-x509-key-identifier|binary-security-token`, `--wsse-token-id`, `--wsse-body-id` и `--wsse-timestamp-id|created|expires`. Параметры, неуместные для команды, отклоняются до чтения и записи.

`batch run --manifest batch.json [--key … --secret-file …] --authorize` выполняет элементы `hash`, `sign` (`cms|cms-detached|raw`), `verify` (с необязательным `detached`) и `extract`, у каждого уникальный `id`. Манифест проверяется целиком до чтения источников и открытия ключей. Файлы назначения не должны существовать, и выход одного элемента не может быть входом другого. Результат элемента публикуется сразу после его завершения, поэтому при последующем сбое или отмене уже записанные файлы остаются. Недоступный источник ломает только свой элемент. Код выхода 0, 2 или 3 определяется худшей проверкой, 4 ставится, если хотя бы один элемент с ошибкой или не запущен, 130 при отмене.

В Windows Ctrl-Break, отправленный группе дочерних процессов, завершает работу с кодом 130; отмена срабатывает между операциями чтения.

## Плагины (`oncl plugin`)

```text
oncl plugin operations --manifest plugin.toml [--wasm plugin.wasm] [--json]
oncl plugin call       --manifest plugin.toml --module plugin.wasm --operation OP --caller LABEL
                       --output - [--allow-import NAME …] [request] [key and grants]
```

Установка плагина не даёт ему прав. Оператор, который запускает команду, сам называет вызывающего (метка `LocalOperator`), операцию, точные импорты, ключ и адреса PKI, и плагин не может их расширить. Графического интерфейса, origin браузера и запросов пользователю здесь нет: если операции нужен диалог, она возвращает `InteractionRequired`, а согласие никто не спрашивает. Обе команды работают только локально; с `--endpoint` они отклоняются с `RemoteUnsupported` до чтения и записи.

### `plugin operations`: что объявлено

Команда перечисляет `[[operations]]` манифеста, чтобы права можно было написать, не читая TOML. Используется тот же разборщик (`Manifest::operations()` из `oncl-plugin`), что и в `plugin call` и `cargo xtask plugin-ops-check`. Ключи не открываются, код плагина не запускается.

| Флаг | Значение |
|---|---|
| `--manifest PATH` | `plugin.toml` плагина (не больше 64 КиБ) |
| `--wasm PATH` | Дополнительно скомпилировать модуль (не больше 16 МиБ) и сверить его с манифестом: каждый импорт, объявленный операцией, должен быть импортом модуля, а каждый импорт модуля должен быть объявлен как возможность (capability), как в `plugin-ops-check`. Если не сходится, код 1 |
| `--json`, `--report PATH` | Отчёт в JSON (глобальные флаги; `--report` создаёт новый файл и ничего не печатает) |

```text
$ oncl plugin operations --manifest plugins/example/plugin.toml
plugin test.cli 1.0.0: 2 declared operation(s)
operation sign
  label: "a"
  server: yes  manual: no
  cli: yes
  imports: keys_sign_raw
  network: pki
  param file: document (at most 4096 bytes)
  key: raw, content param:file
    signs with your key: a raw signature of the content
operation manual-only
  label: "a"
  server: no  manual: yes
  cli: no (not for the CLI: server = false)
  imports: none
  network: none
  param file: document (at most 4096 bytes)
  key: none
```

Строка `cli:` показывает, может ли `plugin call` выполнить операцию: нужны `server = true` и содержимое, которое хост умеет обработать. Операция с содержимым `derived` выводится как `cli: no (not runnable: derived content)`: такие операции сейчас не запускает ни один хост, и `plugin call` отказывает с `subcode=not-declared`. Описания использования ключа и профиля берутся из английских текстов хоста в окне установки и показывают, что ядро навязывает подписи. `label` и `plugin's xpath` написаны самим плагином, им нельзя доверять, поэтому они печатаются в кавычках и с экранированием. Для плагина без `[[operations]]` печатается `declares no operations`.

Поля JSON-отчёта (`code` равен `Completed` или `InvalidInput`, если `--wasm` не подходит; `applied` всегда `NotApplied`; отсутствующие необязательные поля опускаются):

| Поле | Значение |
|---|---|
| `code`, `applied` | см. выше |
| `plugin` | `{id, version}` |
| `operations[]` | по объекту на каждую объявленную операцию, в порядке манифеста |
| `operations[].name`, `.label` | имя операции; английская метка от плагина (недоверенная) |
| `.server`, `.manual` | объявленные флаги |
| `.runnable`, `.derived` | `runnable` равен `false` тогда и только тогда, когда `derived` равен `true` (производное содержимое) |
| `.cli` | `server` и `runnable` одновременно: такую операцию принимает `plugin call` |
| `.imports` | объявленные импорты хоста; больше этого `--allow-import` назвать не может |
| `.network` | `{"kind":"none"}`, `{"kind":"pki"}` или `{"kind":"urls","urls":[…]}` |
| `.params[]` | `{name, kind}`, где `kind`: `document` (`max_bytes`), `text` (`max_chars`), `choice` (`choices`), `flag` или `locale` |
| `.keys[]` | по элементу на каждое использование ключа: `kind` (`raw`, `cms`, `cms_ex`, `xml`, `xml_ex`, `xades`), `content` (`param:<name>` или `derived`), `words` и `profile` (навязанные параметры словами, если они есть) |
| `.xpaths` | XPath профиля от плагина (недоверенные), если есть |
| `module` | с `--wasm`: `{ok}`, а при `false` ещё `error` с причиной |

### `plugin call`: флаги

| Флаг | Значение |
|---|---|
| `--manifest`, `--module` | Манифест (до 64 КиБ) и модуль (до 16 МиБ) единственного плагина, установленного на время этого процесса |
| `--operation OP` | Операция, объявленная с `server = true`, а для плагина без объявлений метка, которую задаёт оператор |
| `--caller LABEL` | Метка оператора, которая записывается как вызывающий. Это никогда не origin и никогда не значение от плагина |
| `--allow-import NAME` | Точные импорты хоста, которые выдаются плагину (флаг повторяется, только известные имена, не больше 80). Для объявленной операции они должны входить в её объявленные импорты; без флага выдаются все объявленные. Для плагина без объявлений отсутствие флага означает, что импортов нет |
| `--output PATH\|-` | Куда записать ответ (без перезаписи; `-` означает stdout, и тогда нельзя выводить `--json` в stdout) |
| `--args-file PATH\|-` | Произвольный JSON-запрос до 256 КиБ. Его принимает плагин без объявлений; объявленная операция тоже его допускает, и тогда за содержимое запроса отвечает оператор |
| `--param NAME=VALUE` | Параметр `text`, `choice` или `locale` объявленной операции (флаг повторяется) |
| `--param-file NAME=PATH\|-` | Параметр `document` из файла (`-` означает stdin; stdin можно использовать один раз на команду) |
| `--param-flag NAME` | Параметр `flag` со значением true; не названный объявленный флаг равен false |
| `--key PATH [--alias A]` или `--key-name N --key-config FILE` | Ключ, который получает handle `--key-handle` (по умолчанию 1); см. [«Именованные источники ключей»](#именованные-источники-ключей) |
| `--secret-file PATH` \| `--secret-interactive` | Пароль ключа, как у `sign` |
| `--authorize` | Обязателен, если указан ключ: подтверждает это использование ключа |
| `--plugin-bytes` | Согласие оператора на использование ключа в объявленной операции (см. ниже); требует ключа |
| `--plugin-pki-endpoint GET=URL` / `POST=URL` | Точные адреса PKI, к которым может обращаться проверка ключа плагина (не больше 16; требует объявленного `network = "pki"`) |
| `--profile` | Не принимается (`oncl: ProfileFromManifest`): профиль подписи объявленной операции берётся из манифеста, его навязывает ядро |

Глобальные флаги (`--json`, `--report`, параметры доверия и `--timeout-seconds`) работают так же, как у других команд. `--args-file` нельзя сочетать с флагами `--param*` (`InvalidCombination`). Ошибками в аргументах считаются: неверная запись `NAME=VALUE`, имя, не подходящее под `^[a-z][a-z0-9_]{0,31}$`, больше 16 параметров одного вида, два источника stdin (`StdinConflict`), а также stdin вместе с `--secret-interactive`. Такие ошибки не показывают значений и ничего не открывают.

### Типизированные параметры

Если у объявленной операции нет `--args-file`, ядро строит запрос из шаблона в манифесте так же, как ручное окно (`Engine::plugin_server_request`). `module` и `method` берутся только из манифеста; каждый плейсхолдер, занимающий всю строку, заменяется значением параметра; документ кодируется стандартным base64; ключи сортируются, запись компактная. Всё проверяется до чтения секрета и открытия ключа. Операции без параметров флаги не нужны.

Правила:

- каждый объявленный параметр задаётся ровно один раз (флаг можно опустить, тогда он false). Необъявленное имя даёт `unknown-param`, повтор `duplicate-param`, пропуск `missing-param`;
- документ передаётся только через `--param-file`, а text, choice и locale только через `--param`, иначе `param-wrong-kind`. Значение choice должно входить в объявленные `choices`, locale может быть `ru`, `kk` или `en`, text не длиннее `max_chars` символов. Если text читает профиль, он должен быть корректным абсолютным XPath. Если text подписывается, в нём не допускаются управляющие символы кроме `\n` и `\t` (поэтому `\r` тоже отклоняется), а также двунаправленные и невидимые символы. Нарушения дают `param-invalid-value` или `param-too-large`;
- файл документа читается только для объявленного документа и не дальше его `max_bytes` и общего предела запроса 256 КиБ. Файл больше предела даёт `InputLimit` с `subcode=param-too-large`, пустой файл `param-invalid-value`;
- весь запрос должен уместиться в 256 КиБ, иначе `request-too-large`.

Текстовый параметр, который читает профиль ключа (`element = "param:xpath"`), участвует и в сверке гранта `--plugin-bytes`: грант покрывает профиль только с этим значением, поэтому плагин, который подписывает другой элемент, получает `options-mismatch`.

Плагин без `[[operations]]` принимает только `--args-file`. Флаги `--param*` или отсутствие `--args-file` отклоняются (`PermissionDenied`, `subcode=not-declared`), потому что сверять параметры не с чем. `--plugin-bytes` на такой плагин не действует, о чём выводится предупреждение.

`plugin call` запускает только операции с `server = true`. Плагины из каталога `plugins/` объявляют 30 операций, все с `manual = true` для ручного окна настольной программы ([руководство](manual-plugins.md)) и ни одной с `server = true`. Поэтому `oncl plugin call` отказывает каждой из них с `subcode=not-declared`, хотя `plugin operations` их перечисляет.

### Согласие и аудит

CLI ничего не спрашивает у пользователя. Для объявленной операции ядро выдаёт билет на каждое использование ключа и сверяет его с объявлением: одно использование, объявленные вид и параметры. CLI не может связать байты, которые подписывает плагин, с документом, поэтому для использования ключа нужен `--plugin-bytes`. Этим флагом согласие даёт оператор, который запускает команду, и он соглашается с тем, что байты для подписи выбирает плагин.

С произвольным `--args-file` грант привязывает только операцию, вид и параметры, а что подписывать, решает плагин. С типизированными параметрами грант привязывает и содержимое: содержимое билета должно совпадать с байтами параметра, к которому привязано использование ключа (текст в UTF-8, документ как байты файла). Иначе использование отклоняется до ключа с `subcode=content-mismatch`. Использование в форме дайджеста нельзя вычислить до открытия ключа, поэтому оно отклоняется с `subcode=content-binding-unavailable`.

Без флага использование ключа отклоняется до применения ключа (`subcode=not-granted`). `--plugin-bytes` покрывает одно использование объявленного вида с точно объявленными параметрами (параметры, которые профиль читает из `--param`, равны переданным значениям). Расхождение даёт `options-mismatch`, второе использование за вызов `key-use-spent`.

Собственного журнала у CLI нет, записью для оператора служит stderr. Перед использованием ключа разрешённое использование объявленной операции пишет одну строку с доверенными данными билета ядра (документ, значения параметров, секрет и nonce в неё не попадают), а после него обычную строку `private_use`:

```text
oncl: plugin_use operation_id=7 plugin=test.cli version=1.0.0 package=2:<sha256 of manifest+module> operation=sign caller=local-operator declared=true grant=cli-plugin-bytes content_sha256=<sha256 of the bytes signed> content_len=14 prehashed=false options_sha256=<sha256 of the forced options> ticket=<sha256 digest of the ticket>
oncl: private_use operation_id=7 applied=Applied succeeded=true
```

`grant=cli-plugin-bytes` обозначает согласие оператора; при интерактивном одобрении на этом месте был бы хеш nonce. `package=2:…` содержит хеш пакета вида 2, посчитанный по двум файлам, которые вы указали. Отклонённое использование ключа вместо этого пишет `oncl: plugin_refused operation_id=… subcode=… plugin=… operation=…`, и ключ не используется.

### Коды выхода, отказы и строка сбоя

| Код выхода | Значение |
|---:|---|
| 0 | Завершено (для `plugin operations`: список выведен, а с `--wasm` модуль подходит) |
| 1 | Любой отказ или сбой, включая ошибки в аргументах и неподходящий `--wasm` |
| 130 | Отменено (Ctrl-C или Ctrl-Break) |

При сбое в stderr печатается `oncl: <code>; subcode=<id>; applied=<NotApplied|Applied|Unknown>` (`subcode=` только если он есть у отказа), а в stdout ничего. Отклонённая команда плагина не печатает JSON-отчёт. JSON-поле `subcode` есть только у элементов `batch run` и в HTTP-ошибках `oncl-server`, а здесь результат передают строка сбоя, код выхода и `applied`. Постоянные подкоды `plugin call`:

| Код | `subcode` | Причина |
|---|---|---|
| `PermissionDenied` | `not-declared` | Операция не объявлена, не имеет `server = true` или производная; импорт сверх объявленного; типизированные параметры (или отсутствие `--args-file`) у плагина без объявлений; плагин вызывает необъявленное имя |
| `PermissionDenied` | `no-key-use` | `--key` для операции, которая не объявляет использования ключа |
| `PermissionDenied` | `network-not-declared` | `--plugin-pki-endpoint` без `network = "pki"` |
| `PermissionDenied` | `not-granted` | Использование ключа без `--plugin-bytes` (или для другого плагина либо операции) |
| `PermissionDenied` | `key-mismatch` | Использование не того ключа, который открыла команда (как на сервере; единственное разрешённое использование при этом не расходуется) |
| `PermissionDenied` | `content-mismatch`, `content-binding-unavailable` | Типизированные параметры: плагин подписывает не те байты, что переданы, или привязанное использование в форме дайджеста |
| `PermissionDenied` | `options-mismatch`, `kind-mismatch`, `key-use-spent`, … | Использование ключа расходится с объявлением (полный список в проектной документации ручных плагинов, §4.8). Ключ не применялся, кроме случая `key-use-spent`: первое использование остаётся `Applied` |
| `InvalidInput` | `unknown-param`, `duplicate-param`, `missing-param`, `param-wrong-kind`, `param-invalid-value`, `invalid-template` | Неверный типизированный параметр (см. выше) |
| `InputLimit` | `param-too-large`, `request-too-large` | Параметр больше объявленного размера или запрос больше 256 КиБ |

### Примеры

Объявленная операция с параметром-документом и ключом (Git Bash). Манифест объявляет `sign` с `server = true`, параметр-документ `file`, импорт `keys_sign_raw` и `network = "pki"`:

```sh
oncl plugin operations --manifest plugin.toml                    # what may I grant?
oncl plugin call --manifest plugin.toml --module plugin.wasm \
  --operation sign --caller ops-laptop --output signature.b64 \
  --param-file file=statement.pdf \
  --key signer.p12 --secret-file secrets/signer.secret --authorize --plugin-bytes \
  --root nca-root.der --pki-endpoint https://pki.example.test \
  --plugin-pki-endpoint GET=https://pki.example.test/ocsp --plugin-pki-endpoint POST=https://pki.example.test/ocsp
```

Объявленная операция без ключа с параметрами text, choice и flag:

```sh
oncl plugin call --manifest plugin.toml --module plugin.wasm --operation note \
  --caller ops-laptop --output - \
  --param text='hello' --param pick=two --param lang=kk --param-flag on
```

Плагин без объявлений: метку и импорты называет оператор, запрос произвольный.

```sh
oncl plugin call --manifest plugin.toml --module plugin.wasm --operation hash \
  --caller ops-laptop --allow-import hash --args-file request.json --output -
```

`plugin call --json` печатает `{operation_id, code: "Completed", applied, response_bytes}` после записи ответа; сам ответ записывается в `--output`.

## Параметры legacy XML (`XmlSignSpec` / `XadesSpec`)

`sign --profile xml|xades-b|xades-t|xades-lt --legacy` включает режим, совместимый с Kalkan и NCALayer. Строгая проверка перед использованием закрытого ключа и защита ключа в нём те же. Каждый параметр соответствует одному полю SDK:

- `--legacy-element`, `--legacy-parent`, `--legacy-namespace PREFIX=URI`, `--legacy-other-prefix-uri`;
- `--legacy-placement document-element|first-child`;
- `--legacy-signature-method|--legacy-digest-method rsa-sha256|gost2004|gost2015-512`;
- `--legacy-signed-info-c14n`, `--legacy-transform enveloped|inclusive|…` (enveloped первым и один раз, не больше одной канонизации);
- `--signature-id`, `--legacy-signing-time-id|--legacy-signing-time|--legacy-signing-time-reference`;
- `--legacy-line-breaks`, `--legacy-base64-line-breaks on|off`;
- `--legacy-output as-is|serialize` с `--legacy-xml-declaration`, `--legacy-standalone-no`, `--legacy-keep-outer-whitespace`;
- для XAdES `--legacy-chain CERT.der`: сертификаты издателей, не больше 16 файлов по 16 КиБ.

Неподдерживаемые сочетания отклоняются с `InvalidCombination` или `TsaRequired` до чтения и записи. К ним относятся legacy CMS, PDF, WSSE и XAdES-LTA, `--add`, `--target-id`, параметры XML для XAdES, уровень со штампом времени без `--tsa-url`, неверные привязки пространств имён и управляющие символы. Ни один параметр не принимает путь к ключу, URI алгоритма или произвольное преобразование.

XAdES T, LT и LTA (и базовый, и legacy) требуют `--tsa-url` и `--tsa-policy OID`, иначе `TsaPolicyRequired` до чтения и записи. Токен с политикой, отличной от запрошенной, отклоняется уже после использования ключа, с `applied=Applied`. Базовому XAdES нужен ещё `--signature-id`.

## Именованные источники ключей

`--key-name NAME --key-config keys.json` (в `sign`, `jws`/`jwt`, `batch` и `plugin`) находит ключ NAME в JSON-файле оператора. Файл не содержит секретов; ограничения: до 64 КиБ, до 64 записей, неизвестные поля запрещены, относительные пути отсчитываются от файла. Файл определяет, какой контейнер или считыватель открывается по имени, поэтому он читается по тем же правилам, что файл секрета: из каталога с доступом только для владельца, с проверками владельца, ACL и ссылок, только обычный файл. Его размер входит в общий бюджет конфигурации, а чтение идёт частями с проверками между ними.

```json
{"keys":[{"source":"file","name":"main","path":"signer.p12","alias":null},
         {"source":"token","name":"card","reader":"<PC/SC reader>","kind":"kaztoken","alias":"<key alias>"}]}
```

Имя служит идентификатором ключа при авторизации (`named:NAME`). Путь к контейнеру и считыватель в командной строке не появляются, а `--key-name` нельзя сочетать с `--key` и `--token-reader`. `inspect --profile named-key --key-name … --key-config … --secret-file …` показывает открытые метаданные именованного источника (файл, JKS, PKCS#12 или токен) через провайдер только для чтения; закрытый ключ при этом не используется.

## Токены и программный эмулятор

`--token-reader` и именованные записи токенов проверяются в тестах на программных токенах из репозитория. Для этого программу собирают с `--features token-emulator` и задают `ONCL_TOKEN_EMULATOR=<oncl-token emulator config.toml>`. Переменная существует только в сборке с этой feature, в релизных сборках её нет. Если файл не читается, команда отказывает и не переходит на другой источник.

## Отмена, сроки и итоговые отчёты

Пакет, остановленный Ctrl-C, Ctrl-Break или по `--timeout-seconds`, всё равно выдаёт итоговый отчёт: для каждого элемента статус `Completed|Failed|NotRun`, `applied`, `published` и хеш `digest`. Память для этого отчёта резервируется до первого использования закрытого ключа. Код выхода 130 при отмене и 4 по истечении срока. Файл `--report` после остановки создаётся сразу (без перезаписи), без промежуточного временного файла. Прерванный элемент получает статус `Failed` с кодом `Cancelled` или `DeadlineExceeded`. Приоритет кодов выхода пакета: 130 > 4 > 2 > 3 > 0. Ctrl-C при вводе секрета даёт `Cancelled` (130).

Если частичный пакет остановлен не отменой и не по сроку, а его отчёт доставить нельзя (stdout закрыт, `--report` недоступен для записи), код выхода 1. Коды 130 и 4 сохраняются при сбое отчёта только после отмены или истечения срока.

## Известные ограничения

* **Терминалы.** Отключение эха, восстановление режима терминала и Ctrl-C проверены только в Windows ConPTY. Путь Unix `termios` и сигналы Linux и macOS не проверялись.
* **Токены.** PC/SC проверялся только на программном эмуляторе, с физическим токеном не работали. Отказ при секрете-символической ссылке не проверялся.
* **Уровень XAdES.** Уровень XAdES-LT или LTA (`ades_level` и профили проверки `xades-lt`/`xades-lta`) засчитывается только при наличии штампа подписи, значений отзыва и `CertificateValues` со всеми сертификатами пути подписанта выше листового, включая якорь доверия (ETSI EN 319 132-1 §5.4.2). `sign --profile xades-lt` всё это добавляет. Документ без этих данных получает уровень `T`, а профиль `xades-lt` отклоняет его с `InvalidInput`. Для CAdES и PAdES уровень LT требует только штампа и статуса отзыва, это требование мягче. Проверяется только путь подписанта; путь службы штампов времени и полнота её `TimeStampValidationData` на уровень не влияют.
* **`--add` поверх существующей подписи.** `sign --profile xml --add` отклоняется до использования ключа (`InvalidInput; applied=NotApplied`), если ссылка существующей подписи покрывает место новой: весь документ, объемлющий элемент или член Manifest, если только эта ссылка не исключает подписи.
* **XAdES с полным CRL НУЦ.** `verify --profile xades-b|t|lt|lta` принимает встроенный CRL до 32 МиБ на один CRL и до 48 МиБ всего. XAdES-LT от NCANode или Kalkan размером около 27 МБ (полный CRL НУЦ в base64) получает обычный отчёт, а не `MetadataLimit`: подпись `Passed`, цепочка и отзыв оцениваются по `--root` и `--as-of`, как для XAdES-T. CRL другого издателя статуса отзыва не даёт; CRL, в котором есть подписант, отзывает его. При подписи и продлении XAdES-LT/LTA полный CRL НУЦ (около 20 МБ) не помещается: CRL в подписи не больше примерно 190 КиБ (256 КиБ × 3/4, оценка по коду, тестом не измерялась), больший даёт `MetadataLimit`. Подробности в руководстве по SDK (`docs/dev/sdk.md`).
* **Долгосрочный статус (`lt`/`lta`).** Статус отзыва, встроенный в подпись, оценивается на момент, который доказывает штамп подписи, а не по вашим часам. Если `--as-of` или часы хоста позже, документ CAdES, PAdES или XAdES уровня `lt`/`lta` всё равно оценивается по данным, свежим в доказанный момент, при условии что сертификаты подписанта и цепочки тогда были действительны. Для тестовых файлов NCANode, чьи штампы здесь не проверяются, это не гарантируется. Статус с `nextUpdate` свеж, пока доказанное время раньше `nextUpdate`. Статус без `nextUpdate` (OCSP НУЦ) должен быть выпущен не раньше чем за 300 с до доказанного момента. Отклоняется статус, выпущенный после момента проверки (для OCSP больше чем через 300 с), просроченный по `nextUpdate` на доказанный момент, недоверенный, отзыв не позже доказанного момента или статус другого сертификата. Подпись без проверенного штампа (`b`) и статус, который проверяющий получает сам, оцениваются по текущему времени. Правило и ссылки на стандарты есть в `docs/dev/sdk.md`.
* **Доказательства для LT/LTA.** Подпись CAdES-LT/LTA и PAdES-LT/LTA и `extend` без ключа работают. Материалы передаёт оператор: `--evidence-certificate`, `--evidence-ocsp`, `--evidence-crl` (открытые файлы DER, не больше 64 каждого вида, до 256 КиБ каждый и до 8 МиБ всего). Их размер входит в общий бюджет конфигурации и проверяется до чтения документа или ключа; флаги допустимы только для подписи CAdES/PAdES и `extend`. Эти пределы касаются подписи, а 32 МиБ на CRL относятся к проверке. Нужны `--tsa-url` и `--tsa-policy`. Ответ OCSP без `nextUpdate` должен быть выпущен не раньше чем за 300 с до штампа, иначе в нём должен быть `nextUpdate` позже штампа; ответ не может быть выпущен позже `--as-of`. Подпись LT/LTA без сертификатов и OCSP или CRL отклоняется с `EvidenceMaterialRequired` до чтения и записи. Если SDK решит, что материалов недостаточно, это выяснится уже после использования ключа (`applied=Applied`). Подписи PAdES-LT/LTA и PDF после `extend` (T→LT→LTA) проверены также pyHanko: подпись целая, действительная и доверенная по данным отзыва только из DSS при обязательной проверке отзыва и выключенной загрузке; содержимое DSS и DocTimeStamp корректны. Изменённый байт даёт код выхода 2 у CLI, и pyHanko тоже отклоняет такую подпись.
* **JKS.** Подпись работает с той же строгой проверкой, что и PKCS#12 (`--alias` выбирает запись). Подпись ГОСТ проверяется только самим SDK, независимой реализацией ГОСТ не сверялась. Режим legacy XML отклоняет подписанта ГОСТ-2015 (`InvalidInput`, до использования ключа); базовый XML с ГОСТ работает.
* **Файловая система.** Для публикации результата нужен том с поддержкой жёстких ссылок, и файл назначения должен лежать на том же томе. На FAT, exFAT и SMB публикация завершается сбоем уже после использования ключа. Память WASM плагина ограничена 1 МиБ. `--pki-pin` задаёт привязку DNS-имени к адресу, это не PIN-код.
* **Папка результата в Linux и macOS.** Результат пишется через временный файл в той же папке, а временный файл не создаётся в папке, куда могут писать группа или остальные пользователи, если у папки нет sticky-бита, как у `/tmp`. В Ubuntu и Fedora новые папки получают режим `0775` (umask `0002`), и подпись в такую папку завершается ошибкой `Io` с `applied=NotApplied` до использования ключа (проверено запуском `oncl sign` на Linux: с `0775` ошибка `Io`, с `0755` и `0700` подпись проходит). Решение: `chmod g-w <папка>` или другая папка. Окно «Инструменты» по коду подчиняется тому же правилу, но запуском это не проверялось.
* `inspect --profile container` требует `--alias`.
* **Шифрование.** Команд шифрования и расшифрования в CLI нет. Библиотека `oncl-pki` умеет CMS EnvelopedData и AuthEnvelopedData только для получателей RSA. Профилей ГОСТ нет: их не с чем сверить, а придумывать профиль по российским OID нельзя.

## Поля отчёта `--json`

`--json` печатает один JSON-объект. Общие ключи: `operation_id` (число), `code` (`Completed` при успехе) и `applied` (`NotApplied`, `Applied` или `Unknown`: применялся ли закрытый ключ). Значения, помеченные как *текст*, выводятся через представление `Debug` перечисления или структуры SDK. Их можно читать, но они меняются вместе с SDK, поэтому скрипты лучше строить на `code`, `applied`, `verdict` и коде выхода.

| Команда | Поля |
|---|---|
| `hash` | `operation_id`, `code`, `applied`, `digest` (шестнадцатеричная строка в нижнем регистре), `bytes_in` |
| `sign`, `extend` (выход записан) | `operation_id`, `code`, `applied` (*текст*), `profile` (*текст*), `provenance` (*текст*), `bytes_in`, `bytes_out`, `signer_count`; `xml` (*текст*), только если операция выдала отчёт XML |
| `extract` | `operation_id`, `code`, `applied` (`NotApplied`), `bytes_out`, `verified` (всегда `false`) |
| `verify` | `operation_id`, `code`, `applied` (всегда `NotApplied`), `verdict` (`Valid`/`Invalid`/`Indeterminate`), `policy` (*текст*), `checked_at` (секунды Unix), `ades_level` (*текст* или `null`), `signers`; `xml` / `pdf` (*текст*), если документ XML / PDF |
| `signers[]` | `signature`, `chain`, `validity`, `revocation`, `timestamp`, `key_usage`, `time_basis` (все *текст*), `claimed_signing_time` (секунды Unix или `null`), `ades_level` (*текст* или `null`), `reasons` (*текст*) |
| `inspect` | `operation_id`, `code`, `applied` (`NotApplied`), `kind` (*текст*), `container_integrity` (*текст* или `null`), `entries`; `cms` (*текст*) для CMS |
| `entries[]` | `alias`, `certificate_sha256`, `subject_cn`, `serial_hex`, `signature_algorithm_oid`, `public_key_algorithm_oid`, `not_before`, `not_after` (секунды Unix); любое может быть `null` |
| `batch run` | `operation_id`, `code` (`Completed`/`Partial`/`Cancelled`/`DeadlineExceeded`), `attempted`, `completed`, `total`, `stop` (текст или `null`), `items[]` |
| `items[]` | `id`, `status` (`Completed`/`Failed`/`NotRun`), `code`, `subcode` (удалённые элементы с ошибкой, у которых есть точная причина), `applied`, `verdict` (элементы verify), `published` (элементы с выходом), `digest` `{algorithm, hex}` (элементы hash) |

Отсутствующие необязательные поля опускаются, а не выводятся как `null`. `timestamp`, `jws`, `jwt` и `plugin call` печатают свои, более короткие отчёты: `operation_id`, `code`, `applied` и, где уместно, счётчики байт, `profile`, `verdict`, `policy` или `facts`. Отчёт `plugin operations` описан в разделе [«Плагины»](#плагины-oncl-plugin). Структуры отчётов определены в `crates/oncl-cli/src/reports.rs`, `local.rs`, `public.rs` и `batch.rs`.

## Удалённый режим (`--endpoint`)

```text
oncl --endpoint https://signing.internal:13579 --token-file client.token --ca-file ca.pem sign --profile cms --key-name corporate-signing --authorize --input doc.bin --output doc.p7s
```

Эта команда выполняет операцию на сервере, описанном в [server.md](server.md) и [http-api.md](http-api.md). Клиентом служит `oncl_api::client::ApiClient` (feature `client` крейта `oncl-api`; только `ureq` и `rustls`, без Tokio, axum и hyper).

### Файлы

Все локальные пути читает и пишет клиент. Документы отправляются потоком из файлов или stdin как части multipart-запроса: с `Content-Length`, если размер известен, и chunked для stdin. Результаты сначала пишутся во временный файл в приватном каталоге рядом с местом назначения и публикуются без перезаписи, как при локальном запуске. Сервер никогда не открывает пути клиента: поля пути в запросе нет, а путь в любом строковом поле отклоняется (`remote::server_cannot_open_client_path`).

Результат публикуется только после того, как получены завершающая запись `final`, закрывающий разделитель multipart и конец HTTP-сообщения. Если ответ оборвался раньше (до артефакта или внутри него, до записи `final` или внутри неё, при штатном закрытии без `final`, без закрывающего разделителя или без последнего чанка), ничего не публикуется и временные файлы не остаются. Клиент печатает `oncl: ResponseLost; applied=Unknown` (для операций без ключа `NotApplied`) и завершается с кодом 1. Автоматических повторов, ключа идемпотентности и отката нет, и выполнение ровно один раз не гарантируется: сервер мог применить ключ, это видно в его журнале аудита. Ранее записанные файлы по другим путям, в том числе прежние выходы пакета, не затрагиваются.

Каждый артефакт, указанный в завершающей записи, должен прийти один раз и с той длиной, которую называет запись. Это касается извлечения (`bytes_written`), токенов штампа времени (`bytes_out` равен длине токена) и создания JWS/JWT (`bytes_out`; сервер проверяет его, когда пишет запись артефакта). Корректно оформленная часть неверной длины ничего не публикует: `ProtocolViolation: artifact length differs from the final record`, код выхода 1, `applied` равен `NotApplied` для операций без ключа и `Unknown`, если ключ мог применяться. Для подписи и продления CMS, CAdES, XML и PDF длины не сравниваются: сервер берёт длину артефакта из подготовленного выхода, а `bytes_out` в записи содержит счётчик SDK (например, 8250 для CMS размером 1561 байт). Там проверяется только, что пришёл нужный артефакт и что он один, а отчёт показывает фактическую полученную длину.

### `applied`

Сервер начинает операцию с закрытым ключом только после того, как принял всё тело запроса. Сбой во время отправки тела даёт `NotApplied`. Потерянный ответ после последнего байта тела даёт `Unknown`, если запрос мог использовать закрытый ключ. Типизированный отказ или завершающая запись передают значение, которое сообщил сервер.

### Токен и транспорт

Токен задаётся через `--token-file PATH` (каталог с доступом только для владельца, те же правила и предел 4096 байт, что у `--secret-file`) или `--token-stdin` (тогда stdin не может быть документом). В аргументах и переменных окружения токен не передаётся. Он не попадает в диагностику, отчёты и ошибки (тесты ищут его в stdout, stderr и во всех файлах клиента). Сообщения об ошибках не содержат тела ответа, только код, статус HTTP и типизированный код сервера.

`https://` проверяется по встроенным корням webpki. `--ca-file` (PEM или DER, флаг повторяется) заменяет их для частного сервера: доверие получают только этот CA или собственный сертификат сервера. Отключить проверку нельзя. `http://` принимается только для `localhost`, `127.0.0.0/8` и `::1`. Для любого другого хоста по простому http нужен `--allow-plain-http`; токен и документы тогда идут без шифрования, так что это годится только для защищённой внутренней сети за доверенным прокси. При каждом запуске с этим флагом и хостом `http://` не из loopback в stderr печатается `oncl: warning: --allow-plain-http sends the API token and every document over an unencrypted, unauthenticated connection …` (без токена). Без флага такой адрес отклоняется до соединения (`PlainHttpRefused`).

Перенаправления не выполняются: ответ 3xx даёт `UnexpectedStatus (HTTP 307)`, и токен bearer никуда не пересылается. `HTTP_PROXY` и `ALL_PROXY` игнорируются; тесты проверяют, что ни цель перенаправления, ни прокси из окружения соединения не получают.

### Ключи

`--key-name NAME` ссылается на ключ оператора на сервере, секрет на клиенте не нужен. Ключ покидает клиентский процесс только с `--key PATH --secret-file … --inline-key` (и `inspect --profile container … --inline-key`): контейнер и пароль передаются как части `secret` и на клиенте тоже хранятся только в памяти. Серверу для этого нужен `inline_pkcs12`, включённый глобально и для токена. Считыватели токенов (`--token-reader`) и `--key-config` относятся к локальной машине и в удалённом режиме отклоняются.

### Что настраивает сервер

Корни доверия, политика проверки, сеть PKI, часы, TSA, issuer и audience для JWT и установка плагинов задаются в конфигурации сервера. Поэтому следующие флаги отклоняются с `RemoteUnsupported` до чтения и записи, а не игнорируются: `--root`, `--intermediate`, `--pki-endpoint`, `--pki-pin`, `--tsa-url`, `--tsa-policy`, `--offline`, `--as-of`, `--configuration-bytes`, `timestamp acquire --tsa/--algorithm`, `timestamp verify --policy-oid`, `jwt verify --issuer/--audience/--leeway-seconds`, `inspect --alias`, `--token-reader`, `--key-config` и все команды `plugin`. `sign` по-прежнему требует `--authorize`.

С тем же `RemoteUnsupported` отклоняются параметры, которых нет в HTTP-контракте: параметры WS-Security кроме `--soap-version` и `--wsse-body-id` (`--wsse-role`, `--wsse-required-header`, `--wsse-timestamp-*`, `--wsse-token-reference`, `--wsse-token-id`) и параметры legacy XML кроме элемента, родителя, методов подписи и дайджеста (пространства имён, размещение, c14n, преобразования, время подписания, переводы строк, объявление XML, формат вывода и цепочка).

### Доступные операции

`hash`, `verify`, `extract`, `sign` (cms, cades-*, xml, wsse с `--soap-version`/`--wsse-body-id`, xades-b/t, pdf, pades-*, а также `--legacy` xml/xades-b/xades-t с элементом, родителем и методами подписи и дайджеста), `extend` (cms/pdf t|lt|lta, xml lt|lta), `inspect`, `timestamp`, `jws`, `jwt` и `batch run`. Подписи `raw`/`digest-*` и подписи XAdES LT/LTA в контракте нет: подпишите `xades-t`, затем выполните `extend` без ключа. Материалы из `--evidence-certificate/-ocsp/-crl` отправляются как открытые части-документы. Шифрования и расшифрования нет ни в CLI, ни в HTTP-контракте.

Типизированный отказ службы с `subcode` печатается как `oncl: <code>; subcode=<id>; applied=<state>`. Клиент сверяет id с опубликованным шаблоном и неверный не печатает.

### Отчёты и коды выхода

Коды выхода те же, что локально: 0 завершено или `Valid`, 2 `Invalid`, 3 `Indeterminate`, 4 неполный пакет, 1 сбой, 130 отмена. Вердикт, политика и все проверки по каждому подписанту совпадают с локальным запуском. Отличия: в HTTP-контракте нет подробностей структуры PDF и XML и уровня AdES верхнего уровня (поле опускается); `time_basis` передаётся вариантом, а момент лежит в `time_basis_unix`; `bytes_in` считает байты документа, отправленные клиентом, `bytes_out` размер полученного артефакта; данные `timestamp` передаются объектом. `jwt decode` выводит полезную нагрузку, декодированную сервером (недопустимый UTF-8 сервер заменяет).

### Пакеты

Манифест читает клиент; источник, который не открывается, ломает только свой элемент. Выходы сначала пишутся во временное хранилище: в общий каталог назначения, если он один, иначе в `--temporary-directory` или текущий каталог, который должен быть на том же томе, что и места назначения. После завершающей записи они ставятся на место жёсткими ссылками, по строке на элемент (`published` на каждый выход). Сервер выполняет `/v1/batch`, токену нужно право `batch`.

Если выходы лежат в разных каталогах, до любого запроса в каждом из них создаётся и удаляется пробная жёсткая ссылка. Если не получилось, ответ `DestinationNotLinkable` с `NotApplied`, и ключ не используется для результата, который нельзя опубликовать. Проба проверяет саму возможность создать ссылку, поэтому каталог на томе без жёстких ссылок тоже отклоняется.

### Обрывы, отмена и что не проверялось

Если сервер ответил, пока клиент ещё отправляет тело (например, отказал после метаданных при большом теле), он держит соединение открытым и ещё до одной секунды и около 8 МиБ читает и отбрасывает данные. Клиент, уложившийся в эти пределы, получает типизированный ответ. Если клиент продолжает отправку дольше, соединение сбрасывается, ответ может потеряться, и результат будет сбоем транспорта с `applied=NotApplied`: тело дошло не полностью, а служба принимает всё тело multipart и повторно проверяет полномочия, прежде чем рабочий поток сможет использовать ключ (`crates/oncl-server/src/service/operations.rs` и `operations/intake.rs`).

Отмена и срок (`--timeout-seconds`) проверяются каждые 50 мс ожидания, поэтому Ctrl-C прерывает вызов к серверу, который совсем не отвечает, в течение нескольких секунд с кодом 130. `applied` при этом `Unknown`, если ключ мог использоваться и тело было отправлено полностью, иначе `NotApplied`. Брошенный обмен заканчивается вместе с процессом, повторов нет.

Документы по 1 ГиБ и потребление памяти, подпись PDF и XML и продление PAdES до LT/LTA через этот клиент проверены приёмочным прогоном `cargo xtask platform-proof`, где клиентом служит `oncl --endpoint`. Не проверялись: Linux и macOS, Windows 7, TLS с закреплённым ключом (есть только файл CA или листового сертификата), `jws add`, `cms add` и `wsse` в удалённом режиме (поля контракта сопоставлены, но удалённых тестов CLI нет) и прямая удалённая подпись PAdES LT/LTA (покрыта тестами `oncl-api` на уровне HTTP).
