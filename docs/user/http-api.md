# Типизированный контракт HTTP-запросов

Кроме сырого `POST /v1/hash` автономная служба предоставляет `POST /v1/operations`. Оба маршрута
требуют индивидуальный bearer-токен и точно настроенный авторитет `Host`, описанные в
[server.md](server.md). Запрос не может задать псевдонимы совместимости с NCANode, пути
файловой системы, корни доверия, права, лимиты, подмену метода, административные действия,
повторы или сохраняемые задания.

## JSON-small

Используйте `Content-Type: application/json`. Тело целиком ограничено 65 536 байтами, независимо
от лимита документа. Документы передаются текстом UTF-8, base64 для больших файлов не
предусмотрен. Ошибкой считаются повторяющиеся имена документов, неизвестные поля, неиспользуемые
части, повторяющиеся идентификаторы элементов или частей и часть, привязанная не к тому элементу.
Идентификаторы элементов и частей состоят из 1–128 ASCII-букв, цифр, `_` и `-`.

```json
{
  "metadata": {
    "items": [
      {"id":"invoice","operation":{"kind":"hash","algorithm":"sha256","input":"source"}}
    ],
    "parts": [
      {"name":"source","item_id":"invoice","role":"document"}
    ]
  },
  "documents": {"source":"abc"}
}
```

Алгоритм операции `hash` задаётся явно, одним из `sha1`, `sha256`, `sha512`, `gost34311`,
`streebog256`, `streebog512`; по имени файла или содержимому он не определяется. Для `hash` нужно
действие `hash`, выбрать ключ такой запрос не может. Право хешировать SHA-1 не даёт права
подписывать.

Для `verify` токену нужно отдельное действие `verify`, и оно проверяется до приёма документа.
Метаданные: `{"kind":"verify","profile":"cms","input":"signature"}`; необязательное поле
`detached` называет вторую объявленную открытую часть-документ. Профили: `cms`, `cades_b`,
`cades_t`, `cades_lt`, `cades_lta`, `pdf`, `pades_b`, `pades_t`, `pades_lt`, `pades_lta`, `xml`,
`xml_kalkan`, `xades_b`, `xades_t`, `xades_lt`, `xades_lta` и `wsse`. Профиль выбирает код
проверки, имя файла на выбор не влияет. Корни доверия, режим проверки и доступ к сети в запросе
не передаются. Набор доверия службы по умолчанию пуст, а сеть PKI запрещена, поэтому
криптографически верная подпись без настроенного доверия доверенной не становится.

Криптографически неверная подпись даёт завершённый результат HTTP 200 с `kind:"verification"` и
`verdict:"Invalid"`. Результат содержит проверки по каждому подписанту (подпись, цепочка, срок
действия, отзыв, штамп времени, использование ключа), политику хоста, время проверки и его
источник. Диагностические причины поясняют результат, но типизированные поля проверок не
заменяют. Подпись может быть криптографически цела, но нарушать правило базового профиля
CAdES/PAdES: например, Kalkan пишет в CMS для PAdES атрибут signing-time, который запрещает EN
319 142-1. Тогда все проверки будут `Passed` или `Unavailable`, но появится причина `Profile(...)`
и `verdict:"Invalid"`. Поэтому смотрите на вердикт и причины, а не только на шесть проверок.

## Multipart с метаданными в первой части

Используйте `Content-Type: multipart/form-data; boundary=<boundary>`. Граница состоит из 1–70
ASCII-символов допустимого для multipart алфавита. Первое поле должно иметь
`Content-Disposition: form-data; name="metadata"` без имени файла и содержать только объект
`metadata` из примера JSON, не больше 65 536 байт. Сервер разбирает его до того, как определит
действие и выдаст права, так что отдельный заголовок с правами или вторая копия метаданных не
нужны.

После первого поля отправьте каждую объявленную часть один раз под её именем:

```text
--example-boundary\r\n
Content-Disposition: form-data; name="metadata"\r\n
\r\n
{"items":[{"id":"invoice","operation":{"kind":"hash","algorithm":"sha256","input":"source"}}],"parts":[{"name":"source","item_id":"invoice","role":"document"}]}\r\n
--example-boundary\r\n
Content-Disposition: form-data; name="source"; filename="invoice.bin"\r\n
Content-Type: application/octet-stream\r\n
\r\n
<actual binary document bytes>\r\n
--example-boundary--\r\n
```

Здесь `\r\n` обозначает байты CRLF, а не четыре печатных символа. Неизвестные, повторяющиеся,
отсутствующие и пришедшие не в своё время поля отклоняются. Операция hash принимает только роль
`document`; часть с ролью `secret` нельзя выдать за документ, даже если у неё есть имя файла или
тип содержимого документа. Имя файла в Content-Disposition служит только для отображения и как
имя в файловой системе не используется. Открытые документы сохраняются как неизменяемые снимки
SDK со случайными именами, доступные только владельцу, в заданном оператором
`scratch_directory`; файлы по именам из запроса не создаются. Если каталог уже существует, он
должен быть закрытым. Временные данные удаляются, когда освобождается их последний владелец;
архивом или постоянной очередью этот каталог не служит.

Content-Length необязателен. Сервер считает фактически полученные байты, в том числе при
chunked-передаче неизвестной длины и при попытках переполнения. Чанки передачи могут разрезать
любой разделитель и CRLF; чанк в 64 КиБ допустим и из-за размера не отклоняется. Байты
документов и обрамления учитываются в отдельных квотах. Закрывающий разделитель, прочитанный
заранее, и оставшиеся байты тела тоже учитываются, поэтому слишком большой эпилог не может
занять неиспользованный запас документа или затянуть время перед отказом.

Обрамление учитывается по мере того, как разборщик потребляет байты, включая частично
полученные заголовки и преамбулы, до дальнейшего ожидания тела и до выделения памяти под
заголовки. Полный или частичный заголовок части сверх бюджета даёт `FramingLimit`/413, даже если
тело документа не отправлялось. Превышение отдельного предела на заголовки даёт
`MetadataLimit`/413, искажённое или усечённое обрамление `InvalidRequest`/400. Первая
зафиксированная причина сбоя (транспорт, ресурс, отмена) общая для разборщика, читателя полей,
рабочего потока и выбора итогового статуса, даже если передача рабочему потоку задержалась за
пределы срока. Она не выводится из текста ошибки и не заменяется более поздней отменой.

### Лимит документа и подписанные результаты

`input_bytes` ограничивает документ: документ на один байт больше даёт `InputLimit`/413. Часть
`input` элемента `verify`, `extend`, `extract` или `sign` может уже быть подписанным результатом,
то есть документом вместе с байтами подписи, ревизии или конверта, которые добавила эта служба
или другая программа. Поэтому она может превышать `input_bytes` на эти байты, но не больше чем на
`container_bytes` (по умолчанию 1 ГиБ, как в SDK) или на границу, которую задаёт сам формат
(например, около 188 МиБ добавленных ревизий PDF). Сервер записывает такую часть во временный
файл размером до `input_bytes + container_bytes`, не трогая запас документа, а затем движок
читает её так же, как файл, переданный через SDK или CLI: находит байты подписи, списывает
`input_bytes` за документ, а остальное за счёт запаса контейнера. Благодаря этому подписанный
результат документа размером ровно `input_bytes` снова принимается той же службой, а документ на
один байт больше `input_bytes` даёт `InputLimit`, подписан он или нет. Байты, которые движок не
может разобрать, в этой роли дают `InvalidRequest`/400.

Верхняя граница тела запроса с таким входом равна
`input_bytes + container_bytes + framing_bytes + 64 KiB` (64 КиБ отведены на метаданные), для
любого другого multipart-запроса `input_bytes + framing_bytes + 64 KiB`, а `/v1/hash` принимает
сырое тело не больше `input_bytes`. Все остальные части-документы (отсоединённые данные,
проверяемый контейнер, вход JOSE) должны целиком укладываться в `input_bytes`.
Части-свидетельства (`certificate`, `ocsp`, `crl`) документами не считаются: каждая ограничена 1
МиБ и лимитами свидетельств движка и не расходует запас документа, так же как файлы
свидетельств в CLI. Полный CRL НУЦ (около 20 МБ) через HTTP передать нельзя: часть-свидетельство
не больше 1 МиБ, а CRL внутри подписи XAdES-LT/LTA не больше примерно 190 КиБ (число получено из
кода).

Слишком большой подписанный вход движок обнаруживает уже после того, как выбран статус ответа,
поэтому в потоковом ответе об этом сообщает завершающая запись с ошибкой `InputLimit` и
`NotApplied`, а поток не обрывается. CAdES подчиняется тому же правилу для verify, extend и
`add`. Присоединённая подпись считается документом с подписью. Отсоединённая подпись (часть
`input`) считается только контейнером, а её данные передаются отдельным документом не больше
`input_bytes`, поэтому подпись и данные размером ровно `input_bytes` принимаются вместе.

### Временный каталог и размеры

Уменьшая `input_bytes`, уменьшайте и `container_bytes`. При значениях по умолчанию одна часть
`input` элемента verify, extend, extract или sign занимает во временном каталоге до
`input_bytes + container_bytes` (2 ГиБ), прежде чем движок отклонит неподдерживаемый документ, а
затем движок копирует ещё около `input_bytes`. Для verify, extend и add CAdES движок при разборе
копирует данные ещё раз, до `input_bytes + container_bytes` плюс один фрагмент 256 КиБ, прежде
чем отклонить враждебный вход; вместе с файлом загрузки это до примерно 4 ГиБ при значениях по
умолчанию. Так что враждебная загрузка может записать несколько ГиБ, прежде чем её отклонят. Это
ограничено `temp_per_operation`, `total_temp`, `max_uploads` (число одновременно принимаемых тел)
и `max_in_flight`.

Измеренные пики: подпись документа на пределе занимает во временном каталоге около
3x `input_bytes`, проверка подписанного результата около 2x. Практическое правило:
`temp_per_operation >= 3 * (input_bytes + container_bytes)`. Конфигурация это правило не
проверяет. Проверяется только, что явный `max_uploads` позволяет каждой загрузке одновременно
записать свой наибольший вход:
`max_uploads <= total_temp / (input_bytes + container_bytes)`. Если `max_uploads` не задан, он
равен `min(8, max(1, total_temp / (input_bytes + container_bytes)))`.

Запрос, который объявляет длину больше верхней границы, сразу отклоняется с `InputLimit`.
Загрузка без объявленной длины отклоняется с `FramingLimit`, когда переходит границу. Элемент
sign или extend принимает не больше 64 ссылок на свидетельства, при большем числе запрос
отклоняется с `InvalidRequest` до чтения частей. `container_bytes` должен быть положительным, а
`input_bytes + container_bytes + framing_bytes + 64 KiB` должно помещаться в 64 бита.

### Разбор multipart

Для разбора multipart используется закреплённая версия `multer` 3.1.0. При разборе заголовков и
преамбулы части неизвестной роли разборщик получает не больше 8 192 новых байт сверх одного
предыдущего блока данных в 4 096 байт и окончания границы. Опрос кооперативный, чтобы постоянно
готовая загрузка не накапливалась в разборщике. Число заголовков дополнительно ограничено
разборщиком, а метаданные задают точные допустимые имена и общее число частей. Буфер чтения Hyper
ограничен 32 768 байтами. Накладные расходы HTTP и TLS на соединение учитываются отдельно от
рабочих буферов SDK. Память на запрос (разборщик, разобранные метаданные, удерживаемые входные
данные) резервируется до выделения. Это описание не гарантирует, что обработка XML и PDF размером
1 ГиБ уложится в ресурсы.

## Результат и ошибки

Завершённый ответ на `hash` имеет `Content-Type: application/json`:

```json
{"type":"final","operation_id":1,"status":"completed","results":[{"item_id":"invoice","applied":"NotApplied","result":{"kind":"hash","algorithm":"sha256","digest":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad","bytes_in":3}}]}
```

Идентификатор операции меняется, идентификаторы элементов повторяют метаданные запроса.
`bytes_in` элемента считает фактические байты документа, в том числе из сохранённых снимков;
повторное чтение снимка входную квоту второй раз не расходует. Успехом считается только полный
завершённый результат.

## Потоковые ответы с артефактами

`extract` извлекает содержимое из структуры CMS средствами SDK; подпись при этом не проверяется.
Метаданные запроса: `{"kind":"extract","input":"container"}` с указанием открытого документа.
Нужны отдельное действие токена `extract` и настроенный закрытый `scratch_directory`.

На запросы с извлечением сервер отвечает `multipart/mixed` со случайной границей. Части JSON
`progress` содержат идентификатор операции и общие счётчики байт; успеха они не подтверждают.
Двоичные части `artifact` несут `Content-ID`, созданный сервером, и точный `Content-Length`. Часть
JSON `final` связывает идентификатор `artifact` в результате извлечения с этими байтами и
единственная подтверждает завершённый результат. Адресов обратного вызова, сохраняемых заданий и
отдельных путей для скачивания артефактов нет.

Сервер полностью принимает и сохраняет вход до начала ответа, поэтому клиенту, который сначала
отправляет запрос, а потом читает ответ, не нужно читать и писать одновременно. Обработка SDK
выполняется в рабочем потоке. Он формирует ограниченный по размеру выход и освобождает своё
место, так что медленное чтение ответа клиентом не держит рабочий поток занятым. При доставке
ответ читается фрагментами по 256 КиБ через тот же ограниченный исполнитель. Задача чтения
принимает только готовый артефакт и его владельца, произвольную область от вызывающего она не
принимает. Исходный контекст, файлы выхода и резервы остаются привязанными к байтам ответа,
пока не освобождена последняя их копия.

Метаданные progress и final и обрамление MIME учитываются как выход; байты артефактов, созданные
SDK, второй раз не списываются. Перед ростом файла резервируется место во временном хранилище,
запись идёт ограниченными порциями, успешные частичные записи фиксируются, а перед тем как
артефакт станет доступен для чтения, проверяются flush, sync и размер. Сервер удаляет только
созданные им самим файлы; неполный или неудачный выход никогда не отдаётся.

Клиент должен сохранять байты артефакта во временное место и использовать их только после того,
как получены завершающая запись, закрывающий разделитель MIME и полное окончание тела HTTP. Сбой
выполнения, чтения или истечение срока после отправки заголовков могут оборвать соединение.
Корректное начало ответа или часть progress частичным успехом не считаются. Если завершающей
записи нет, результат не публикуется, но это не значит, что уже совершённое действие с закрытым
ключом отменено.

До завершённого ответа ошибки выполнения возвращаются в стабильном конверте с `code` и `applied`,
как у сырого маршрута: 403 PermissionDenied, 400 InvalidRequest, 413 при превышении лимитов байт
и ресурсов, 503 CapacityExceeded или AuditUnavailable, 504 DeadlineExceeded (в том числе для
загрузки, которая остановилась или идёт медленнее минимальной скорости, см. [руководство по
серверу](server.md)). Рядом с `code` может стоять необязательная строка `subcode` (см. «Подкоды
ошибок»). Хеширование никогда не использует закрытый ключ.

Аутентификация выполняется до приёма тела. Приём тела идёт отдельной фазой со своим лимитом
`max_uploads`: запрос занимает слот загрузки до чтения первого байта тела, а ожидание медленного
клиента и запись документов во временный каталог не занимают ни слот `max_in_flight`, ни рабочий
поток, ни привязку аудита. Поэтому застрявшая загрузка мешает другим запросам только тем, что
держит один слот загрузки.

`503 CapacityExceeded` означает одно из двух. Либо до чтения тела за `admission_wait_ms` не
освободился слот загрузки или слот операции (`max_in_flight`): сервер проверяет оба слота до
первого байта тела и ждёт до `admission_wait_ms`, после чего отказывает, не принимая загрузку, а
клиенту с `Expect: 100-continue` разрешение на отправку тела так и не приходит. Либо тело уже
принято, но за `admission_wait_ms` не освободился слот операции. В обоих случаях ничего не
применялось. Проверка до тела не гарантирует слот: его могут занять, пока идёт загрузка, и тогда
отказ придёт после тела.

### Закрытие соединения после отказа

Сервер решает об отказе по части метаданных, ещё до документов, и клиент в этот момент может
продолжать отправлять большое тело. Если бы сервер сразу закрыл сокет, клиент увидел бы сброс
соединения или разрыв канала (broken pipe) вместо типизированного ответа: закрытие сокета, в
который партнёр ещё пишет, сбрасывает соединение и может стереть уже отправленный ответ (в том
числе в Windows). Поэтому сервер закрывает соединение поэтапно (RFC 9112, раздел 9.6): после
ответа закрывает свою сторону на запись, затем читает и отбрасывает то, что клиент ещё присылает,
пока клиент не закроется, но не дольше одной секунды и не больше примерно 8 МиБ, и только потом
закрывает сокет. Обе границы фиксированы и не настраиваются. Клиент, который отправляет быстрее,
к моменту сброса может успеть протолкнуть в буферы ядра больше 8 МиБ.

Всё это время соединение держит своё разрешение `max_connections`, но не ресурсы операции: слот
`max_in_flight`, временные файлы и бюджеты освобождаются после отправки ответа. Если
`max_connections` клиентов держат сокеты открытыми после ответа, новое соединение не
принимается, пока не пройдёт эта секунда. Клиент, который успевает закончить тело в этих
пределах, получает типизированный отказ, а тот, кто отправляет больше, получает сброс, как и без
поэтапного закрытия. Клиенту следует читать ответ во время отправки или отправить
`Expect: 100-continue` и дождаться ответа до отправки тела; эталонный клиент так и делает.

Учёт ресурсов запроса начинается до приёма метаданных, и тот же контекст становится контекстом
авторизованной операции. Очередь, работа SDK, владение ответом и запись в сеть подчиняются
исходному сроку и общим бюджетам. Если ответ отброшен, работающий рабочий поток от этого не
освобождается, а пока байты ответа удерживаются или скопированы, остаётся занятым и их исходный
резерв.

## Семейства операций

Все операции используют один и тот же конверт `metadata` (JSON-small или multipart с метаданными
в первой части). `GET /v1/openapi.json` требует индивидуального токена, но не требует какого-либо
действия (в отличие от `GET /health`, которому нужно действие `hash`), и публикует описание
OpenAPI 3.1 с примерами запросов и ответов, которые разбираются и сериализуются настоящими DTO.
Каждой операции нужно своё действие токена:

| `kind` | Действие токена | Выход |
|---|---|---|
| `hash` | `hash` | JSON |
| `verify` (`cms`, `cades_*`, `pdf`, `pades_*`, `xml`, `xml_kalkan`, `xades_*`) | `verify` | JSON; Invalid — завершённый отчёт HTTP 200 |
| `extract` | `extract` | артефакт `multipart/mixed` |
| `sign` (`cms`, `cades_b/t/lt/lta`, `pdf`, `pades_b/t/lt/lta`, `xml`, `xades_b/t`, `wsse`, `xml_legacy`, `xades_legacy_b/t`; профиля подписи `xades_lt/lta` нет; `mode` `create`/`add` для CMS/CAdES; XML принимает необязательные идентификаторы элементов `target`/`parent`/`signature_id`) | `sign` плюс право на ключ | артефакт `multipart/mixed` |
| `extend` (`cades_t/lt/lta`, `pades_t/lt/lta`, `xades_lt/lta`) | `extend` (без ключа; провайдер и аудит не используются) | артефакт `multipart/mixed` |
| `jws_sign`, `jws_add`, `jwt_encode` | `sign` плюс право на ключ | артефакт `multipart/mixed` |
| `jws_verify`, `jwt_verify` | `verify` | JSON; подпись, доверие хоста и claims сообщаются отдельно |
| `jwt_decode` | `extract` | JSON; `verified` всегда `false` |
| `inspect` (`certificate`, `cms`, `container`, `named`) | `inspect` (для `named` нужно ещё право на этот ключ) | JSON |
| `plugin` | точный грант оператора для (токен, плагин, операция); элементу плагина, называющему ключи, нужны ещё право `sign` токена и каждый ключ в `keys` токена (и в `keys` гранта), иначе 403 | JSON |
| `stamp` | `stamp` | артефакт-токен `multipart/mixed` |
| `verify_stamp` | `verify_stamp` | JSON |

Несколько элементов в `/v1/operations` выполняются последовательно с общим сроком и бюджетом:
элементы независимы, а завершающая запись одна, по принципу «всё или ничего». Пакет SDK с
явным одобрением хоста и отдельной записью по каждому элементу выполняет `POST /v1/batch` (см.
ниже). Маршрутов шифрования и расшифрования нет: для них нужен внешний бэкенд конвертов ГОСТ, и
маршрут «только RSA» или маршрут с ответом Unsupported его не заменяют.

Профили `sign` включают также `wsse` (подпись SOAP Body, `soap` = `soap11`/`soap12`,
необязательный `body_id`), `xml_legacy` (раскладка Kalkan; XPath `element`/`xpath_parent`, URI
`signature_method`/`digest_method`, которые должны подходить ключу; по умолчанию, как в Kalkan,
используется значение, соответствующее алгоритму подписи сертификата) и `xades_legacy_b`.
`verify` принимает `wsse`. Неподдерживаемые сочетания полей и профилей отклоняются по одним
метаданным (400), до обращения к ключу, секрету или документу. `xades_legacy_t` подписывает
через TSA хоста, для которого нужен OID политики (см. ниже).

`plugin` вызывает установленную оператором операцию плагина через `Engine::plugin_call` в
контексте исходного запроса. Установка плагина прав не даёт: каждой тройке (токен, плагин,
операция) нужна запись оператора `[[plugins.permissions]]` с перечнем разрешённых импортов хоста,
именованных ключей и точных URL статуса PKI (GET). Вызывающий определяется по токену, а не по
`origin` из запроса или данных. Плагин, который объявляет свои операции (`[[operations]]` в
манифесте), обязан им следовать: Core навязывает объявленные параметры подписи (запрос не может
добавить атрибуты, свой TSA и т. п.), `cosign` не допускается, а для использования ключа в гранте
нужен явный `plugin_bytes = true` (см. ниже). Каждое неотклонённое использование ключа
записывается в аудит вместе с билетом. Для плагинов без объявлений правила прежние. Обязательные
диалоги завершаются `InteractionRequired` (403), отклонённый вложенный импорт даёт
`PermissionDenied`, использование ключа записывается в аудит и сообщается как `Applied` или
`Unknown`. Ключи на токенах (PC/SC) настраиваются как именованные ключи оператора. Без
считывателя или карты операция с ними отклоняется (NotApplied, без BEGIN), а транзакции с картой
на одном устройстве никогда не пересекаются.

## Подкоды ошибок

Ответ с ошибкой (ошибка HTTP до заголовков, `error` неудачной записи `final`, `error` неудачного
элемента пакета) имеет вид `{"code": ..., "applied": ...}`. Если у отказа есть точная причина,
добавляется поле `"subcode": "<id>"`:

```json
{"code":"PermissionDenied","applied":"NotApplied","subcode":"not-granted"}
```

* Поле необязательное. `ErrorCode` (19 стабильных кодов) и статусы от него не зависят, ошибка
  без причины выглядит без этого поля. Схема OpenAPI перечисляет `subcode` и сохраняет
  `additionalProperties: false` для всего, что может отправить сервер. Клиент на Rust
  (`oncl_api`) игнорирует неизвестные поля и отбрасывает подкод, если это не строка. Клиент,
  который отвергает неизвестные поля, не сможет разобрать отказ плагина с подкодом (и потеряет
  вместе с ним `code` и `applied`), поэтому обновляйте клиентов вместе с сервером.
* Идентификатор соответствует `^[A-Za-z][A-Za-z0-9_-]{0,63}$`. Сервер выдаёт идентификаторы в
  нижнем регистре через дефис, а шаблон задаёт допустимую форму. `InteractionRequired` подкода не
  имеет. Набор подкодов открытый: могут появиться новые, а неизвестный подкод следует
  обрабатывать как простой `code`. Подкод называет причину, но не является сообщением и никогда
  не содержит байтов документа, ключа или параметров. Значение, не подходящее под шаблон, клиент
  отбрасывает, а типизированный `code` сохраняет.
* Подкоды сейчас есть только у отказов плагинов. Такой отказ всегда `NotApplied`, кроме
  `key-use-spent`: это второе использование ключа в одном запросе (один `OperationId`; два
  элемента плагина одного запроса считаются вместе), а первое использование было настоящим и
  остаётся `Applied`. Подкоды, которые сервер на практике возвращает для операций плагинов:

| `subcode` | `code` | Значение |
|---|---|---|
| `not-granted` | `PermissionDenied` | Операция объявляет использование ключа, а в гранте нет `plugin_bytes = true`; либо ни один грант не покрывает использование по билету |
| `options-mismatch` | `PermissionDenied` | Плагин запросил параметры подписи, отличные от объявленного профиля (или профиль, называющий параметр, который сервер не может сопоставить) |
| `package-changed` | `PermissionDenied` | Пакет плагина — не тот, что установлен |
| `key-mismatch` | `PermissionDenied` | Ключ не из названных в гранте |
| `kind-mismatch` | `PermissionDenied` | Вид подписи не входит в объявленные использования ключа |
| `caller-mismatch` | `PermissionDenied` | Вызывающий в билете — не токен клиента службы (через HTTP недостижимо: токен без подходящего гранта получает `not-granted`) |
| `ticket-uses` | `PermissionDenied` | Билет допускает не ровно одно использование |
| `key-use-spent` | `PermissionDenied` | Один запрос попытался использовать ключ дважды (`applied` — `Applied`) |
| `not-declared` | `PermissionDenied` | Операция не объявлена плагином (грант сервера на неё пропускается при запуске, поэтому запрос обычно получает простой 403 без подкода; этот идентификатор сообщает CLI `oncl plugin`) |

Остальные подкоды того же семейства (`PluginRefusalCode` в `oncl_core::plugins`, всего 49
идентификаторов) относятся в основном к ручному окну настольной программы. Полная таблица есть в
[руководстве по ручному окну](manual-plugins.md#отказы-как-читать-код-на-странице) и в
руководстве по SDK.

Клиент на Rust (`oncl_api::client::ClientError`) возвращает подкод в поле `server_subcode`
(`Option<String>`, уже проверен, печатать его безопасно), а `describe()` выводит
`PermissionDenied; subcode=not-granted`. CLI `oncl` печатает
`oncl: PermissionDenied; subcode=not-granted; applied=NotApplied` и добавляет `subcode` в строку с
ошибкой отчёта `batch --json`. Если причины нет, строка выводится без подкода.

## Ключи и роли секретов

Элемент подписи называет ключ одним из двух способов: `{"source":"named","name":"..."}`
(псевдоним, настроенный оператором; это имя должно быть указано в `keys` токена) или
`{"source":"inline","container":"<part>","password":"<part>","alias":"..."}`. Для inline нужны и
глобальный `inline_pkcs12 = true`, и `inline_pkcs12 = true` у токена. Тогда сервис выдаёт право
только на точный неизменяемый InlineID, вычисленный по полученному контейнеру и псевдониму.
Выбрать ключ по пути к файлу на клиенте, по считывателю токена, по отпечатку сертификата или по
кэшу PIN нельзя.

Части с `role:"secret"` хранятся в ограниченной памяти фиксированного размера и затираются после
использования (контейнер до 4 МиБ, пароль до 4096 байт). Они объявляются первыми и должны прийти
раньше любой части `document`. Они никогда не пишутся во временный каталог документов и в ответ и
сохраняют свою роль, какое бы имя файла или Content-Type ни было у части. В JSON-small секреты
отклоняются. Сетевые буферы и буферы транспорта разборщика, которые не принадлежат хранилищу
секретов службы, не затираются. Инспекция контейнера использует те же роли секретов и
показывает только псевдонимы, перечисленные в `metadata_aliases` токена.

## Аудит и состояние Applied

Перед применением ключа служба записывает в журнал аудита запись BEGIN с синхронизацией на диск;
запись привязана к аутентифицированному субъекту (principal) и точной метке ключа. После
применения пишется FINAL. Сбой аудита до использования ключа даёт ошибку
`AuditUnavailable`/`NotApplied`. Если сбой случился после возможного применения ключа,
завершающая запись сообщает `Applied` или `Unknown`; отката, повтора и гарантии «ровно один раз»
нет. Закрытая привязка аудита остаётся занятой (идентификатор операции нельзя привязать заново)
до истечения исходного срока или до освобождения всех владельцев операции (контекст, рабочий
поток, ответ, артефакт), смотря что наступит раньше. Поэтому завершённые запросы не переполняют
ограниченную таблицу привязок.

## Части-свидетельства, порядок проверки прав и статусы

`sign` и `extend` принимают `evidence`: `[{"kind":"certificate|ocsp|crl","input":"<document part>"}]`
(не больше 64 открытых частей DER до 1 МиБ каждая). Уровням LT и LTA нужны данные OCSP или CRL,
полученные вызывающим (иначе ошибка `InvalidRequest` с текстом `PAdES extension requires
acquired status material`). Свидетельство никогда не становится корнем доверия. PAdES-LT/LTA и
большие свидетельства требуют больше памяти на операцию, чем задано по умолчанию (бюджет
метаданных по умолчанию 64 МиБ); такой запрос отклоняется до BEGIN аудита (см. «Профили ресурсов
и материалов»).

Права проверяются в таком порядке: действие токена, затем, до резервирования памяти и чтения
любого байта секрета, право на ключ, право на inline (глобальное и у токена) и
`metadata_aliases`. Inline-ключ без части `password` отклоняется (400) до привязки и приёма
документа. Точный InlineID проверяется после чтения контейнера ограниченного размера. `hash`
принимает только роль `document`.

Статусы до заголовков ответа:

* 400 InvalidRequest;
* 403 PermissionDenied;
* 404 для неизвестного маршрута (маршрутов плагинов, шифрования и NCANode нет, `/v1/batch` есть)
  или для `KeyNotFound`, когда Core не смог найти ключ, которым токену разрешено пользоваться.
  Право токена на ключ проверяется первым, поэтому имя не из `keys` токена даёт 403, а не 404, и
  по ответу нельзя узнать, существует ли ключ. Две причины 404 различаются полем `code`:
  `InvalidRequest` с `NotApplied` для маршрута, `KeyNotFound` для ключа;
* 405 с заголовком `Allow`;
* 408 Cancelled;
* 413 при превышении лимитов ресурсов;
* 422 ValidationFailed или OperationFailed;
* 500 Internal;
* 503 CapacityExceeded, AuditUnavailable, MissingConfiguration или MissingTemporaryStore;
* 504 DeadlineExceeded.

После отправки заголовков о сбое может сообщить только завершающая запись `final` или обрыв
соединения. При обрыве клиент причину не получает, её записывает в журнал сервер (см.
«Прерванные потоки ответов» в `server.md`).

Части progress берутся из канала, хранящего только последнее значение: не больше одного кадра на
изменение, без очереди кадров на каждую контрольную точку. Каждый кадр списывается как выход и
метаданные в бюджете запроса, поэтому долгая операция не может породить неограниченный поток
progress.

## Профили ресурсов и материалов (отказ до любого использования ключа)

- `cades_lt/lta` и `pades_lt/lta` (sign и `extend`) и `xades_lt/lta` (extend) требуют данных о
  статусе, полученных вызывающим: в `evidence` должна быть хотя бы одна часть `ocsp` или `crl`,
  иначе 400 до обращения к секрету, ключу или документу.
- XAdES LT/LTA получают так: sign `xades_t`, затем `extend` без ключа до `xades_lt`, затем до
  `xades_lta`. Профиля подписи `xades_lt/lta` нет, потому что запрос подписи XML в SDK не несёт
  данных о статусе. Эта цепочка проверена по HTTP независимой библиотекой lxml; продление
  никогда не использует ключ.
- `pades_lt/lta` требуют памяти и метаданных для плана обновления PDF. Потребность вычисляется
  функциями `oncl_pdf::budget::plan_memory` и `plan_metadata` (по тем же формулам резервируют
  память читатель PDF, план обновления, код подписи и представление проверки) по данным,
  известным до открытия ключа: существующим подписям PDF, размерам частей-свидетельств запроса и
  размеру набора доверия оператора, плюс фиксированные резервы хоста (4 буфера ввода-вывода, 64
  КиБ метаданных, одна копия свидетельств). Проверка выполняется по бюджету запроса после приёма
  тела. Если ресурсов не хватает, запрос получает 413 `MemoryLimit` или `MetadataLimit`,
  `NotApplied`, до BEGIN аудита. При лимитах по умолчанию и небольших тестовых свидетельствах
  порог около 380 МиБ, поэтому `memory_per_operation` по умолчанию (256 МиБ) не пропускает PAdES
  LT/LTA; свидетельства CRL в несколько МиБ требуют порядка 600 МиБ памяти и 72 МиБ метаданных.
  Эти оценки проверены на тестовых PDF и наборах свидетельств: прогоны с шагом 1 МиБ около
  порогов ни разу не дали BEGIN с последующим сбоем по ресурсам. Для произвольного PDF или
  других свидетельств это не доказано. Если общий бюджет во время работы заняли другие запросы
  или вход отличается от проверенных, сбой после использования ключа всё ещё возможен; тогда он
  сообщается с настоящим состоянием `Applied` или `Unknown`. PDF, который не удаётся прочитать
  (искажённый или с подписью с SubFilter не PAdES), даёт 400 `InvalidRequest` до BEGIN; документ,
  который с новой подписью превысил бы лимит числа подписей, даёт 413 `InputLimit`. Истечение
  срока, отмена и нехватка мест при предварительной проверке сообщаются своими кодами.
- Подпись PAdES B/T/LT/LTA поверх PDF с уже действительными подписями поддерживается. Старые
  ревизии остаются побайтно неизменными, новая подпись должна достичь запрошенного уровня, а
  LT/LTA поднимают и прежние подписи, так что свидетельства должны покрывать и их. Документ с уже
  недействительной подписью отклоняется с 400 до использования ключа.
- `xades_t` и `xades_legacy_t` требуют TSA хоста с OID политики (`[pki.tsa] policy`), потому что
  SDK привязывает политику TSA для XAdES T/LT/LTA. Без него запрос получает 503
  `MissingConfiguration`, `NotApplied`, без BEGIN. CAdES и PAdES T принимают TSA без политики.

После приёма всего тела и до того, как рабочий поток начнёт работу с закрытым ключом, права
проверяются ещё раз. Если за время долгой загрузки токен отозвали, право на ключ сняли или
сменилось поколение политики, запрос получает 403 без BEGIN и без использования ключа. Изменения
после этой проверки, пока операция уже выполняется, не учитываются; это окно фиксируют записи
BEGIN и FINAL в аудите.

## Справочник по настройке плагинов

```toml
[[plugins]]
id = "vendor.example"            # must equal the manifest id
manifest = "/private/plugins/vendor.example.toml"   # <= 64 KiB
wasm = "/private/plugins/vendor.example.wasm"       # <= 16 MiB
max_memory = 1048576             # <= oncl-plugin MAX_MEMORY; default 1 MiB
max_transfer = 262144            # <= oncl-plugin MAX_TRANSFER; default 256 KiB

[[plugins.permissions]]          # one per (token, operation); duplicates are refused
token = "accounting-service"     # the caller identity: a configured token id
operation = "run"
imports = ["hash", "keys_sign_raw"]   # exact host imports (Import::name())
keys = ["ops-key"]                    # operator-named keys, also in the token's keys
pki_endpoints = ["http://pki.example/ocsp"]   # exact GET URLs for nested validation
plugin_bytes = false                  # default; see below
```

`plugin_bytes = true` означает, что оператор согласен: байты, которые подписывает выданный ключ,
выбирает плагин или его клиент. Сервер не может привязать содержимое к документу (`args`
передаются свободным JSON, типизированных параметров и частей-документов для плагинов нет),
поэтому без этого флага использование ключа в объявленной операции отклоняется
(`PermissionDenied`, подкод `not-granted`, `NotApplied`, до `BEGIN` и до обращения к ключу; отказ
может быть записан в журнал). Флагу нужна хотя бы одна запись в `keys`: `plugin_bytes = true` без
ключей конфигурация не пропускает. Для плагина без объявлений флаг не действует, и сервер пишет
предупреждение. Даже с флагом использование должно точно соответствовать объявлению: плагин, хеш
пакета, операция и токен как вызывающий в билете, именованный ключ из гранта, объявленный вид и
объявленные параметры (иначе `options-mismatch`). Кроме того, это должно быть единственное
использование ключа в запросе, второй элемент плагина или вторая подпись в том же запросе дают
`key-use-spent`.

Операция, профиль которой ссылается на параметр (источники `param:`, например элемент XML,
который вводит пользователь), не может использовать ключ на сервере: серверу не с чем сопоставить
значение, и использование всегда отклоняется как `options-mismatch`. Плагины из каталога
`plugins/` объявляют 30 операций, но ни одна не объявляет `server = true`. Поэтому ни одну из
них нельзя выдать на сервере или запустить через `oncl plugin call`: сервер пропускает такой
грант с ошибкой в журнале, а CLI отказывает с `not-declared`.

При запуске грант объявленного плагина сверяется с манифестом. Если грант шире объявления, он
пропускается с ошибкой в журнале, а остальные гранты и сервер продолжают работать. Шире
объявления считаются: операция, которую плагин не объявляет (ошибка перечисляет объявленные),
объявляет без `server = true` или с содержимым `derived` (такие не запускаются); импорт не из
`uses.imports` (пустой `imports` означает все объявленные импорты); `keys` или `plugin_bytes` для
операции, которая не использует ключ; `pki_endpoints` без `network = "pki"`. Грант с
несуществующим импортом, неизвестным токеном или повтором пары (токен, операция) делает
конфигурацию недопустимой. Грант плагина без объявлений принимается с предупреждением при
запуске, что параметры подписи не навязываются.

Границы конфигурации (их нарушение делает конфигурацию недопустимой): не больше 16 `[[plugins]]`
и 256 разрешений на плагин; `id` плагина, `token` и `operation` гранта не длиннее 64 байт; `id`
плагина должен совпадать с `id` манифеста, повтор `id` плагина отклоняется; `imports` не больше
72, `keys` не больше 8, `pki_endpoints` не больше 16 длиной до 2048 байт. На сервере
`pki_endpoints` допускают только GET (CLI принимает и `POST=`).

Выходные файлы плагинов (файлы `take_output`) и привязанные входные файлы по HTTP недоступны.
SDK поддерживает их через исходный контекст, но способа связать файл с HTTP-запросом нет,
поэтому импорты `file_*` никогда не выдаются. Импорты диалогов всегда завершаются
`InteractionRequired`.

## Контейнеры

Inline- и именованные контейнеры ключей проверены только в формате PKCS#12. Контейнеры JKS проект
умеет только читать, создавать их он не умеет. Поэтому тестовый контейнер JKS с цепочкой до
loopback-CA с адресами статуса для подписи со строгой проверкой создать нельзя, и подпись ключом
из JKS по HTTP не проверена.

## Завершающие записи потоковых ответов

В записи `final` поле `status` равно `completed` или `failed`. Запись `failed` содержит
`error: {code, applied}`, и все артефакты запроса при этом недействительны (частичного успеха
нет); значения `applied` выполненных ранее элементов видны в `results`. Сбои ресурсов, срока и
отмены, при которых ключ ни разу не применялся, обрывают соединение. Поток без завершающей
записи `completed` результатом не является. Причину такого обрыва клиент не получает, он видит
только потерянный ответ. Сервер записывает типизированную причину в журнал (код ошибки, элемент,
состояние применения, прошедшее время, счётчики байт, без пользовательских данных) и учитывает её
в `oncl.stream.aborted`, см. «Прерванные потоки ответов» в `server.md`. Клиенту этот журнал
недоступен.

## Закрытый пакет (`POST /v1/batch`)

Запрос передаётся в том же конверте, что и для `/v1/operations` (multipart с метаданными в первой
части или JSON-small): `items` (от 1 до 1024 элементов с уникальными идентификаторами, порядок в
манифесте задаёт порядок выполнения) и `parts` (сначала секреты, затем документы). Допустим
любой вид элемента из таблицы выше, кроме `plugin` (в пакете SDK нет операции плагина, запрос
получает 400). Метаданные не содержат одобрения, гранта или флага полномочий: неизвестные поля
отклоняются.

Права определяет только политика оператора, а не содержимое запроса:

1. До чтения любого байта документа или секрета проверяется, что у токена есть отдельное право
   `batch` (`actions = [..., "batch"]`; это не действие SDK, и других прав оно не даёт), а для
   каждого элемента есть действие его операции, право на именованный ключ, право на inline или
   `metadata_aliases`. Если хотя бы одному элементу права не хватает, отклоняется весь пакет (403,
   ничего не запускается, ключи не открываются, секреты не читаются).
2. После приёма тела та же проверка выполняется ещё раз (отзыв, смена поколения политики), затем
   каждый источник фиксируется как неизменяемый снимок (`Engine::capture_batch`). Ключи
   разрешаются до получения сертификата, но закрытый ключ на этом шаге не применяется.
3. Служба выдаёт одобрение хоста (`BatchApproval`), только если зафиксированный план поэлементно
   совпадает с составом, который разрешила политика оператора: идентификаторы и порядок,
   действие, профиль подписи, идентификаторы ключей и размеры источников. Другой план (или
   одобрение для другого плана) отклоняется с 403 до использования закрытого ключа. Одобрение
   одноразовое и привязано к исходной операции.
4. Выполнение (`run_batch_with_outputs`) идёт в исходном контексте запроса. Каждое использование
   закрытого ключа записывается в аудит с порядковым номером элемента пакета (`BEGIN` и `FINAL`
   на каждый элемент).

Ответ всегда `multipart/mixed`; статус выбирается в момент одобрения, а отказы до этого приходят
типизированными JSON-ошибками с `NotApplied`. Ответ состоит из частей `progress`, которые также
сообщают положение в пакете (`items`: `total`, `finished`, `current` `{index,item_id}`), одной
части `artifact` на каждый завершённый выход и обязательной последней части `final` с
`type = "batch_final"`:

- `status`: `completed` (выполнены все элементы; проверка с результатом `Invalid` считается
  выполненным элементом с `verdict = "Invalid"`), `partial` (какой-то элемент не удался или не
  запускался) или `failed` (ничего не удалось запустить).
- `items[]` в порядке манифеста. У каждого есть `item_id`, `index`, `outcome` (`completed`,
  `failed`, `not_run`), `applied` (`NotApplied`/`Applied`/`Unknown`), `verdict`,
  `error {code, applied}` для неудавшихся элементов, `result` для выполненных (те же виды
  результатов, что у `/v1/operations`; `artifact` содержит Content-ID только выполненного
  выхода) и `sources` (SHA-256 и длина зафиксированных байтов).
- Неудача элемента не стирает результаты, артефакты и значения `applied` выполненных элементов.
  После сбоя, касающегося только элемента (нечитаемый источник, отсутствующий ключ), следующие
  элементы выполняются. После остановки всего пакета (квота, сбой аудита, истечение срока или
  отмена во время элемента) следующие элементы получают `not_run`, а поле `stop` объясняет
  причину (`kind` `item`/`control`, `code`, `item_index`). Повторов, ключей идемпотентности и
  отката нет.
- Байты выхода учитываются один раз, как подготовленный выход SDK. Служба копирует каждый
  выполненный выход в своё хранилище артефактов, поэтому на время элемента место на диске
  ненадолго занято дважды. Артефакт держит исходный контекст, срок и учёт временного каталога,
  пока не освобождена последняя отправляемая его часть.
- Отчёты XML и PDF выполненных элементов держат свой резерв метаданных до конца пакета (так
  устроен SDK; `/v1/operations` освобождает его после каждого элемента). Поэтому пакету из
  нескольких подписей XML или PDF нужен соответственно больший `metadata_bytes` на операцию. По
  измерениям три обычные подписи XML и одна XAdES-B помещаются в 96 МиБ, а одна подпись XML и
  вторая не помещаются в 64 МиБ. Когда резерв исчерпан, элемент завершается с `MetadataLimit` и
  настоящим состоянием Applied, следующие элементы получают `not_run`, а артефакты выполненных
  элементов остаются.
- Исходный срок покрывает загрузку, очередь, каждый элемент и доставку. Если он истекает (или
  клиент отключается) посреди пакета, дальше не может уйти ни одного байта, и ответ обрывается
  без завершающей записи. Отсутствие `final` означает неизвестный исход, но не успех. Журнал
  аудита хранит факты по каждому элементу, а рабочий поток держит исходный контекст до возврата.
  Если срок истёк, пока клиент ещё отправляет тело, ответ будет `504 DeadlineExceeded`
  (`NotApplied`) до каких-либо заголовков. Обрыв соединения по сроку или из-за отключения
  клиента строку в журнал не пишет; обрыв потока с типизированным сбоем пишет, см. «Прерванные
  потоки ответов» в `server.md`.

## Тесты с внешними инструментами

Тесты на настоящих сокетах сверяют результаты с независимыми инструментами. `openssl` и `python`
(с `lxml` и `cryptography`) ищутся в `PATH`. Тесту PAdES нужно окружение Python с `pyhanko`,
`pyhanko-certvalidator` и `cryptography`; путь к его исполняемому файлу python задаётся в
`ONCL_PYHANKO_PYTHON`. Если переменная не задана или файла нет, тест завершается с ошибкой и этим
пояснением, а не пропускается.

## Конфигурация оператора (кратко)

`[pki]` задаёт `anchors`, `intermediates`, `endpoints` с привязкой адресов, необязательный
`[pki.tsa]` (`url`, необязательный `policy`, `timeout_ms`, `skew_ms`), который нужен для подписи
`*_t/lt/lta` и для `stamp`, и `[pki.jwt]` (`expected_issuer`, `expected_audience`). Токенам доступны
действия `extend`, `inspect`, `stamp`, `verify_stamp` и `batch` и список `metadata_aliases`. Ничего
из этого нельзя передать в запросе. Операции с закрытым ключом используют строгую проверку: им
нужны настроенные корни и доступные данные об отзыве, иначе они завершаются ошибкой до
применения ключа.

Для шифрования нужен ещё контракт внешнего бэкенда ГОСТ. Этот документ не описывает обработку
документов размером 1 ГиБ и потребление памяти, а также поддерживаемые платформы.

## Эталонный клиент

`oncl_api::client::ApiClient` (feature `client` крейта `oncl-api`, только `ureq` + `rustls`) служит эталонным клиентом этого контракта и транспортом `oncl --endpoint` ([cli.md](cli.md#удалённый-режим---endpoint)). Он пишет multipart-запрос с метаданными в первой части как ограниченный поток: сначала секреты, затем тела документов с точной объявленной длиной или chunked. Клиент отправляет `Expect: 100-continue`, не следует перенаправлениям и читает `multipart/mixed` по `Content-Length` каждой части ограниченным читателем. Ответ считается результатом, только когда получены `final`, закрывающий разделитель и конец тела HTTP. Иначе исход `ResponseLost` с `Unknown` (закрытый ключ мог быть применён) или `NotApplied`, без повтора. Собственное описание формата ответа в клиенте (`client::wire`) сверяется с каждым опубликованным примером OpenAPI (`tests/client.rs`).

Заявленные длины артефактов клиент проверяет только там, где их задаёт сервер (извлечение, токен штампа времени, создание JWS/JWT; у элементов пакета не проверяет). `ExecuteOptions.control` опрашивается каждые 50 мс, поэтому при остановке клиент сообщает `Unknown` только тогда, когда тело, способное привести к использованию ключа, было отправлено полностью.
