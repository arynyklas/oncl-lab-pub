# Автономный HTTP-сервис

`oncl-server` не зависит от настроек десктопа, его диалогов, хранилищ секретов ОС, установки
доверия и автозапуска. Без подкоманды он не открывает сокет. Подкоманде `serve` нужен явный
закрытый файл конфигурации, а HTTP остаётся выключенным, пока в нём не задано `enabled = true`
или оператор не передал `--enable-api`.

## Закрытый каталог оператора и токены

Создайте отдельный каталог, которым владеет только учётная запись сервиса. Сервис проверяет,
что права и ACL оставляют доступ одному владельцу, отказывает при ссылках и чужих файлах и
никогда сам не исправляет права существующих объектов. Конфигурация, файл API-токена и файлы с
ключами и PIN должны лежать в таком каталоге как закрытые обычные файлы с одной жёсткой
ссылкой. Каталог данных десктопа для этого не подходит.

```text
oncl-server token-create --directory /private/oncl-operator --name client.token
```

Команда создаёт закрытый каталог, если его нет, записывает в `client.token` новый 256-битный
токен из CSPRNG ОС (файл создаётся исключительно, существующий не перезаписывается),
синхронизирует его на диск и печатает только верификатор. Обращайтесь с файлом токена как с
паролем: передавайте его клиенту через средство секретного ввода, не через аргументы командной
строки и не через журналы. Верификатор вычисляется как HMAC-SHA-256 с фиксированным
версионированным доменным ключом, а сравнение выполняет проверка MAC фиксированного размера из
ring с постоянным временем. В конфигурации хранятся идентификатор токена, верификатор и ACL, сам
токен там не хранится. Ни токены, ни типы с ключами, PIN и паролями не печатают своё содержимое
через `Debug`.

Запишите `server.toml` в закрытый каталог оператора, подставив свой верификатор и абсолютный
каталог журнала:

```toml
enabled = false
bind = "127.0.0.1:13579"
audit_directory = "/private/oncl-audit"
recover_audit = false
max_in_flight = 2
# max_uploads = 8   # не задано: min(8, total_temp / (input_bytes + container_bytes)); явное значение не может превышать эту границу
blocking_workers = 2
queue_capacity = 2
admission_wait_ms = 1000
operation_timeout_ms = 300000
upload_idle_timeout_ms = 30000
upload_min_bytes_per_second = 1024
max_connections = 32
header_timeout_ms = 5000
input_bytes = 1073741824
container_bytes = 1073741824   # надбавка на подпись/конверт у подписанного `input`; уменьшайте вместе с input_bytes, см. http-api.md
memory_per_operation = 268435456
total_memory = 536870912
temp_per_operation = 8589934592
total_temp = 17179869184
framing_bytes = 67108864
metadata_bytes = 67108864   # по умолчанию 64 МиБ; увеличьте для пакетов подписей XML/PDF
# Необязательно, нужно для multipart-снимков публичных документов:
# scratch_directory = "/private/oncl-scratch"
inline_pkcs12 = false

[[tokens]]
id = "accounting-service"
verifier = "<64 строчных шестнадцатеричных знака верификатора>"
actions = ["hash"]   # все права: "hash", "verify", "extract", "inspect", "extend", "stamp", "verify_stamp", "sign", "sign_digest"; "batch" — отдельное право на POST /v1/batch
keys = []
```

Ещё два ключа аудита в примере не показаны: `audit_segment_bytes` (по умолчанию 1 048 576) и
`audit_quota_bytes` (по умолчанию 67 108 864, больше 64 МиБ задать нельзя). Файл конфигурации
не может быть больше 64 КиБ. Допустимые значения: `max_in_flight` от 1 до 256,
`blocking_workers` от 1 до 64, `queue_capacity` не больше 256, `max_connections` от 1 до 1024,
`operation_timeout_ms` от 1 до 86 400 000. `admission_wait_ms` и `header_timeout_ms` не могут
превышать `operation_timeout_ms`, `metadata_bytes` не может быть меньше 32 КиБ. В конфигурации
допускается не больше 256 токенов, 64 ключей, 16 плагинов и 32 записей `hosts`.

```text
oncl-server serve --config /private/oncl-operator/server.toml --enable-api
```

Если `hosts` не задан, loopback-слушатель принимает в заголовке `Host` только собственный адрес
сокета вместе с фактическим портом. Если клиенты обращаются по имени, задайте
`hosts = ["localhost:13579"]`. Шаблонов в `hosts` нет, и заголовок `Origin` никаких привилегий
не даёт. Для IPv6 loopback укажите в `bind` явный IPv6-адрес. Конфигурация разбирается строго:
неизвестные поля и небезопасные пределы отвергаются. При `enabled = false` процесс завершается,
не открывая журнал, TLS-ключи и слушатель.

Без `--shutdown-stdin` корректную остановку запрашивают через Ctrl-C (SIGINT). Если процессом
управляет супервизор, флаг `--shutdown-stdin` включает чтение управляющего канала на stdin:
перевод строки или EOF останавливает слушатель, отменяет соединения и дожидается возврата уже
принятых в работу потоков. Ctrl-C при этом флаге не обрабатывается. Сетевого API
администрирования у этого канала нет. Остановка не затрагивает другие слушатели и сервисы, а
файлы аудита остаются на диске.

## Маршруты

Сервис обслуживает только следующие маршруты:

* `POST /v1/hash`: SHA-256 сырого тела запроса, требует права `hash`.
* `POST /v1/operations`: типизированные хеширование, проверка, подпись и потоковое извлечение в
  форме JSON-small или multipart с метаданными в первой части; см. [контракт HTTP](http-api.md).
* `POST /v1/batch`: упорядоченный пакет операций, требует отдельного права `batch`.
* `GET /v1/openapi.json`: опубликованный контракт. Нужен действительный токен, право `hash` не
  проверяется.
* `GET /health`: требует права `hash` и сообщает фактическое состояние локального аудита.

Передавайте `Authorization: Bearer <содержимое файла токена>`, настроенный `Host` и документ
потоковым телом. Ответ на хеш трёх байт `abc`:

```json
{"operation_id":1,"algorithm":"sha256","digest":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad","bytes_in":3}
```

Идентификатор операции от запроса к запросу меняется. Content-Length необязателен: тело
неизвестной длины (chunked) учитывается в тех же пределах ресурсов, включая контрольный байт
N+1 сверх предела. Тело для хеширования не собирается в памяти и не пишется на диск. Искажённое
или усечённое обрамление никогда не даёт успешного хеша.

Сервис отвергает параметры запроса (query), селекторы ключей, заголовки подмены метода,
несовпадающий `X-Oncl-Operation` и трейлеры запроса. Маршрут никогда не выполняет другую
операцию, даже если она названа в теле. Цель запроса должна быть точным путём в origin-form, без
схемы и авторитета; абсолютный URL отвергается, даже если его авторитет совпадает с `Host`.
Методы сравниваются точно: POST для хеша, GET для health, HEAD не считается GET. Неизвестный
путь и неверный метод дают HTTP 404 и 405 с конвертом `InvalidRequest`/`NotApplied`. Запрос,
который Hyper не может разобрать, может быть отвергнут на транспортном уровне без JSON-конверта.

Ошибки содержат стабильные поля `code` и `applied`. Маршрут хеширования не использует закрытый
ключ и поэтому всегда сообщает `NotApplied`. Неверная авторизация даёт HTTP 403, искажённый
запрос 400, превышение байтовых пределов 413, нехватка мест в очереди (`CapacityExceeded`) 503,
`DeadlineExceeded` 504. Сервис не повторяет запросы сам и не хранит очередь документов.
Подпись и продление выполняются через `POST /v1/operations` и `POST /v1/batch` (см. [контракт
HTTP](http-api.md)); для них токену нужно право `sign`, `extend` или `batch` и именованный ключ
оператора. Маршрутов шифрования и расшифрования нет, потому что для них нужен казахстанский
ГОСТ-бэкенд. Административных маршрутов тоже нет.

## Явный доступ из локальной сети

Для привязки к адресу, отличному от loopback, нужно явно задать режим доступа и точный список
разрешённых хостов. Режимов два. Первый:

```toml
bind = "0.0.0.0:13579"
hosts = ["signing.internal:13579"]
exposure = { mode = "tls", certificate = "/operator/server.crt", private_key = { directory = "/private/oncl-operator", name = "server.key" } }
```

Это TLS на rustls с PEM-цепочкой сертификатов оператора и закрытым PEM-ключом в каталоге,
доступном только владельцу. Сервис не создаёт и не устанавливает CA. Доверие на клиентах
настраивайте явно и не отключайте проверку сертификата.

Второй режим: TLS завершает обратный прокси в защищённой сети бэкенда.

```toml
bind = "0.0.0.0:13579"
hosts = ["signing.internal"]
exposure = { mode = "trusted_proxy", peers = ["192.0.2.10"] }
```

К такому слушателю допускаются только соединения, у которых фактический IP-адрес пира сокета
есть в списке. `Forwarded`, `X-Forwarded-For`, `Origin`, поля URL и роли доверия к прокси не
дают и индивидуальный API-токен не заменяют. Участок между прокси и сервисом в этом режиме идёт
без TLS, поэтому защищайте его политикой хоста и сети. Пир не из списка получает отказ, даже если
присылает поддельную цепочку пересылки. IPv4-mapped IPv6-адреса (`::ffff:a.b.c.d`) в настройке и
в соединении приводятся к одному IPv4-адресу. Обычный IPv6 и IPv4-совместимый IPv6 считаются
разными адресами; приведение не расширяет loopback-привязку и не открывает доступ соседним
адресам. Неопределённые адреса, в том числе mapped unspecified IPv4, в списке недопустимы.

## Именованные ключи оператора и аудит

Сервис создаёт один Engine, один общий бюджет ресурсов (SharedBudget), один ограниченный
исполнитель, настоящие `KeySources`, реестр доступа к считывателям токенов и долговременный
журнал аудита ONCLAU02. Конфигурация оператора связывает непрозрачные имена с файлами PKCS#12
или JKS либо с поддерживаемыми токенами. Пути на сервере клиент в запросе передать не может.

```toml
[[keys]]
source = "file"
name = "corporate-signing"
path = "/operator/corporate.p12"
# alias = "signing" # опускайте только для контейнера с одной записью
secret = { directory = "/private/oncl-operator", name = "container.password" }

# Вариант с токеном (точный существующий вид хранилища и фактический считыватель PC/SC):
# [[keys]]
# source = "token"
# name = "card-signing"
# reader = "Operator PCSC Reader"
# kind = "AKKaztokenStore"
# alias = "signing"
# secret = { directory = "/private/oncl-operator", name = "card.pin" }
```

Эти ключи используют маршруты подписи. Чтобы применить закрытый ключ, вызывающему нужно право
на действие и точное право ACL на именованный ключ, а его аутентифицированный субъект
привязывается к операции до обращения к ключу. Запись BEGIN синхронизируется на диск до
использования ключа. Если после использования ключа не удалось записать FINAL, операция
остаётся в состоянии Applied или Unknown, дальнейшая работа с закрытыми ключами блокируется, а
результат не выдаётся как успешный. Режима аудита «разрешить всё» и второго журнала нет.
Публичная проверка по умолчанию работает с пустым набором доверия и без доступа к сети PKI и
доверенного вердикта не выдумывает. Подпись идёт по отдельным маршрутам со своими правами, и
через запрос проверки до неё добраться нельзя.

Новый журнал создаётся здоровым. Чтобы открыть существующий журнал, оператор перезапускает
сервис с `recover_audit = true`. Восстановление отвергает полностью повреждённый журнал, журнал
чужого или старого формата и журнал, которым владеет работающий процесс. Чужой журнал оно не
переносит и молча не чинит. Идентичность журнала, блокировка, ротация, квота и непрозрачные
метки субъектов и ключей работают так же, как в библиотеке аудита.

### Код ошибки в записи `FINAL`

`FINAL` называет причину неудачного применения ключа: байт 127 кадра содержит стабильный номер
кода ошибки API. `0` означает, что кода нет: применение удалось или причина процессу неизвестна
(`FINAL` записало восстановление после перезапуска). Если восстановление в том же процессе
закрывает применение с известным исходом, в `FINAL` записывается настоящий код. У успешного
применения кода нет, и ненулевой код в `FINAL` с `succeeded` считается повреждением. Номера
кодов:

| Число | Код | Число | Код |
|---|---|---|---|
| 1 | `PermissionDenied` | 11 | `TempLimit` |
| 2 | `InteractionRequired` | 12 | `MetadataLimit` |
| 3 | `InvalidRequest` | 13 | `OutputLimit` |
| 4 | `CapacityExceeded` | 14 | `AuditUnavailable` |
| 5 | `DeadlineExceeded` | 15 | `MissingConfiguration` |
| 6 | `Cancelled` | 16 | `KeyNotFound` |
| 7 | `InputLimit` | 17 | `ValidationFailed` |
| 8 | `FramingLimit` | 18 | `OperationFailed` |
| 9 | `MissingTemporaryStore` | 19 | `Internal` |
| 10 | `MemoryLimit` | 255 | число, которого читатель не знает |

Номера не меняются и не используются повторно, новый код получает следующий номер. Если в
`FINAL` встретилось число не из таблицы (его записал более новый сервер), читатель понимает его
как `255` и повреждением не считает. Ненулевой байт 127 в кадре другого вида и неверная
контрольная сумма считаются повреждением. Размер кадра, магия `ONCLAU02` и остальные поля те же,
что и в версиях, где байт 127 всегда был нулевым, и такие журналы читаются без изменений.

Откат на версию без кодов в `FINAL`: она считает ненулевой байт 127 повреждением и над журналом с
такими записями завершится с `fatal_corruption`. Перед откатом переместите весь каталог аудита в
архив, чтобы старый сервер начал новый журнал.

### Свидетельства и полный CRL НУЦ

Часть-свидетельство запроса (`certificate`, `ocsp`, `crl`) не может быть больше 1 МиБ; этот
предел проверяется раньше предела движка. Предел движка в 2 МиБ на CRL относится к
свидетельствам внутри проверяемого или продлеваемого контейнера. Полный CRL НУЦ (около 20 МБ)
сервер не принимает. CLI и сервер подписывают XAdES-LT/LTA с CRL не больше примерно 190 КиБ.

### Записи плагинов в журнале аудита

Журнал остаётся в формате `ONCLAU02` с кадрами по 160 байт и контрольной суммой. Журнал без
записей плагинов побайтно совпадает с журналом версий без поддержки плагинов, за исключением
байта 127 в `FINAL` неудачного применения (см. выше). Операции плагинов, объявляющие применение
ключей (`[[operations]]` в манифесте), добавляют два новых вида кадров. Версии без поддержки
плагинов такой журнал прочитать не могут: они сообщают о повреждении и требуют осмотра
оператором. Не запускайте такой сервер над журналом с этими кадрами.

* Разрешённое применение. Перед `BEGIN` пишется один или несколько кадров `PluginDetail`:
  идентификатор плагина, хеш пакета (вид `1` файл / `2` loose и SHA-256), версия, имя операции,
  дайджест билета, SHA-256 одноразового значения (nonce) одобрения, если одобрял пользователь
  (самого nonce в журнале нет), SHA-256 и длина содержимого, признак заранее вычисленного
  дайджеста, SHA-256 параметров, вид вызывающего (`browser` / `local-operator` /
  `service-client`), `declared` и покрывший применение грант оператора. Детали и `BEGIN`
  пишутся одной записью с одной синхронизацией, поэтому сбой между ними оставляет детали без
  `BEGIN`: применение не началось, ключ не использовался. Идентификатор ключа и субъект
  хранятся в `BEGIN` в виде обычных непрозрачных меток. `FINAL` записывается как обычно:
  `Applied`, `NotApplied` или `Unknown`; если `FINAL` нет, исход `Unknown`.
* Отказ. Отклонённое применение ключа по билету пишет те же кадры `PluginDetail` и кадр
  `PluginRefusal` со стабильным подкодом (например, `content-mismatch`, `not-granted`,
  `no-consent-guard`). `BEGIN` не пишется, ключ не использовался. В журнал попадает не больше
  четырёх отказов на операцию, так что плагин, который продолжает просить, не вытеснит ранние
  записи. Все отказы также выводятся как события уровня `warn` с target `oncl::plugin_audit`.
  Вызывающий получает `PermissionDenied`. Подкод предназначен оператору и, где HTTP-контракт
  его передаёт, клиенту API, но плагину он не сообщается.

Для плагинов без объявлений ничего не меняется: нет ни билета, ни записи плагина (отсутствие
записи означает `declared=false`). Байты документов, параметры, секреты и nonce в журнал не
попадают. Инструменты читают эти записи через `DurableAuditGuard::plugin_records()`.

Что важно оператору:

* Отказы записываются, когда это возможно. Запись пропускается (отказ только выводится в лог),
  если журнал нездоров, если ожидается завершение применения ключа и сегмент заполнен, если
  достигнута квота, если операция не привязана (неаутентифицированные и неразрешённые запросы не
  пишутся никогда), после четвёртого отказа одной операции или если факты невозможно
  закодировать. Запись отказа не блокирует работу и не меняет ответ. Применение, факты которого
  нельзя записать (версия плагина или id гранта длиннее 255 байт), отклоняется как
  `audit-fact-too-long` без использования ключа и до обращения к журналу; на здоровье аудита это
  не влияет. Версия в манифесте ограничена 64 знаками, id плагина, токен гранта и операция 64
  байтами каждый, так что на сервере эта проверка срабатывает только при ошибке в коде.
* В записи плагина хранится SHA-256 подписываемого содержимого и его длина. Тот, кто может
  читать журнал и угадать содержимое, по этому дайджесту опознает документ, поэтому защищайте
  каталог аудита так же, как каталог секретов ключей. В лог дайджест попадает только на уровне
  `debug`.
* Применение записывается несколькими кадрами сразу. При потере питания файловая система может
  сохранить более поздние кадры без более ранних, и в журнале остаётся дыра. Это повреждение:
  `open` завершается ошибкой, сервер не запускается (до `recover_audit` дело не доходит), но
  `BEGIN` никогда не будет прочитан неверно. Аккуратно обрезанный хвост (сбой до конца последней
  записи) дырой не считается: его исправляет `recover_audit = true`, после чего
  `plugin_records()` по-прежнему читается.
* Откат. Сервер без поддержки плагинов над журналом с кадрами плагинов завершается с
  `fatal_corruption`. Перед откатом переместите весь каталог аудита в архив или ротируйте
  журнал, чтобы старый сервер начал новый.
* Виды кадров `0x80` и выше зарезервированы для записей, которые незнакомый с ними читатель
  может пропустить (порядковый номер при этом учитывается). Виды `0x00..0x7f` читатель обязан
  понимать, иначе журнал считается повреждённым. Вид `0x80` пока не используется, номер формата
  `ONCLAU02` не меняется, а текущий читатель пропуск не реализует и любой неизвестный вид
  считает повреждением.
* Подкоды отказов: `not-declared`, `package-changed`, `options-mismatch`, `approval-expired`,
  `approval-missing`, `ticket-missing`, `ticket-uses`, `key-use-spent`, `key-mismatch`,
  `operation-mismatch`, `kind-mismatch`, `action-mismatch`, `content-mismatch`,
  `caller-mismatch`, `operation-id-mismatch`, `certificate-changed`, `approval-replayed`,
  `busy`, `not-manual`, `not-granted`, `no-consent-guard`, `audit-fact-too-long`,
  `unknown-plugin`, `derived-unsupported`, а также подкоды ошибок запроса и подготовки (среди
  них `resource-budget` и `no-temporary-store`, которые выдаёт проверка бюджета ручного окна до
  открытия ключа). Всего идентификаторов 49.

Встроенные (inline) ключи PKCS#12 доступны по HTTP, только если включены оба флага:
глобальный `inline_pkcs12 = true` и `inline_pkcs12 = true` у токена. По умолчанию оба выключены
(см. «Ключи и роли секретов» в [контракте HTTP](http-api.md)). Сервис выдаёт право только на
точную идентичность inline-селектора, вычисленную по полученным контейнеру и alias
(`AccessPolicy::authorize_inline`); такое право не распространяется на селекторы File и Token,
и никакая идентичность, присланная клиентом, правом не становится. Провайдер Core держит
секретные контейнеры в ограниченной памяти и никогда не пишет их во временный каталог
документов. `KeySelector::is_inline` сообщает только вид селектора, без секретных байтов и путей.

## Плагины

WASM-плагин устанавливает оператор в `[[plugins]]`; установка только делает код доступным.
Доступ даёт отдельная запись `[[plugins.permissions]]` на каждую пару (токен, операция), и
вызывающий определяется по токену. Полный справочник находится в разделе «Справочник по
настройке плагинов» [контракта HTTP](http-api.md), образец в `deploy/server/server.example.toml`.

```toml
[[plugins]]
id = "vendor.sign"
manifest = "/private/plugins/sign.toml"
wasm = "/private/plugins/sign.wasm"

[[plugins.permissions]]
token = "accounting-service"
operation = "sign-file"            # объявленная операция с `server = true`
imports = ["keys_sign_cms_ex"]     # ⊆ объявленных импортов; пусто = все объявленные
keys = ["corporate-signing"]       # именованные ключи оператора, они же в `keys` токена
plugin_bytes = true                # плагин / его клиент выбирает, что подписывает ключ
```

Плагины, объявляющие операции (`[[operations]]` в `plugin.toml`). Грант должен укладываться в
объявление: операция с `server = true`, импорты из объявленных, ключи только для объявленного
применения ключа, `pki_endpoints` только при `network = "pki"`. Более широкий грант
пропускается со строкой `oncl-server: error:`, остальной сервер продолжает работать. Core
навязывает объявленные параметры подписи при каждом вызове. Сервер не может связать
подписываемые байты с документом, поэтому для любого применения ключа в гранте нужен
`plugin_bytes = true`. Без него применение отклоняется до `BEGIN` и до обращения к ключу, и
может быть записан отказ (`PermissionDenied`, подкод `not-granted`, `NotApplied`). Грант с
ключами без `plugin_bytes` запускается с предупреждением, что каждое применение ключа будет
отклонено. Такое же предупреждение получает грант `plugin_bytes` на операцию, профиль ключа
которой ссылается на `param:`: такие операции не могут использовать ключи на сервере
(`options-mismatch`). Каждый пропущенный грант и каждое предупреждение дополнительно выводятся
как событие `tracing` с target `oncl::plugin_grants`, а итоговая строка сообщает, сколько
грантов пропущено.

Если хотя бы у одного гранта есть `plugin_bytes = true`, значение `audit_segment_bytes` должно
быть не меньше 4640 (29 кадров по 160 байт: одно применение плагина пишет кадры деталей и
`BEGIN` и резервирует место под `FINAL` в одном сегменте). Меньшее значение считается ошибкой
конфигурации. Применение, которое всё же не помещается в сегмент, отклоняется как
`audit-fact-too-long` до обращения к журналу; ключ не используется, аудит остаётся здоровым.
Один запрос (один идентификатор операции) может применить ключ только один раз; второй элемент
плагина или вторая подпись в нём завершается с `key-use-spent`. Применение считается
потраченным только после того, как журнал его принял. Если журнал применение не принял (закрытая
привязка, полный или сбойный журнал), оно не тратится, и повторный вызов плагина проверяется
заново.

Плагины без объявлений работают по-старому: грант состоит из меток оператора, параметры не
навязываются, аудит пишет `declared=false`, и при старте для каждого такого гранта выводится
`oncl-server: warning: grant without declaration ...`. `plugin_bytes` для них принимается, но не
действует (с предупреждением). `plugin_bytes = true` без `keys` отвергается проверкой
конфигурации.

Запись аудита разрешённого и отклонённого применения описана в разделе «Записи плагинов в
журнале аудита»; грант в ней записан как `<токен>:<плагин>:<операция>`. Отказы приходят клиенту в
поле `subcode` ответа об ошибке ([подкоды ошибок](http-api.md)).

### Рекомендации оператору по грантам плагинов

* Поставляемые плагины объявляют в сумме 30 операций, все с `manual = true` и ни одна с
  `server = true` (см. [руководство по ручному окну](manual-plugins.md)). Серверный грант на них
  пропускается со строкой `oncl-server: error:`. Гранты нужны только для сторонних плагинов,
  объявляющих `server = true`, и для плагинов без объявлений.
* Включая `plugin_bytes = true`, вы соглашаетесь, что байты для подписи именованным ключом
  выбирает клиент или плагин: сервер не может связать их с документом. Объявленный профиль всё
  равно соблюдается (вид, параметры, одно применение на запрос), вызывающим должен быть токен
  гранта, ключ должен входить в `keys` гранта, а пакет должен быть установленным. Запрос также
  проверяется по правам токена: элементу `plugin`, который называет ключи, нужны право `sign` и
  каждый названный ключ в `keys` токена в дополнение к гранту оператора, иначе он получает 403 и
  ничего не запускается. Выдавайте `plugin_bytes` только токену, клиенту которого вы доверяете
  этот ключ.
* Проверяйте журнал старта после каждого изменения конфигурации или плагина. Пропущенный грант
  (`oncl-server: error: ... grant skipped: ...`), грант с ключами без `plugin_bytes` и грант
  плагина без объявлений (`warning: grant without declaration ...`) выводят по одной строке, а
  сервер при этом продолжает работать.
* Для каждого применения ключа плагином журнал хранит идентификатор плагина, хеш пакета (вид `1`
  файл пакета или `2` loose manifest+module и SHA-256), версию, операцию, дайджест билета,
  SHA-256 nonce одобрения (у гранта оператора его нет), SHA-256 и длину содержимого, признак
  заранее вычисленного дайджеста, SHA-256 параметров, вид вызывающего, `declared` и грант
  (`<токен>:<плагин>:<операция>`), а затем обычные `BEGIN` и `FINAL`. Если `FINAL` нет, исход
  `Unknown`, и ключ следует считать, возможно, использованным. Запись отказа содержит те же
  факты и подкод, без `BEGIN`, не больше четырёх на операцию. Прочитать их можно через
  `DurableAuditGuard::plugin_records()`.
* Ручное окно десктопа в этот журнал не пишет: у него нет файла `ONCLAU02`, его применения
  ключей и отказы выводятся в `tracing` с target `oncl::plugin_audit`.
* Перед запуском сервера без поддержки плагинов уберите весь каталог аудита (см. «Записи
  плагинов в журнале аудита»): журнал с кадрами плагинов остановит такой сервер с `fatal_corruption`.
* Пределы конфигурации (не больше 16 плагинов, 256 грантов на плагин, 8 ключей и 16
  PKI-адресов на грант, идентификаторы до 64 байт; по умолчанию `max_memory` 1 МиБ и
  `max_transfer` 256 КиБ) перечислены в [контракте HTTP](http-api.md).

## Отзыв прав и пределы

Изменения конфигурации и ACL автономного сервиса вступают в силу после корректного перезапуска.
Встраивающее приложение может отозвать идентичности через `AccessPolicy::revoke` или атомарно
заменить проверенный ACL через `AccessPolicy::replace`; из сетевого запроса ни один из этих
методов не вызвать. Смена поколения политики запрещает всем ранее аутентифицированным объектам
Principal получать новые права. Уже принятая в работу операция сохраняет выданное ей право и
сообщает свой настоящий исход; отзыв ничего не откатывает.

Запрос принимается в работу до чтения тела, в два шага. Сначала запрос с телом занимает один из
слотов загрузки `max_uploads` (см. «Загрузки»): пока клиент передаёт тело и документы пишутся на
диск, слот `max_in_flight` и рабочий поток не заняты. Когда тело получено целиком, операция
занимает слот `max_in_flight`, привязку аудита и рабочий поток. Места в пуле и очереди берутся до
`spawn_blocking`, и одновременно выполняется не больше `blocking_workers` блокирующих задач.
Операция в очереди сохраняет исходные пределы и срок, истечение срока в очереди сообщается явно.
Отключение клиента или отмена прекращают ожидание и приём тела, но слот и ресурсы блокирующего
вызова остаются занятыми, пока этот вызов не вернётся.

Рабочий поток (его разрешение и счётчик выполняющихся задач, датчик `oncl.executor.running`)
освобождается при возврате вызова, до передачи результата. Поэтому тот, кто получил результат,
например кадр ответа с подготовленным артефактом, никогда не видит рабочий поток, который ещё
занят этой операцией. Слот освобождается после результата и после того, как доля рабочего
потока в телеметрии запроса закрыта, так что простаивающий исполнитель уже успел отчитаться о
последнем запросе. Байты ответа удерживают исходные пределы и резервы, пока их не отправят в
сеть.

У операции один общий срок, а не отдельный таймаут на каждой стадии. Этот срок, механизм отмены
и отслеживание отключения действуют и при передаче тела ответа. Если срок истёк до первой
отправки, успешные байты не отправляются; таймер срока обрывает ожидающий вывод, а при каждой
записи и сбросе проверяется, не истёк ли срок, даже для байтов, уже лежащих в буфере Hyper.
Пределы приёма и заголовков могут сократить срок операции, но не продлить его. После отправки
заголовков истечение срока обрывает соединение, нового JSON-ответа с ошибкой уже не будет.
Таймеры не освобождают удерживаемые копии байтов ответа и выполняющийся блокирующий вызов: их
владельцы освобождают их сами.

### Прерванные потоки ответов

Если поток ответа уже начался (сервер выбрал статус `200` и начал передачу; сколько заголовков
и кадров успело дойти до клиента, зависит от момента), а затем случился сбой, сервер обрывает
ответ без завершающей записи, потому что JSON-ошибку уже не отправить. Так обрабатываются сбои
ресурсов, срока или отмены, случившиеся до применения ключа (`MetadataLimit`, `OutputLimit`,
`MemoryLimit`, `TempLimit`, `CapacityExceeded` и другие), сбои, которые поток замечает между
кадрами, и сбои при построении кадров потока или завершающей записи. Клиент видит только
потерянный ответ (`ResponseLost`) и различить эти случаи не может. Причину знает только сервер:
на каждый такой поток он пишет ровно одну строку в stderr и те же факты как событие `tracing`
(target `oncl::stream_abort`, уровень `error`). Автономная программа подписчика `tracing` не
устанавливает, поэтому журналом там служит stderr.

```
oncl-server: stream aborted: operation=1 route=operations item=0 kind=sign code=metadata_limit cause=MetadataLimit applied=not_applied elapsed_ms=6 bytes_in=0 bytes_out=218
```

| Поле | Значение |
|---|---|
| `operation` | идентификатор операции (`operation_id` кадров прогресса и, для закрытой операции, записей журнала аудита) |
| `route` | `operations` или `batch` |
| `item`, `kind` | индекс в манифесте и вид операции (закрытые значения `oncl.operation.kind`) выполнявшегося элемента; `none` до первого элемента |
| `code` | закрытое значение `oncl.error.code` типизированной причины (`metadata_limit`, `output_limit`, `memory_limit`, `temp_limit`, `capacity_exceeded`, `deadline_exceeded`, `cancelled`, `invalid_request`, …) |
| `cause` | имя варианта типизированного сбоя (`MetadataLimit`, `OutputLimit`, …); никогда не его текст |
| `applied` | `not_applied`, `applied` или `unknown`: состояние применения ключа у элементов, завершившихся до обрыва |
| `elapsed_ms` | миллисекунды от начала потока ответа |
| `bytes_in`, `bytes_out` | счётчики байт последнего снимка прогресса |

Все значения в строке являются числами или именами из закрытого списка. Текст ошибки,
идентификатор элемента, имя части или файла, содержимое документа, ключ, пароль, токен, URL и
путь в неё не попадают никогда; тесты проверяют это на узнаваемых значениях в запросе. Каждый
такой обрыв также увеличивает счётчик `oncl.stream.aborted`. Не учитываются клиент, который
отключился после заголовков ответа, и обрыв по таймеру срока соединения: в этих случаях тело
заканчивается без типизированного сбоя потока.

Журнал аудита обрыв не меняет. `BEGIN` пишется только при применении закрытого ключа, а
перечисленные выше сбои случаются до него, так что завершать в журнале нечего. Если поток
оборвался уже после применения ключа, в журнале остаются `BEGIN` и `FINAL`, которые записало само
применение (`applied`, `succeeded`), а строка лога содержит `applied=applied`. Код ошибки в
`FINAL` (раздел «Код ошибки в записи `FINAL`») описывает только исход самого применения ключа.
Причину последующего обрыва называет строка лога, а её поле `operation` совпадает с
`operation_id` в журнале.

### Запросы, прерванные до ответа

Запрос, на который сервер так и не ответил, тоже оставляет одну строку в stderr и событие
`tracing` (target `oncl::request_abort`; уровень `warn` для истечения срока, `info` для
остальных причин):

```
oncl-server: request aborted: route=hash reason=deadline_exceeded elapsed_ms=1500
```

| Поле | Значение |
|---|---|
| `route` | `hash`, `operations` или `batch` |
| `reason` | `deadline_exceeded`: вышел срок операции или сработало правило простоя или минимальной скорости загрузки (клиент получает `504`); `cancelled`: операция отменена; `client_disconnected`: клиент закрыл или сбросил соединение, пока читалось тело запроса; `abandoned`: запрос сброшен до ответа (соединение пропало или сервер останавливался) |
| `elapsed_ms` | миллисекунды от начала запроса |

Значения здесь тоже только числа и имена из закрытого списка: ни токена, ни адреса клиента, ни
идентификаторов, ни содержимого запроса. Каждый запрос попадает в журнал не больше одного раза.
Запрос, закончившийся ответом без истечения срока и отмены, строку не пишет. Причины
`deadline_exceeded` и `client_disconnected` проверены тестами с настоящим процессом, `cancelled`
и `abandoned` тестами не покрыты.

### Загрузки

Приём тела запроса идёт отдельной фазой со своим пределом `max_uploads` (от 1 до 256; если не
задан, 8 или меньше, когда в `total_temp` помещается меньше временных файлов загрузки, см. ниже).
Запрос с телом (`POST /v1/hash`, `/v1/operations`, `/v1/batch`) занимает слот загрузки после
аутентификации, до чтения первого байта тела, и держит его, пока ждёт клиента, пишет документы
во временный каталог и, получив тело целиком, ждёт слот `max_in_flight`. Клиент, застрявший
посреди тела, занимает один слот загрузки, свой временный файл и свои резервы диска и памяти.
Слот `max_in_flight`, рабочий поток из `blocking_workers` и привязка аудита ему не достаются.
Запросы без тела (`GET /health`, `GET /v1/openapi.json`) слот загрузки не занимают.

Если все слоты загрузки заняты, запрос ждёт до `admission_wait_ms` (освободившийся слот получает
тот, кто ждёт дольше всех). Если за это время слот не освободился, запрос получает
`503 CapacityExceeded`/`NotApplied` ещё до чтения тела. Hyper отправляет `100 Continue` только при
первом чтении тела, поэтому клиент с `Expect: 100-continue` получит отказ, не начав передачу. Так
же сервер поступает, когда заняты все слоты `max_in_flight`: до слота загрузки запрос проверяет,
что слот операции свободен, и ждёт его до `admission_wait_ms` (ожидание слота загрузки получает
остаток этого времени, а не ещё столько же). Эта предварительная проверка не гарантирует слот:
его могут занять, пока идёт загрузка, и окончательное решение принимается после приёма тела.

Слот загрузки, временный файл и резерв диска освобождаются при любом выходе из фазы: когда
тело получено и у операции есть слот `max_in_flight` (до этого операция в очереди держит слот
загрузки), при отключении клиента, по таймауту простоя или минимальной скорости (ниже), по сроку
операции, при отмене, остановке и любом отказе, например `InputLimit`.

Ожидание клиента асинхронно и рабочий поток не занимает. Принятые части (один кадр Hyper; он не
ограничен 32-КиБ буфером разбора, на практике встречались кадры по 49 152 и 57 344 байта)
списываются из бюджета как 64 КиБ. Это расчётное значение, а не гарантия: буфер чтения Hyper
растёт максимум до 65 536 байт, а больший кадр был бы учтён не полностью. Части собираются в
буфер 256 КиБ, который списывается из бюджета памяти операции один раз на запрос, и пишутся на
диск короткой блокирующей секцией на каждые 256 КиБ, по одной за раз на загрузку, в блокирующем
пуле среды выполнения. Накопленное записывается до того, как сервер снова начнёт ждать клиента
(поэтому данные застрявшего клиента уже на диске, а время записи не засчитывается клиенту в
правилах скорости ниже), и в конце каждого документа. Записываются данные, которые уже отдал
разборщик multipart. Он придерживает до длины границы минус 1 последних байт документа, пока они
могут оказаться началом границы (если содержат `\r`), поэтому последние присланные байты могут
ещё не быть на диске. В пуле `blocking_workers + max_uploads` потоков, чтобы долгая операция не
мешала загрузкам. Маршрут `POST /v1/hash` хеширует каждую часть сразу по приходе на потоках среды
выполнения и на диск ничего не пишет; зависшая загрузка хеша тоже держит только слот загрузки.

`max_uploads` лежит в пределах от 1 до 256 и не превышает
`total_temp / (input_bytes + container_bytes)` (целочисленное деление; при значениях по
умолчанию 16 ГиБ / 2 ГиБ = 8). Каждая загрузка должна иметь возможность одновременно
зарезервировать в общем бюджете диска самый большой временный файл, который ей может
понадобиться: подписанный вход занимает до `input_bytes + container_bytes`.

* Если `max_uploads` не задан, действует `min(8, max(1, total_temp / (input_bytes +
  container_bytes)))`. Когда бюджет снижает значение ниже 8, сервер один раз при старте пишет в
  stderr: ``oncl-server: `max_uploads` is not set; lowered from 8 to N because total_temp
  holds M spool(s) of input_bytes + container_bytes``. Например, при `total_temp` 8 ГиБ и
  остальных значениях по умолчанию получится 4. `total_temp` меньше одного временного файла
  допустим (тогда значение равно 1), но более крупная загрузка отклоняется с `TempLimit`.
* Явное значение 0, больше 256 или больше границы отвергается при старте; сообщение называет
  ключ и границу (`` `max_uploads` must be 1..=256 and at most N ``).

Задавать `max_uploads` вручную нужно, только чтобы опуститься ниже значения по умолчанию или,
при большом `total_temp`, подняться выше 8. Бюджет диска ограничивает каждую загрузку в любом
случае: загрузка, которой не хватило резерва, отклоняется с `TempLimit`.

Ожидание слота операции. `max_in_flight` ограничивает число одновременно выполняющихся
операций. Запрос с полученным телом ждёт свободный слот до `admission_wait_ms`, проверяя каждые
10 мс, без гарантированного порядка между ожидающими. Если слот не освободился, запрос получает
`503 CapacityExceeded`/`NotApplied`: ничего не применено, временный файл удалён. Пока запрос ждёт
слот `max_in_flight`, он держит слот загрузки и временный файл, поэтому такие операции тоже
считаются в `max_uploads`. Срок операции отсчитывается с момента входа запроса в фазу загрузки и
включает загрузку. `admission_wait_ms` в срок не добавляется, но срок за это время продолжает
идти. Принятая операция ждёт свободный рабочий поток не дольше того же `admission_wait_ms`; при
`blocking_workers >= max_in_flight` (так по умолчанию) это ожидание обычно не возникает.

Зависшие и медленные загрузки. Без отдельных правил остановившаяся загрузка держала бы слот и
временный файл весь `operation_timeout_ms` (по умолчанию 300 с), и `max_uploads` молчащих
клиентов заблокировали бы все маршруты с телом на пять минут. Поэтому каждое ожидание следующей
порции тела (тело хеша, JSON, метаданные и документы multipart, эпилог) подчиняется двум
правилам. Учитывается только время ожидания клиента, без времени на хеширование, запись на диск
и очередь, так что медленный сервер клиенту в вину не ставится.

* `upload_idle_timeout_ms` (по умолчанию 30 000, от 1 000 до 86 400 000): если за это время не
  пришло ни одного байта, запрос завершается.
* `upload_min_bytes_per_second` (по умолчанию 1 024, `0` выключает правило). Одного таймаута
  простоя мало: клиент, присылающий по байту каждые 29 с, держал бы слот до конца срока
  операции. Поэтому каждое окно ожидания длиной в таймаут простоя должно приносить не меньше
  этого числа байт в секунду, иначе запрос завершается. 1 КиБ/с соответствует примерно 8 кбит/с,
  это медленнее любого канала, по которому реально передают документы. Правило оценивает только
  целые окна: клиент, присылающий 64 КиБ каждые 25 с, проходит, а один байт в секунду нет.
  Значение не может превышать 1 ГиБ/с. Если TLS завершает сам сервер, TLS-запись (до 16 КиБ)
  должна прийти целиком, поэтому таймаут простоя должен быть больше, чем 16 КиБ, делённые на
  скорость самого медленного допустимого канала. Например, таймаут простоя 1 с отсекает клиентов
  медленнее примерно 16 КиБ/с.

Оба правила завершают запрос с `504 DeadlineExceeded`/`NotApplied`. Это происходит при приёме
тела, до использования закрытого ключа, поэтому привязка аудита и `BEGIN` не пишутся, временный
файл удаляется, а слот загрузки сразу освобождается. Срок операции эти правила не заменяют: он
по-прежнему ограничивает и нормальную передачу, и для загрузки 1 ГиБ по медленному каналу нужно
увеличить `operation_timeout_ms`. Клиента, который передаёт не медленнее минимальной скорости и
без пауз длиннее таймаута простоя, они не останавливают.

Чем грозит зависшая загрузка. Другим запросам она рабочие потоки и слоты операций не
перекрывает, но держит один слот `max_uploads` до таймаута простоя. Если зависли одновременно
`max_uploads` аутентифицированных клиентов, любой другой запрос с телом ждёт `admission_wait_ms`
и получает `503 CapacityExceeded`, пока зависание не кончится; `/health` при этом отвечает.
Выполняющиеся операции делят с загрузками бюджеты `total_temp` и `total_memory`. Зависшие загрузки
держат свои временные файлы (до `input_bytes + container_bytes` каждый) и по буферу 256 КиБ, так
что `max_uploads` таких загрузок могут занять весь `total_temp` (8 x 2 ГиБ при значениях по
умолчанию), и операция, которой понадобится место на диске, получит `TempLimit`. Предела загрузок
на один токен нет, так что один токен, в том числе утёкший, может занять все слоты. Если клиент
отключился во время блокирующей записи на диск, запись завершается сама и держит свой буфер (до
256 КиБ; он списан до конца запроса, так что на время одной записи этот объём не учтён). Таких
записей в этот момент может быть больше `max_uploads`; их число ограничено размером пула, пока
диск не завис. Чтобы увеличить запас, уменьшите `upload_idle_timeout_ms` (не ниже, чем нужно
самому медленному допустимому каналу) и увеличьте `max_uploads`, насколько позволяет бюджет
диска. Клиент, передающий ровно с минимальной скоростью, держит слот загрузки весь
`operation_timeout_ms`; в локальной сети поднимите `upload_min_bytes_per_second` до десятков
КиБ/с. Обратное направление не регулируется: клиент, который не читает большой ответ, держит слот
выполнения до конца срока операции.

### Соединения и платформы

До аутентификации действуют свои пределы на соединения, заголовки и TLS-рукопожатие. Число
заголовков HTTP/1 ограничено 64, буфер разбора соединения 32 КиБ. Эти сетевые буферы и
накладные расходы среды выполнения не входят в бюджет рабочей памяти документов в Core, и
счётчики ресурсов не описывают общий RSS процесса. После ответа соединение держит своё
разрешение `max_connections` (ресурсы операции к тому времени освобождены), пока клиент не
закроет свою сторону или не закончится поэтапное закрытие, но не дольше одной секунды (см.
[контракт HTTP](http-api.md)). Если `max_connections` клиентов держат сокеты открытыми после
ответа, новое соединение не принимается до истечения этой секунды.

Серверный стек собирается только для сервера: минимальные крейты SDK и сборки десктопа и Win7
не зависят от Axum и Hyper, а сборка со статическим CRT не изменилась (состав зависимостей SDK
проверяет `cargo xtask sdk closure`). Проверка на документах размером 1 ГиБ
(`cargo xtask platform-proof`) проходила на Windows x64; на Linux, macOS и Win7 запускались
только проверки распакованных архивов (см. «Что проверено у упакованных программ»).

## Явные корни PKI и закреплённые адреса

Неявного хранилища доверия для проверки документов нет, исходящий трафик PKI по умолчанию
запрещён. Доверенные сертификаты и точные адреса для каждого источника (origin) задаются в
закрытой конфигурации оператора, в метаданных запроса их передать нельзя:

```toml
[pki]
anchors = ["/operator/roots/root.der"]
intermediates = ["/operator/roots/intermediate.der"]

[[pki.endpoints]]
origin = "https://ca.example:443"
addresses = ["203.0.113.10:443"]
```

Каждый файл содержит один сертификат DER или PEM размером не больше 1 МиБ; всего настроенных
сертификатов не больше 16 МиБ, не больше 256 корневых и 256 промежуточных. Защищайте эти файлы
от изменения. У каждого источника не больше 16 явных адресов, источников не больше 128.
Литеральный хост нельзя молча перенаправить на другой IP или порт: закрепления проверяет сетевая
политика SDK. Входящий URL, корень из сертификата или флаг в JSON доверия не устанавливают.
Сертификаты TLS-слушателя и корни для проверки документов настраиваются отдельно. Сервис не
устанавливает сертификаты в хранилища ОС и браузеров.

## Необязательная телеметрия OTLP

Сервис умеет экспортировать метрики и трассы в OTLP-коллектор оператора. По умолчанию экспорт
выключен: без таблицы `[telemetry]` или при `enabled = false` процесс не запускает поток экспорта,
не создаёт экспортёр и не подключается ни к какому коллектору. Экспорт логов по OTLP не
реализован, локальные технические логи и журнал аудита работают отдельно. Крейты SDK, CLI и
приложение десктопа этого кода и его зависимостей не содержат.

```toml
[telemetry]
enabled = true
endpoint = "http://127.0.0.1:4318"   # базовый URL OTLP/HTTP; /v1/traces и /v1/metrics дописываются
service_name = "oncl-server"         # атрибут ресурса `service.name` (значение оператора)
metrics = true
traces = true
trace_sample_ratio = 1.0             # только трассы; метрики никогда не семплируются
export_interval_ms = 10000           # интервал метрик и задержка пакета спанов (100 .. 3 600 000)
export_timeout_ms = 3000             # жёсткий предел одного HTTP-вызова экспорта (100 .. 60 000)
connect_timeout_ms = 1000            # <= export_timeout_ms
queue_size = 2048                    # спанов в очереди, ещё не экспортированных (16 .. 65 536)
batch_size = 512                     # <= queue_size
shutdown_timeout_ms = 5000           # предел последнего сброса (100 .. 60 000)
# headers = { authorization = "Bearer <учётные данные коллектора>" }   # не более 8, секрет оператора; только https или loopback
# ca_file = "/private/oncl-operator/collector-ca.pem"                  # только https: CA коллектора (PEM)
```

Включённая конфигурация проверяется при старте. URL должен быть `http` или `https` без user
info, query и fragment; должно быть включено хотя бы одно из `metrics` и `traces`; имена
заголовков должны быть токенами и не могут быть `host`, `content-*`, `connection` и подобными,
значения допускают только печатаемый ASCII. `headers` с учётными данными коллектора
отвергаются, если endpoint не `https` и его хост не loopback (`localhost`, `127.0.0.0/8`, `::1`),
чтобы учётные данные не уходили в сеть открытым текстом. `ca_file` требует `https`. С
недопустимой конфигурацией сервис не запускается, а сообщение об ошибке не повторяет значения
заголовков. Неизвестные ключи отвергаются.

### Транспорт и ограничения

* Экспорт идёт по OTLP/HTTP с телами protobuf, одним POST на экспорт, без gRPC, сжатия,
  перенаправлений и прокси из окружения. Клиентом служит `ureq` (rustls с ring). При `https`
  сертификат коллектора проверяется по встроенным корням web PKI или, если задан `ca_file`,
  только по сертификатам CA из этого файла (не больше 8, до 1 МиБ). Набор доверия `[pki]` здесь
  не используется. Переменные `OTEL_*` и переменные прокси конфигурацией не считаются: endpoint
  и таймаут берутся из этой таблицы, заголовки из окружения транспорт отбрасывает, а настройки
  сжатия (`OTEL_EXPORTER_OTLP_*COMPRESSION`) игнорируются. Коллектор является исходящим
  адресатом, которому доверяет оператор, и закрепления `[[pki.endpoints]]` к нему не относятся.
* Потоков экспорта не больше двух, по одному на включённый сигнал: `oncl-otlp-traces` для
  спанов и `OpenTelemetry.Metrics.PeriodicReader` для метрик. Короткий поток
  `oncl-otlp-shutdown` существует только во время остановки. Потоки операций в сеть не ходят:
  они кладут данные в очередь фиксированного размера (`queue_size`) через `try_send` и никогда
  не ждут.
* Переполненная очередь, неудачный экспорт и пауза после сбоя приводят к потере затронутых
  спанов, и потери считаются. Счётчик доступен через `Telemetry::stats()` и, когда коллектор
  снова отвечает, как метрика `oncl.telemetry.dropped{oncl.signal=spans|metrics}`. Метрики
  агрегируются на месте (набор измерений закрыт, см. ниже), поэтому сорваться может только их
  экспорт, а память под них не растёт.
* На каждый пакет одна попытка. После сбоя поток экспорта делает паузу
  (`export_interval_ms · 2^n`, не больше 30 с) и отбрасывает то, что отправил бы за это время.
  Зависший коллектор блокирует только поток экспорта и не дольше `export_timeout_ms`.
* `serve` завершается последним сбросом, который ограничен `shutdown_timeout_ms`, так что
  мёртвый или зависший коллектор не задержит процесс дольше. Экспорт, который к этому сроку
  ещё внутри HTTP-вызова, бросается без ожидания.
* Аудит от телеметрии не зависит. Семплирование трасс (`trace_sample_ratio`), потери,
  недоступный коллектор или сбой экспортёра не могут убрать, задержать или заменить
  обязательную запись аудита, и данные OTLP не доказывают, что аудит записан. Здоровье аудита
  видно по его собственной проверке и по `/health`.

### Что может покинуть процесс

Каждый атрибут принадлежит небольшому закрытому типу (`SafeAttr`), у которого нет конструктора
из строки, пути, идентификатора или текста ошибки. Автоматической инструментации тел и
заголовков нет, идентификаторов запроса, клиента, ключа и токена нет, меток метрик с
неограниченным числом значений тоже нет. Атрибуты ресурса: только `service.name` и
`service.version`; область инструментации `oncl-server`; у спанов нет событий, ссылок и
exemplar.

| Атрибут | Значения |
|---|---|
| `oncl.route` | `hash`, `operations`, `batch` |
| `oncl.operation.kind` | `hash`, `verify`, `extract`, `sign`, `extend`, `jws_sign`, `jws_add`, `jws_verify`, `jwt_encode`, `jwt_decode`, `jwt_verify`, `plugin`, `inspect`, `stamp`, `verify_stamp` |
| `oncl.operation.family` | (только sign) `cms`, `cades`, `pdf`, `pades`, `xml`, `xades`, `wsse`, `xml_legacy`, `xades_legacy` |
| `oncl.outcome` | `ok`, `rejected` (отказ до работы), `failed`, `aborted` |
| `oncl.error.code` | стабильные публичные коды ошибок (`permission_denied`, `invalid_request`, `capacity_exceeded`, `deadline_exceeded`, `audit_unavailable`, `validation_failed`, `operation_failed`, …) |
| `oncl.key.applied` | `not_applied`, `applied`, `unknown` |
| `http.response.status_code` | статус заголовка ответа (`200`, `400`, `403`, `404`, `408`, `413`, `422`, `500`, `503`, `504`) |
| `oncl.delivery` | `complete`, `aborted` |
| `oncl.stage` | `wait`, `run` |
| `oncl.signal` | `spans`, `metrics` |

Спаны: корневой `oncl.request` (маршрут, исход, код ошибки, статус, доставка) и его потомки в той
же трассе. `oncl.admission` длится от начала запроса до передачи исполнителю; для запроса с телом
в него входят приём тела и ожидание слотов загрузки и операции, поэтому основную часть занимает
загрузка клиентом, а не очередь. Дальше идут `oncl.executor.wait`, `oncl.executor.run`,
`oncl.operation` (по одному на выполненный элемент: вид, семейство, исход, код ошибки, состояние
применения ключа) и `oncl.delivery` (доставка тела ответа).

Метрики. Счётчики: `oncl.requests`, `oncl.operations`, `oncl.key.uses` (число операций, которые
применили или могли применить закрытый ключ, без указания ключа), `oncl.stream.aborted` (потоки
ответов, оборванные сервером после заголовка, по маршруту, `oncl.error.code` и
`oncl.key.applied`; см. «Прерванные потоки ответов»), `oncl.executor.rejected`,
`oncl.telemetry.dropped`. Гистограммы в секундах: `oncl.request.duration`,
`oncl.admission.duration` (включает загрузку), `oncl.executor.duration`,
`oncl.operation.duration`, `oncl.delivery.duration`, а также `oncl.response.size` в байтах.
Датчики: `oncl.requests.in_flight`, `oncl.executor.running`, `oncl.executor.queued`.

### Чего телеметрия не покрывает

* Запросы health и OpenAPI и транспортные сбои до маршрутизации (искажённый HTTP, пределы
  соединений) не наблюдаются.
* Потоковый ответ получает статус `200`, даже если какой-то элемент потом упадёт. Исходы
  элементов видны в спанах `oncl.operation` и счётчике `oncl.operations`, а исход запроса
  становится `failed`, если упал хотя бы один элемент. Элементы `/v1/batch` не имеют отдельной
  длительности (SDK выполняет пакет целиком), поэтому они видны только в счётчиках
  `oncl.operations` и `oncl.key.uses` и в исходе запроса, спанов у них нет.
* Длительности, размеры ответов и время запросов экспортируются и могут дать оператору
  коллектора общее представление об активности. Идентификаторы трасс и спанов случайны и не
  выводятся из данных запроса. Считайте коллектор частью доверенного окружения сервиса и
  защищайте `headers`.
* При медленном или недоступном коллекторе потери ожидаемы и считаются. Телеметрия не
  гарантирует доставку и не заменяет журнал аудита.
* TLS к коллектору всегда проверяет сертификат. По умолчанию доверие строится на встроенных
  корнях web PKI, `ca_file` заменяет их собственным CA оператора. Проверка отзыва и клиентские
  сертификаты (mTLS) не поддерживаются.
* Входящие заголовки `traceparent` и `tracestate` игнорируются: каждый запрос начинает новую
  трассу, и клиент не может присоединиться к чужой трассе или повлиять на семплирование.

## Пакет, сервис и контейнер

`oncl-server` поставляется отдельным архивом `oncl-server-<version>-<flavor>.zip` (Windows:
`win-x64`, `win-x86`, `win7-x64`, `win7-x86`) или `.tar.gz` (`linux-x64`, собран под glibc 2.28;
`osx`, универсальный), рядом с архивом командной строки `oncl-<version>-<flavor>`. Эти архивы
собирает workflow выпуска как артефакты запуска, к релизу они не приложены (см. «Ограничения
поставки»). В пакет десктопа OpenNCALayer они не входят и сами ничего не устанавливают, не
включают и не запускают: нет установщика, автозапуска, изменений хранилища доверия и
самообновления. В архиве лежат программа, `README.md`, `server.example.toml` (API выключен, нет
ни токена, ни ключа, ни секрета), `docs/`, `THIRD-PARTY.txt` (лицензии стороннего кода именно
этого варианта сборки; в архивы для Unix добавлен AWS-LC, в архивах для Windows его нет),
`LICENSE`, `NOTICE`, а в архиве для Linux ещё `deploy/openncalayer-server.service` и
`deploy/Dockerfile`. Сертификатов, ключей, паролей, токенов и тестовых файлов в архиве нет.
Мейнтейнер собирает, проверяет и испытывает архивы командой `cargo xtask package platform`
(справка: `cargo xtask package platform --help`); она ничего не загружает и не публикует.

Обновляет сервис оператор: распакуйте новый архив, замените программу и перезапустите сервис
(или пересоберите образ из нового архива). Программа к серверу обновлений не обращается. Замена
программы не затрагивает конфигурацию, контейнеры ключей и журнал аудита.

### Что проверено у упакованных программ

`cargo xtask package platform` распаковывает только что собранные архивы в пустой каталог и
запускает распакованные программы без GUI. Проверяется следующее: `oncl --version`;
`oncl hash` файла и stdin со сверкой по независимому SHA-256; `oncl verify` отказывает файлу,
который не является подписью; `oncl-server` без подкоманды и `serve` с поставляемой примерной
конфигурацией завершаются сами при открытом управляющем канале, таблица сокетов ОС не показывает
слушателя на настроенном порту, а соединение с ним отклоняется. Затем включается loopback
(токен из `token-create`, именованный синтетический ключ RSA, loopback-OCSP/CRL синтетического
PKI, `--enable-api`), и проверяется, что в таблице сокетов ровно один loopback-слушатель процесса
сервера, `oncl --endpoint … sign` создаёт подпись CMS, которую `oncl verify` признаёт `Valid`,
`extract` возвращает документ, журнал аудита создан, а перевод строки в `--shutdown-stdin`
останавливает сервис и закрывает порт. `cargo xtask package platform-smoke` повторяет только эту
проверку на уже собранных архивах.

### Учётная запись Linux и systemd

Юнит поставляется файлом, который вы копируете сами. Копирование не включает и не запускает
сервис, а `ConditionPathExists` не даёт ему стартовать без конфигурации.

```sh
tar -xzf oncl-server-<version>-linux-x64.tar.gz
cd oncl-server-<version>-linux-x64
sudo useradd --system --user-group --home-dir /var/lib/oncl-server --no-create-home --shell /usr/sbin/nologin oncl-server
sudo install -m 0755 oncl-server /usr/local/bin/oncl-server
sudo install -d -m 0700 -o oncl-server -g oncl-server /etc/oncl-server
sudo install -m 0600 -o oncl-server -g oncl-server server.example.toml /etc/oncl-server/server.toml
sudo install -m 0644 deploy/openncalayer-server.service /etc/systemd/system/openncalayer-server.service
sudo systemctl daemon-reload
```

Юнит запускает сервис от `oncl-server` с `NoNewPrivileges`, пустым набором capabilities,
`ProtectSystem=strict` (запись разрешена только в каталог состояния `/var/lib/oncl-server` и в
`/etc/oncl-server`, потому что API закрытых файлов открывает конфигурацию на чтение и запись),
`PrivateTmp`, `PrivateDevices`, `PrivateUsers`, только семействами адресов IPv4 и IPv6, фильтром
системных вызовов, `MemoryMax=1G` (примерно вдвое больше `total_memory`, потому что стек HTTP и
обрамление не входят в бюджет документов), `TasksMax`, без дампов памяти и с `UMask=0077`.
`systemd-analyze security --offline=true` на systemd 255 даёт оценку 1.1 (OK). Юнит задаёт
`KillSignal=SIGINT`, потому что принятые операции сервис дожидается только по SIGINT;
`TimeoutStopSec=330` больше 300 с `operation_timeout_ms` по умолчанию. По SIGTERM сервис
завершается сразу с кодом 143. С примерной конфигурацией (`enabled = false`) команда
`systemctl start openncalayer-server` сразу завершается, оставляя в журнале `disabled: no
listener`, и порт не открывается. Сервис начинает слушать только после того, как вы настроите
токен, включите API и сами выполните `sudo systemctl enable --now openncalayer-server`.

Существующий журнал аудита открывается только при `recover_audit = true`, и после корректной
остановки перезапуск с `false` отвергается. Поэтому у включённого сервиса, который может
перезапускаться (`Restart=on-failure`, перезагрузка), должно стоять `recover_audit = true`.
Первый запуск создаёт журнал и этого флага не требует.

### Выдача токена

Выполните подкоманду от учётной записи сервиса. Она создаёт новый 256-битный файл токена в
закрытом каталоге, не перезаписывая существующий, и печатает только верификатор:

```sh
sudo -u oncl-server /usr/local/bin/oncl-server token-create --directory /etc/oncl-server --name accounting.token
# verifier=<64 шестнадцатеричных знака>
```

В `server.toml` записывается верификатор, а не токен. Сам файл пишите от учётной записи сервиса с
`umask 077`: конфигурацию, которую может прочитать или заменить кто-то ещё, сервис отвергает.

```sh
sudo -u oncl-server sh -c 'umask 077 && cat > /etc/oncl-server/server.toml' <<'EOF'
enabled = true
bind = "127.0.0.1:13579"
audit_directory = "/var/lib/oncl-server/audit"
recover_audit = true
scratch_directory = "/var/lib/oncl-server/scratch"

[[tokens]]
id = "accounting"
verifier = "<верификатор, напечатанный выше>"
actions = ["hash", "verify"]
keys = []
EOF
```

Передайте `accounting.token` клиенту по надёжному каналу и положите его в каталог, доступный
только владельцу (`install -d -m 0700 ~/.oncl`, файл записывается с `umask 077`; файл токена,
который могут читать другие, клиент отвергает). Клиент получает его через `--token-file`. Затем
удалите файл с сервера (`sudo -u oncl-server rm /etc/oncl-server/accounting.token`), серверу
нужен только верификатор. Чтобы сменить токен, создайте новый, замените верификатор и
перезапустите сервис.

Загруженные данные (OCSP, CRL) клиент складывает в текущий рабочий каталог, если
`--temporary-directory` не указывает другой, а в Unix отвергает каталог, доступный другим
пользователям. Поэтому при проверке подписи с онлайн-PKI запускайте `oncl` из каталога, доступного
только владельцу.

Windows. Проверка закрытых файлов требует защищённого ACL с ровно одной наследуемой записью для
владельца, а `icacls` и PowerShell `Set-Acl` такой ACL создать не могут. Создавайте файлы самой
программой: она использует тот же API закрытых файлов, никогда не перезаписывает файлы и
печатает только имя и размер.

```bat
oncl-server install-file --directory %ProgramData%\oncl-operator --name server.toml --input server.toml
oncl-server install-file --directory %ProgramData%\oncl-operator --name corporate.p12 --input corporate.p12
type corporate.password | oncl-server install-file --directory %ProgramData%\oncl-operator --name corporate.password
oncl-server token-create --directory %ProgramData%\oncl-operator --name accounting.token
oncl-server serve --config %ProgramData%\oncl-operator\server.toml --enable-api
```

Каталог `--directory`, если его нет, создаётся доступным только владельцу, а существующий должен
быть закрытым. `--name` задаёт одно простое имя файла: без пути, диска, потока и
зарезервированных имён устройств вроде `NUL`, только латинские буквы, цифры, `-`, `_` и `.`, не
длиннее 64 знаков. Ввод не может быть больше 16 МиБ. При отклонённом имени или слишком большом
вводе ничего не создаётся, даже каталог. Если запись файла не удалась, файл удаляется, а
созданный командой каталог остаётся пустым; если не удалась последняя синхронизация каталога,
готовый файл остаётся на месте. На Linux эта команда тоже работает и заменяет
`install -m 0600`. Исходные файлы после этого удалите.

### Выдача TLS (доступ из локальной сети)

Для привязки не к loopback нужны `hosts` и либо TLS, либо доверенный прокси (см. [Явный доступ
из локальной сети](#явный-доступ-из-локальной-сети)). Сервис не создаёт CA и не устанавливает
сертификаты. Создайте ключ от учётной записи сервиса, доступный только владельцу, и запрос на
сертификат для вашего CA:

```sh
sudo -u oncl-server sh -c 'umask 077 && install -d -m 0700 /etc/oncl-server/tls && cd /etc/oncl-server/tls && openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key && openssl req -new -key server.key -subj "/CN=signing.internal" -addext "subjectAltName=DNS:signing.internal" -out server.csr'
```

Цепочку сертификатов, которую вернёт CA (PEM, сертификат сервера первым), положите в
`/etc/oncl-server/tls/server.crt`. Для лабораторного стенда без CA подойдёт самоподписанный
сертификат конечного субъекта (`CA:FALSE`), которому клиенты явно доверяют. Сертификат,
созданный `openssl req -x509` с настройками по умолчанию, имеет `CA:TRUE`, и клиент отвергает
его как сертификат сервера с ошибкой `TlsFailed`. Для рабочей эксплуатации такой сертификат не
годится:

```sh
sudo -u oncl-server sh -c 'umask 077 && cd /etc/oncl-server/tls && openssl req -x509 -key server.key -days 365 -subj "/CN=signing.internal" -addext "subjectAltName=DNS:signing.internal,IP:127.0.0.1" -addext "basicConstraints=critical,CA:FALSE" -addext "keyUsage=critical,digitalSignature" -addext "extendedKeyUsage=serverAuth" -out server.crt'
```

```toml
bind = "0.0.0.0:13579"
hosts = ["signing.internal:13579"]
exposure = { mode = "tls", certificate = "/etc/oncl-server/tls/server.crt", private_key = { directory = "/etc/oncl-server/tls", name = "server.key" } }
```

Клиент доверяет ровно этому сертификату: `oncl --endpoint https://signing.internal:13579 --ca-file server.crt --token-file ~/.oncl/accounting.token hash --algorithm sha256 --input document.bin`. Без `--ca-file` он завершается с ошибкой `TlsFailed`; флага, отключающего проверку, нет.

### Контейнер

`deploy/Dockerfile` собирает образ из архива выпуска, без исходников и загрузок, на базе Debian
12 slim, закреплённого по дайджесту. Сервис работает от непривилегированного пользователя
(uid/gid 10001), конфигурации внутри образа нет. Собирайте образ из каталога, где лежит архив:

```sh
tar -xzf oncl-server-<version>-linux-x64.tar.gz
docker build -f oncl-server-<version>-linux-x64/deploy/Dockerfile --build-arg VERSION=<version> -t oncl-server:<version> .
```

Точки монтирования задаются явно. `/etc/oncl-server` содержит закрытую конфигурацию, контейнеры
ключей и ключ TLS. В `/var/lib/oncl-server` сервис при первом запуске создаёт журнал аудита
`audit/` и каталог `scratch/`; смонтируйте сюда том, чтобы журнал пережил контейнер, и не создавайте
`audit/` заранее: существующий пустой каталог отвергается. Необязательный `/run/oncl-secrets`
предназначен для паролей, ключа TLS и файлов токенов. Правила закрытых файлов действуют и в
контейнере, поэтому готовьте тома от пользователя образа (uid 10001, режим 0700) и не монтируйте
домашний каталог:

```sh
docker volume create oncl-config
docker volume create oncl-state
docker run --rm -i --user 10001:10001 -v oncl-config:/etc/oncl-server --entrypoint sh oncl-server:<version> -c 'umask 077 && cat > /etc/oncl-server/server.toml' < server.toml
docker run --rm --user 10001:10001 -v oncl-config:/etc/oncl-server oncl-server:<version> token-create --directory /etc/oncl-server --name accounting.token
docker run -d --name oncl-server --read-only --cap-drop ALL --security-opt no-new-privileges \
  --memory 1g --memory-swap 1g --pids-limit 256 --tmpfs /tmp:rw,size=64m,mode=1777,noexec,nosuid \
  -v oncl-config:/etc/oncl-server -v oncl-state:/var/lib/oncl-server \
  -p 127.0.0.1:13579:13579 oncl-server:<version>
```

Ключ TLS кладут в том так же: `… --entrypoint sh … -c 'umask 077 && mkdir -p /etc/oncl-server/tls && cat > /etc/oncl-server/tls/server.key' < server.key`, а токен читают через `--entrypoint cat`. Внутри контейнера `bind` должен быть `0.0.0.0:13579`, `hosts` должен совпадать с адресом, по которому обращаются клиенты, и нужен TLS или `trusted_proxy`. `-p 127.0.0.1:…` публикует порт только на loopback хоста. С примерной конфигурацией контейнер печатает `disabled: no listener` и завершается с кодом 0. Не используйте `--privileged`.

Образ задаёт `STOPSIGNAL SIGINT`, поэтому `docker stop` дожидается принятых операций; задайте ему
`--time` больше `operation_timeout_ms` (по умолчанию Docker ждёт 10 с). `--memory 1g` рассчитан
на `total_memory` из примера. Место на диске для временных файлов ограничено `total_temp`, так что
подберите под него размер тома `oncl-state` или уменьшите `temp_per_operation` и `total_temp`.
Меньший `total_temp` уменьшает и число одновременно принимаемых тел: если `max_uploads` не задан,
сервер берёт `min(8, total_temp / (input_bytes + container_bytes))` (не меньше 1) и один раз при
старте пишет сниженное значение в лог, а явный `max_uploads` выше этой границы отвергается при
старте (см. «Загрузки»). `HEALTHCHECK` образа проверяет только, что порт (`ONCL_HEALTH_PORT`, по
умолчанию 13579) принимает TCP-соединение изнутри контейнера. Для `GET /health` нужен токен,
которого в образе быть не должно, поэтому опрашивайте его из своей системы мониторинга токеном с
правом `hash`.

### Ограничения поставки

* Программы и архивы не подписаны (нет ни Authenticode, ни нотаризации) и не опубликованы ни в
  реестре, ни в релизе, ни в магазине расширений. Архивы `oncl` и `oncl-server` к релизу не
  приложены: workflow `release.yml` собирает их только как артефакты запуска (`platform-*`,
  хранятся 30 дней). Собирайте архивы сами (`cargo xtask package platform`) или из исходников.
* В workflow `release.yml` собираются все шесть вариантов `platform` (`win-x64`, `win-x86`,
  `win7-x64`, `win7-x86`, `linux-x64`, `osx`, включая универсальную сборку macOS и tar.gz) и
  CycloneDX SBOM (`platform-sbom`). Эти проверки подтверждают, что распакованные программы
  запускаются без GUI, но не проверяют установку пользователем. Сборки для Win7 проходят
  проверку импортов, но запускаются на `windows-2025` (Windows Server 2025), а не на Windows 7.
