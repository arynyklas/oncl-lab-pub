# Аутентификация обновлений через TUF

Клиент проверяет индекс обновлений только через TUF. Здесь описано, как устроена эта схема.

[TUF](https://theupdateframework.github.io/specification/latest/) (The Update Framework) задаёт набор подписанных метаданных. `root` перечисляет ключи, которым разрешено подписывать, `targets` перечисляет файлы и их хеши, `snapshot` фиксирует, какие версии метаданных действуют вместе, а `timestamp` подтверждает, что всё это актуально сейчас. Схема позволяет заменить любой ключ без выпуска клиента, разделяет роли и ограничивает срок, в течение которого подмена может действовать.

## Слои

Индекс обновлений (`updates/v1/{stable,beta}.json`, формат описан в [`update-index.md`](update-index.md)) в терминах TUF является целью (target) с путём `indexes/stable.json` или `indexes/beta.json`. Вокруг него лежат метаданные, клиентский верификатор и инструменты выпуска. Пакеты ядра, расширение и плагины целями TUF не являются: это ассеты GitHub Releases, на которые ссылается индекс, и проверяются они по `sha256` и `size` из индекса.

Цепочка доверия клиента:

```
встроенный root.json (версия 1)
  → цепочка root N+1, N+2, … (опубликованные корни)
    → timestamp → snapshot → targets
      → индекс канала (цель) → пакет (sha256 + size из индекса)
```

## Роли, ключи, сроки

Используется только Ed25519: `keytype` и `scheme` равны `ed25519`. Других алгоритмов подписи нет, хеш только sha256.

| Роль | Что подписывает | Ключей / порог | Срок `expires` | Где ключ |
|---|---|---|---|---|
| `root` | открытые ключи всех четырёх ролей, порог каждой | 1 / **1** | 365 дней | офлайн у владельца |
| `targets` | пути, длины и sha256 индексов | 1 / 1 | 30 дней | офлайн у владельца |
| `snapshot` | версию `targets` | 1 / 1 | 30 дней | офлайн у владельца |
| `timestamp` | версию и sha256 `snapshot` | 1 / 1 | **7 дней** | **онлайн**: секрет окружения GitHub |

Все четыре ключа различны, `consistent_snapshot` равен `true`. Делегирований, зеркал (`mirrors`), `path_hash_prefixes`, RSA и ECDSA нет.

Сроки отсчитываются от момента подписи и записываются в формате RFC 3339 (`YYYY-MM-DDTHH:MM:SSZ`). `timestamp` действует 7 дней и перевыпускается ежедневно (см. «Подпись timestamp при публикации Pages»).

Единственный ключ root с порогом 1 избавляет от церемонии с несколькими носителями. Цена этого описана в разделе «Ротация и компрометация»: если ключ root потерян или украден, всем придётся переустановить программу.

### Идентификатор ключа

Объект ключа в `root.json`:

```json
{"keytype": "ed25519", "scheme": "ed25519", "keyval": {"public": "<64 hex>"}}
```

`keyid` равен sha256 канонического JSON (см. ниже) этого объекта в виде строчных hex-цифр. Клиент сам пересчитывает `keyid` каждого ключа из `keys` корня и отвергает корень, где ключ записан под чужим идентификатором. Подпись в метаданных имеет вид `{"keyid": "<hex>", "sig": "<128 hex>"}`. Порог считается по различным `keyid` роли; подписи неизвестных ключей и повторы одного ключа в порог не засчитываются.

### Канонический JSON и подпись

Подписывается не файл, а объект `signed`, приведённый к каноническому JSON OLPC ([spec §4.1](https://theupdateframework.github.io/specification/latest/#metaformat)): без пробелов, ключи объектов отсортированы по байтам, в строках экранируются только `"` и `\`, числа только целые. Клиент соблюдает такие правила:

- каноническая форма строится из произвольного `serde_json::Value`, а не из типизированной структуры. Неизвестные поля остаются в подписи, и добавление поля в метаданные подпись не ломает;
- подпись Ed25519 ставится по этим байтам, проверяет её `ring`;
- в типизированную модель метаданные разбираются только после проверки подписи.

Метаданные, где `signed` содержит нецелое число или `_type` не соответствует имени роли, отвергаются.

## Раскладка

Файлы лежат в репозитории и на сайте проекта под `tuf/v1/` (`https://arynyklas.github.io/OpenNCALayer/tuf/v1/`). GitHub Pages отдаёт файлы с `Cache-Control: max-age=600`, и заголовками управлять нельзя. Поэтому включён `consistent_snapshot: true`: каждая версия метаданных и каждая цель имеют своё имя, и за 10 минут кэша разные снимки не смешиваются.

| Путь | Содержимое |
|---|---|
| `metadata/<N>.root.json` | корень версии N; **хранятся все версии** |
| `metadata/timestamp.json` | единственный файл без номера; в git не хранится, создаётся при публикации Pages |
| `metadata/<N>.snapshot.json` | снимок версии N |
| `metadata/<N>.targets.json` | метаданные целей версии N |
| `targets/indexes/<sha256>.<name>.json` | индекс: `<name>` — последняя часть пути цели (`stable.json`, `beta.json`), `<sha256>` — хеш содержимого; байты те же, что в `updates/v1/<name>.json` |

Клиент делает только запросы `GET` по HTTPS (перенаправление на `http://` отвергается) и к API GitHub не обращается.

## Как клиент проверяет

Ниже кратко пересказан [процесс клиента из спецификации (§5)](https://theupdateframework.github.io/specification/latest/#detailed-client-workflow). Какое подмножество реализовано, видно из раздела «Что клиент отвергает».

1. Корень. Доверенный корень берётся из `crates/oncl-update/keys/root.json`, который встраивает `build.rs`. Если проверка уже проходила, за ним идёт цепочка принятых корней из состояния, и клиент заново проверяет её от встроенного корня: оба порога на каждом шаге, версия ровно +1. Сохранённый корень, подписанный только собственными ключами, сам по себе ничего не доказывает. Затем клиент запрашивает `metadata/<N+1>.root.json`, пока не получит 404. Каждый следующий корень должен проходить по подписи и порогу как ключей предыдущего корня, так и своих собственных, а его `version` должна быть ровно N+1. Если N+1 существует, а за один обход клиент уже прошёл `max_roots` корней (по умолчанию 128), это ошибка «цепочка слишком длинна». Пройденные корни сохраняются, и следующий обход продолжит с них. Последний корень цепочки не должен быть просрочен. Если в новой версии корня изменился ключ или порог `timestamp`, `snapshot` или `targets`, сохранённые версии этих трёх ролей удаляются. Спецификация (§5.3.11) называет только первые две роли; `targets` добавлен потому, что иначе после быстрой перемотки версий `targets` (fast-forward) замена его ключа не вернула бы клиента в рабочее состояние. Удаление снимает запрет «версия назад» после ротации.
2. Timestamp. `metadata/timestamp.json` должен быть подписан ключом `timestamp` из актуального корня, его `version` не меньше сохранённой, срок не истёк. В нём записана версия `snapshot` (и, если есть, длина и хеш).
3. Snapshot. `metadata/<N>.snapshot.json` с версией из timestamp: подпись, совпадение версии и хеша, срок. Версии в `meta` не меньше сохранённых.
4. Targets. `metadata/<N>.targets.json` с версией из snapshot: подпись, версия, срок. Поле `delegations` программа с `0.1.2` здесь не разбирает: обновление ядра и индекса от него не зависит, есть ли оно, пустое ли и можно ли его прочитать. Клиенты `0.1.0` и `0.1.1` отвергают `targets` с этим полем.
5. Цель. Клиент ищет путь `indexes/<channel>.json` в `targets`, скачивает `targets/indexes/<sha256>.<channel>.json` и сверяет длину и sha256 с метаданными. Если записи канала в `targets` нет, канал пуст («В канале пока нет выпусков»).
6. Индекс. Дальше действуют правила индекса: схема, `channel` совпадает с каналом клиента, `seq` не меньше последнего принятого. Правило «30 дней с `generated`» здесь не применяется: свежесть задают `expires` ролей, а `expires` самого индекса остаётся просто полем формата (см. [`update-index.md`](update-index.md)).
7. Сохранение. Цепочка корней и версии ролей записываются в состояние сразу после своих проверок. Корни записываются одной записью вместе с удалением версий из п. 1, даже если корень дальше по цепочке отвергнут. Запись всегда атомарная (`oncl_pki::fsutil`).

Истёк ли срок, клиент определяет по своим часам: и при обновлении метаданных, и при скачивании цели (`download_target` получает текущее время, и набор, в котором что-то истекло, не используется). От неверных часов TUF не защищает ([spec §7.1](https://theupdateframework.github.io/specification/latest/#support-for-bogus-clocks)).

### Что клиент отвергает

- метаданные с неверной подписью, с подписями ниже порога, с чужим `keyid`, с повтором `keyid` в роли или с ключом под неверным идентификатором; корень, где один ключ служит двум ролям (ключ `timestamp` хранится онлайн и не должен давать права на `targets`); файл одной роли на месте другой (отказ по подписи и по `_type`);
- корень с версией не `N+1`, корень без подписей прежних ключей в пределах порога, корень без подписи собственных ключей, просроченный последний корень;
- `timestamp`, `snapshot` и `targets` с версией ниже сохранённой или не той, что названа выше по цепочке; просроченные метаданные;
- цель с неверной длиной или sha256;
- `delegations` в `targets` у клиентов `0.1.0` и `0.1.1` (с `0.1.2` поле при проверке `targets` не разбирается, см. п. 4);
- ключ не `ed25519`, хеш не sha256;
- `consistent_snapshot`, не равный `true`;
- индекс чужого канала и индекс с `seq` ниже последнего принятого.

Поля `mirrors` и `path_hash_prefixes` клиент не читает: они входят в подпись, но ничего не значат (`path_hash_prefixes` бывает только в делегированиях, которые обновление программы не читает, а зеркал в корне версии 1.x нет).

Любая из этих причин даёт отказ, и другого пути проверки клиент не пробует.

## Состояние клиента

Каталог `<данные>/update/tuf/` содержит файл `state.json` и файл блокировки `lock`. В `state.json` лежат цепочка принятых корней в том виде, как они скачаны (начиная от встроенного), и версии последних принятых `timestamp` (вместе с тем, что он перечислил), `snapshot` и `targets`. Сами файлы метаданных каждый раз скачиваются заново, их имена несут версию и хеш. Исключение составляет последний принятый файл `targets`: он сохраняется как скачан, чтобы индекс, сохранённый каталогом плагинов, можно было проверить без сети. При этом подпись `targets` заново проверяется по цепочке корней от встроенного, сроки `targets` и корня учитываются, а сроки `timestamp` и `snapshot` нет: они подтверждают актуальность, и их срок измеряется днями. Запись атомарная (`oncl_pki::fsutil`), размер файла ограничен 1 МиБ и при чтении, и при записи. Последний принятый `seq` каждого канала хранится в `<данные>/update/state.json` ([`update-index.md`](update-index.md)).

Индекс читают два потребителя: модуль обновления (`crates/openncalayer/src/update.rs`) и каталог плагинов (`crates/openncalayer/src/plugins.rs`, `crates/oncl-plugin/src/store.rs`). Оба работают через один клиент TUF и один каталог состояния. Так версии метаданных не расходятся, и `timestamp`, принятый одним потребителем, другой не отвергнет как откат. Каждая запись берёт блокировку каталога (файл `lock`) на время чтения, слияния и записи, сливает состояние на диске с сохраняемым, никогда не понижает версию роли и не заменяет корень более старым. Версии из более новой эпохи ключей (после ротации) вытесняют версии прежней.

Если состояние повреждено (не JSON, другая схема, лишнее поле, файл больше лимита, сохранённый корень не является корнем, цепочка корней не проходит от встроенного), клиент начинает со встроенного корня, заменяет состояние и сообщает причину через `Trusted::state_was_reset()`; вызывающий код пишет её в журнал. Ошибка чтения другого рода, например отказ в доступе, остаётся ошибкой и к сбросу не ведёт. Если встроенный корень новее всего сохранённого, версии `timestamp`, `snapshot` и `targets` из состояния тоже забываются, потому что ключи промежуточных корней неизвестны. Встроенный корень нельзя восстановить из сети, он приходит только вместе с пакетом программы.

## Подпись timestamp при публикации Pages

`timestamp.json` подписывается автоматически, и его ключ единственный из секретов попадает в CI.

- Ключ `timestamp` хранится в окружении (environment) GitHub, доступ к нему ограничен правилом окружения: только `main`. Остальные три ключа CI никогда не видит.
- `pages.yml` публикует Pages раз в сутки по расписанию и при каждом слиянии. Задание окружения сначала проверяет клиентским кодом, что `snapshot` подписан ключом из актуального корня и согласован с `targets` и индексами, и только потом подписывает `timestamp`. Подписать чужой снимок CI не может: он подписывает лишь версию и хеш `snapshot`, который уже подписал владелец.
- `version` у timestamp равна Unix-времени в секундах на момент подписи, `expires` наступает через 7 дней. Так версия растёт без хранимого счётчика.
- Файл попадает только в артефакт Pages и в git не коммитится. Ежедневный коммит ради подписи потребовал бы права записи для CI и засорил бы историю, а пользы не дал бы: `version` берётся из времени, и подпись не привязана к ревизии.

Если Pages не публикуется 7 дней, `timestamp` истекает, и клиенты перестают принимать обновления (см. «Сбои»).

## Ротация и компрометация

Любая роль заменяется новым `root.json` версии N+1, подписанным ключом root версии N (порог 1). Клиенты получают его при очередной проверке, новая версия клиента для этого не нужна.

| Ключ | Ротация | Что даёт украденный ключ | Чего он не даёт |
|---|---|---|---|
| `timestamp` (онлайн) | новый root, новый ключ в окружении; клиенты удаляют сохранённые timestamp и snapshot | заморозку: тот, кто ещё и контролирует выдачу Pages, может без конца перевыпускать старый снимок, пока не истечёт `expires` у `snapshot` (30 дней), и откатывать клиентов на ещё не истёкший снимок | установку кода: `targets` и `snapshot` подписаны не им |
| `snapshot` | новый root | смесь ещё действующих версий `targets` | новое содержимое индекса |
| `targets` | новый root | подмену индекса, то есть ссылок и sha256 пакетов, а значит произвольную установку; нужны ещё `snapshot` и `timestamp` (все три офлайн у одного владельца, один носитель означает одну точку отказа) | подпись нового корня |
| `root` | новый root, подписанный старым ключом root | всё: корень с новыми ключами всех ролей; клиенты, дошедшие до него, доверяют атакующему | — |

Потеря или утечка ключа root означает переустановку у всех. Порог 1 значит, что ключ один и резерва нет. Если ключ потерян, подписать новый корень некому. Если украден, атакующий выпустит корень N+1 раньше владельца или вместо него, и клиенты, получившие этот корень, перестанут доверять владельцу. Утечка остальных трёх ключей закрывается ротацией через root. Root продлевается раз в год (срок 365 дней): просроченный корень клиент не принимает, а цепочка должна оставаться непрерывной.

Ротация защищает клиентов, только пока атакующий не контролирует ещё и хостинг. Если он отдаёт клиенту поддельные метаданные вместо опубликованного нового корня, клиент о ротации не узнает ([spec §6.1](https://theupdateframework.github.io/specification/latest/#key-management-and-migration)).

## Церемония владельца

Команды (`cargo xtask tuf …`) и их порядок описаны в [`docs/dev/release.md`](../dev/release.md), раздел 10.

1. Создать на машине владельца четыре различных ключа Ed25519. Секретные ключи шифруются паролем и в рабочее дерево git не пишутся.
2. Ключ `timestamp` внести как секрет окружения GitHub, остальные три хранить офлайн.
3. Подписать корень версии 1 (срок 365 дней), положить его в `crates/oncl-update/keys/root.json` и выпустить сборку с этим корнем.
4. При каждом выпуске индекса подписывать `targets` и `snapshot` ключами владельца. Их срок 30 дней, поэтому даже без выпусков их надо обновлять не реже раза в 30 дней (`refresh`). `timestamp` подписывает CI.
5. Раз в год выпускать новую версию `root`.

## Сбои

- Истёк `timestamp` (Pages не публиковался 7 дней). Клиент отвергает метаданные, обновлений нет, ошибка видна в журнале и окне настроек. Установленная версия продолжает работать, ничего не откатывается. Исправляется публикацией Pages.
- Истёк `snapshot` или `targets`. Последствия те же, исправляется подписью владельца.
- Не удалось подписать или проверить `timestamp` при публикации Pages (репозиторий не проходит проверку клиентским кодом, `snapshot` истёк, секрета нет). Сайт не публикуется, запуск красный. Сайт без `metadata/timestamp.json` дал бы каждому клиенту 404, то есть ошибку проверки, а прежний сайт продолжает отдавать свой `timestamp`, который действует до 7 дней.
- Сеть недоступна: повтор через 30–120 минут. При ошибке проверки следующая попытка в обычный срок (`update-index.md`, «Обновление в демоне»).
- Ответ 404 на `timestamp.json`, пока клиент не принял ни одного `timestamp`, или отсутствие записи канала в принятых `targets` означают, что репозиторий или канал ещё не опубликованы. В окне настроек пишется «В канале пока нет выпусков», в журнал уходит `info`, следующая проверка в обычный срок. Ответ 404 на `timestamp.json` после первой принятой публикации, а также на `snapshot`, `targets` или файл цели считается ошибкой проверки: опубликованный репозиторий файлов не теряет, и подмена ответом 404 не должна незаметно останавливать обновления. В журнал уходит `warn`, повтор через 30–120 минут. 404 на корень N+1 означает конец цепочки корней.
- Корень N+1 подписан неверно: цепочка не принимается, клиент остаётся на последнем принятом корне и пишет ошибку.

## Почему нет запасного пути

Другого способа проверить индекс у клиента нет, и ветки «если TUF не удался, попробовать иначе» тоже. С запасным путём защита свелась бы к более слабому из двух: атакующий, который мешает TUF (подменяет ответ или блокирует его), перевёл бы клиента на путь без ротации, порогов и разделения ролей.

## Почему нет делегирований

Клиенты `0.1.0` и `0.1.1` отвергают метаданные `targets` с `delegations`, даже с пустыми. Программа с `0.1.2` это поле при проверке `targets` не разбирает и делегированных ролей пока не читает: обновление ядра и индекса работает и без делегирований, и с ними, и с полем, которое нельзя прочитать. Так делегирования можно добавить в `tuf/v1`, не остановив обновления у `0.1.2` и новее; клиенты младше `0.1.2` после этого обновляться перестанут. Сторонних поставщиков плагинов пока нет, все порты собирает проект. Роли издателей, их ключи и пути, отзыв чужого плагина и реестр издателей описаны в [`publishers.md`](publishers.md). Доставка встроенных модулей ядра через индекс потребует ещё отдельной роли с порогом больше 1.

## Ограничения платформы

Верификатор реализован в `oncl-update` на `ring` (Ed25519), `serde_json`, `sha2` и `time`, новых зависимостей он не добавил. TLS обеспечивает только rustls на ring. `aws-lc-*` на Unix разрешён, но в крейт обновлений не входит, иначе не собралась бы версия для Windows 7. Клиент блокирующий и работает поверх `oncl_pki::http::HttpTransport`.
