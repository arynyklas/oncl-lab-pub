# Сторонние издатели плагинов

Статус: код слит; впереди выпуск `0.1.3` с каталогом издателей, ротация корня и подключение первого издателя (раздел «Миграция и порядок выкладки»). Документ описывает, как сторонний издатель (вендор) выпускает плагины в каталог OpenNCALayer своей подписью, без подписи владельца на каждом выпуске. Механизм: делегированные роли TUF ([спецификация 1.0.37](https://theupdateframework.github.io/specification/latest/), разделы 4.5, 5.6 и 5.7) в том же репозитории `tuf/v1`, из которого клиенты получают индексы. Опирается на [`tuf.md`](tuf.md), [`update-index.md`](update-index.md) и [`plugins.md`](plugins.md) (жизненный цикл и каталог). Пункт плана: «сторонние издатели» в [`roadmap.md`](roadmap.md); в [`tuf.md`](tuf.md) раздел «Делегирования».

Места, которые не удалось проверить по коду или по документации, помечены «Открытый вопрос» и собраны в конце.

## Решения владельца

Р1. Издатель подписывает свою делегированную роль TUF (`targets`): записи каталога и хеши пакетов. Владелец делегирует один раз, дальше издатель выпускает без подписи владельца.

Р2. Издатель появляется только после одобрения владельца: PR с ключом, именем и пространством имён издателя, слияние делает владелец.

Р3. Издатель владеет префиксом идентификаторов плагинов (обратный домен, например `kz.ecc.`) и явным списком имён `module`, одобренным при подключении.

Р4. Издатель сам выбирает для каждой версии `beta` или `stable`. Сверка с оригиналом (`conformance`) к плагинам издателей не применяется.

Р5. Окно установки и окно «Плагины» показывают «Издатель: <имя>», наши порты: «Издатель: OpenNCALayer».

Р6. У издателя три состояния в `publishers.json`: `active`, `retired`, `revoked` (раздел «Состояния издателя»). `retired`: новых версий нет, установленные работают, кроме версий, отозванных владельцем или самим издателем до перевода. `revoked`: все плагины издателя выключаются у клиентов при следующей проверке каталога.

Р7. Сайт показывает плагины издателей с именем издателя.

Р8. Ключ `snapshot` репозитория `tuf/v1` уходит в CI (окружение GitHub `tuf-snapshot` и секрет, как у `timestamp`). Переход делается ротацией корня `tuf/v1`, выпуск клиента для него не нужен. `root` и верхний `targets` остаются офлайн.

Р9. Выпуск: издатель открывает PR в наш репозиторий со своим подписанным файлом роли. Если PR трогает только файлы этого издателя и проверки CI зелёные (подпись, префикс, модули, архив исходников, пересборка, лимиты), бот кладёт нашу пересборку и архив исходников в наши Releases и сливает PR сам.

Р10. Клиент скачивает пакеты издателей только из GitHub Releases нашего репозитория. Туда уходят байты пересборки нашего CI (они равны байтам издателя, иначе PR не сливается) и архив исходников, каждый пакет в своём неизменяемом выпуске `pub-<издатель>-<sha256>`. Адрес копии (`url`) вычисляется из подписанных полей; издатель знает его заранее и подписывает в роли.

Р11. Если издатель просит модули, которые обслуживает наш порт, решает владелец при подключении. Если одобрил, порт уходит из каталога, а клиентам с портом плагин издателя предлагается как обновление, с окном разрешений.

Р12. По умолчанию у издателя один ключ; несколько ключей и порог допускаются.

Р13. Инструменты издателя: `cargo xtask vendor …` в клоне нашего репозитория (ключ, архив исходников, сборка в эталонном образе, подпись роли, проверка) и переиспользуемый workflow `publisher-build.yml` для Actions издателя.

Р14. Отдельного репозитория `tuf/v2` нет. Делегирования и `publishers.json` лежат в верхнем `targets` репозитория `tuf/v1`, роли издателей — рядом с его метаданными.

Р15. Клиент `0.1.2` терпит член `delegations` в верхнем `targets` `tuf/v1`: обновления ядра и индекс работают, есть ли делегирования и можно ли их разобрать. Сами делегирования читает клиент, который умеет каталог издателей (ниже Y, первый такой выпуск). Делегирования появляются в `tuf/v1`, когда подключается первый настоящий издатель.

Р16. Клиенты младше `0.1.2` отвергают `targets` с делегированиями и после их появления в `tuf/v1` перестают обновляться. Таким установкам понадобится ручная переустановка; владелец это принял.

Р17. Издателя владелец проверяет вручную при одобрении подключения: владение доменом префикса, без автоматики `.well-known` или DNS и без подписи заявления ключом НУЦ.

Р18. Владелец может отозвать отдельные версии издателя своей записью в `publishers.json`, вплоть до всех его версий, не только издателя целиком.

Р19. Не больше одного выпуска издателя в час; CI проверяет это по истории git файлов издателя.

Р20. Разрешения плагина хранятся в подписанной записи каталога (`custom.oncl.capabilities`); сайт пакеты не скачивает.

Р21. CI до слияния скачивает архив исходников каждого нового пакета, проверяет его, пересобирает пакет в эталонном образе в песочнице без сети и сравнивает с подписанной целью байт в байт. На пересобранных байтах сверяет манифест (`id`, версия, модули, `min_core`) и равенство `custom.oncl.capabilities` разрешениям манифеста. Если хоть одна проверка не прошла, PR целиком не сливается автоматически. Пакет с адреса издателя не скачивается. Клиент сверяет пакет ещё раз при установке.

Р22. Казахская строка для «Издатель»: «Жариялаушы».

Р23. Версии крейтов SDK остаются общими с версией программы (`docs/dev/sdk.md`, раздел 6): ломающие изменения API `oncl-update` вышли в `0.1.2-beta.1` и входят в `0.1.2`, изменения `oncl-plugin` выходят в `0.1.3`. Каждая поломка описана заметкой о миграции.

Р24. Плановая ротация ключа издателя: новый ключ добавляется рядом со старым, издатель переподписывает роль, затем старый ключ убирается. xtask не убирает старый ключ, пока последний файл роли не подписан порогом новых ключей. При утечке ключа владелец переводит издателя в `retired` и отзывает версии через `revoked_versions`; по умолчанию все версии издателя, а не только выпущенные после утечки. Вернуть издателя в `active` с новым ключом может только владелец.

Р25. Если опубликованный снимок нельзя скачать или проверить, `tuf snapshot` останавливается. Флага обхода нет, исправление ручное по `docs/dev/release.md`.

Р26. Частота проверки каталога: раз в 1–3 часа, если установлен хоть один плагин издателя, иначе раз в 6–24 часа. Если версия снимка сменилась с прошлой применённой, каталог читается и применяется целиком. Отдельного ежечасного опроса `timestamp.json` нет.

Р27. Отдельная видимая настройка «Проверять отзывы плагинов», включена по умолчанию. При выключенных обновлениях клиент проверяет каталог по расписанию только с ней и только применяет отзывы.

Р28. Издатель, которого нет в проверенном `publishers.json`, недоступен, а не отозван. `tuf check` запрещает удалять записи из `publishers/`, так что пропажа записи означает ошибку инструментов.

Р29. Незнакомое клиенту значение `state` делает недоступным только этого издателя; остальной `publishers.json` читается. Правила такого издателя (префикс, модули, бандлы, порты из `supersedes`) остаются за ним, а отзывы версий владельцем действуют.

Р30. В репозитории включены неизменяемые выпуски GitHub (immutable releases). Каждый скопированный пакет издателя лежит в своём выпуске; бот создаёт его черновиком, прикладывает файлы, проверяет и только потом публикует, до слияния PR (раздел «Копии пакетов в наших Releases»).

Р31. Каждый выпуск издателя собран из опубликованного архива исходного кода; sha256 и длина архива подписаны в роли издателя. Лицензия плагина и его зависимостей, попадающих в wasm, из списка OSI (SPDX, `isOsiApproved`). Это обязательно для всех издателей.

Р32. Эталонная сборка: образ `ghcr.io/arynyklas/oncl-plugin-builder` по digest из `publishers/builders.toml` (Linux x86_64, тулчейн, tar и компрессор внутри). Издатель собирает в нём локально или нашим переиспользуемым workflow в своих Actions и подписывает хеш результата своим ключом. Наши порты переходят на тот же сборщик позже, отдельной работой.

Р33. Архив исходников — канонический `.src.tar.gz` по любому анонимному адресу HTTPS. Репозиторий git (`source.vcs`) необязателен: CI проверяет его, когда может, а сайт показывает его как подтверждённый или не проверенный; клиент его не показывает. SFTP не поддерживается. Списка разрешённых репозиториев издателя (`source_repos`) нет. Пока сайт не читает итог проверки 25 (он в `BUILDINFO.json` выпуска), он показывает репозиторий как «заявлено издателем» и ссылается на `BUILDINFO.json`.

Р34. `pull_request_target` использует только `publisher-pr.yml`; другие workflow его не используют.

Р35. Владелец никогда не подписывает отдельные выпуски издателей. Выпуск подписывает только ключ издателя; снимок и метку времени подписывает CI онлайн-ключами; офлайн-ключ `targets` владельца нужен при подключении, отзыве, `retired`, смене ключей издателя и ежемесячном продлении (таблица «Кто что подписывает»). Для этого до подключения первого издателя один раз проводится ротация корня `tuf/v1`, которая переводит ключ `snapshot` в CI (этап 2, Р8).

Р36. Окно установки и окно «Плагины» показывают у плагина издателя строку «Исходный код» со ссылкой на архив исходников в наших Releases и лицензией, и прямо говорят, что код OpenNCALayer не проверял.

Р37. `publishers.json` до 1 МиБ: не больше 128 издателей и не больше 8000 записей `revoked_versions` на всех вместе. Короткой формы «все версии до даты» нет: отзыв всегда явный список версий.

Р38. «Проверить сейчас» при выключенных обновлениях применяет только отзывы: выключает отозванные плагины и никогда не ставит и не обновляет версии.

Р39. Y — это `0.1.3`: `0.1.2` stable — повышенный `0.1.2-beta.1`, клиент каталога издателей выходит в `0.1.3`. `min_core` выпуска издателя не ниже `0.1.3` (проверка 6).

Р40. Список лицензий OSI — закреплённая копия списка SPDX в `xtask/assets/spdx/`, её обновляет ручной PR, когда нужно. Устаревшие идентификаторы SPDX и `LicenseRef-` (а с ними `DocumentRef-` и `AdditionRef-`) отвергаются везде, даже как один из вариантов `OR`, и в `source.license`, и у зависимостей.

Р41. `THIRD-PARTY.txt` содержит полные тексты лицензий каждой зависимости, попавшей в wasm, из её собственных файлов (`LICENSE*`, `LICENCE*`, `COPYING*`, `NOTICE*`, `UNLICENSE*`), взятых без сети. Крейт без такого файла — провал проверки 20: стандартный текст SPDX его не заменяет.

Р42. Изменение правил действует только на новые версии. `tuf check` сообщает о последних ролях, нарушающих сегодняшние правила PR, предупреждением `publisher-rules`, не ошибкой.

Р43. Проверка 25 идёт в отдельном контейнере с выходом только в интернет, без доступа к раннеру и его сетям, с выключенными перенаправлениями git.

Р44. SDK (`oncl-pdk`, `oncl-protocol` и остальная цепочка из `docs/dev/sdk.md`, раздел 7) не публикуется в crates.io. Издатель берёт его из нашего репозитория как git-зависимость с тегом выпуска (`git = "https://github.com/arynyklas/OpenNCALayer", tag = "v0.1.3"`), копировать SDK в свой архив не нужно. Считается только коммит, закреплённый в `Cargo.lock`: тег в `Cargo.toml` нужен для удобства, но тег можно передвинуть. Проверка 17 принимает из нашего репозитория только крейты SDK и только по адресу ровно `https://github.com/arynyklas/OpenNCALayer` со ссылкой `tag` или `rev` (ветку нельзя). Коммит должен быть в `publishers/sdk-revisions.toml` на `main`. В этот список шаг выпуска дописывает коммит нового тега (`cargo xtask sdk revision add v<версия>`). Записи списка не меняются и не удаляются, а `vendor check-onboarding --base` сверяет их с тегами: каждый тег из списка указывает на коммит одной из своих записей. Если ещё не опубликованный тег передвинули (исправление процесса выпуска), в конец добавляется вторая запись того же тега с новым коммитом, а прежняя остаётся: плагин мог уже закрепить её в `Cargo.lock`. Это допустимо, только если SDK в обоих коммитах одинаков. Сравниваются без checkout git-деревья `crates/<крейт>` для всех 12 крейтов цепочки (`sdk_delivery::CHAIN`) по id объекта и таблицы `[workspace.package]` и `[workspace.dependencies]` корневого `Cargo.toml`, которые эти крейты наследуют, как значения TOML. Остальное в корневом `Cargo.toml` (`[patch]`, `[profile]`, `members`) до git-зависимости не доходит. Так проверка 17 по-прежнему принимает оба коммита. `cargo fetch` клонирует наш репозиторий в `$CARGO_HOME/git` целиком; `oncl-pack fetch` ограничивает этот прирост 256 МиБ (на `v0.1.2` около 43 МБ).

Дополнительное требование владельца к коду: каждое решение по API, типам, ошибкам и тестам Rust следует навыку `rust-skills` (раздел «Типы и ошибки Rust» ниже).

## Что есть сейчас

Пути от корня репозитория.

- Клиентская библиотека делегирований слита (#86): `crates/oncl-update/src/tuf/delegation.rs` (`Delegations`, `DelegatedRole`, `RefusedRole`), `names.rs` (`PublisherName`, `RoleName`, `TargetPath`, `PathPattern`), `TufClient::delegated` и `TufClient::verify_cached_role` в `client.rs`, версии и хеши принятых ролей в `TrustState.delegated` (`store.rs`), векторы python-tuf `crates/oncl-update/tests/fixtures/tuf/delegated-*`.
- У клиента два профиля (`Profile` в `crates/oncl-update/src/tuf/model.rs`), по умолчанию `Delegating` (#101). `Profile::Legacy` отвергает любой член `delegations`, даже пустой (`TufError::Unsupported`); так ведут себя выпущенные `0.1.0` и `0.1.1`. `Profile::Delegating` не разбирает `delegations` при чтении `targets`: член необязателен, `Targets::delegations()` разбирает его по запросу, длину с sha256 снимок обязан указать только у записей ролей (`DelegationError::Unhashed`). Приложение создаёт клиента в профиле `Delegating` (`crates/openncalayer/src/repository.rs`).
- Один и тот же `refresh` нужен апдейтеру ядра (`crates/openncalayer/src/update.rs`, `INDEX_BASE` = `…/tuf/v1`) и каталогу плагинов (`repository.rs`). С `0.1.2` он от делегирований не зависит: `targets` с ними, без них или с нечитаемым членом `delegations` обновлений ядра не останавливает.
- xtask для одного репозитория `tuf/v1` (шаг 6 плана): реестр издателей `xtask/src/publishers.rs` (`publishers/<имя>/publisher.toml` → `delegations` и `publishers.json` в верхнем `targets`, как только в реестре есть запись; состояния `active`, `retired`, `revoked`; `revoke_all` и перевод в `retired` `tuf update` разворачивает в `revoked_versions` самого `publisher.toml`); проверки ролей, снимка и реестра в `xtask/src/tuf/check.rs`; режим снимка в `tuf/v1.toml` (файла нет, значит `offline`); `tuf snapshot` с обязательным `--previous` и `tuf root --rotate-snapshot --online`. Код `tuf/v2` (`--repo`, `check_v2.rs`, вектор `cross-repo`) удалён. В `publishers/` пока только `builders.toml` без записей, `tuf/v1.toml` нет: издателей нет, снимок офлайн.
- Каталог (`crates/oncl-update/src/catalog/*`, #94, #102): `PublisherPolicy`, `PublisherRelease`, `DeclaredCapabilities`, `Catalog`, правила старшинства, состояния издателя, `choose_plugin` на `&Catalog`. Подключён к приложению (пункт «Клиент Y, приложение» ниже).
- Библиотека клиента Y (шаг 8 плана): `TryFrom<&DeclaredCapabilities> for Capabilities` в `crates/oncl-plugin/src/manifest.rs` (те же правила, что у таблицы `[capabilities]` манифеста, `builtin` запрещён); `CatalogBuilder::capabilities` отбрасывает запись, чьи `capabilities` не читаются (`EntryRejection::CapabilitiesUnreadable`); `Catalog::publisher_state_of`, `Catalog::is_installed_revoked` и `choose_installed` (`crates/oncl-update/src/plugins.rs`) учитывают издателя, записанного при установке, и издателя по префиксу (шаг 1 раздела «Отзыв»); собственные отзывы ролей учитываются по издателю. Хранилище плагинов (`crates/oncl-plugin/src/store.rs`): `Installed.publisher`, `Store::install(.., publisher)`, `set_publisher`, `StoreState.declined_replacements` и `set_declined_replacement`, `save_publishers`/`load_publishers`, `save_role`/`load_roles`/`prune_roles` (временные файлы записи `*.tmp` не трогает). `PublisherName` (де)сериализуется строкой с проверкой.
- Клиент Y, приложение (шаг 9 плана): `Repository::catalog` (`crates/openncalayer/src/repository.rs`) после `refresh` с новой версией снимка читает индекс, `publishers.json` (не больше `PublisherPolicy::MAX_LEN`) и роли (`TufClient::delegated`), на них плановой проверке и пользователю даётся ещё `PUBLISHERS_TIMEOUT` (120 с), странице нет; сбой стороны издателей индекс не трогает и пишется в журнал один раз, пока не изменится. Сохранённое проверяется без сети: `Repository::verify_kept_publishers`, `verify_kept_role` и `kept_top_level` (`TufClient::verify_cached_top_level`, верхний `targets` с делегированиями). `crates/openncalayer/src/plugins/catalog.rs` собирает `Catalog` из проверенного: верхние цели, встроенные модули, `CatalogBuilder::capabilities` через `Capabilities::try_from`, при нечитаемых делегированиях `CatalogBuilder::delegations_unavailable` (все издатели недоступны, отзывы владельца действуют). Если `publishers.json` не скачался, берётся сохранённый, когда его байты и есть нынешняя цель. Роли пишутся `save_role` и чистятся `prune_roles` одной проверкой за раз (блокировка `checking`). `apply_index` выбирает версию через `choose_installed` с записанным издателем, восстанавливает его по префиксу (`set_publisher`), а `PublisherRevoked` выключает плагин с уведомлением `PluginNotice::PublisherRevoked`. Установка записывает издателя; `check_manifest` сверяет `capabilities` записи с манифестом (несовпадение помечает версию плохой); согласие на установку из каталога применяется под `changing`, только если каталог в использовании всё ещё предлагает ту же версию с тем же пакетом (`still_offered`). При старте `Store::prune_files` удаляет пакеты и настройки, которых нет у установленных плагинов (их мог оставить сбой между записью состояния и удалением файлов). Частота: раз в 1–3 часа с установленным плагином издателя, иначе 6–24 часа (`catalog::check_every`); плановая проверка, которая застаёт снимок последнего каталога, прочитанного целиком и применённого в этом запуске так, что каждый плагин пришёл к выбранному состоянию (без ошибки загрузки, плохой версии, нового ожидания согласия), ничего больше не читает. При выключенных обновлениях «Проверить сейчас» применяет только отзывы (`Apply::RevocationsOnly`, `Apply::with_updates`); проверка по расписанию делает то же, пока включена настройка «Проверять отзывы плагинов» (`UpdateSettings::check_revocations`), а без неё к репозиторию не обращается (`Apply::scheduled` даёт `None`). Замена порта (Р11): `PluginService::replacements` берёт `Catalog::replacement` для каждого порта, установленного из каталога (версия `Q` не плохая, `Q` ещё не установлен и не отложен неудачной загрузкой). Такой порт в `apply_index` получает только отзывы; при `Apply::Full` и без отказа от этого `Q` (`StoreState.declined_replacements`) `Q` скачивается, проверяется и предлагается в окне установки как замена (`InstallRequest::replaces_port`, в окне `RequestKind::ReplacePort`). Согласие (`finish_replacement`, под `changing`) применяется, только если `P` не изменился, обновления включены и каталог в использовании всё ещё предлагает для `P` ту же версию `Q` с тем же пакетом (`still_replacing`); иначе ничего не меняется и отказ не записывается. Тогда `P` выгружается, `Q` загружается (только проверяется, если `P` выключен); не загрузился — `P` загружается снова, версия `Q` помечается плохой (если модуль занят другим плагином — нет), и весь `Q` (любая его версия) больше не предлагается до смены плагинов; загрузился — `Store::replace` одной записью состояния ставит `Q` с издателем и включённостью `P`, забывает `P` и отказ, затем удаляет пакет и настройки `P`, а в трее «Порт заменён» (`PluginNotice::PortReplaced`). `Store::replace` отказывает (`AlreadyExists`), если `Q` уже установлен. Отказ («Не сейчас», закрытое окно или окно, которое нельзя показать) записывается `set_declined_replacement`; строка «Доступна замена от издателя …» в окне «Плагины» (`InstalledView::replacement`, только при включённых обновлениях) и `PluginService::replace_port` предлагают замену снова. `Q`, который заменяет установленный порт (включённый, выключенный, отозванный или не загрузившийся), не показывается в «Доступно», не называется в `PluginNotice::Needed` и не ставится рядом с портом ни из окна (`install_from_catalog`), ни по `installBundle` страницы. `Store::remove` порта забывает и отказ от его замены.
- `Store::prune_files` при старте не трогает файлы, изменённые за последние `Store::PRUNE_AFTER` (10 минут): пакет, который `oncl plugin install` в другом процессе уже записал, а состояние с ним ещё не сохранил, остаётся.
- `tuf/v1` сегодня: корень версии 1 (порог 1), `targets` и `snapshot` версии 7, снимок подписан офлайн на 30 дней и перечисляет `targets.json` с длиной и sha256, `timestamp` подписывает CI на 7 дней (`pages.yml`, job `timestamp`). Job `snapshot` в `pages.yml` уже есть (шаг 7 плана), но пока `tuf/v1.toml` нет, ничего не делает.
- Пакеты плагинов целями TUF не являются: клиент берёт `url`, `size` и `sha256` из записи индекса или из цели роли издателя (`PluginService::download` в `crates/openncalayer/src/plugins.rs`), затем сверяет манифест. Порты лежат в наших Releases под тегами `plugins-YYYYMMDD` (`plugins.yml`).
- `choose_plugin` и `choose_installed` не трогают плагин, версии которого нет в каталоге (`crates/oncl-update/src/plugins.rs`). Пропажа записи не отзыв, поэтому отзыв издателя распознаётся явно.
- Запись установленного плагина: `Installed { version, sha256, source, enabled, withdrawn, publisher }` (`crates/oncl-plugin/src/store.rs:53-75`), `Source` только `Catalog | Local` (`store.rs:95-103`), без `deny_unknown_fields`. Издателя, имя которого эта версия не принимает, она читает как `None` (журнал `warn`), не теряя остального состояния.
- Путь отзыва: `PluginChoice::Withdrawn` и `PluginChoice::PublisherRevoked` выгружают плагин, пишут `withdrawn` и сообщают `PluginNotice::Withdrawn` или `PluginNotice::PublisherRevoked` (`PluginService::withdraw` в `crates/openncalayer/src/plugins.rs`).
- При выключенных обновлениях и включённой настройке «Проверять отзывы плагинов» клиент проверяет каталог по тому же расписанию и применяет только отзывы (`PluginService::scheduled_check`); с выключенной настройкой по расписанию не проверяет. Настройки обновлений: `UpdateSettings` (`enabled`, `channel`, `check_revocations`) в `crates/oncl-desktop/src/settings.rs`; флажок в окне настроек (`crates/oncl-ui/ui/settings.slint`).

## Обзор схемы

Один репозиторий `tuf/v1`. Цепочка доверия клиента Y:

```
встроенный root v1 (версия 1)
  → корни v1 N+1, N+2, …
    → timestamp (CI) → snapshot (CI после ротации корня, до неё офлайн) → верхний targets (офлайн, владелец)
         ├─ indexes/<канал>.json  → индекс владельца → пакеты портов (sha256 + size из индекса)
         ├─ publishers.json       → правила издателей (префиксы, модули, имена, состояния, отзывы версий)
         └─ delegations: pub-<издатель> (ключи издателя, paths plugins/<издатель>/*/*)
              → роль pub-<издатель> (подпись издателя) → пакет (length + sha256 цели) из наших Releases
```

Апдейтер ядра проходит только `root → timestamp → snapshot → targets` и член `delegations` не читает. Клиенты `0.1.2` и новее читают такой `targets` и без делегирований, и с ними. Клиенты `0.1.0` и `0.1.1` читают его, пока делегирований нет.

Выкладка идёт этапами (подробно в разделе «Миграция и порядок выкладки»):

1. `0.1.2` терпит `delegations`. В `tuf/v1` ничего не меняется.
2. Ротация корня `tuf/v1`: ключ `snapshot` уходит в CI. Старые клиенты проходят её обычным путём.
3. Выпуск Y с каталогом издателей.
4. Подключение первого издателя: в верхнем `targets` появляются `delegations` и `publishers.json`. С этого момента клиенты младше `0.1.2` не обновляются.

## Раскладка TUF

### Файлы `tuf/v1`

| Путь | Что | Кто подписывает | В git |
|---|---|---|---|
| `metadata/<N>.root.json` | корень, все версии | `root`, офлайн | да |
| `metadata/<N>.targets.json` | верхний `targets` | `targets`, офлайн | да |
| `metadata/<N>.pub-<издатель>.json` | делегированная роль издателя, все версии | ключи издателя | да |
| `metadata/<N>.snapshot.json` | снимок | до ротации: `snapshot` офлайн, `N` подряд; после: `snapshot` в CI, `N` = `max(Unix-время подписи, предыдущая + 1)` | до ротации да, после нет (артефакт Pages) |
| `metadata/timestamp.json` | как сейчас | `timestamp`, CI | нет |
| `targets/indexes/<sha256>.<канал>.json` | индекс владельца | | да |
| `targets/<sha256>.publishers.json` | правила издателей | | да, с этапа 4 |

Режим снимка записан в `tuf/v1.toml` рядом с репозиторием (`snapshot = "offline"` или `"online"`, файла нет = `offline`). Его меняет PR ротации корня. Pages этот файл не публикует: копируется только `tuf/v1/`.

Имя делегированного файла `<версия>.<роль>.json` следует разделу 3.1.2.1 и правилу согласованных снимков (6.2): `layout::delegated_path` (`crates/oncl-update/src/tuf/layout.rs`).

Пакеты издателей в репозитории TUF не лежат: цели `plugins/…` описывают байты пакета, а лежат они в наших Releases (Р10).

### Роли и имена

- Имя издателя (`PublisherName`): `^[a-z0-9][a-z0-9-]{1,30}[a-z0-9]$`. Зарезервированы `openncalayer`, `oncl`, `owner`, `builtin`, `port`, `ports`, `root`, `targets`, `snapshot`, `timestamp`.
- Имя роли (`RoleName`): ровно `pub-<имя издателя>`. Строится только из `PublisherName`, разбирается обратно в него. Совпасть с именем верхней роли не может.
- Делегирования одного уровня: роль издателя дальше не делегирует (клиент отвергает `delegations` в роли издателя).

### Делегирование в верхнем `targets`

```json
"delegations": {
  "keys": {
    "<keyid>": {"keytype": "ed25519", "scheme": "ed25519", "keyval": {"public": "<64 hex>"}}
  },
  "roles": [
    {
      "name": "pub-ecc",
      "keyids": ["<keyid>"],
      "threshold": 1,
      "paths": ["plugins/ecc/*/*"],
      "terminating": true
    }
  ]
}
```

Член `delegations` появляется не сразу. Пока `publishers/` пуст, `tuf update` не пишет `delegations` и `publishers.json`, и `tuf/v1` читают все выпущенные клиенты. Первая запись в `publishers/` (этап 4) добавляет оба. Записи из `publishers/` не удаляются (Р28), поэтому `delegations` после появления остаётся навсегда, даже пустой: `{"keys": {}, "roles": []}`. `tuf check` следит за обоими правилами.

Правила профиля (xtask не даёт записать иное; клиент Y проверяет при чтении):

- `delegations` разбирается только в шаге каталога (`TufClient::delegated`). Если член не разбирается целиком (не тот тип поля, `keyid` не равен хешу ключа, ключ не Ed25519, имя роли не `pub-…`, повтор имени), все издатели недоступны, а ядро и индекс владельца работают дальше. Отзывом это не считается.
- `paths` ровно `["plugins/<имя>/*/*"]`, где `<имя>` берётся из имени роли. Шаблон в смысле раздела 4.5: `*` не пересекает `/`. `path_hash_prefixes` отвергается. Роль с другой формой шаблона недоступна.
- `terminating: true` у каждой роли. Пути ролей не пересекаются по построению, поэтому порядок ролей в массиве не важен, и обход шага 5.6.7 сводится к одной роли на путь.
- `keyid` каждого ключа пересчитывается из ключа, как в корне. Ключ издателя не совпадает ни с одним ключом корня, ни с ключом другого издателя.
- `threshold` от 1 до числа `keyids` (Р12); дубликаты `keyids` отвергаются.
- Имена ролей уникальны (раздел 4.5 требует того же).
- Не больше 32 ролей (`Limits::max_delegations`).
- Роль есть ровно у издателей `active`. У `retired` и `revoked` xtask роль снимает. При переводе в `retired` `tuf update` сначала переносит в `revoked_versions` каждую цель последней роли издателя с `revoked: true` (дата: день перевода), поэтому отзывы самого издателя переживают снятие роли.

Нарушение правила одной роли делает недоступной только эту роль (`RefusedRole`).

### Цели издателя

Путь цели: `plugins/<издатель>/<id>/<версия>.onclp`. `<id>` и `<версия>` взяты из пути однозначно: разделитель `/` в них невозможен (`id` из `[a-z0-9.-]`, версия из `[0-9A-Za-z.-]`). Метаданных сборки semver (`+…`) у версий издателей нет: CI и клиент такую запись отвергают, потому что GitHub переименовывает файлы выпуска с особыми символами в имени, а версии, различные только метаданными сборки, равны по старшинству semver.

```json
"plugins/ecc/kz.ecc.market/1.2.0.onclp": {
  "length": 123456,
  "hashes": {"sha256": "<64 hex>"},
  "custom": {
    "oncl": {
      "schema": 1,
      "id": "kz.ecc.market",
      "version": "1.2.0",
      "url": "https://github.com/arynyklas/OpenNCALayer/releases/download/pub-ecc-<64 hex>/kz.ecc.market-1.2.0.onclp",
      "source": {
        "archive_sha256": "<64 hex>",
        "archive_length": 2345678,
        "fetch": "https://downloads.ecc.kz/oncl/kz.ecc.market-1.2.0.src.tar.gz",
        "path": "crates/market",
        "license": "Apache-2.0",
        "builder": "sha256:<64 hex>",
        "vcs": {"url": "https://git.ecc.kz/oncl/market.git", "rev": "<40 hex>"}
      },
      "channel": "stable",
      "min_core": "0.1.3",
      "modules": ["kz.ecc.market.Signer"],
      "replaces": {"symname": "kz.ecc.market", "version": "1.2.0"},
      "name": {"ru": "…", "kk": "…", "en": "…"},
      "capabilities": {"keys": true, "http": ["https://api.ecc.kz/"]},
      "rollout": 100,
      "revoked": false
    }
  }
}
```

Поля `custom.oncl` повторяют запись `plugins[]` индекса ([`update-index.md`](update-index.md), таблица полей), с отличиями:

- `size` и `sha256` не повторяются: это `length` и `hashes.sha256` самой цели.
- `id` и `version` обязаны совпасть с путём цели.
- `url` — копия пакета в наших Releases (Р10, Р30), ровно `https://github.com/arynyklas/OpenNCALayer/releases/download/pub-<издатель>-<sha256>/<id>-<версия>.onclp`, где `<sha256>` — 64 строчные шестнадцатеричные цифры `hashes.sha256` цели, а `<id>` и `<версия>` из пути цели. Другую форму клиент отвергает (запись отбрасывается). Адрес вычисляется из подписанных полей, поэтому издатель знает его до подписи, а одни и те же байты всегда попадают в один и тот же выпуск.
- `channel`: `beta` или `stable` (Р4). `stable` предлагается клиентам обоих каналов, `beta` только каналу `beta`. Предварительная версия semver с `stable` отвергается.
- `source` — архив исходников, из которого собран пакет (Р31, Р33): обязателен у каждой цели издателя. Поля и правила — раздел «Открытые исходники и проверяемая сборка», «Поле `source`». Подпись роли покрывает `source` вместе с `length` и `hashes` пакета: издатель утверждает, что эти байты — сборка этого архива этим сборщиком.
- `revoked` один на версию, не на канал.
- `capabilities` (Р20): таблица `[capabilities]` манифеста пакета в JSON, те же ключи и правила, что в `plugin.toml` ([`plugins.md`](plugins.md), раздел «Capabilities»). Её заполняет `vendor add` из манифеста. CI требует, чтобы поле было равно разрешениям манифеста (Р21). Клиент сверяет то же при установке и обновлении, рядом с `check_manifest` (`crates/openncalayer/src/plugins.rs:1448`).
- `min_core` не ниже Y, то есть `0.1.3` (решение владельца: `0.1.2` stable — это повышенный `0.1.2-beta.1`, клиент каталога издателей выходит в `0.1.3`; константа `MIN_CORE` в `xtask/src/vendor/mod.rs`).
- Незнакомые поля внутри `oncl` клиент пропускает, CI их отвергает. `schema` выше 1 клиент не читает: такая запись пропускается. Новые возможности добавляются полями при `schema = 1`.

### `publishers.json`

Цель верхнего `targets`, подписана владельцем. Нужна потому, что `paths` не выражают права на модули и бандлы, а у издателя без делегирования роли нет.

```json
{
  "schema": 1,
  "publishers": [
    {
      "name": "ecc",
      "state": "active",
      "display": {"ru": "ТОО «…»", "kk": "…", "en": "…"},
      "id_prefix": "kz.ecc.",
      "modules": ["kz.ecc.market.Signer"],
      "bundles": ["kz.ecc.market"],
      "supersedes": {"io.github.arynyklas.openncalayer.port.market": "kz.ecc.market"},
      "revoked_versions": [{"id": "kz.ecc.market", "version": "1.1.0", "date": "2027-02-10"}],
      "homepage": "https://ecc.kz/"
    },
    {
      "name": "leaked",
      "state": "retired",
      "display": {"ru": "…", "kk": "…", "en": "…"},
      "id_prefix": "kz.leaked.",
      "modules": ["kz.leaked.Signer"],
      "bundles": [],
      "revoked_versions": [
        {"id": "kz.leaked.sign", "version": "1.0.0", "date": "2027-04-01"},
        {"id": "kz.leaked.sign", "version": "1.1.0", "date": "2027-04-01"}
      ]
    },
    {
      "name": "old",
      "state": "revoked",
      "display": {"ru": "…", "kk": "…", "en": "…"},
      "id_prefix": "kz.old.",
      "revoked": "2027-03-01"
    }
  ]
}
```

- `state`: строка `active`, `retired` или `revoked` (раздел «Состояния издателя»). Незнакомая строка делает недоступным только этого издателя (Р29), клиент пишет `warn` с именем и значением (не длиннее 32 символов). Правила такого издателя (префикс, модули, бандлы, `supersedes`, `revoked_versions`) разбираются так же строго, как у активного, и ошибка в них делает недействительным весь файл. Член `state` без значения или не строкой — ошибка разбора всего файла. Владелец такую запись выпустить не может: `tuf check` и `tuf update` принимают только три значения, так что опечатка в `publisher.toml` не доходит до подписи.
- Записи вечные: издатель в любом состоянии остаётся в файле. По префиксу клиент узнаёт плагины издателя, даже если запись установки потеряла его имя, а владелец не выдаст тот же префикс другому по ошибке.
- `retired` и издатель с незнакомым `state` сохраняют свои правила: префикс, модули, бандлы и порты из `supersedes` остаются за ними, и никто другой их не займёт. Сама замена порта у них не действует.
- `bundles`: разрешённые `replaces.symname` (по аналогии с модулями Р3; список может быть пустым).
- `supersedes`: порты, которые заменяет издатель (Р11), порт → идентификатор плагина издателя под его префиксом; один плагин заменяет не больше одного порта (клиент заменяет порт одним плагином одной записью). Замена действует только у `active`.
- `revoked_versions` (Р18): версии издателя, которые отозвал владелец. Для клиента такая версия отозвана, что бы ни писал издатель в своей роли. Запись под чужим префиксом делает файл недействительным. Форма одна, явный список (Р37): «все версии» xtask разворачивает в записи по истории ролей в git (раздел «Подключение издателя»), так что клиенту не нужно понимать шаблон. Запись занимает около 100 байт, поэтому 8000 записей укладываются в лимит файла; `tuf update` отказывает, если выходит за любой из лимитов.
- Не больше 128 издателей и 8000 записей `revoked_versions`, файл до 1 МиБ (Р37).

Клиент проверяет файл целиком: префиксы не вложены друг в друга и не лежат под `io.github.arynyklas.openncalayer.`; модули, бандлы и порты из `supersedes` двух издателей (кроме `revoked`) не пересекаются, причём модули и бандлы сравниваются без учёта регистра; порт из `supersedes` не лежит под префиксом ни одного издателя, а плагин из `supersedes` не заменяет двух портов; ни один модуль не встроенный. Нарушение, `schema` не 1 или файл не разбирается: все издатели недоступны, индекс владельца работает дальше.

Сверка с `delegations` (PR #94, `check_delegations`): у каждого `active` есть роль; роль есть только у издателя, который назван в файле и не `revoked`. У `retired` и у издателя с незнакомым `state` роль может быть или не быть (xtask у `retired` её снимает, перенеся отзывы издателя в `revoked_versions`; клиент терпит оба случая). Роль издателя, которого нет в файле или который `revoked`, и `active` без роли означают ошибку инструментов: все издатели недоступны.

### Снимок

Снимок перечисляет `targets.json` и каждую роль `pub-*`, файл которой хоть раз был в git, с `version`, `length` и `hashes.sha256`. Роль `retired` и `revoked` издателя остаётся в снимке навсегда с последней версией: раздел 5.5.5 и наш клиент (`client.rs:591-611`) считают пропавшую запись откатом. Клиент эту роль не скачивает, если её нет в `delegations`.

xtask пишет длину и хеш у каждой записи. Клиент требует их только у записей ролей: роль без них недоступна. У `targets.json` клиент их не требует, чтобы ошибка в этой части не задела ядро.

## Почему один репозиторий

Делегирования лежат в `tuf/v1`, а не в отдельном репозитории со своим корнем. Отдельный репозиторий понадобился бы только потому, что выпущенные `0.1.0` и `0.1.1` отвергают `targets` с `delegations` на шаге 5.6 и перестают обновляться. Онлайн-снимок и смена ключей делаются ротацией корня `tuf/v1`, а её выпущенные клиенты поддерживают ([`tuf.md`](tuf.md)).

`0.1.0` и `0.1.1` вышли несколько дней назад (индексы `0.1.1` подписаны 2026-11-18). Поэтому клиент `0.1.2` учится терпеть `delegations`, обновления доносят его до живых установок за дни, а делегирования появляются в `tuf/v1` только с первым настоящим издателем.

Что это убирает: второй офлайн-корень и вторую церемонию; смену встроенного анкера (ошибка в нём отрезала бы клиента от обновлений навсегда); двойные ежемесячные подписи и двойную ротацию `targets`; атаку «файлы одного репозитория поданы клиенту другого»; сверку индексов двух репозиториев; вопрос, когда закрывать `tuf/v1`.

Цена (Р16): установки младше `0.1.2`, которые не обновились к этапу 4 (обновления выключены, машина долго не включалась, сборка без самообновления), остаются без обновлений ядра и, после срока сохранённого `targets`, без каталога. Нужна ручная переустановка.

## Каталог

### Как он собирается

Каталог клиента Y: индекс владельца канала плюс записи издателей, приведённые к `PluginRelease` (`crates/oncl-update/src/plugins.rs`, PR #94).

| `custom.oncl` / цель | `PluginRelease` |
|---|---|
| `id`, `version` (равны пути) | `id`, `version` |
| `url`, `length`, `hashes.sha256` | `package.url`, `package.size`, `package.sha256` |
| `min_core`, `modules`, `replaces`, `name`, `rollout`, `revoked` | одноимённые поля; `revoked` ещё и `true`, если версия есть в `revoked_versions` издателя |
| `channel` | фильтр: запись входит, если `stable`, или если канал клиента `beta` |
| имя роли | поле `publisher: Option<PublisherName>` с `#[serde(skip)]`: из JSON индекса его не прочесть, так что индекс владельца не может выдать порт за плагин издателя |
| `capabilities` | поле `capabilities: Option<DeclaredCapabilities>` с `#[serde(skip)]`; у портов `None`, у плагинов издателей обязательно. Разбирает его в `oncl_plugin::Capabilities` код каталога через `TryFrom<&DeclaredCapabilities>`; не разобралось: запись отбрасывается |
| `source` | в `PluginRelease` не переносится; клиент только проверяет его форму. Адрес архива для окна установки вычисляется из `url`: тот же выпуск, файл `<id>-<версия>.src.tar.gz` |

Порядок старшинства, если источники расходятся. Слово владельца сильнее слова издателя, как в предпорядковом обходе шага 5.6.7.

1. Отзыв версии владельцем (Р18): версия из `revoked_versions` отозвана, даже если роль издателя пишет `revoked: false`. Действует при издателе `active`, `retired` и недоступном. Снять отзыв может только владелец. Целей `plugins/…` в верхнем `targets` нет: xtask их не пишет, а клиент, встретив такую цель, считает все издатели недоступными.
2. Тот же `id` в индексе владельца и у издателя: выигрывает индекс владельца (журнал, `warn`). xtask не даёт владельцу добавить в индекс `id` под префиксом издателя, так что это защита от ошибки.
3. Модуль или `replaces.symname` у записи владельца и у записи издателя: выигрывает владелец. Исключение: порт, заменённый издателем (`supersedes` активного издателя), см. «Замена порта».
4. Между издателями конфликтов нет по построению: префиксы, модули и бандлы не пересекаются, а запись издателя вне его префикса, модулей или бандлов отбрасывается.

Запись издателя отбрасывается (журнал `warn`, остальные записи роли живут), если `id` не под префиксом издателя, модуль не из его списка, `replaces.symname` не из `bundles`, модуль встроенный, `id` под `io.github.arynyklas.openncalayer.`, `id`/`version` не совпали с путём, версия с `+`, `url` не копия в наших Releases с хешем этой цели, `source` нет или он не проходит правила таблицы «Поле `source`» (`EntryRejection::Source`), `rollout` больше 100, модулей нет или больше 32, `stable` у предварительной версии, `capabilities` нет или они не разбираются по правилам манифеста.

### Состояния издателя

Для каждого издателя каталог знает одно из четырёх состояний (`PublisherState`, PR #94):

| Состояние | Когда | Что с плагинами |
|---|---|---|
| активен (`Active`) | `state = "active"`, роль скачана и проверена | записи в каталоге: установка, обновления, отзывы |
| на покое (`Retired`) | `state = "retired"` | новых версий нет, ничего не предлагается для установки; установленные работают, кроме отозванных версий (такие выключаются, `Withdrawn`) |
| недоступен (`Unavailable`) | роль, `publishers.json` или `delegations` не скачались или не прошли проверку; `state` незнакомый (Р29); издателя нет в проверенном `publishers.json` (Р28) | не обновляются, ничего не предлагается; выключаются только отозванные версии, если `publishers.json` проверен |
| отозван (`Revoked`) | проверенный `publishers.json` пишет `state = "revoked"` | все плагины издателя выключаются (`PublisherRevoked`) |

Отзыв решается только по проверенным верхнему `targets` и `publishers.json` (свежим или сохранённым и проверенным заново офлайн). Ошибка сети или подписи никогда не отзывает.

Отозванная версия здесь: версия из `revoked_versions` владельца или, если роль издателя всё ещё делегирована и проверена, цель этой роли с `revoked: true`. У `retired` роли нет: его собственные отзывы `tuf update` переносит в `revoked_versions` при переводе. Роль без права выпуска может остаться только у издателя с незнакомым `state`; клиент читает из неё лишь отозванные цели. У недоступного по ошибке роли или `publishers.json` действует только то, что удалось проверить.

## Клиент

### Профиль репозитория

`TufClient` получает профиль `Profile::{Legacy, Delegating}`:

- `Legacy`: модель выпущенных `0.1.0` и `0.1.1`. `delegations` в `targets` отвергаются. Им пользуется xtask, чтобы сказать, читают ли выпущенные клиенты дерево, и тесты, которые закрепляют это поведение.
- `Delegating`: клиент `0.1.2` и новее, приложение создаёт клиента только так. Член `delegations` необязателен и при чтении `targets` не разбирается: `Targets` хранит его как подписан, а `Targets::delegations()` разбирает по запросу. Длину и хеш в снимке профиль требует только у записей ролей.

### Шаги

Шаги 5.1–5.6.6 не меняются. Апдейтер ядра делает только их (`refresh`) и делегированные роли не скачивает.

Шаг каталога, `TufClient::delegated(&mut self, trusted: &Trusted, now) -> Result<Delegated, TufError>`, его зовёт `Repository` каталога после `refresh`:

1. `delegations` верхнего `targets`: члена нет — ноль ролей; не разбирается — ошибка шага, все издатели недоступны.
2. Скачать цель `publishers.json` (`download_target`, лимит 1 МиБ) и разобрать её в `PublisherPolicy`. Ошибка: все издатели недоступны. Это делает код каталога в приложении, не `TufClient`.
3. Обойти `delegations.roles` по порядку (раздел 5.6.7: предпорядок, верхний `targets` уже пройден). Для каждой роли, не больше `max_delegations` (32):
   1. Роль с уже встреченным именем пропускается (защита от циклов из 5.6.7.1).
   2. Профиль роли: имя `pub-<имя>`, `paths`, `terminating`, ключи. Нарушение: роль недоступна.
   3. Запись `pub-<имя>.json` в проверенном снимке обязательна и с длиной и sha256. Нет: роль недоступна.
   4. Скачать `metadata/<версия>.pub-<имя>.json` не длиннее указанной в снимке длины (и не длиннее `Limits::delegated`, 128 КиБ), сверить длину и sha256 до подписи (как 5.6.2).
   5. Подпись: порог `threshold` различных `keyid` из `keyids` роли, ключи из `delegations.keys`; ключ корня в роли не годится.
   6. `_type` равен `targets`; `version` равна версии из снимка (5.6.4) и не меньше сохранённой; срок не истёк (5.6.5); члена `delegations` нет (глубина 1).
   7. Каждая цель роли подходит под её `paths`. Цель вне путей: роль недоступна целиком. Спецификация лишь не доверяет такой цели; мы строже, потому что CI такой файл не сольёт.
   8. Сохранить версию роли и sha256 принятого файла (5.6.6) и вернуть проверенную роль.
4. Ошибка одной роли не трогает другие и не трогает индекс владельца. Ошибка записи состояния (`TufError::Store`) обрывает весь шаг.

Отличие от спецификации, записанное в комментарий модуля `client.rs`: шаг 5.6.7 ищет одну цель, а каталогу нужен список всех целей всех издателей. Клиент проходит все делегированные роли с теми же ограничениями; при непересекающихся терминальных делегированиях это даёт для любого пути тот же ответ, что поиск 5.6.7.

5.7 для пакетов издателей делает приложение, как сегодня для пакетов индекса: HTTPS по `url` (наши Releases), длина и sha256 из цели TUF, затем `Package::read`, `check_manifest` и сверка `capabilities` записи с манифестом. Ошибка сети (`Download::Unreachable`) повторяется при следующей проверке; несовпавшие длина, sha256, манифест или разрешения помечают версию плохой (`Download::Bad`). Пока замена не установлена (ошибка сети, плохая версия, ждёт согласия пользователя), отозванная установленная версия выключена; неотозванная работает дальше.

### Когда клиент проверяет каталог

| Обновления | «Проверять отзывы плагинов» | Плагин издателя установлен | Проверка | Что применяется |
|---|---|---|---|---|
| вкл. | (вкл., не меняется) | да | раз в 1–3 часа | всё: установка, обновления, отзывы |
| вкл. | (вкл., не меняется) | нет | раз в 6–24 часа | всё |
| выкл. | вкл. (по умолчанию) | да | раз в 1–3 часа | только отзывы |
| выкл. | вкл. | нет | раз в 6–24 часа | только отзывы |
| выкл. | выкл. | любой | по расписанию нет; только «Проверить сейчас» | по кнопке только отзывы (Р38) |

Срок выбирается случайно внутри интервала. Каждая проверка — обычный `refresh` (`timestamp`, `snapshot`, `targets`). Если версия снимка равна версии при прошлом применённом каталоге, на этом всё. Если другая, клиент читает индекс, `publishers.json` и роли и применяет каталог (Р26). Снимок переподписывается на каждой публикации Pages (раз в сутки и после каждого слияния), так что полное чтение бывает не реже раза в сутки.

Настройка «Проверять отзывы плагинов» (Р27): `UpdateSettings.check_revocations: bool`, по умолчанию `true`, в окне настроек под переключателем обновлений. При включённых обновлениях флажок показан включённым и неактивным с подсказкой «Входит в автообновления». Подсказка под флажком: «Раз в несколько часов OpenNCALayer обращается к arynyklas.github.io и выключает плагины, которые отозвал их издатель или OpenNCALayer. Новые версии при этом не устанавливаются.» Те же сетевые запросы описаны в документации о приватности.

### Состояние

- TUF: прежние `<data>/update/tuf/state.json` и `lock`. `TrustState.delegated` (версия и sha256 принятого файла каждой роли) уже есть (#86), с `default` и `skip_serializing_if`. Клиент `0.1.2` его не пишет. Ротация ключей `snapshot`/`timestamp`/`targets` корнем забывает и `delegated` (`client.rs`, те же правила, что для версий верхних ролей).
- `TrustState` объявлен с `deny_unknown_fields`, а `0.1.0`/`0.1.1` поля `delegated` не знают. Установка, откаченная проверкой здоровья с Y прямо на `0.1.1`, не прочтёт состояние и начнёт с встроенного корня; после этапа 4 она всё равно не обновится (Р16).
- Файлы ролей в состоянии TUF не хранятся (32 роли по 128 КиБ больше лимита состояния 2 МиБ, `MAX_STATE_LEN`, `store.rs:28`). Их байты лежат в хранилище плагинов, как индекс: `<data>/plugins/catalog/publishers.json` и `<data>/plugins/catalog/roles/pub-<имя>.json`.
- Проверка сохранённого без сети: `verify_cached_target` для `publishers.json` и `verify_cached_role(&RoleName, bytes, now)` (#86): цепочка корней от встроенного, сохранённый верхний `targets`, делегирование роли в нём, sha256 принятого файла, подпись ключами делегирования, версия, срок, пути. После срока роли издатель недоступен, не отозван.
- Хранилище плагинов: `Installed.publisher: Option<PublisherName>` с `#[serde(default, skip_serializing_if = "Option::is_none")]`; `StoreState.declined_replacements: BTreeMap<String, String>` (порт → плагин издателя, от которого пользователь отказался), так же с `default`. Новый вариант `Source` не нужен: версия младше Y, откаченная проверкой здоровья, не прочла бы состояние с незнакомым вариантом.

### Отзыв

В `apply_index` (`crates/openncalayer/src/plugins.rs:944-1004`), до выбора версии, для каждого плагина `Source::Catalog`:

1. Издатель плагина: `Installed.publisher`, а если поля нет, издатель, чей `id_prefix` покрывает `id` (в любом состоянии). Найденное без поля записывается в `Installed.publisher`. Если записанный издатель не тот, чей префикс покрывает `id` (запись или `publishers.json` испорчены), выбор закрывается: действует более строгое состояние из двух (`Revoked`, затем `Unavailable`, `Retired`, `Active`), версия отозвана, если её отозвал любой из них, а обновить плагин могут только выпуски записанного издателя.
2. По состоянию издателя (таблица выше): `Active` — обычный выбор версии; `Retired` и `Unavailable` — `Withdrawn`, если версия отозвана (`revoked_versions` проверенного `publishers.json` или `revoked: true` в проверенной роли, которая всё ещё делегирована), иначе `Keep`; `Revoked` — тот же путь, что `PluginChoice::Withdrawn` (выгрузить, `set_withdrawn(true)`, удалить ожидающее обновление), с уведомлением `PluginNotice::PublisherRevoked { name, publisher }`.
3. Издатель снова активен (владелец вернул его) и версия не отозвана: ветка «the plugin's version is no longer revoked» (`plugins.rs:960-979`) снимает `withdrawn`.

При выключенных обновлениях и включённых отзывах применяются только переходы, которые выключают плагин или снимают `withdrawn`; установка и обновление версий не выполняются. Отозванная установленная версия в этом режиме выключается (`Withdrawn`), даже если каталог предлагает ей замену (`Update` или `Downgrade`); замену поставит первая проверка с включёнными обновлениями.

### Замена порта (Р11)

Порт `P` из индекса владельца считается заменённым, если активный издатель называет его в `supersedes`, и в каталоге этого клиента (канал, `min_core`, раскатка, не плохая) есть версия плагина издателя `Q`. Пока такой версии нет, порт остаётся в каталоге как был.

- Заменённый порт не предлагается для новой установки, `missing(module)` и `installBundle` выбирают `Q`.
- Установленный `P` (`Source::Catalog`): `apply_index` скачивает и проверяет `Q` и показывает окно замены (всегда, даже без новых разрешений: другой `id`, другой издатель). Согласие: под `changing` выгрузить `P`, загрузить `Q`; если `Q` не загрузился, загрузить `P` обратно и пометить версию `Q` плохой; если загрузился, записать `Q` (`publisher` задан) и удалить `P` с его пакетом и настройками. Отказ: `declined_replacements[P] = Q`, `P` работает дальше без обновлений каталога, окно «Плагины» показывает «Доступна замена от издателя …» с кнопкой, повторного уведомления нет.
- Издатель `retired`, `revoked` или недоступен: `supersedes` не действует, `P` (если он ещё в индексе владельца) снова обычный порт.
- Клиенты младше Y `publishers.json` не читают и продолжают обновлять `P` из индекса.

### Типы и ошибки Rust

Все решения в коде по навыку `rust-skills`: типизированные ошибки (`err-custom-type`, `err-thiserror-lib`), новые типы для имён и путей (`api-newtype-safety`, `type-no-stringly`), разбор на границе TUF (`api-parse-dont-validate`, `serde-try-from-validate`), без `unwrap`/`expect` вне тестов (`err-no-unwrap-prod`), явные `match` по своим перечислениям (`pat-exhaustive-enum`), точечные регрессионные тесты с описательными именами (`test-descriptive-names`).

Типы в `oncl-update` (часть публичного API опубликованного крейта). Изменения `Targets` и `PluginRelease` ломают API; они вышли в `0.1.2-beta.1` с заметкой о миграции (`docs/dev/sdk.md`, «Переход с 0.1.1 на 0.1.2», Р23):

| Тип | Инвариант, который держит конструктор |
|---|---|
| `PublisherName` | грамматика и зарезервированные имена |
| `RoleName` | ровно `pub-<PublisherName>`; `RoleName::of(&PublisherName)`, `RoleName::publisher()` |
| `TargetPath` | грамматика пути цели; `Targets.targets` — `BTreeMap<TargetPath, Target>` |
| `PathPattern` | только форма `plugins/<имя>/*/*`; `matches(&TargetPath) -> bool` |
| `Targets` | член `delegations` хранится как подписан (`Option<Value>`, поле закрыто); `Targets::delegations() -> Result<Option<Delegations>, TufError>` |
| `Delegations`, `DelegatedRole`, `RefusedRole` | ключи с пересчитанными `keyid`, порог, уникальные имена; роль вне профиля — `RefusedRole` |
| `VerifiedRole` | конструктор приватный, создают только `TufClient::delegated`/`verify_cached_role` |
| `PublisherPolicy`, `Publisher`, `Standing` | `publishers.json`: `Active`, `Retired`, `Revoked`, `Unknown { state }`; непересекающиеся префиксы, модули, бандлы |
| `PublisherRelease` | `custom.oncl` через `try_from`, совпадение с путём цели, форма `url` копии |
| `DeclaredCapabilities` | JSON-объект `custom.oncl.capabilities` не больше 16 КиБ; разбор в `oncl_plugin::Capabilities` через `TryFrom<&DeclaredCapabilities>` в `oncl-plugin` |
| `Catalog`, `PublisherState` | индекс владельца, `PublisherPolicy`, состояния издателей; `offer`/`choose_plugin` принимают `&Catalog` |

Ошибки:

- `TufError::Delegation { role: RoleName, error: DelegationError }`. `DelegationError` (`thiserror`, `#[non_exhaustive]`) различает `NotInSnapshot`, `Unhashed` (запись роли в снимке без длины или sha256), `Nested`, `PathOutside { path }`, `Pattern`, `KeyReused { keyid }`, `Threshold`, `TooMany { max }`, `NotDelegated`, `NotAccepted` и обёртки существующих причин. `TufError::DelegationsMissing` удаляется: отсутствие делегирований — ноль издателей, а не ошибка.
- Каталог: `CatalogError` для `publishers.json` и `EntryRejected { path: TargetPath, reason: EntryRejection }` для отброшенных записей.
- Сообщения строчные, без точки; причина в `source` (`err-source-chain`); журнал пишет структурные поля `publisher`, `role`, `path` (`obs-structured-fields`), каждую ошибку один раз.

## Онлайн-снимок (Р8)

Автослияние (Р9) требует, чтобы снимок подписывался без владельца: каждый выпуск издателя меняет версию его роли в снимке.

- Ротация корня `tuf/v1` (этап 2): `cargo xtask tuf root --rotate-snapshot --online` пишет корень `N+1` с новым ключом `snapshot`, а сам ключ — строкой `oncl-tuf-ed25519-seed-v1:<64 hex>` для секрета (формат онлайн-ключа: `SEED_PREFIX` и выбор онлайн-ролей в `xtask/src/tuf/keystore.rs`; сейчас онлайн у `tuf/v1` только `timestamp`). Тот же PR ставит `snapshot = "online"` в `tuf/v1.toml`. Поднять порог корня в той же ротации `tuf root` не умеет (открытый вопрос 5).
- Окружение GitHub `tuf-snapshot` с секретом `TUF_SNAPSHOT_KEY`, ветки развёртывания только `main`. Секрет заводится до слияния PR ротации.
- `pages.yml`: новый job `snapshot` (окружение `tuf-snapshot`) до `timestamp`, устроен как нынешний `timestamp`: xtask собирается до появления секрета, кэша сборки нет, подпись последним шагом, файл уходит выходом job. При `snapshot = "offline"` job ничего не делает.
- `cargo xtask tuf snapshot --out <копия tuf/v1> --previous <URL опубликованного tuf/v1>`: `--previous` обязателен. Команда читает опубликованный `timestamp.json` и названный им снимок и проверяет его подпись ключом `snapshot` последнего корня или, для первого снимка после ротации, корня, который он сменил. Если опубликованное не скачалось или не прошло проверку, команда останавливается, флага обхода нет (Р25): job красный, Pages не публикуется, прежний сайт отдаёт свои `snapshot` и `timestamp` до 7 дней, владелец чинит по `docs/dev/release.md`. Дальше команда проверяет клиентским кодом корни, верхний `targets` и каждую роль `pub-*` (последняя версия активного издателя подписана его ключами; роль `retired` и `revoked` только перечисляется), строит `meta` (все роли, хоть раз бывшие в git, с длиной и sha256), подписывает версию `max(Unix-время, предыдущая + 1)` на 7 дней и проверяет свой результат клиентским кодом от корня `N+1`: ключ в секрете, не совпавший с корнем, останавливает job до `oracle` и развёртывания. Подписать снимок над непроверенным файлом CI не может.
- Предыдущий снимок кладётся в артефакт рядом с новым: клиент, у которого в кэше Pages (`max-age=600`) ещё старый `timestamp.json`, найдёт названный им снимок.
- `timestamp` подписывается в job `timestamp` после проверки снимка.
- Условия job: `deploy` идёт только при успешных `build` и `oracle`; пропущенный `oracle` допускается, только если подписанного репозитория нет (`needs.build.outputs.tuf != 'signed'`); `oracle` и `verify` называют свои условия явно (`!cancelled()` и `needs.<job>.result == 'success'`).

Сбой job `snapshot` останавливает публикацию всего сайта, включая обновления ядра для всех версий клиента. Это осознанная цена Р25: у владельца 7 дней до истечения прежних `snapshot` и `timestamp`.

## Копии пакетов в наших Releases (Р10, Р30)

В репозитории включены неизменяемые выпуски. После публикации выпуска к нему нельзя добавить файл, а приложенные нельзя заменить или удалить. Тег закреплён за коммитом; если выпуск удалить, тег можно удалить, но имя тега больше не используется никогда, даже после пересоздания репозитория. Черновик изменяем полностью. При публикации GitHub сам делает аттестацию выпуска (`gh release verify`, `gh release verify-asset`). Источник: [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

Поэтому один пакет — один выпуск, и выпуск публикуется уже полным:

- Тег: `pub-<издатель>-<sha256>`, где `<sha256>` — 64 строчные шестнадцатеричные цифры sha256 пакета (`hashes.sha256` цели; это и sha256 нашей пересборки, иначе PR не дошёл бы до копирования). Предварительный выпуск без флага Latest, заголовок `<издатель>: <id> <версия>`, в описании ссылка на PR и путь роли. Тег стоит на голове `main` в момент создания; на что он указывает, для клиента неважно.
- Файлы выпуска: `<id>-<версия>.onclp` (наша пересборка), `<id>-<версия>.src.tar.gz` (архив исходников, скачанный по `source.fetch`), `<id>-<версия>.src.diff` (job `verdict`: единый diff распакованных архивов прошлой версии того же `id` и новой; у первой версии его нет), `THIRD-PARTY.txt` (шаг лицензий job `rebuild`) и `BUILDINFO.json` (job `verdict`: digest образа, sha256 архива, `Cargo.lock` и пакета, итог проверки `vcs`). Аттестация сборки (`actions/attest-build-provenance`) и аттестация выпуска, которую GitHub делает при публикации, — для публичной проверки; клиент их не читает. Аттестация сборки `pub-*` подписана workflow `publisher-pr.yml` этого репозитория и доказывает только одно: эти байты пакета получены пересборкой в CI проекта из архива исходников, sha256 которого подписал издатель, и прошли проверки бота. Она не говорит, что код издателя кто-то прочитал или что пакет — программа OpenNCALayer. Поэтому проверка файлов самого проекта всегда называет workflow: `gh attestation verify <файл> --repo arynyklas/OpenNCALayer --signer-workflow arynyklas/OpenNCALayer/.github/workflows/release.yml` (порты — `plugins.yml`); без `--signer-workflow` её прошёл бы и пакет издателя.
- Хеш в теге делает копирование идемпотентным: одни и те же байты пакета всегда попадают в один выпуск. Если PR не слился после публикации копии, повторный PR с теми же байтами находит готовый выпуск. Другие байты той же версии получат другой тег.
- Теги `pub-*` не запускают ни `release.yml` (`v*`), ни `plugins.yml` (`plugins-*`). Выпуски, которые создаёт бот токеном `GITHUB_TOKEN`, вообще не запускают workflow; пропуск тегов `pub-*` в job `dispatch` `pages.yml` нужен для выпуска, опубликованного человеком вручную. Список выпусков для сайта (`xtask/src/registry/inputs.rs:153`, где уже пропускаются `plugins-*`) пропускает и `pub-*`.

Порядок в job `mirror` бота (раздел «Jobs `publisher-pr.yml`»), для каждого нового пакета PR, до слияния:

1. Скачать артефакты `rebuild` (пакет, `THIRD-PARTY.txt`), `verdict` (`BUILDINFO.json`, `.src.diff`) и `publisher-check` (архив) и заново посчитать sha256 и длину пакета и архива; они равны подписанным в роли (значения берутся из выходов job `verdict`, а не `publisher-check` или `rebuild`).
2. Найти выпуск с тегом `pub-<издатель>-<sha256>` (`gh release view`; токен с `contents: write` видит и черновики):
   - опубликован: скачать `.onclp` и `.src.tar.gz` и сверить sha256 с ролью; совпало — пакет уже скопирован, перейти к следующему; иначе или файлов нет — PR красный, нужен ручной разбор;
   - черновик (остался от прерванного прогона): удалить его (`gh release delete <тег> --yes`, без `--cleanup-tag`: у черновика тега ещё нет) и продолжить;
   - нет: продолжить.
3. `gh release create <тег> --draft --prerelease --latest=false --target <sha головы main> --title … --notes … <файлы>`, затем аттестация сборки.
4. Проверить черновик: список файлов ровно ожидаемый, у пакета и архива размер и sha256 (скачать через API) равны подписанным.
5. Опубликовать: `gh release edit <тег> --draft=false`. С этого момента файлы и тег неизменны.

Затем слияние и запуск Pages. Копии публикуются до слияния: роль на `main` никогда не ссылается на ещё не существующий адрес. Если слияние сорвалось, лишний выпуск безвреден: его байты ничего не значат без подписанной роли. Удалять такие выпуски не нужно (тег всё равно не освободится). Это действие CI, а не подпись выпуска.

После приёма хост издателя, его git и `source.fetch` больше не нужны: всё для проверки выпуска лежит в выпуске.

Ограничения GitHub (проверено по документации 2026-11-18):

- до 1000 файлов в выпуске, каждый меньше 2 ГиБ, общий размер выпусков и трафик не ограничены ([About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)). Пакет не больше `MAX_PACKAGE` (32 МиБ), архив не больше 64 МиБ, в выпуске пять файлов;
- предела числа выпусков в репозитории документация не называет. Список выпусков отдаётся страницами по 100 (`per_page`), так что сборка сайта с ростом числа выпусков делает больше запросов;
- создание контента: не больше 80 запросов в минуту и 500 в час ([Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)); создание выпуска шлёт уведомления и прямо названо в числе таких запросов ([Releases API](https://docs.github.com/en/rest/releases/releases)). На пакет уходит около 7 запросов (черновик, пять файлов, публикация), поэтому PR несёт не больше 8 новых пакетов (проверка 6), а выпуск издателя не чаще раза в час (Р19);
- GitHub переименовывает файлы выпуска с особыми символами в имени ([Release assets API](https://docs.github.com/en/rest/releases/assets)); поэтому в версиях издателей нет `+` (раздел «Цели издателя»), а `id` и версия состоят из букв, цифр, `.` и `-`.

Удалять выпуски `pub-*` нельзя: на них ссылаются роли в git, а тег после удаления не вернуть. Отозванная версия остаётся в Releases; её выключает отзыв в каталоге.

## Открытые исходники и проверяемая сборка (Р31–Р36)

Решения Р31–Р36 (раздел «Решения владельца»): архив исходников и только OSI, эталонный образ по digest, пересборка нашим CI с копией пересборки и архива в Releases, необязательный git, `pull_request_target` только у бота, владелец не подписывает выпуски, строка «Исходный код» в окне установки.

Регулярная пересборка уже принятых выпусков в первую реализацию не входит (открытый вопрос 8).

### Кто что подписывает

| Ключ | Где | Что подписывает | Когда |
|---|---|---|---|
| `root` `tuf/v1` | офлайн, владелец | новый корень | ротация ключей; один раз до первого издателя — перевод `snapshot` в CI (этап 2) |
| `targets` `tuf/v1` | офлайн, владелец | верхний `targets`: индексы, `publishers.json`, `delegations` | ежемесячное продление (как сейчас); один раз при подключении издателя; при отзыве версии или издателя, при `retired`, при смене ключей издателя. Не при выпуске издателя |
| ключ издателя | у издателя | роль `pub-<имя>`: цели, хеши пакетов, `source` с хешем архива | каждый выпуск, изменение раскатки или отзыв своей версии |
| `snapshot` `tuf/v1` | до этапа 2 офлайн у владельца, после — CI, онлайн | снимок: версии `targets.json` и каждой роли `pub-*` | до этапа 2 с каждым `tuf update`; после — каждая публикация Pages |
| `timestamp` `tuf/v1` | CI, онлайн (как сейчас, `pages.yml`) | метку времени снимка | каждая публикация Pages |

CI ничего не подписывает в TUF своими решениями о выпуске: пересборка, проверки и копия в Releases только пропускают или не пропускают PR. Пока код `main` не подменён, онлайн-ключи подписывают лишь то, что прошло клиентскую проверку от офлайн-корня и офлайн-`targets` (раздел «Онлайн-снимок»).

Почему `targets` не переподписывается при выпуске: делегирование в верхнем `targets` называет только ключи, порог и `paths` роли, а не её версию. Версию и хеш файла роли перечисляет `snapshot` (спецификация TUF, разделы 4.4 и 5.6.4; так же устроен `xtask/src/tuf/snapshot.rs:13-14`). Новый файл роли требует нового снимка, но не нового `targets`.

Почему нужна ротация корня `tuf/v1`. Сейчас `cargo xtask tuf update` подписывает снимок `tuf/v1` офлайн-ключом владельца (`xtask/src/tuf/update.rs:249-270`). Без переноса ключа каждый выпуск издателя ждал бы подписи снимка владельцем. Поэтому этап 2 (раздел «Онлайн-снимок») проводится один раз и обязательно до подключения первого издателя (этап 4); выпуск клиента для него не нужен.

### Сборщик

- Образ собирает наш CI из `xtask/assets/plugin-builder/Dockerfile` (базовый образ по digest, тулчейн по версии с sha256, бинарник `oncl-pack` из того же коммита) и подписывает аттестацией. Digest попадает в `publishers/builders.toml` только PR владельца. Записи оттуда не удаляются: старые выпуски должны пересобираться.
- `oncl-pack source` делает канонический архив исходников из каталога или из ревизии git (раздел «Архив исходников»).
- `oncl-pack build` повторяет `xtask::plugin::pack` (проверка манифеста, версии крейта, ABI, `min_core`, `oncl_plugin::archive`) и добавляет: распаковку архива в `/build/src`; `env -i`; фиксированные пути `/build/src`, `/build/target`, `/build/target-again`, `/cargo`; свой `TMPDIR` у каждой сборки (`/build/tmp-target`, `/build/tmp-target-again`); каталоги сборок создаёт сам и отказывается найти их существующими; `SOURCE_DATE_EPOCH=315532800` (1980-01-01, как время в архиве пакета; времени коммита может не быть); `CARGO_INCREMENTAL=0`; `--config profile.release.{codegen-units=1,incremental=false,debug=false,strip=true}` и последними флагами rustc `-Ccodegen-units=1 -Cdebuginfo=0 -Cstrip=symbols`, которые перекрывают и настройки пакетов в профиле издателя; `--frozen`; `--remap-path-prefix` как в `remap_flags`. `rust-toolchain.toml` издателя не читается. Две сборки в одном контейнере, в чистых target-каталогах, сравниваются. `build` и `verify` на Linux не запускаются, если в контейнере есть сетевой интерфейс кроме `lo`.
- Шаги: `cargo fetch --locked` в том же образе с сетью (git-зависимость, то есть SDK из нашего репозитория, клонируется в `/cargo/git` целиком; больше 256 МиБ прироста `oncl-pack fetch` не принимает, Р44), затем сборка в отдельном контейнере `--network=none --read-only` с `/cargo` только для чтения; `verify` — так же, двумя контейнерами. На раннере архив не распаковывается и `cargo`/`rustup` не запускаются. В образе нет rustup: тулчейн распакован в `/opt/rust` из архивов static.rust-lang.org, сверенных по sha256 из `channel-rust-<версия>.toml`, поэтому `rust-toolchain.toml` издателя читать некому; образ задаёт `CARGO_HOME=/cargo`; `.cargo/config*` запрещён проверкой 16. Контейнер идёт от непривилегированного пользователя, с `--cap-drop=ALL`, `--security-opt no-new-privileges`, без сокета Docker, с лимитами памяти, числа процессов и времени.
- Выход контейнера сборки: только `<id>-<версия>.onclp` в рабочем томе; каталоги хоста на запись не монтируются. Наш шаг на раннере забирает его `docker cp` после завершения контейнера, принимает ровно один обычный файл (не ссылку) не длиннее `MAX_PACKAGE` и сам считает его хеш; выводу контейнера не верит. Проверку 20 и `THIRD-PARTY.txt` делает отдельный контейнер до сборки (`cargo metadata --locked` по скачанным исходникам, код издателя не запускается). `BUILDINFO.json` пишет job `verdict` из digest образа и посчитанных им хешей.
- `wasm-opt` и другие шаги после rustc не поддерживаются.

### Архив исходников

Канонический `tar.gz`, ровно такой, какой выдаёт `oncl-pack source`:

- один корневой каталог `src/`; только обычные файлы и каталоги (без симлинков, жёстких ссылок, устройств); пути относительные, без `..`, `.` и пустых компонентов, не длиннее 255 байт, UTF-8; в компонентах нет `\`, `:`, символов 0x00–0x1F и 0x7F, имён устройств Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, с любым расширением и в любом регистре) и точки или пробела в конце. Распаковка создаёт каждый файл заново и не перезаписывает существующий, так что имена, совпадающие на файловой системе без учёта регистра, отвергаются при распаковке;
- записи по возрастанию пути; режим 0644 или 0755; uid и gid 0, имена владельцев пустые; время 315532800;
- заголовки ustar, расширенный заголовок pax только с `path` для имён длиннее 100 байт, поле `prefix` пустое, в конце два нулевых блока без добивки записи; gzip — компрессор образа (flate2 на zlib-rs, уровень 9), без имени файла, время 0, байт ОС 255;
- сжатый до 64 МиБ, распакованный до 256 МиБ, не больше 20 000 записей;
- из ревизии git: дерево ревизии целиком, без каталога `.git` (как `git archive`), затем та же нормализация.

CI проверяет каноничность так: распаковывает архив строгим разбором и пакует заново тем же `oncl-pack source`. Байты должны совпасть.

### Поле `source`

`custom.oncl.source` обязательно у каждой цели издателя:

| Поле | Правило |
|---|---|
| `archive_sha256` | sha256 канонического архива |
| `archive_length` | длина архива, не больше 64 МиБ |
| `fetch` | адрес `https://`, откуда CI один раз скачивает архив: анонимно, без учётных данных и фрагмента, не длиннее 2048 байт. После приёма не нужен: клиент и сайт ссылаются на копию в Releases |
| `path` | каталог крейта внутри `src/`, `/`-разделитель, без `..` и ведущего `/`; `""` для корня |
| `license` | выражение SPDX из `Cargo.toml` крейта. Клиент проверяет только синтаксис SPDX; что каждый идентификатор из списка OSI, проверяет CI (проверка 12), чтобы старый клиент не отбрасывал записи с лицензией, позже добавленной в список |
| `builder` | `sha256:<64 hex>`, digest из `publishers/builders.toml` |
| `vcs` | необязательно: `{"url": "https://…", "rev": "<40 или 64 hex>"}`; 40 hex — репозиторий SHA-1, 64 hex — SHA-256 |

Адреса в Releases вычисляются (раздел «Копии пакетов»): `url` цели — `…/download/pub-<издатель>-<sha256 пакета>/<id>-<версия>.onclp`, архив — тот же выпуск, `<id>-<версия>.src.tar.gz`.

Клиент отбрасывает запись (журнал `warn`, `EntryRejection::Source`), если `source` нет или он не проходит правила таблицы. Клиент ничего не собирает и `vcs` не показывает. `publishers.json` новых полей не получает. В `publisher.toml` есть необязательное `binary_files = ["src/fonts/x.ttf", …]`.

### Исходники не на GitHub

Архив исходников — единственный обязательный вход (Р33). Отсюда:

- Собственный git-сервер издателя (GitLab, Gitea, cgit) или исходники вне git: издатель делает канонический архив у себя (`vendor source`) и кладёт его на любой анонимный HTTPS: свой сайт, объектное хранилище, выпуск своего репозитория на любом хостинге. CI скачивает его один раз по `source.fetch`.
- Закрытая сеть: раннер GitHub до неё не достаёт, поэтому архив выкладывается на публичный HTTPS. `vcs` такого издателя CI не проверит, и сайт покажет «заявлено издателем, не проверено».
- SFTP не поддерживается: CI понадобились бы учётные данные в job, который разбирает чужие данные, или анонимный SFTP и ещё один клиент.
- Класть архив в PR или в наш репозиторий нельзя: проверка 1 разрешает ровно один новый файл роли, а архив каждой версии навсегда остался бы в истории git.
- Формат объектов git (SHA-1 или SHA-256) неважен: целостность исходника держит подписанный sha256 архива. CI выбирает `--object-format` для проверки `vcs` по длине `rev`.

Что ограничивает выпуск по украденному ключу. Ключ издателя позволяет подписать сборку любого архива, поэтому:

1. Второй фактор: бот сливает только PR от аккаунта из списка `github` издателя (проверка 2). Нужны и ключ, и аккаунт GitHub издателя с его двухфакторной защитой.
2. Исходник любого выпуска навсегда публичен в Releases, а подпись роли связывает его с издателем: вредный выпуск виден и приписан.
3. Такой выпуск замечают по открытым следам: копия и архив исходников в наших Releases, `.src.diff` к прошлой версии и страница издателя на сайте. Отдельного уведомления издателю нет.
4. Время на отзыв: клиенты с плагином издателя проверяют каталог раз в 1–3 часа (Р26); порог из двух ключей по желанию издателя (Р12).

Прослеживаемость держится на архиве в Releases, его sha256 в подписанной роли и `.src.diff` к прошлой версии: разница готова, ничего не нужно клонировать. `vcs` — необязательная ссылка; CI проверяет её, когда хост доступен, и записывает итог в `BUILDINFO.json`. Поэтому клиент `vcs` не показывает (непроверенная ссылка выглядела бы как гарантия), а сайт показывает с пометкой «подтверждено» или «заявлено издателем, не проверено». Пока сайт не читает `BUILDINFO.json`, он пишет только «заявлено издателем».

### Проверки PR издателя (дополняют 1–11)

Проверка 10 заменяется проверками 12–25. Пакет с адреса издателя не скачивается: проверяются байты нашей пересборки.

12. `source` проходит правила таблицы; `builder` есть в `publishers/builders.toml` на `main`.
13. Архив скачивается по `fetch`: только `https`, перенаправления только на `https`, не больше `archive_length` байт, тайм-аут 120 секунд. Длина и sha256 равны подписанным. Не скачался — PR не сливается.
14. Архив канонический (раздел «Архив исходников»): строгий разбор и повторная упаковка дают те же байты.
15. В архиве есть `src/<path>/Cargo.toml`, `src/<path>/plugin.toml`, `Cargo.lock` рабочего пространства крейта и файл лицензии в `src/`; `license` крейта равен `source.license`.
16. Нет `.cargo/config*` ни в `src/`, ни на пути к `<path>`.
17. Источники `Cargo.lock`: реестр crates.io; крейты SDK из `https://github.com/arynyklas/OpenNCALayer` по `tag` или `rev` на коммите из `publishers/sdk-revisions.toml` (Р44); git-форки из `deny.toml` с коммитом; `path`-зависимости только внутри `src/`. То же правило ещё раз применяется к тому, что разрешил `cargo metadata` в сборщике.
18. Нет файлов с сигнатурами wasm, ELF, PE, Mach-O, `ar`, zip, gzip, `.onclp`; прочие бинарные файлы больше 64 КиБ только из `binary_files`.
19. Пересборка в сборщике (`--network=none`, тайм-аут 30 минут) успешна, две внутренние сборки совпали.
20. Лицензии зависимостей в wasm — из списка OSI.
21. sha256 и длина пересобранного пакета равны цели.
22. `Package::read`, манифест против `custom.oncl` и `capabilities` против манифеста (как прежняя 10) на пересобранных байтах; `plugin.toml` в пакете побайтно равен `src/<path>/plugin.toml`.
23. `url` равен вычисленному адресу копии.
24. История роли (дополнение к 8): у записи, которая уже была в прошлой версии, `source` не меняется.
25. `vcs`, если указан: CI пробует получить ревизию (тайм-аут 5 минут) и делает из неё канонический архив. Совпал — «подтверждено»; хост недоступен или ревизии нет — «не проверено», PR это не останавливает; архив другой — PR отклоняется. Итог пишется в `BUILDINFO.json`.

### Jobs `publisher-pr.yml`

- `publisher-check` (`contents: read`): проверки 1–9, 11–18, 23, 24; сначала проверки 1 и 2, при их провале job останавливается. Архив скачивается и разбирается как данные, код издателя не запускается. Архив уходит артефактом.
- `provenance` (`permissions: {}`, только после успешного `publisher-check`): проверка 25. Только git и наш код, без кода издателя: `git fetch` в голый репозиторий без выгрузки рабочего дерева, внутри контейнера без сети к раннеру.
- `rebuild` (`permissions: {}`, без кэша, без `environment` и `secrets.*`, `persist-credentials: false`, matrix по новым целям, только после успешного `publisher-check`): контейнер лицензий (проверка 20, `THIRD-PARTY.txt`), затем контейнер сборки `--network=none` (проверка 19). Наружу берётся только файл пакета. Выходам и файлам job не верим: хеши считает `verdict`.
- `verdict` (`contents: read`): сам считает хеши артефактов, проверки 21, 22; читает итог 25; пишет `BUILDINFO.json` и `.src.diff` (архив прошлой версии скачивается из её копии в наших Releases и сверяется с подписанным sha256), так что в `mirror` нет ни cargo, ни xtask.
- `mirror` (`contents: write`, `id-token: write`, `attestations: write`; только после успешного `verdict`): копии в неизменяемые выпуски по шагам раздела «Копии пакетов».
- `merge` (`contents: write`, `pull-requests: write`, `actions: write`): после `mirror`, как описано в «Workflow и права»; затем `gh workflow run pages.yml` (снимок и метка времени подписываются онлайн).
- `xtask/tests/workflows_publishers.rs` закрепляет: у `rebuild` и `provenance` `permissions: {}`, нет `actions/cache` и `rust-cache`, контейнеры запускает только xtask (`docker run --network=none` по digest с `--cap-drop=ALL` и непривилегированным `--user` закрепляют тесты `xtask/src/vendor/docker.rs`), Docker этих job стоит на файловой системе ограниченного размера; в `publisher-pr.yml` нет `environment:` и `secrets.` (событие `pull_request_target` идёт на ref `main`, так что правило веток окружения `tuf-snapshot` такой job не остановило бы); `verdict` не читает выходов `rebuild` и `provenance`, а `mirror` и `merge` — выходов кроме выходов `verdict`.

Пересборка с `codegen-units = 1` растягивает выпуск через бота примерно до 15–25 минут (оценка, не замер).

## xtask

### Команды владельца

Репозиторий один: `--repo`, `--v2-*`, `tuf init --repo v2`, `tuf root --repo v2` удалены.

- `tuf update`: пишет `tuf/v1/metadata/<N+1>.targets.json` (индексы; при непустом `publishers/` — `publishers.json` с отзывами версий владельцем и `delegations` активных издателей) и, пока `snapshot = "offline"`, `<N+1>.snapshot.json`. Источник делегирований и `publishers.json`: `publishers/<имя>/publisher.toml`; `state` там только `active`, `retired` или `revoked`, иначе команда отказывает (опечатка не доходит до подписи, хотя клиент и пережил бы её по Р29). Отказывается убрать ключ издателя, пока последний файл его роли не подписан порогом оставшихся ключей (Р24). Проверка после записи: `tuf check`, при отказе написанное удаляется.
- `tuf check`: `repo::classify` узнаёт `metadata/<N>.pub-<имя>.json` и `targets/<sha256>.publishers.json`. Проверки: `state` каждой записи `publishers/` и подписанного `publishers.json` — одно из трёх значений; `delegations` и `publishers.json` совпадают с тем, что собрал бы `tuf update` из `publishers/`; член `delegations` есть ровно с первой записи `publishers/` и не пропадает; ни одна запись `publishers/` не удалена и не сменила `name` или `id_prefix` относительно базы (Р28); каждая версия каждой роли издателя на месте, версии подряд, история не переписана; последняя роль активного издателя проходит правила PR издателя; при `snapshot = "online"` в дереве нет снимков, подписанных ключом `snapshot` действующего корня. Отдельной строкой `tuf check` сообщает, читают ли дерево клиенты `0.1.0`/`0.1.1` (профиль `Legacy`).
- `tuf snapshot`: см. «Онлайн-снимок».
- `tuf verify-published --url …/tuf/v1/`: клиент по HTTPS в профиле `Delegating`, `delegated` по всем ролям, сверка `publishers.json`. Пакеты издателей не скачивает: их проверил CI при слиянии.
- `tuf root --rotate-snapshot --online`: см. «Онлайн-снимок».
- `index add-plugin`, `index check`: при проверке модулей и бандлов учитывают последние роли издателей и `supersedes`; `id` под префиксом издателя в индекс владельца не пускают.
- `registry …`: сайт (раздел «Сайт»).
- `sdk revision add v<версия>`: шаг выпуска, коммит нового тега в конец `publishers/sdk-revisions.toml` (Р44). После переноса ещё не опубликованного тега команда запускается снова и дописывает вторую запись этого тега, если SDK не изменился (Р44). `vendor check-onboarding --base` в `index-check.yml` не даёт менять прежние записи и сверяет записи с тегами.

### Команды издателя (Р13)

Работают в клоне нашего репозитория; ключи вне рабочего дерева git, как у `tuf init`.

| Команда | Что делает |
|---|---|
| `vendor keygen --name <имя> --out <каталог>` | ключ Ed25519, зашифрован паролем (формат `keystore.rs`), печатает открытый ключ и `keyid` |
| `vendor onboard --name … --prefix … --module … [--bundle …] --display-ru/kk/en … --github <логин>… --key <hex>… [--threshold N] [--homepage URL] [--contact …]` | пишет `publishers/<имя>/publisher.toml` и проверяет его (`vendor check-onboarding`) |
| `vendor source (--dir <каталог> \| --git <каталог репозитория> --rev <ревизия>) --out <файл>` | канонический архив исходников через `oncl-pack source` в образе |
| `vendor build --source <архив> --path <крейт> [--builder <digest>]` | сборка в эталонном образе (Docker/Podman), выход в каталог: пакет, `THIRD-PARTY.txt`, `BUILDINFO.json` |
| `vendor add --name … --build <каталог выхода> --fetch <https> [--vcs-url … --vcs-rev …] --channel beta\|stable [--rollout N]` | добавляет цель в черновик `target/vendor/<имя>/role.json` (от последней роли из git): длина и sha256 пакета, `source`, вычисленный `url`, `id`, версия, `min_core`, модули, `replaces`, название и `capabilities` из манифеста; проверяет `id` и модули по `publisher.toml` |
| `vendor set --name … --id … --version … [--channel stable] [--rollout N] [--revoke\|--unrevoke]` | меняет изменяемые поля записи |
| `vendor prune --name … --id … --version …` | убирает запись, если разрешено (см. «Проверки») |
| `vendor sign --name … --keys <каталог> [--expires-days 90]` | пишет `tuf/v1/metadata/<N+1>.pub-<имя>.json`, подписанный ключами из каталога |
| `vendor cosign <файл> --keys <каталог>` | добавляет подписи для порога больше 1 |
| `vendor check --name … [--offline]` | те же проверки, что CI, против `origin/main` |
| `vendor check-pr --base <rev> --head <rev> --author <логин> --out <каталог>` | вход CI (раздел «Автослияние»): статические проверки и скачанный архив для jobs `rebuild` и `mirror` |
| `vendor verify --name … --id … --version …` | скачивает архив из Releases, пересобирает в образе и сравнивает с целью (для любого, не только издателя) |

Все проверки живут в одной функции `vendor::check_pr`, ей пользуются `vendor check`, `vendor check-pr` и `tuf check` (для последних ролей). Переиспользуемый workflow `.github/workflows/publisher-build.yml` (`workflow_call`, на тегах нашего репозитория) должен делать `vendor source` и `vendor build` в Actions издателя, прикладывать аттестацию и выкладывать архив в выпуск его репозитория; этот адрес подходит для `fetch`. Этого workflow ещё нет: издатель собирает локально (`docs/dev/publishers.md`).

## Автослияние PR издателя (Р9)

### Проверки

PR сливается ботом, только если выполнено всё:

1. Изменён ровно один путь, и это новый обычный файл `tuf/v1/metadata/<V>.pub-<имя>.json`: не правка, не удаление, не переименование, не симлинк, не смена режима, до 128 КиБ. Издатель `<имя>` активен в последнем верхнем `targets` на `main`.
2. Автор PR есть в списке `github` из `publishers/<имя>/publisher.toml` на `main`. Это защита от спама, не от подделки: подделку ловит подпись.
3. `V` ровно на 1 больше последней версии этой роли на `main` (1 для первой).
4. Файл разбирается клиентским кодом (канонический JSON, повтор ключей отвергается), подпись набирает порог ключами делегирования, `_type` равен `targets`, `delegations` нет.
5. `expires` от `now + 14 дней` до `now + 180 дней`, где `now` берётся в момент проверки CI.
6. Каждая цель: путь `plugins/<имя>/<id>/<версия>.onclp`, версия без `+`, `custom.oncl` проходит строгий разбор (незнакомые поля отвергаются), все правила раздела «Как он собирается»; `url` ровно `…/releases/download/pub-<имя>-<sha256>/<id>-<версия>.onclp` с sha256 этой цели; `source` по правилам таблицы «Поле `source`» (проверка 12); `capabilities` разбираются по правилам манифеста; `min_core` не ниже Y; не больше 256 целей; не больше 8 новых пакетов на PR (лимит создания контента GitHub, раздел «Копии пакетов»).
7. Каталог после слияния: модули и бандлы уникальны среди индексов владельца (кроме заменённых портов) и всех последних ролей издателей.
8. История роли: запись, которая уже была в прошлой версии, сохраняет `length`, `hashes`, `url`, `source`, `id`, `version`, `modules`, `replaces`, `min_core`, `capabilities`; менять можно `rollout`, `name`, `revoked`, `channel` из `beta` в `stable`. Убрать запись можно, только если она не `revoked`, её нет в `revoked_versions` владельца и у того же `id` есть более новая неотозванная версия в том же или более широком канале; отозванные записи не убираются.
9. Частота (Р19): последний коммит `main`, который трогал `tuf/v1/metadata/*.pub-<имя>.json`, сделан не меньше часа назад (`git log -1 --format=%ct -- <пути издателя>`; коммит слияния создаёт GitHub). Первый выпуск проходит всегда. Два PR одного издателя в один час обойти правило не могут: по проверке 3 у них одно имя файла.
10. Пакеты (Р21): заменена проверками 12–25 раздела «Открытые исходники и проверяемая сборка». Пакет с адреса издателя не скачивается; скачивается архив исходников по `source.fetch`, а пакет пересобирается нашим CI. Для записей, которые уже были в прошлой версии роли, ничего не скачивается и не пересобирается: копия уже в Releases.
11. `tuf check` дерева `main` плюс этот файл проходит.

### Workflow и права

`.github/workflows/publisher-pr.yml`:

```yaml
on:
  pull_request_target:
    types: [opened, synchronize, reopened, ready_for_review]
    branches: [main]
permissions: {}
concurrency:
  group: publisher-pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true
jobs:
  publisher-check:  # contents: read; секретов нет
  provenance:       # permissions: {}
  rebuild:          # permissions: {}; matrix по новым целям
  verdict:          # contents: read
  mirror:           # contents: write, id-token: write, attestations: write; needs: verdict
  merge:            # contents: write, pull-requests: write, actions: write
```

- `publisher-check` выгружает только `main` (`persist-credentials: false`), собирает xtask из `main` без кэша сборки, затем `git fetch origin pull/<n>/head` без выгрузки. Файлы PR читаются как данные через `git cat-file` после проверки списка путей; код из PR не собирается и не запускается. Архивы исходников скачивает здесь же `xtask vendor check-pr` и разбирает как данные; код издателя в этом job не запускается. Выход job — только matrix для `rebuild` (архив, `source.path`, `builder` каждой новой цели) и их число; архивы и `verdict.json` — артефакт. Голову, издателя, версию роли и цели `verdict` выводит заново. Что делают `provenance`, `rebuild`, `verdict` и `mirror`, описано в разделе «Jobs `publisher-pr.yml`».
- Правила `main`: один ruleset требует статус `check`, обход только у роли Admin, обязательного ревью нет. Статус `check` даёт последнее задание `ci.yml`. Оно ждёт задание `index`, которое вызывает `index-check.yml` и для PR, меняющего `tuf/`, запускает `tuf check`. PR, который меняет только `tuf/` и `updates/`, кроме `index` проходит лишь быстрые задания (`fmt`, `privacy`, `actionlint`, `site`), так что 30 минут ожидания в `merge` ему хватает.
- `pull_request_target` запускается всегда: настройки одобрения запусков из форков (`first_time_contributors`) его не задерживают. Поэтому у события фильтр `paths: ["tuf/v1/metadata/*.pub-*.json"]`, `publisher-check` первым делом проверяет 1 и 2 и останавливается при провале, а `provenance`, `rebuild` и `mirror` идут только после его успеха. Обязательную проверку `check` для первого PR из форка владелец одобряет вручную; пока он не одобрил, `merge` ждёт не дольше 30 минут и завершается неудачей, PR перезапускается позже.
- `merge` не выгружает репозиторий и не запускает cargo. Порядок: после `mirror` ждёт обязательные проверки головы PR (`gh pr checks <n> --required --watch`, не дольше 30 минут); проверяет, что PR открыт, не черновик, идёт в `main` с проверенной головой, а `main` всё ещё тот коммит, на котором шли проверки (иначе издатель пушит ещё раз; перезапуск jobs берёт прежние коммиты и не помогает; смена базы PR — событие `edited` — отменяет прогон); `gh pr merge <n> --squash --match-head-commit <head_sha> --subject "publisher <имя>: role version <V>"`; `gh workflow run pages.yml --ref main` (слияние токеном `GITHUB_TOKEN` не запускает `push`-события).
- Копии публикуются в job `mirror` до слияния: роль на `main` не ссылается на адрес, которого ещё нет. Если слияние не прошло, лишний неизменяемый выпуск безвреден: его байты ничего не значат без подписанной роли.
- `pull_request_target` берёт описание workflow из `main`, а не из PR: PR, который правит этот файл или xtask, проверяется старым кодом и отвергается проверкой 1. Это единственный workflow с `pull_request_target` (Р34). С 2 декабря 2026 GitHub по умолчанию блокирует это событие в публичных репозиториях, и владелец разрешает в политике Actions ровно `publisher-pr.yml` ([changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/)). `xtask/tests/workflows_publishers.rs` проверяет, что других файлов с этим событием нет.
- Pages после слияния: `snapshot` включает новую версию роли, `timestamp`, проверка, `oracle`, развёртывание, `verify`. Клиенты увидят выпуск на следующей проверке каталога (1–3 или 6–24 часа) или по «Проверить сейчас».

### Что может попробовать вредный PR

| Попытка | Почему не выйдет |
|---|---|
| Поправить workflow, xtask, `publishers/`, индекс или чужую роль вместе с файлом роли | проверка 1: ровно один новый путь своей роли; описание workflow и код берутся из `main` |
| Подписать роль чужим ключом или ключом другого издателя | проверка 4: ключи берутся из делегирования этой роли в верхнем `targets` |
| Выпустить `id`, модуль или бандл вне одобренного | проверки 6 и 7; клиент отбрасывает такую запись и сам |
| Путь вида `../`, `pub-other`, лишнее расширение | строгий разбор пути файла и имени роли (`RoleName`) |
| Огромный файл роли или пакет, zip-бомба | 128 КиБ на роль, 256 целей; CI и клиент читают пакет не больше `length` и `MAX_PACKAGE` с лимитами `Package::read` |
| Дописать коммит после проверки | `--match-head-commit` |
| Повтор старого файла, прыжок версии | проверка 3: ровно `N+1` |
| Срок 2099 года, чтобы пережить отзыв | проверка 5; отзыв идёт через `publishers.json` и делегирование, срок роли его не задерживает |
| Указать в записи меньше разрешений, чем просит пакет | проверка 22 на пересобранных байтах; клиент сверяет ещё раз |
| Пакет, собранный не из того архива, или готовый wasm в архиве | проверки 18, 19, 21: наша пересборка из архива не совпадёт с целью |
| `fetch`, закрытый для раннеров или без архива | проверка 13: PR не сливается |
| `fetch` или `vcs.url` на внутренние адреса раннера | в `publisher-check` и `provenance` нет секретов и прав записи; ответ только сверяется с хешем |
| `build.rs` или процедурный макрос, который что-то делает при пересборке | `rebuild` без прав, кэша и секретов, контейнер `--network=none --read-only`; вердикт выносит другой job по своим хешам |
| Подменить источник зависимостей через `.cargo/config` или `[patch]` | проверки 16 и 17 |
| Вредный архив: zip-бомба, `..`, симлинки | лимиты архива и строгий разбор, проверка 14 |
| Ложный `vcs` | клиент его не показывает; сайт пишет «не проверено», а несовпавший архив отклоняет PR (проверка 25) |
| Подменить байты уже выпущенной версии | проверка 8; копия лежит в неизменяемом выпуске с sha256 в теге, другой файл получит другой выпуск |
| `url` не на копию или на чужую копию | проверки 6 и 23; клиент сверяет форму `url` и хеш |
| Код в пакете, который выполнится в CI | пакет разбирается как данные (`Package::read`), модуль не выполняется |
| Убрать отозванную версию, чтобы установки на ней остались | проверка 8 |
| Поток PR, частые выпуски | `concurrency`, список авторов (проверка 2), не больше выпуска в час (проверка 9) |
| Два PR одного издателя с одной версией | второй не сольётся: файл с тем же именем уже есть |
| Слияние сразу после того, как издатель стал `retired` или `revoked` | проверка 1 требует `active`; новую роль без делегирования никто не скачивает |

## Подключение издателя (Р2)

PR издателя (сливает только владелец):

`publishers/<имя>/publisher.toml`:

```toml
name = "ecc"
state = "active"
display = { ru = "ТОО «…»", kk = "…", en = "…" }
id_prefix = "kz.ecc."
modules = ["kz.ecc.market.Signer"]
bundles = ["kz.ecc.market"]
github = ["ecc-release"]
homepage = "https://ecc.kz/"
contact = "security@ecc.kz"
threshold = 1

[[keys]]
public = "<64 hex>"

# Только с одобрения владельца (Р11):
# supersedes = { "io.github.arynyklas.openncalayer.port.market" = "kz.ecc.market" }

# Пишет только владелец (Р18, Р24), не издатель:
# revoke_all = "2027-04-01"   # все версии, бывшие в ролях издателя на эту дату
# [[revoked_versions]]
# id = "kz.ecc.market"
# version = "1.1.0"
# date = "2027-02-10"
```

Схема строгая (`deny_unknown_fields`). Правила: имя и префикс по грамматикам выше, префикс не вложен в чужой и не под `io.github.arynyklas.openncalayer.`; модули и бандлы не встроенные, не чужие и не обслуживаются портом, кроме портов из `supersedes`; ключи различны между собой и с ключами корней и других издателей; `display` не содержит «OpenNCALayer» и управляющих символов. `state`: `active`, `retired` или `revoked`; у `revoked` обязательна дата `revoked`. Файл нельзя удалить, а `name` и `id_prefix` нельзя менять (`tuf check`, Р28).

Проверка издателя (Р17): владелец вручную сверяет владение доменом префикса. PR подключения открывается по шаблону `.github/PULL_REQUEST_TEMPLATE/publisher.md`, который просит указать:

- юридическое название и регистрационный номер (БИН для Казахстана), страну;
- домен, из которого получен префикс (`kz.ecc.` → `ecc.kz`), и ссылку на страницу официального сайта на этом домене, где издатель называет свой аккаунт GitHub из `github` и `keyid` своих ключей;
- адрес почты на этом домене, на который владелец пришлёт одноразовую фразу; издатель повторяет её комментарием к PR от аккаунта из `github`;
- контакт для сообщений о безопасности;
- какие плагины издатель собирается выпускать, какие модули и бандлы оригинала они обслуживают и зачем каждый модуль;
- нужна ли замена порта (`supersedes`) и почему;
- кто держит ключи, сколько их и где они хранятся, нужен ли порог больше 1;
- лицензия кода (OSI) и откуда CI будет брать архивы исходников (адрес HTTPS), есть ли публичный репозиторий git;
- согласие с правилами: открытый исходный код и проверяемая сборка в нашем образе, автослияние только своих файлов, копирование пакетов и архивов исходников в Releases OpenNCALayer, отзыв версий или издателя владельцем, не больше выпуска в час.

Владелец сверяет страницу на домене и ответ с фразой, решает по `supersedes` и отмечает проверку в PR. Ничего из этого xtask не проверяет.

`ci.yml` на PR запускает `vendor check-onboarding`. Активация: владелец на ветке PR выполняет `cargo xtask tuf update` (новый верхний `targets` с делегированием и `publishers.json`), коммитит, сливает. Выпуски для копий создаёт бот на каждый пакет, владельцу заранее ничего создавать не нужно. Первый выпуск издатель делает следующим PR. Для первого издателя это и есть этап 4.

Плановая ротация ключа издателя (Р24), три шага:

1. PR издателя добавляет новый `[[keys]]` рядом со старым. Владелец сливает его и подписывает верхний `targets` (`tuf update`).
2. Издатель подписывает новую версию роли новым ключом обычным PR выпуска.
3. PR убирает старый ключ. `tuf update` отказывается убрать ключ, если последний файл роли на `main` не набирает порог ключами, которые останутся.

Номер версии роли продолжается: правило «ровно N+1» не даёт укравшему ключ задрать номер.

Утечка ключа издателя (Р24):

0. Сразу, без офлайн-подписи: PR владельца убирает логины из `github` в `publisher.toml`, и бот останавливается на проверке 2. `tuf check` остаётся зелёным: `github` в `publishers.json` не попадает.
1. Владелец ставит `state = "retired"` и отзывает версии: по умолчанию `revoke_all = "<дата>"`, и `tuf update` разворачивает его в `revoked_versions` по всем целям всех версий роли издателя в git на эту дату; если известно, когда украден ключ, можно перечислить только версии после этого. Выполняет `tuf update` (делегирование уходит), сливает.
2. Клиенты при следующей проверке (1–3 часа при установленном плагине издателя) перестают получать новые версии и выключают отозванные (`Withdrawn`).
3. Вернуть издателя: PR с новым ключом, владелец ставит `state = "active"`. Отозванные версии остаются отозванными, номер роли продолжается.

Издатель перестал выпускать (договорились или пропал): владелец ставит `state = "retired"` без отзыва версий. Установленные плагины работают, новых версий нет, префикс и модули остаются за ним.

Отзыв издателя (Р6): владелец ставит `state = "revoked"` и дату, выполняет `tuf update` (делегирование уходит, запись остаётся), сливает. Клиенты выключают все его плагины при следующей проверке. Это для вредного издателя; для утечки ключа достаточно `retired` с отзывом версий.

Отзыв одной версии (Р18): владелец добавляет `[[revoked_versions]]`, выполняет `tuf update`, сливает. Клиенты на этой версии уходят на лучшую неотозванную версию издателя (в том числе вниз), а если такой нет, плагин выключается. При выключенных обновлениях плагин выключается (раздел «Отзыв»). PR издателя, который трогает `publishers/`, автоматически не сливается (проверка 1), так что снять такой отзыв издатель не может.

## Интерфейс (Р5, Р27)

- `InstallRequest` (`crates/openncalayer/src/plugins.rs:85-100`) и `InstallPluginRequest` (`crates/oncl-ui/src/install_plugin.rs:53`) получают `origin_kind` вместо `local: bool` (в приложении `ReleaseOrigin`, в окнах `PluginOrigin`): `Project`, `Publisher(PublisherOrigin { display, source })`, `Unknown`, `LocalFile`. `source` — имя архива, адрес и лицензия из `Catalog::source_archive` (адрес строится из подписанного выпуска, `source.fetch` не используется); `Unknown` — плагин каталога, издатель которого неизвестен (запись его потеряла, каталога нет): строки издателя нет, «OpenNCALayer» называется только у портов проекта. То же поле есть у установленного (`InstalledPlugin`), доступного (`AvailablePlugin`) и ждущего обновления (`PendingUpdate`).
- Окно установки (`install_plugin.slint`): новые свойства `publisher`, `publisher-note` и `source` (текст ссылки; её адрес остаётся в Rust и открывается, только если это архив в наших Releases). Имя издателя показывается без невидимых символов, до 128 знаков; лицензия целиком. Окно остаётся поверх остальных, пока пользователь не откроет ссылку: тогда оно перестаёт быть поверх, чтобы браузер открылся перед ним. Строки ru/kk/en (Р22; остальные казахские строки пишет переводчик, открытый вопрос 3):
  - порт: «Издатель: OpenNCALayer» / «Жариялаушы: OpenNCALayer» / «Publisher: OpenNCALayer»;
  - издатель: «Издатель: {name}» / «Жариялаушы: {name}» / «Publisher: {name}» и под ней «Плагин подписан издателем и собран OpenNCALayer из опубликованного исходного кода. Сам код OpenNCALayer не проверял.» / «The publisher signed this plugin, and OpenNCALayer built it from the published source code. OpenNCALayer did not review the code.»;
  - издатель, ещё строка (Р36): «Исходный код: {id}-{версия}.src.tar.gz · {license}» / «Source code: {id}-{версия}.src.tar.gz · {license}»; ссылка открывает архив в наших Releases; в окне установки она стоит после списка возможностей, чтобы длинные id и лицензия не вытесняли согласие с первого экрана;
  - из файла: прежнее предупреждение `local`, строки издателя нет.
- Строка замены «Заменит установленную версию {v} ({source})» получает третий источник «от издателя {name}».
- Окно замены порта (окно установки, `RequestKind::ReplacePort`): заголовок «Замена порта», над всем строка «Плагин издателя заменит установленный порт "{port}" (версия {version}). Порт и его настройки будут удалены.» (название порта в кавычках и очищено, как название плагина), затем название нового плагина, строки издателя, фраза о непроверенном коде, «Новый плагин сможет:» с его разрешениями и строка исходного кода, как при установке; кнопки «Заменить» и «Не сейчас».

- Окно настроек: флажок «Проверять отзывы плагинов» с подсказкой (раздел «Когда клиент проверяет каталог»).

## Миграция и порядок выкладки

Как клиент младше `0.1.2` встречает `targets` с делегированиями: `TufError::Unsupported` на шаге 5.6, `refresh` проваливается, апдейтер пишет ошибку и пробует в обычный срок; каталог остаётся на сохранённом индексе до срока сохранённого `targets` (30 дней), потом без каталога. Новую версию ядра такой клиент уже не получит.

Порядок:

1. `0.1.2`: приложение читает `tuf/v1` в профиле `Delegating` (терпит `delegations`, не разбирает их для ядра). В `tuf/v1` ничего не меняется. `0.1.2` уходит в индексы обычным порядком.
2. xtask и Pages для одного репозитория: делегирования и `publishers.json` в `tuf/v1`, онлайн-снимок по режиму из `tuf/v1.toml`, job `snapshot`. Пока `publishers/` пуст и режим `offline`, опубликованные байты `tuf/v1` не меняются.
3. Ротация корня `tuf/v1` (этап 2, Р35): секрет `TUF_SNAPSHOT_KEY`, PR с корнем `N+1` и `snapshot = "online"`. Проводится один раз и обязательно до подключения первого издателя: без неё каждый выпуск издателя ждал бы офлайн-подписи снимка владельцем. Корень после публикации назад не взять, поэтому до слияния владелец подписывает пробный онлайн-снимок над копией `tuf/v1` (`tuf snapshot --key-file`; задания Pages с ключами на ветке PR не запускаются), и в лаборатории `0.1.0`, `0.1.1` и `0.1.2` проходят новый корень и этот снимок. После развёртывания — `verify-published`. Лучше делать заранее, отдельно от этапа 4: если что-то пойдёт не так, издателей это не затронет.
4. Выпуск Y (этап 3): каталог издателей, отзывы, частота проверки, настройка «Проверять отзывы плагинов», интерфейс. Гейт: лаборатория на дереве с делегированиями и тестовым издателем: Y видит его плагины, `0.1.2` обновляется до Y.
5. Подключение первого издателя (этап 4): только когда Y в `stable`. Перед слиянием владелец смотрит по счётчикам скачиваний ассетов Releases, сколько установок ещё на `0.1.0`/`0.1.1` (решение не меняет, но говорит, кого предупредить). Заметка к выпуску и страница сайта объясняют, что установки младше `0.1.2` нужно переустановить. `min_core` плагинов издателей не ниже Y (проверка 6).

Откат Y проверкой здоровья на `0.1.2`: та читает `tuf/v1` с делегированиями и обновляется как раньше. Установленные плагины издателей у неё `Source::Catalog` без записи в индексе: они работают дальше, не обновляются и не отзываются, пока не вернётся Y. `0.1.2`, переписав `plugins/state.json`, теряет поле `publisher` (serde не сохраняет незнакомые поля); Y восстановит его по префиксу из `publishers.json`.

## Угрозы

| Угроза | Что получает атакующий | Что ограничивает |
|---|---|---|
| Утёк ключ издателя | без аккаунта GitHub из `github` издателя ничего (проверка 2). С ключом и аккаунтом — вредную версию из любого исходника в пределах префикса и модулей издателя; автообновление без окна, если разрешения не растут. Заметить такой выпуск можно только по копии и архиву исходников в наших Releases, `.src.diff` к прошлой версии и сайту: отдельного уведомления издателю нет | `retired` и отзыв версий (по умолчанию всех) доходят до клиентов с плагином издателя за 1–3 часа после публикации (Р26); не больше выпуска в час; порог больше 1 (Р12); окно разрешений при росте; песочница плагинов |
| Издатель сам вредный | то же | одобрение при подключении, ручная проверка домена владельцем, отзыв версии, `revoked` |
| Пропал или взломан хост издателя (`fetch`, `vcs`) после слияния | ничего: клиент скачивает копию из наших Releases, архив исходников тоже там | копия и архив в неизменяемом выпуске сделаны до слияния; sha256 в теге и в роли |
| `build.rs` или макрос при пересборке | код в job без прав, кэша, секретов и сети | `rebuild` с `permissions: {}`, `--network=none`; вердикт в другом job |
| Взлом нашего CI при пересборке | ничего: хеш подписан издателем по своей сборке, и пересборка с другими байтами не пройдёт проверку 21 | проверка 21; любой может пересобрать выпуск из архива (`vendor verify`) |
| Вредный или обфусцированный код в опубликованном архиве | проходит | вне проверок: окно установки прямо говорит, что код не проверялся |
| Запись каталога показывает меньше разрешений, чем просит пакет | ничего | CI при слиянии и клиент при установке сверяют `capabilities` с манифестом |
| Чужой PR с файлом роли | ничего | подпись ключами делегирования; список авторов |
| Вредный PR правит workflow или xtask | ничего | `pull_request_target` из `main`, проверка 1 |
| Скомпрометирован токен бота или `main` | слияние чего угодно и лишние выпуски в Releases; через jobs `snapshot` и `timestamp` всё, что даёт утечка онлайн-ключей (строка ниже). Офлайн-подписей нет: ни делегирования, ни индекса; роль, не подписанная ключами из делегирования, клиентом отвергается; файл в Releases без подписанной роли ничего не значит. Заранее опубликованный выпуск `pub-<издатель>-<sha256>` с чужим файлом сжигает этот тег: такие байты не скопировать, издателю придётся пересобрать пакет (отказ в обслуживании одной версии) | офлайн-ключи; проверка подписи роли клиентом; клиент сверяет sha256 копии; бот сверяет файл опубликованного выпуска и не сливает PR при расхождении |
| Утёк онлайн-ключ `snapshot` | смесь действующих версий ролей и `targets`: например, удержать старую версию роли до её срока | версия ролей не ниже сохранённой у клиента; срок `timestamp` 7 дней; ротация корнем |
| Взломан аккаунт GitHub владельца (оба онлайн-ключа и Pages) | заморозка каталога до срока верхнего `targets` (до 30 дней), в том числе отзыва у клиентов, не видевших новый `targets`; отзыв версии самим издателем — до срока его роли | срок верхнего `targets`; клиенты, уже видевшие отзыв, не откатываются |
| Утёк ключ `targets` | всё, как сегодня: делегирование самому себе или подмена индекса | офлайн, ротация корнем |
| Неразбираемый `delegations` в подписанном `targets` | все издатели недоступны до исправления; ядро и порты работают | профиль `Delegating` не разбирает член для ядра; подпись `targets` офлайн |
| Сломанная или просроченная роль издателя | этот издатель недоступен | изоляция ролей |
| Ошибка инструментов убрала издателя из `publishers.json` | этот издатель недоступен, не отозван | Р28; `tuf check` запрещает удаление |
| `state`, которого клиент не знает | этот издатель недоступен | Р29 |
| Много ролей и целей, большие файлы | ничего | 32 роли, 128 КиБ, 256 целей, лимиты `Package::read` |
| Издатель выдаёт себя за OpenNCALayer | ничего | `display` одобряет владелец, запрет имени |
| Издатель занимает модуль встроенного или чужого плагина | ничего | `publishers.json` и проверка записей клиентом; запрет встроенных модулей |
| Откат Y проверкой здоровья | плагины издателей у `0.1.2` не отзываются, пока не вернётся Y | Y восстанавливает издателя по префиксу и отзывает |
| Клиент долго офлайн | отзыв доходит при первой проверке онлайн | срок сохранённого каталога: корень, `targets`, роль |
| Сбой job `snapshot` | никакой выгоды; сайт не обновляется, через 7 дней истекают `snapshot` и `timestamp` у всех клиентов | Р25: ручное исправление по `docs/dev/release.md`; красный прогон Pages |

## Открытые вопросы

1. Поведение python-tuf 7.0.1 на неразбираемом `delegations` (ожидается отказ всего `targets`) не проверено; проверит вектор `delegated-unreadable`.
2. Отдаёт ли CDN Pages после развёртывания ещё до 10 минут прежний `timestamp.json`. От этого зависит, обязательно ли класть предыдущий снимок в артефакт; сейчас он кладётся всегда.
3. Казахские тексты новых строк, кроме «Жариялаушы».
4. Не проверено, что запуск `pages.yml` через `gh workflow run` из workflow, запущенного `pull_request_target`, проходит под правилами окружений `tuf-snapshot` и `tuf-timestamp` (ветка `main`, событие `workflow_dispatch`). Для job `dispatch` это работает с событием `release`.
5. Поднимать ли порог корня `tuf/v1` (например, 2 из 3) в ротации этапа 2. Сейчас порог 1, и потеря ключа означает переустановку у всех (`tuf.md`). `cargo xtask tuf root` даёт заменённой роли один ключ с порогом 1, так что для этого нужна доработка команды.

7. Получают ли подписчики уведомлений о выпусках письмо на каждый предварительный выпуск `pub-*`. Если да, их число растёт с числом выпусков издателей; документацию об этом не нашёл.
8. Нужна ли регулярная пересборка уже принятых выпусков (например, еженедельный `publisher-rebuild.yml`: последние версии активных издателей из `.src.tar.gz` в Releases тем же `builder`, issue при расхождении или недоступном образе, отзыв решает владелец).
