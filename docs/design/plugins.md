# Плагины

Плагин OpenNCALayer представляет собой модуль WebAssembly, который обслуживает запросы сайтов к одному или нескольким `module`-именам протокола NCALayer. Обычно это порт стороннего плагина оригинала, и отвечает он тем же JSON, что оригинал. Плагин работает в песочнице и получает от ядра только те возможности, которые заявил в манифесте. Общая модель описана в разделе 3.2 [дорожной карты](roadmap.md).

Формат пакета и манифеста читает и проверяет крейт `oncl-plugin`. Он же исполняет плагины интерпретатором WebAssembly [Wasmi](https://github.com/wasmi-labs/wasmi), без JIT. ABI и SDK для плагинов находятся в крейте `oncl-pdk`.

## Пакет

Пакет плагина представляет собой zip-архив с расширением `.onclp`. Правила:

- файл пакета не больше 32 МиБ;
- в корне архива ровно два файла:
  - `plugin.toml`: манифест в UTF-8, не больше 64 КиБ;
  - `plugin.wasm`: модуль WebAssembly не больше 16 МиБ, который начинается с `\0asm` и версии 1 (байты `00 61 73 6D 01 00 00 00`);
- имена сравниваются побайтно, с учётом регистра;
- пакет отвергается, если в нём есть:
  - каталоги, в том числе пустые;
  - файлы с другими именами, в подкаталогах, с `..`, с абсолютным путём или с `\`;
  - два файла с одним именем;
  - символические ссылки;
  - зашифрованные файлы;
- размеры считаются по байтам, которые фактически получились при распаковке. Размерам из заголовков zip ядро не доверяет: если файл распаковывается больше заявленного или больше лимита, пакет отвергается;
- sha256 пакета считается от байтов всего файла `.onclp` и сверяется с записью в индексе обновлений, подлинность которого проверяет TUF ([`update-index.md`](update-index.md), [`tuf.md`](tuf.md)).

Сжатие допускается `deflate` или никакого.

## Манифест

`plugin.toml` написан в TOML. Неизвестный ключ считается ошибкой, поэтому манифест более новой версии формата не будет прочитан как более слабый.

```toml
id = "kz.example.echo"
version = "1.0.0"
min_core = "0.2.0"
modules = ["kz.example.Echo"]

[name]
ru = "Эхо"
kk = "Жаңғырық"
en = "Echo"

[description]
ru = "Возвращает запрос обратно"
kk = "Сұрауды кері қайтарады"
en = "Returns the request back"

[replaces]
symname = "kz.example.echo"
version = "1.2.1"

[capabilities]
keys = true
dialogs = true
files = true
http = ["https://tsp.pki.gov.kz/", "https://*.gov.kz/"]
origins = ["https://*.ecc.kz", "http://client2.kazynashylyk.kz"]
http_insecure = ["http://ncalayer.uchet.kz:8080/"]
key_files = true
page_files = true
page_files_ext = ["cms"]
settings = true
shared = true
```

| Поле | Обязательно | Правило |
|---|---|---|
| `id` | да | Строчные латинские буквы, цифры, `.` и `-`; от 3 до 64 символов; начинается и заканчивается буквой или цифрой; есть хотя бы одна точка (`^[a-z0-9][a-z0-9.-]{1,62}[a-z0-9]$`). Обычно — обратное доменное имя автора |
| `version` | да | Версия плагина, semver |
| `min_core` | да | Минимальная версия ядра, semver |
| `modules` | да | От 1 до 32 `module`-имён, без повторов; каждое — латинские буквы, цифры, `.`, `_`, `-`, от 1 до 128 символов (`^[A-Za-z0-9._-]{1,128}$`) |
| `name` | да | Название в окне «Плагины»: `ru`, `kk` и `en`, каждое непустое и не длиннее 128 символов |
| `description` | нет | Описание: `ru`, `kk` и `en`, каждое не длиннее 2048 символов |
| `replaces` | нет | Бандл оригинала, который заменяет плагин: `symname` (`^[A-Za-z0-9._-]{1,128}$`) и `version` — версия оригинала как строка OSGi, не semver; непустая, не длиннее 64 символов |
| `capabilities` | нет | Возможности плагина. Всё, что не указано, выключено |
| `builtin` | нет | Зарезервировано для модулей ядра (см. [Встроенные модули](#встроенные-модули)). Пакет с `builtin = true` или с `id`, который начинается с `io.github.arynyklas.openncalayer.builtin.`, не устанавливается |

`replaces` нужен модулю `accessory`. `getBundles` показывает `symname` и `version` установленных и включённых плагинов (версию в форме OSGi, `major.minor.micro`, как её печатает оригинал), а `installBundle` по `symname` находит порт.

Возможности (`capabilities`):

| Ключ | По умолчанию | Что разрешает |
|---|---|---|
| `keys` | `false` | Работа с ключами пользователя: открыть хранилище, подписать |
| `dialogs` | `false` | Показ диалогов |
| `files` | `false` | Чтение и запись файлов, которые пользователь выбрал в диалоге |
| `http` | `[]` | HTTPS-запросы по адресам с указанными префиксами, не больше 32 префиксов |
| `origins` | `[]` | `http_request_ex` к origin самой страницы, если он подходит под один из шаблонов (не больше 32); относительные адреса — только от него |
| `http_insecure` | `[]` | `http_request_ex` по HTTP без TLS под точными префиксами, не больше 8 |
| `key_files` | `false` | `keys_open` хранилища по пути, который назвала страница (нужен `keys`); каждый файл — только после согласия пользователя |
| `page_files` | `false` | `page_file_read` и `page_file_write`: файлы и каталоги, которые назвала страница; каждый файл (каталог) — только после согласия пользователя |
| `page_files_ext` | `[]` | Расширения файлов, которые пишет `page_file_write` (нужен `page_files`): до 16, латинские буквы и цифры, сравниваются без учёта регистра |
| `settings` | `false` | `settings_get`, `settings_put`: настройки плагина на диске |
| `shared` | `false` | `shared_get`, `shared_put`: данные, общие для всех экземпляров плагина (а значит, для всех сайтов) в процессе |
| `builtin` | `false` | Зарезервировано для модулей ядра: функции capability `builtin`. Манифест без `builtin = true` с этим ключом — ошибка |

Окно установки показывает каждую возможность отдельной строкой: префиксы `http`, сайты `origins`, префиксы `http_insecure` с пометкой «незащищённое соединение», `key_files`, `page_files` с расширениями записи, `settings` и `shared` («делить данные между сайтами»). Если обновление добавляет возможности (новые флаги, префиксы и шаблоны, которые не покрыты прежними, новые расширения), пользователя спрашивают снова.

Требования к префиксу `http`:

- начинается с `https://` строчными буквами;
- не содержит имени пользователя и пароля (`@` до пути), query (`?`) и fragment (`#`);
- не содержит пробелов, управляющих символов и `\`;
- путь обязателен и заканчивается `/`: подходят `https://a.kz/` и `https://a.kz/api/`, но не `https://a.kz` и не `https://a.kz/api`;
- порт можно указать, без него используется 443;
- в пути нет `;`, `%2f` и `%5c` в любом регистре, потому что с ними префикс не пропустил бы ни одного адреса (см. ниже);
- хост может иметь вид `*.` и домен не меньше чем из двух меток (`https://*.gov.kz/`). Тогда подходит любой хост под этим доменом по границе метки (`a.gov.kz`, `x.y.gov.kz`), но не сам `gov.kz`, не `evilgov.kz` и не `gov.kz.evil`. Формы `https://*.kz/`, `https://*/`, `https://a*.kz/` и `*.` перед IP-адресом запрещены.

Адрес запроса разрешён, если он тоже начинается с `https://`, не содержит имени пользователя, `\`, пробелов и управляющих символов и при этом:

- хост совпадает с хостом префикса без учёта регистра;
- порт совпадает с портом префикса, причём явный `:443` равен отсутствию порта;
- путь начинается с пути префикса;
- если путь префикса не `/`, в пути запроса нет `;`, `%2f` и `%5c` в любом регистре.

Query и fragment запроса не проверяются. Адреса разбираются так же, как в браузерах (стандарт WHATWG URL): сегменты `.` и `..` в пути, в том числе `%2e%2e`, раскрываются до сравнения. Поэтому `https://a.kz/api/../x` не проходит под префикс `https://a.kz/api/`. Адрес `https://a.kz/apix` тоже не проходит, потому что путь префикса заканчивается `/`.

Закодированные `/` и `\` (`%2f`, `%5c`) и параметры пути после `;` разборщик оставляет как есть, а серверы раскрывают их по-разному: одни декодируют `%2f` до раскрытия `..`, другие отбрасывают `;…`. В таком случае `https://a.kz/api/..%2fsecret` или `https://a.kz/api/..;/secret` попали бы за пределы `/api/`, поэтому под префиксом с путём, отличным от `/`, эти адреса запрещены.

Запрос отправляется по адресу в проверенной форме (после разбора и раскрытия сегментов, без fragment), а не по исходной строке. Перенаправлениям хост не следует: ответ 3xx возвращается плагину вместе с `Location`, и следующий запрос плагина по этому адресу снова проходит проверку.

Примеры для префикса `https://tsp.pki.gov.kz/`:

| Адрес | Результат |
|---|---|
| `https://tsp.pki.gov.kz/tsp` | разрешён |
| `https://TSP.pki.gov.kz/x` | разрешён |
| `https://tsp.pki.gov.kz:443/x` | разрешён |
| `https://tsp.pki.gov.kz.evil/` | запрещён: другой хост |
| `https://tsp.pki.gov.kz@evil/` | запрещён: имя пользователя, хост `evil` |
| `https://tsp.pki.gov.kz:8443/` | запрещён: другой порт |
| `http://tsp.pki.gov.kz/` | запрещён: не HTTPS |

Шаблон `origins` состоит из схемы `https://` или `http://`, хоста (или `*.` и домена не меньше чем из двух меток, как в префиксе) и необязательного порта. Пути, query и fragment в нём нет: `https://*.ecc.kz`, `https://a.kz:8443`. Если порт не указан, используется 443 или 80 по схеме.

Префикс `http_insecure` устроен как префикс `http`, но начинается с `http://`, допускает только точный хост (без `*.`), а порт по умолчанию 80: `http://ncalayer.uchet.kz:8080/`.

### `[[operations]]`: операции ручного окна

Таблица необязательна. Плагин без неё в окне ручных инструментов не виден, и `Manifest::manual_operations()` у него пуст. Операция описывает шаблон запроса, который строит хост, список импортов, сеть и для каждого применения ключа профиль: вид подписи, откуда берётся содержимое и какие опции принуждает ядро. Модель разрешений описана в [manual-plugins.md](manual-plugins.md), код находится в `crates/oncl-plugin/src/operations.rs`.

```toml
min_core = "0.1.0-alpha.7"          # не ниже: старое ядро таблицу отвергает (deny_unknown_fields), новое — по min_core

[[operations]]
name    = "sign-file"               # ^[a-z][a-z0-9-]{0,31}$, уникально; до 32 операций
module  = "example.sign"            # из `modules`
manual  = true                      # показывать в ручном окне (по умолчанию false)
server  = false                     # допускать grant сервера/CLI (по умолчанию false); оба false — ошибка
request = '{"module":"example.sign","method":"signFile","args":["{file:base64}"]}'
label   = { ru = "…", kk = "…", en = "…" }   # недоверенный текст автора: 1–80 символов, без управляющих, bidi и невидимых (Cf) символов, без пробелов по краям

[[operations.params]]               # до 16; ^[a-z][a-z0-9_]{0,31}$, уникальны, все используются в request
name = "file"
kind = "document"                   # document | text | choice | flag | locale
max_bytes = 16777216                # document: 1..=`MAX_DOCUMENT_BYTES` (около 192 МиБ: base64 и шаблон ещё входят в `max_transfer`; по умолчанию 16 МиБ); text: max_chars 1..=65536 (256); choice: choices (1–32)

[operations.uses]
imports     = ["keys_select", "keys_sign_cms_ex", "hash"]   # известные имена импортов; capability манифеста обязана их объявлять
network     = "pki"                 # "none" (по умолчанию) | "pki" | ["https://…/"] (каждый под capabilities.http)
interactive = ["keys_select"]       # ⊆ {keys_select, keys_choose, keys_flow_open, keys_flow_pick} и ⊆ imports

[[operations.uses.key]]             # не больше одной: операция применяет ключ один раз
kind     = "cms_ex"                 # raw | cms | cms_ex | xml | xml_ex | xades
content  = "param:file"             # param:<имя> (bound) | "derived"
max_uses = 1                        # единственное допустимое значение (по умолчанию 1)
[operations.uses.key.profile]       # поля зависят от вида; неизвестное поле — отказ
timestamp = "basics"
```

Шаблон `request` должен быть JSON-объектом: массив или строка в корне не принимаются. Плейсхолдером называется строковое значение, которое целиком равно `"{имя}"` (для text, choice и locale подставляется строка JSON, для flag булево значение) или `"{имя:base64}"` (для document, и `:base64` здесь обязателен). Плейсхолдер может стоять в значении на любой глубине, но не в ключе, не частью строки (`"x{имя}"`) и не парой (`"{a}{b}"`); экранирования скобок нет. Если в корне есть ключ `module`, его значение должно быть фиксированной строкой, равной `module` операции, а когда плагин обслуживает несколько `modules`, корневой `module` обязателен. Ключ `method`, если он есть, должен быть фиксированным текстом без скобок. `args` необязателен и может быть массивом, объектом или любым значением; ключи `module`, `method` и `args` не требуются. Числа допускаются только целые. Повтор ключа отвергается на любой глубине. Пределы шаблона: не больше 16 КиБ, 2048 значений, глубина до 16 (корень считается первым уровнем), до 64 ключей в объекте, ключ до 128 байт без управляющих и невидимых символов. Каждый объявленный параметр должен использоваться, а каждый плейсхолдер должен называть объявленный параметр. Хост строит запрос из разобранного JSON за один проход (ключи по возрастанию, числа как записаны); длина считается до подстановки и сверяется с `max_transfer`. Три формы, которые встречаются у реальных плагинов:

```toml
# 1. Массив args (rating1c, dogovor24, qiwi)
request = '{"module":"x.y","method":"sign","args":["{doc:base64}"]}'
# 2. Объект args (fhs, energy)
request = '{"module":"x.y","method":"sign","args":{"data":"{doc:base64}","who":{"name":"{who}"}}}'
# 3. Ключи в корне, без module и args (esf-osdkz, eproc, efactoring, market)
request = '{"method":"signPlainData","storageName":"PKCS12","data":"{text}"}'
request = '{"type":"text","data":"{text}"}'
```

Содержимым для любого вида подписи (`raw`, `cms`, `cms_ex`, `xml`, `xml_ex`, `xades`) может быть text-параметр: `content = "param:<имя>"`. Тогда подписываются UTF-8-байты набранного текста, и билет вместе с `ApprovedUse` привязан к этим байтам. Пустой текст содержимым не считается (`InvalidValue`).

Текст-содержимое ядро проверяет одинаково для ручного окна, `plugin_prepare` и `plugin_server_request` (общая проверка `plugin_request`). `InvalidValue` вызывает любой символ, кроме `\n` и `\t`, если он управляющий (NUL, `\r`, ESC, DEL, C1) или невидимый, bidi или Cf (U+202A–E, U+2066–9, U+200B–F, U+2028/9, U+FEFF, U+00AD и другие; см. `oncl_plugin::operations::signed_text_problem`). Окно при снятии снимка формы заменяет CRLF на LF и передаёт одну и ту же строку `&str` и в отрисовку, и в `PluginParam::Text`; после снимка текст не обрезается и не нормализуется. Похожие символы из других алфавитов, NBSP, пробелы по краям и формы NFC/NFD допустимы: окно согласия показывает текст дословно, с длиной в символах и байтах и SHA-256, и отмечает пробелы по краям и пробелы вне ASCII. `max_chars` задаётся от 1 до 65536 символов (до 256 КиБ). Дайджест и `raw` по-прежнему принимают только содержимое из параметра, а `derived` для `raw` и `digest` отвергается. В `ConsentSummary.content` для text-параметра лежат имя параметра, длина в байтах и SHA-256. Самого текста в сводке нет: интерфейс показывает его из снимка своей формы и сверяет с этим SHA-256.

Операция с `[[operations.uses.key]]` должна объявить `network = "pki"`, иначе разбор завершается ошибкой `NetworkNeeded`. Окно ручных инструментов подписывает только с хостами PKI, поэтому `none` и список адресов для операции с ключом не принимаются. Каноническая запись объявления имеет версию `ONCLOP2`; прежняя `ONCLOP1` больше не используется.

Каждый импорт из `Import::ALL` отнесён к одному классу в `ImportPolicy::of`. Сопоставление там исчерпывающее, и новый импорт не соберётся, пока его не классифицируют.

- Разрешены: базовые функции, `keys_select/choose/flow_open/flow_pick/describe/chain/release/terminals`, `tokens_scan` (хост отвечает, что токены выключены), `http_request[_ex]`, `tsp_*`, `ocsp_fetch`, `crl_fetch`, `cms_verify`, `xml_verify`, `ca_*`, `pkix_path`.
- Требуют профиля шесть функций `keys_sign_*`.
- Запрещены `dialog_*`, `file_*`, `page_file_*`, `keystore_*`, `settings_*`, `shared_*`, `core_*`, `keys_open`, `tokens_id_card`, `data_*`.

`network = "none"` несовместимо с импортами, которые отправляют запросы (`http_request[_ex]`, `tsp_*`, `ocsp_fetch`, `crl_fetch`, `cms_verify`, `ca_issuer`, `pkix_path`), и с профилем, который ставит метку времени (`timestamp` у cms и cms_ex, уровень `t` у xades). Остальные перекрёстные проверки выполняются при вызове: `interactive` должен входить в `imports` (обратное не требуется), а адреса `network` должны лежать под `capabilities.http`, но не под `origins` или `http_insecure`. Каждому импорту `keys_sign_*` нужна строка `[[operations.uses.key]]` того же вида, и наоборот; применение ключа требует `capabilities.keys`. При компиляции пакета `uses.imports` должен входить в импорты модуля WebAssembly, иначе загрузка завершается ошибкой `LoadError::OperationImport`.

Содержимое `derived` разбирается, но хост его пока не выполняет: `Operation::runnable()` возвращает `false`. Для `raw` и для `content_form = "digest"` оно запрещено.

Профили. Значения по умолчанию задаёт ядро; незаданное поле означает значение по умолчанию, а отклонение от разрешённых значений приводит к отказу. Поля, которых нет в таблице, задать нельзя.

| Вид | Поля (по умолчанию) | Запрещено |
|---|---|---|
| `raw` | нет | любые опции |
| `cms` | `attached` (false), `timestamp` (`none`; `basics`) | `kalkan` |
| `cms_ex` | `encapsulate` (false), `cosign` (`never`), `content_form` (`data`; `digest` — только bound и без `encapsulate`), `timestamp` (`none`/`basics`/`kalkan`), `certificates` (`signer`/`chain`), `output` (`der`/`base64`/`pem`), `content_type`, `message_digest`, `signing_certificate_v2` (true), `signing_time` (`now`/`none`) | `cosign` кроме `never`, `attrs.extra`, `econtent_type`, `digest`, `timestamp = custom`, `certificates = extra` |
| `xml` | `element`, `parent` (только с `element`) | — |
| `xml_ex` | `element`, `parent`, `placement` (`document_element`/`first_child_of_document`/`parent`; `parent` ⇔ задан `parent`), `namespaces`, `other_prefix_uri`, `signature_method`, `digest_method` (из известных URI), `c14n`, `strip_whitespace`, `base64_line_breaks`, `output` (`as_is` / `{ serialize = { declaration, standalone_no, trim } }`), `transforms` (список `"enveloped"` / `{ c14n = "…" }`: `enveloped` первым, затем не больше одной каноникализации; пустой список отвергается, целый документ — только с `enveloped`; поле 12 канонической кодировки пишется только когда задано) | `signature_id`, `signing_time_object`, чужие URI методов |
| `xades` | `level` (`b`/`t`; `lt`/`lta` отвергаются при разборе: ядру нужен `chain` для доказательств), `tsa` (`basics`/`kalkan`), `signature_method`, `digest_method` | `chain`, custom TSA, чужие URI |

`element` и `parent` задаются абсолютным XPath (начинается с `/`) либо как `param:<имя>`. Во втором случае это text-параметр, и введённый пользователем текст показывается в окне согласия. XPath не длиннее 1024 байт и не содержит управляющих, bidi и невидимых символов; `param:` допустим только для text-параметра с `max_chars` не больше 256. Введённый текст должен пройти `Source::check_value` до `options_canonical`, а для непрошедшего значения `options_canonical` возвращает `None`.

Профиль должен покрывать все поля структур аргументов ABI. Тест `the_abi_option_structs_are_all_classified` разбирает эти структуры без `..`, так что новое поле не соберётся, пока его не отнесут к профилю или к полям, которые обязаны иметь значение по умолчанию:

- `SignRawArgs` {handle, data};
- `SignCmsArgs` {handle, data, attached, timestamp};
- `SignCmsExArgs` {handle, content, encapsulate, cosign, econtent_type=None, digest=None, attrs, certificates, timestamp, output};
- `SignedAttrs` {content_type, message_digest, signing_certificate_v2, signing_time, extra=пусто};
- `SignXmlArgs` {handle, xml, element, parent};
- `SignXmlExArgs` {handle, xml, element, parent, namespaces, other_prefix_uri, placement, signature_method, digest_method, signed_info_c14n, transforms=None, signature_id=None, signing_time_object=None, strip_whitespace, base64_line_breaks, output};
- `XadesArgs` {handle, xml, level, tsa, chain=пусто, signature_method, digest_method}.

`handle` связан с проверкой ключа, а байты документа привязывают содержимое. Вызов с `CoSign::Auto` разбор не отвергает (в профиле остаётся `never`): при вызове ядро приводит его к `Never`. Построитель `options_sha256` из разобранных `args` пишет через ту же функцию `Profile::encode`, а расхождения ловят эталонные векторы всех шести видов.

Плагин, который объявляет `[[operations]]`, продолжает работать для сайтов через WSS. Этот путь идёт через `oncl_plugin::PluginModules` (см. [manual-plugins.md](manual-plugins.md)) с обычными диалогами согласия и без билета. Объявления ограничивают только окно ручных инструментов, сервер и CLI. В `Engine::plugin_call` операция вызова должна быть объявлена, каждое применение ключа получает билет, `AuthorizedSigner::sign_digest` отказывает применению без билета ещё до любой другой проверки, а импорты вызова ограничены импортами операции.

Каноническое кодирование служит входом для `options_sha256` билета `PluginUse`. `KeyUse::options_canonical(values)` записывает магию `ONCLOPT1\0`, номер вида (1 raw, 2 cms, 3 cms_ex, 4 xml, 5 xml_ex, 6 xades), затем поля вида в порядке их номеров: `id u8` и значение, длина которого определяется им самим. Булево значение занимает байт 0 или 1. Перечисление занимает один байт с явным значением `tag()`: `Timestamp` 0 none, 1 basics, 2 kalkan; `ContentForm` 0 data, 1 digest; `Certificates` 0 signer, 1 chain; `SigningTime` 0 now, 1 none; `XadesTsa` 0 basics, 1 kalkan; `output` у cms 0 der, 1 base64, 2 pem; placement 0, 1, 2; c14n 0 (нет) или 1–4; level 0 b, 1 t. Строка записывается как длина `u32` BE и UTF-8, необязательное значение как 0 или 1 и само значение, список как счётчик `u32` и элементы. Записываются все поля, включая значения по умолчанию, поэтому незаданное поле и явно заданное значение по умолчанию кодируются одинаково. Набор и порядок полей фиксированы, и у двух разных профилей не бывает одинаковой записи. Поле `param:<имя>` кодируется текстом из `values` как фиксированное значение (без значения результат `None`). Версия кодирования входит в магию. `Operation::canonical()` кодирует всё объявление, кроме `label` (импорты и сеть как множества), и служит для обнаружения изменений.

`Manifest::added_over` дополняет `Capabilities::added_over` списком `AddedOperation`. Явное согласие нужно, если у операции появилось применение ключа (вид, содержимое или профиль, которых не было у установленной операции с тем же именем), у операции с ключом изменились `module`, `request`, параметры или `manual`, добавлен импорт, требующий capability, расширена сеть или включён `server`. Согласия не требуют смена `label`, изменения пробелов в `request` (JSON сравнивается как JSON) и сужение: меньшие лимиты параметров, меньше вариантов выбора, более узкая сеть, выключенный `manual`, убранные импорты.

В приложении `PluginService::manual_plugins()` (`crates/openncalayer/src/plugins/manual.rs`) строит `oncl_core::plugins::PluginRegistry` из установленных плагинов `Store`, которые включены, не отозваны и чей пакет читается (`load_package` сверяет sha256 файла). Манифест, модуль и `PackageHash::File(package.sha256)` берутся из одного `Package`. Для каждой операции из `Manifest::manual_operations()`, кроме операций с `network = [urls]`, вызывающему `manual-window` (`LocalOperator`) выдаётся `allow_declared_with_pki` с хостами PKI `NCA_PKI_HOSTS`, а при `network = "pki"` ещё и с точными адресами ТСП и OCSP НУЦ. Плагин без `[[operations]]` в реестр ручного окна не попадает, а его модули для страниц, как и прежде, обслуживает `PluginModules`. Окно получает список `ManualOperation` (id и версия плагина, имя операции, `label` и имя плагина как недоверенный текст плагина, параметры, признак применения ключа) и `skipped`, то есть установленные плагины с нечитаемым пакетом. Список неподдерживаемых портов и методов в код не зашит, он ведётся в `manual-plugins-inventory.md`.

Автообновление из каталога сравнивает манифесты через `Manifest::added_over`. Если новая версия добавляет возможность или операцию (ключ, сеть, импорты, `server`, смену модуля, запроса или параметров у операции с ключом), она не ставится молча и ждёт явного согласия в окне «Плагины», где появляется строка «предлагать в окне ручных инструментов действия…» с именами операций. Сужение и смена `label` проходят без вопроса. Если установленный пакет не читается, всё, что объявляет новая версия, считается добавленным и ждёт согласия. Откат с отозванной версии (`Downgrade`) идёт через тот же `update_to` с той же проверкой `added_over`: если старая версия объявляет больше установленной, она тоже ждёт согласия.

Окно `install_plugin` для пакета с `[[operations]]` показывает по каждой операции доверенный блок и отдельную рамку плагина. Доверенный блок строится только из проверенных полей:

- идентификатор операции (`^[a-z][a-z0-9-]{0,31}$`, проверяется при разборе и ещё раз при отрисовке);
- вид применения ключа;
- профиль подписи от ядра (`Operation::consent`, `Profile::view`). Все поля профиля разобраны без `..`; показываются существенные и все, что отличаются от значения по умолчанию: `cosign=never`, форма вывода cms_ex, выключенные атрибуты, место и параметры XML, алгоритмы, уровень и TSA для XAdES;
- сеть и признак `server`;
- для обновления: что добавилось или стало шире (`AddedReason`).

Свободный текст манифеста, то есть метка и XPath профиля, попадает только в рамку «Плагин называет это так» как обычный текст: метка до 60 знаков, XPath до 120, дальше «…». Имя плагина в доверенный блок не входит. Блок операций стоит перед списком возможностей. Обновление, которое ждёт согласия и приносит операции, спрашивается в том же окне кнопкой «Обновить» вместо «ОК». Ответ привязан к sha256 показанного пакета (`confirm_update(id, expected_sha256)`): если за это время пришёл другой пакет, ставится `Superseded`, а обновление продолжает ждать и показывается заново. Закрытие окна «Плагины» закрывает и окно согласия.

## ABI

Версия ABI равна `1` (`oncl_pdk::abi::ABI_VERSION`). Плагин собирается как модуль WebAssembly для `wasm32`: 32-битная линейная память, без функции `start`. Модуль экспортирует:

| Экспорт | Тип | Что делает |
|---|---|---|
| `memory` | память | Линейная память плагина |
| `oncl_abi_version` | `() -> i32` | Возвращает версию ABI; другая версия — плагин не загружается |
| `oncl_alloc` | `(len: i32) -> i32` | Выделяет `len` байт и возвращает адрес; `0` — выделить не удалось |
| `oncl_free` | `(ptr: i32, len: i32)` | Освобождает буфер, который вернул `oncl_alloc` |
| `oncl_process` | `(ptr: i32, len: i32) -> i64` | Отвечает на один запрос |

Экспорты и их точные типы проверяются при загрузке. Каждый импорт модуля должен быть host-функцией из модуля `oncl` с типом `(ptr: i32, len: i32) -> i64`. Импорт функции, которой нет в ABI, и импорт функции capability, не заявленной в манифесте, приводят к ошибке загрузки. Хост связывает только функции заявленных capabilities.

Все значения передаются в CBOR в той форме, в которой их пишет serde (крейт `ciborium`). Плагину на другом языке её нужно знать точно:

- структура кодируется как map с ключами-строками, равными именам полей (`{"request": …, "origin": …, "locale": …}`); поле со значением по умолчанию (в `oncl_pdk::abi` оно помечено `#[serde(default)]`) можно не передавать;
- байтовая строка передаётся как байтовая строка CBOR (major type 2), а не как массив чисел;
- `()` и `None` кодируются как `null`, `Some(v)` как само `v`;
- перечисление без данных (`ErrorCode`, `Level`, `Action`, `MessageKind`, `Method`) передаётся текстовой строкой с именем варианта в `snake_case`: `"denied"`, `"warn"`, `"key_info"`;
- результат host-функции `HostResult<T>` (`Result` в Rust) кодируется как map из одной пары с ключом как есть: `{"Ok": значение}` или `{"Err": {"code": "invalid", "message": "…"}}`.

Результат типа `i64` равен `(ptr << 32) | len`, то есть адресу и длине CBOR-байтов в памяти плагина.

Вызов `oncl_process` идёт так:

1. Хост кодирует `Input { request, origin, locale }`: запрос страницы, `Origin` соединения, если он есть, и язык окон OpenNCALayer (`"ru"`, `"kk"` или `"en"`). Запрос содержит текст кадра до конца его первого объекта JSON, как его читает `new JSONObject` оригинала, и может быть в нестрогой форме org.json: одинарные кавычки, слова без кавычек, `;` между парами, запятая перед `}`. Плагин, который читает запрос через `serde_json` (как `oncl_pdk::invoker::invoke`), на такой запрос отвечает `GENERAL_ERROR`.
2. Хост вызывает `oncl_alloc`, записывает `Input` в полученный буфер и вызывает `oncl_process(ptr, len)`. С этого момента буфер принадлежит плагину.
3. Плагин возвращает `Output { response }`, ответ, который уйдёт странице без изменений, в буфере из своего `oncl_alloc`. Хост читает его и вызывает `oncl_free`.

Host-функция получает аргумент `(ptr, len)` в памяти плагина, и буфер остаётся у плагина. Результат `HostResult<T>`, то есть `Ok(T)` или `Err(HostError { code, message })`, хост записывает в буфер, который берёт у `oncl_alloc` плагина; освобождает этот буфер сам плагин. Вызывать host-функции можно только из `oncl_process`. Вызов из `oncl_alloc` или `oncl_free`, пока их вызывает хост (в том числе пока хост выделяет буфер под результат другой host-функции), вызывает trap.

Хост читает и пишет память плагина только с проверкой границ. Буфер за пределами памяти, `0` из `oncl_alloc` и `Output`, который не разбирается, считаются ошибкой плагина. Если не разбирается аргумент host-функции, trap не происходит: функция отвечает `{"Err": {"code": "invalid", …}}`.

Базовые host-функции доступны любому плагину:

| Функция | Аргумент | Результат |
|---|---|---|
| `log` | `LogArgs { level, message }`, `level` — `error`, `warn`, `info`, `debug` | `()`; строка уходит в журнал OpenNCALayer с id плагина и номером сессии, длинная — обрезается до 4 КиБ |
| `now` | `()` | `i64` — время в миллисекундах Unix |
| `random` | `RandomArgs { len }` | байты системного генератора, не больше 1024 |
| `cert_info` | `CertArgs { der }` | `CertInfo`: CN, ИИН, БИН, организация, серийный номер, срок действия (мс Unix), расширенные и обычные назначения ключа, OID алгоритмов подписи и ключа и сертификат в PEM |
| `reply_drop` | `()` | `()`; текущий запрос закончится обрывом соединения без ответа (см. [Ошибки](#ошибки)) |
| `hash` | `HashArgs { alg, data }`, `alg` — `sha1`, `sha256`, `sha512`, `gost34311`, `streebog256`, `streebog512` | хеш данных; ГОСТ 34.311-95 — с параметрами Kalkan, как в подписях |
| `cert_details` | `CertArgs { der }` | `CertDetails`: subject и issuer так, как их пишет Kalkan (`CN=…,SURNAME=…,C=KZ`), типы Kalkan (`SIGNATURE`, `AUTHENTICATION`, `SSL`, `OCSP_RESPONSE_SIGNING`, `TSP_SIGNING`), SKI и AKI строчным hex, серийный номер десятичным числом, адреса OCSP, CA Issuers и CRL, алгоритм подписи ключа (`gost2004`, `gost2015_512`, `rsa_sha256`, `rsa_sha1`), CN издателя (`issuer_cn`; ядро старше `0.1.0-alpha.5` его не пишет) |
| `local_time` | `LocalTimeArgs { unix_ms }` | `LocalTime { offset_seconds }` — смещение часового пояса системы от UTC в этот момент |
| `platform` | `()` | `Platform { os, line_separator }`: `windows`, `macos` или `linux` и разделитель строк системы (`\r\n` в Windows, `\n` в остальных) |
| `ca_list` | `()` | сертификаты CA НУЦ, которым доверяет ядро (DER) |
| `ca_issuer` | `CertArgs { der }` | `Option<Bytes>` — CA из `ca_list`, выпустивший сертификат: по имени издателя, сначала тот, чей SKI совпал с AKI |
| `call_locale` | `LocaleArgs { locale }`, `locale` — `ru`, `kk` или `en` (иначе `invalid`) | `()`; окна ядра показываются на этом языке до конца текущего вызова, следующий вызов снова начинается с языка ядра |
| `pkix_path` | `PathArgs { cert, at }`, `at` — `now`, `not_after_if_expired` (у просроченного сертификата — его notAfter, как у `getSigningEntityDefaultChained` оригинала) или `unix_ms(ms)` | `PathOutcome`: `valid`, `issuer_not_found` — у CA ядра нет издателя, `invalid(причина)` — путь через CA ядра не сходится; не сертификат — `invalid`. Без сети |

Для каждой host-функции записана версия ядра, в которой она появилась (`Import::since`). Ядро, в котором функции нет, не загрузит плагин, импортирующий её (неизвестный импорт приводит к ошибке загрузки), поэтому `min_core` плагина должен быть не ниже `since` всех его импортов. Новые функции добавляются в ABI новыми импортами со своими типами, а `ABI_VERSION` остаётся `1`. Аргументы и результаты существующих функций расширяются только так, чтобы старый плагин этого не заметил: новым полем, которое можно опустить (отсутствующее поле получает значение по умолчанию), и новым вариантом, который появляется только в ответ на новое значение аргумента (`tsp_stamp` возвращает `no_signer` только при `signers = of_cert`).

| Функции | `since` |
|---|---|
| `log`, `now`, `random`, `cert_info`, `keys_choose`, `keys_sign_cms`, `keys_sign_raw`, `keys_sign_xml`, `keys_release`, `dialog_message`, `dialog_confirm`, `file_open`, `file_save`, `http_request` | `0.1.0-alpha.3` |
| Остальные функции этого раздела: `reply_drop`, `hash`, `cert_details`, `local_time`, `platform`, `ca_list`, `ca_issuer` и новые функции `keys`, `dialogs`, `files`, `http`, `page_files`, `settings`, `shared` | `0.1.0-alpha.4` |
| `call_locale`, `pkix_path`, функции capability `builtin` (`core_*`, `dialog_csr`, `dialog_import`, `keystore_*`, `tokens_id_card`, `data_*`), `keys_flow_open`, `keys_flow_pick`, `keys_describe`, `tokens_scan`, `dialog_reader`, `file_choose_kind` | `0.1.0-alpha.5` |

В `since` указывается версия ядра, в которой функция впервые вошла в релиз. Уже выпущенную версию ядра в `since` новой функции не ставят: если функция добавлена после выпуска, `since` и версия рабочего пространства поднимаются до следующей предварительной версии.

Функции capabilities описаны в разделе [Capabilities](#capabilities), типы аргументов и результатов находятся в модуле `oncl_pdk::abi`.

### Экземпляры

Экземпляр плагина создаётся на сессию, то есть на одно WebSocket-соединение или один виртуальный сокет моста, и живёт до её закрытия. Состояние плагина (глобальные переменные, выделенная память, ключи) сохраняется между запросами сессии, а другие сессии его не видят. Сессия `0` (без сессии) получает экземпляр на один вызов. В процессе живёт не больше 64 экземпляров, и их общая линейная память, измеренная при создании экземпляра и после каждого вызова, не превышает бюджета. Когда памяти не хватает, закрывается давно не использованный свободный экземпляр; если заняты все, запрос, которому нужен новый экземпляр, получает `PLUGIN_ERROR`. Память экземпляра WebAssembly не уменьшается, поэтому экземпляр, чья память после вызова больше порога, закрывается, и следующий запрос сессии получает новый.

## Ошибки

Страница получает такой ответ, если плагин не справился с запросом: случился trap (в том числе паника внутри плагина), кончилось топливо, память выросла бы сверх лимита, буфер вышел за пределы памяти или за лимит или ответ не разбирается как `Output`:

```json
{"success":false,"errorCode":"PLUGIN_ERROR"}
```

После такой ошибки экземпляр больше не вызывается, и следующий запрос сессии получает новый. Причина записывается в журнал.

Если плагин во время запроса вызвал `reply_drop`, ответ не отправляется, а соединение закрывается так же, как после запроса, который не является объектом JSON: TCP-соединение закрывается без кадра Close, виртуальный сокет моста получает кадр `close`, после которого расширение закрывает сокет страницы с кодом 1006. Так модули оригинала реагировали на исключение, выброшенное до ответа. Флаг действует только на текущий вызов. Плагин всё равно возвращает `Output`; если тот не разбирается, страница получает `PLUGIN_ERROR`, и обрыва нет. Встроенный модуль при сбое тоже обрывает соединение, см. [Встроенные модули](#встроенные-модули).

Ошибка host-функции не считается ошибкой плагина: плагин получает `HostError` и сам решает, что ответить странице.

| Код | Когда |
|---|---|
| `denied` | Не разрешено: адрес вне префиксов `http`, адрес TSA, OCSP или CRL вне хостов PKI |
| `invalid` | Неверные аргументы: CBOR не того типа, неизвестное хранилище, handle, за которым нет ключа |
| `limit` | Превышен лимит: размер, число ключей, длина текста |
| `failed` | Операция не удалась: ввод-вывод, сеть, подпись |

Отказ пользователя ошибкой не считается: выбор ключа и открытие файла возвращают `None`, вопрос возвращает `false`, сохранение возвращает `None`.

`HostError` может содержать поле `cause` со стабильной строкой `<область>.<вариант>` (константы `oncl_pdk::abi::cause`, полный список в `cause::ALL`). По нему плагин различает сбои ядра так же, как модули оригинала различали варианты ошибок ядра. Поле необязательно: старое ядро его не пишет, старый плагин его не читает, а ошибка без причины кодируется теми же байтами, что и до появления поля. В `message` у таких ошибок лежит текст ошибки ядра.

| Область | Причины | Где |
|---|---|---|

## Встроенные модули

Модули `kz.gov.pki.knca.basics`, `kz.gov.pki.knca.commonUtils`, `kz.gov.pki.knca.applet.Applet` и `kz.gov.pki.ncalayerservices.accessory` написаны как модули WebAssembly того же ABI и вшиты в ядро (`oncl_plugin::Builtins`). Для них ABI 1 расширен новыми функциями и полями (`since` 0.1.0-alpha.5). Часть расширений доступна и плагинам с нужной capability: `call_locale`, `HostError.cause`, потоки выбора ключа `keys_flow_open`/`keys_flow_pick`, `keys_describe`, `tokens_scan`, `dialog_reader`, `file_choose_kind`, `pkix_path`, `SignerSel::OfCert` и `SignCmsExArgs.output`. Функции capability `builtin` (раздел [`builtin`](#builtin)) доступны только встроенным модулям: функции ядра (`core_*`), окна и файлы ключей (`dialog_csr`, `dialog_import`, `keystore_*`), держатель удостоверения (`tokens_id_card`) и данные, которые ядро хранит за модуль (`data_*`). Встроенный модуль:

- читается из `plugin.toml` с `builtin = true` и `id` под префиксом `io.github.arynyklas.openncalayer.builtin.`, причём только из бинарного файла ядра, а не из пакета;
- не устанавливается и не удаляется, в окне «Плагины» его нет; плагин не может занять имя его модуля (`ModuleTaken`, владелец `OpenNCALayer`);
- исполняется с доверием ядра (`Trust::Builtin`). Окна показываются без строки источника (`source` пуст, `detail` выбора ключа без имени плагина), `page_file_read` читает файл без окна согласия, метки времени, OCSP и CRL идут через транспорт ядра к любому адресу, как у модулей оригинала, TSA `basics` берётся из настроек ядра (`HostServices.tsa`), доступны функции capability `builtin`;
- обновляется только вместе с ядром.

Модули вшиты в бинарный файл парами `plugin.toml` + `plugin.wasm`, а не пакетами `.onclp`. Их собирает `build.rs` демона (`oncl-builtins-build`, профиль `builtin-wasm`, цель `wasm32-unknown-unknown`) или берёт готовыми из каталога `ONCL_BUILTINS_DIR` со сверкой `SHA256SUMS`, `SOURCE-SHA256` (исходники и тулчейн) и манифестов рабочего дерева. Путей машины сборки в модулях нет: места паник записаны без имён файлов (`-Zlocation-detail=none`), остальные пути переотображены. `version` и `min_core` манифеста равны версии ядра. Нативного кода у модулей нет. Вшиты четыре модуля:

- `kz.gov.pki.ncalayerservices.accessory`, крейт `oncl-builtin-accessory`;
- `kz.gov.pki.knca.basics`, крейт `oncl-builtin-basics`;
- `kz.gov.pki.knca.commonUtils`, крейт `oncl-builtin-commonutils`; язык окон хранится в общем для процесса ключе `locale` в `shared`;
- `kz.gov.pki.knca.applet.Applet`, крейт `oncl-builtin-applet`, модуль по умолчанию. Число оставшихся попыток PIN хранится в общем для процесса ключе `try_count` в `shared`, документ `signXml` держит ядро, а токен получает только PIN, введённый в окне ядра.

Байты больших документов сверяет с прямыми вызовами `oncl_pki` тест `tests/large_data.rs`. sha256 каждого модуля пишется в журнал при старте, а `openncalayer builtins` печатает строки `<id> <версия> <sha256 plugin.wasm> <sha256 plugin.toml>`. Если модуль не загрузился при старте, это фатальная ошибка с кодом выхода 1, и проверка здоровья обновления откатывает новую версию.

Экземпляры встроенного модуля не привязаны к сессии. Вызов берёт любой свободный экземпляр модуля или создаёт новый; после вызова экземпляр отпускает ключи, пароли, согласия и PIN страниц и возвращается в пул. Свободных экземпляров на модуль хранится не больше двух, а экземпляр, чья память после вызова больше порога, закрывается. Живых экземпляров модуля, занятых и свободных, не больше лимита; когда заняты все, вызов ждёт, пока один освободится. Встроенных модулей не больше четырёх.

На 32-битных системах (Windows 7 x86, 2 ГиБ адресного пространства) сборка проверяет, что одновременно помещаются:

- экземпляры встроенных модулей при наибольшей памяти (4 × 4 × 16 МиБ);
- экземпляры плагинов (64 × 16 МиБ);
- копии аргумента и результата host-функции встроенного модуля;
- данные, которые держит ядро (256 МиБ);
- один ответ со вставленными данными (не больше 128 МиБ);
- одно входящее сообщение WebSocket наибольшего размера (256 МиБ) и куча, в которой оно читается (16 МиБ, см. «Чтение запроса» ниже);
- запас 80 МиБ на код и кучу.

В эту сумму не входят копии буферов host-функций плагинов, сообщения других соединений и кадр, в который ответ копируется после вызова, когда данных вызова уже нет. Документы держит ядро, поэтому экземпляру хватает 16 МиБ. Живых экземпляров модуля четыре: пока одна страница держит окно модуля, вызовы других страниц без окон отвечают сразу. Пул встроенных модулей отделён от пула плагинов и не делит с ним лимит в 64 экземпляра. Общее для процесса состояние модуль хранит в `shared_*` на всё время жизни процесса.

Сбой встроенного модуля (trap, топливо, память, неверный `Output`, паника хоста) не превращается в `PLUGIN_ERROR`. Соединение обрывается без ответа, причина пишется в журнал на уровне `error`, экземпляр закрывается, и следующий вызов получает новый.

Чтение запроса. Кадр читается так же, как его читает `new JSONObject` оригинала (`orgjson::scan`): вложенность не глубже 127 уровней, повтор ключа в любом объекте считается ошибкой, значение ключа `module` не строится (объект или массив в нём читается и отбрасывается). Куча читателя ограничена `orgjson::SCAN_BUDGET`: 16 МиБ на 32-битных системах и 256 МиБ на 64-битных. В неё входят ключи читаемых объектов для проверки повторов (около 100 байт на ключ; объекты закрытых значений освобождаются), текст ключей и слов, которые нельзя взять из кадра как есть (с escape-последовательностями или без кавычек), и значение `module`. Если кадру нужно больше (на 32-битных системах это больше ста тысяч ключей в открытых объектах одновременно), он обрабатывается как любой текст, который org.json не прочитает: соединение обрывается без ответа. Модуль читает свою копию запроса отдельно, без этого предела, в пределах своей памяти. Запрос длиннее буфера между ядром и модулем до копирования и кодирования не доходит, соединение обрывается (`call_heap.rs`).

| Что | Лимит встроенного модуля |
|---|---|
| Линейная память экземпляра | 2 ГиБ на 64-битных системах, 16 МиБ на 32-битных (документы держит ядро; пакет — до 35 000 документов длиной до 1 КиБ в запросе) |
| Память экземпляра, после которой он закрывается по окончании вызова | 64 МиБ на 64-битных системах, 8 МиБ на 32-битных |
| Незанятые экземпляры на модуль | 2 |
| Живые экземпляры на модуль | 32 на 64-битных системах, 4 на 32-битных |
| Топливо на вызов | 200 000 000 000 |
| Буфер между ядром и модулем | 512 МиБ на 64-битных системах, на 32-битных — как память экземпляра |
| Данные, которые ядро держит за модуль (`data_*`) | за вызов 2 ГиБ на 64-битных системах и 256 МиБ на 32-битных; за все вызовы процесса 8 ГиБ и 256 МиБ |
| Ответ со вставленными данными | 2 ГиБ на 64-битных системах, 128 МиБ на 32-битных; длиннее — обрыв соединения |

### Производительность

Замеры находятся в `crates/oncl-builtin-tests/tests/bench.rs`. Это тесты с `#[ignore]`, они запускаются командой `cargo test --release -p oncl-builtin-tests --test bench -- --ignored --test-threads=1` и пишут результаты в `target/builtins-bench.json`. Берётся медиана 7 прогонов после прогрева, окна отвечают по сценарию без задержек, часы фиксированы. Столбец «нативный» показывает ту же работу, сделанную напрямую на Rust: выбор ключа ядром, `oncl_pki`, разбор и запись JSON. Второе сравнение идёт с прямыми вызовами `oncl_pki`. Пороги проверяет сам тест. В CI его запускает job `bench` в `scheduled.yml` (только вручную: `workflow_dispatch` с `run: bench`, на `windows-2025`) и сохраняет `builtins-bench.json` артефактом. Пределы памяти проверяет `tests/limits.rs` для 64 и 32 бит; CI запускает его и на `i686-pc-windows-msvc`. Таблица снята на машине разработчика (Intel Core i9-14900KF, Windows 11 x64, сборка release), а не на раннере CI. На машине, занятой другими сборками, отношения заметно хуже (у `cms` 64 МиБ до 1,7 вместо 1,2), поэтому пороги рассчитаны на свободную машину.

| Сценарий (WASM / нативный, мс) | 1 КиБ | 1 МиБ | 16 МиБ | 64 МиБ | Порог |
|---|---|---|---|---|---|
| `basics` `cms`, RSA, присоединённая | 1,03 / 0,69 | 5,7 / 4,2 (1,35) | 68 / 55 (1,24) | 282 / 242 (1,17) | +15 мс; 1,5; 2,5; 2,5 |
| `basics` `cms`, ГОСТ 2015, отсоединённая | — | 14,3 / 13,5 (1,06) | 103 / 92 (1,12) | — | 1,3; 2,0 |
| `basics` `xml`, весь документ (4 КиБ вместо 1 КиБ) | 1,25 / 0,75 | 19 / 17 (1,10) | 269 / 327 (0,82) | — | как `cms` |
| `commonUtils` `createCAdESFromFile`, RSA (WASM / `oncl_pki`) | — | — | — | 67 / 45 (1,48) | 3,0 |

Загрузка всех модулей занимает 10 мс (порог 250), вызов на новом экземпляре 0,5 мс (порог 20). Окно с 32 ключами и живыми проверками OCSP открывается не позже нативного (разница −11 мс, порог +30). Вшитые `plugin.wasm` вместе занимают меньше 1 МиБ (порог 4).

Документы держит ядро (функции `data_*`, см. раздел `builtin` ниже), и модуль их не копирует. Его память составляет 1,1 МиБ при любом размере данных, а топливо на вызов от размера данных не зависит: около 1,7 млн единиц и при 1 КиБ, и при 64 МиБ. Поэтому `BUILTIN_FUEL` с большим запасом покрывает вызов с данными самого большого сообщения (`fuel_covers_max_message`), а на 32-битных системах `basics` подписывает `cms` с данными 64 МиБ и `commonUtils` подписывает файл страницы 64 МиБ (`sign_max_page_file_fits`, `largest_cms_data`). Ответ с CMS от данных самого большого сообщения больше 256 МиБ проходит на 64-битных системах (`reply_over_256_mib_on_64_bit`); за вызов ядро держит не больше `BUILTIN_MAX_KEPT`. CMS для ответа кодирует само ядро (`SignCmsExArgs.output`), а PDK освобождает буфер `Input` до вызова обработчика.

Данные встроенного модуля держит ядро (`data_*`), а модуль передаёт только маркеры, чтобы документ не копировался через интерпретатор. Перед вызовом строковые значения запроса сохраняются в ядре и заменяются маркерами, если их общая длина не меньше `DATA_KEPT_MIN` (16 КиБ). Сохраняются строки не короче `DATA_KEPT_STRING_MIN` (1 КиБ), а в запросе длиннее `DATA_KEPT_LARGE` (1 МиБ) строки не короче `DATA_KEPT_SHORT_MIN` (64 байта); ключи объектов не сохраняются никогда. Маркер состоит из префикса вызова `oncl-data:<32 случайные hex-цифры>:` (`Input.data_prefix`, странице он неизвестен) и номера. Длиной строки считается длина её JSON-текста между кавычками, escape-последовательности учитываются как записаны. Так в ядре остаются и один длинный документ, и пакет коротких (`signXmls`, массивы `data`). На 32-битных системах экземпляру в 16 МиБ хватает пакета до 35 000 документов длиной до 1 КиБ, и пакет подписывается целиком (`batches_of_documents_are_signed_at_the_documented_size`; измерено 38 000 документов по 1000 байт и 39 000 по 40 байт). Ответ с подписями не длиннее `BUILTIN_MAX_REPLY`, поэтому пакет более длинных документов меньше. Короткие документы (меньше 64 байт) остаются в памяти модуля, и их число ограничивает она, а не ответ.

Запрос, который вместе с маркерами длиннее буфера между ядром и модулем, и запрос, строки которого вместе с записью о каждой (`KEPT_ENTRY_COST`) не умещаются в то, что ядро держит за вызов, отклоняются до копирования, ключей и кодирования, и соединение обрывается. Переписывается только запрос, который является корректным JSON, с проверкой каждой escape-последовательности (одиночный суррогат вроде `\ud800` делает запрос некорректным). Остальные байты запроса не меняются. Некорректный запрос модуль получает как есть и отвечает на него, как на короткий. Запросы переписываются только для модуля, который импортирует хотя бы одну функцию `data_*`; accessory их не импортирует и получает запросы без изменений.

Функции `data_*` принимают маркер этого вызова везде, где принимают данные (или сами данные), сохраняют результат и возвращают его маркер; чужой или неизвестный маркер даёт `invalid`. После вызова каждая JSON-строка ответа, равная маркеру вызова, заменяется данными, записанными так, как org.json пишет строку в `JSONObject.quote` (с `<\/`, как в ответах самих модулей). Данные должны быть в UTF-8, иначе это сбой модуля и обрыв соединения. Ответ собирается в буфер ровно своей длины, не длиннее `BUILTIN_MAX_REPLY`. Все данные вызова отпускаются, когда вызов возвращается. За вызов ядро держит не больше `BUILTIN_MAX_KEPT` байт (2 ГиБ на 64-битных системах, 256 МиБ на 32-битных), за все вызовы процесса не больше `BUILTIN_KEPT_BUDGET` (8 ГиБ и 256 МиБ). При превышении функция возвращает `limit`, и соединение обрывается, когда бы лимит ни был превышен (при разборе запроса или во время подписи) и что бы ни ответил модуль. Встроенные модули сами читают все длинные строки запроса, кроме данных подписи (`data_read`), поэтому их ответы те же, что без маркеров. Плагинам маркеры не выдаются: запрос плагина не переписывается, а функции `data_*` требуют capability `builtin`.

Пароли передаются как `Password::Text` от страницы или `Password::Secret` из окна. Пароли и пути в журнал не пишутся. Закрытый ключ не покидает ядро.

## Capabilities

Окна плагина показывают сайт (`Origin` или `UNIDENTIFIED`) и название плагина на языке окон. Текст плагина выводится как обычный текст, не как разметка. Первая host-функция, которая показывает окно, занимает общую для процесса очередь диалогов и держит её до конца `oncl_process`, а после trap отпускает. Поэтому окна плагина не перемешиваются с окнами basics и других модулей, и второй запрос ждёт, пока закончится первый.

`keys_choose` показывает те же окна, что `PKIExtras.sign`: выбор хранилища (PKCS#12 и JKS, по умолчанию оба), пароль, затем выбор ключа. В окнах видны сайт, название плагина и `detail`. `filter` задаёт те же условия, что `signerParams` и `signingParams`: назначения ключа, ИИН, БИН, серийный номер, просроченные ключи, цепочку CA (по умолчанию CA НУЦ; пустая цепочка отключает построение пути и OCSP) и проверку OCSP. Имена токенов в `storages` (`AKKaztokenStore`, `AKKZIDCardStore`, …) при включённой поддержке токенов дают в окне хранилища считыватели с носителем и поле PIN-кода. Поддержка токенов экспериментальная и по умолчанию выключена; тогда эти строки неактивны, как в `PKIExtras.sign`.

`keys_select` добавляет к `filter` условия `more`; ключ, который им не подходит, виден в окне вместе с причиной.

- `any_ext_key_usages`: хотя бы одно из назначений.
- `exclude_ext_key_usages`: ни одного из них.
- `knca_types`: хотя бы один тип Kalkan (`SIGNATURE`, `AUTHENTICATION`, …); неизвестное имя даёт `invalid`.
- `tin`: БИН сертификата, а если его нет, ИИН.
- `key_usage`: все биты из `digital_signature`, `non_repudiation`, `key_encipherment`, `key_agreement`.
- `obsolete_auth`: запрошенный clientAuth принимает и любой сертификат ГОСТ 2015-512, и sha256RSA с keyEncipherment.

`initial_path` подставляется в окно хранилища, если страница вправе назвать этот путь (локальный файл или сетевой путь, ранее выбранный пользователем в окне ядра); иначе окно открывается как обычно. `order` задаёт порядок ключей в окне по началу срока действия: `newest_first` (по умолчанию) или `oldest_first`.

`keys_open` открывает хранилище, которое назвал плагин, без окна выбора. `source` бывает `page_path` (путь от страницы), `bytes` (само хранилище) или `terminal` (считыватель токена). `password` бывает `text` или `secret` (id пароля из `dialog_password`, который плагин не видел). Для пути от страницы действуют правила:

- он разрешён только с `key_files = true` в манифесте, иначе `denied`; это проверяется при вызове, потому что функция одна и для байтов;
- он читается по правилам путей страницы: устройства (`\\.\…`), каналы и каталоги дают `not_found`, сетевой путь допускается только выбранный ранее в окне ядра, файл больше 64 МиБ даёт `corrupt`; до согласия ничего не читается;
- пару (сайт, путь к файлу) пользователь разрешает в окне ядра «Сайт … через плагин … просит открыть хранилище ключей: <путь>» один раз за сессию; отказ или закрытое окно дают `declined`.

Байты хранилища открываются без окна, потому что они и пароль уже есть у страницы. Поддерживаются хранилища PKCS#12 и JKS. Хранилище PKCS#12 читается один раз. Если в нём больше 16 ключей или больше 4 зашифрованных частей (safe), результат `corrupt`, и это выясняется до проверки пароля и до вывода ключей. Ключи в зашифрованной части считаются после её расшифровки, но до расшифровки любого ключа. Если все ключи хранилища не помещаются в свободные handle, результат `limit`, и не открывается ни один.

Токен (`terminal`) открывается в названном считывателе с PIN-кодом из `password`, и плагин получает все ключи носителя с сертификатом, по handle на каждый. PIN `text` пришёл от страницы или плагина и уходит носителю только с согласия пользователя. Окно ядра называет сайт, плагин, носитель, считыватель и, если носитель их сообщает, оставшиеся попытки. Согласие даётся один раз на пару (сайт, считыватель) в экземпляре. Если попыток осталось две или меньше, окно появляется перед каждым PIN, а после неверного PIN следующий снова требует согласия. PIN `secret` пользователь ввёл сам в окне ядра, и он уходит без вопроса, но повторная отправка PIN, который носитель уже отверг, требует согласия. Ядро само PIN не повторяет. Отказ или закрытое окно дают `declined`, и носителю ничего не отправляется ([tokens.md](tokens.md#pin-от-страницы)). Ответы:

- `no_device`: поддержка токенов выключена, службы смарт-карт нет, в считывателе нет носителя этого хранилища или он извлечён, хранилище облачное;
- `wrong_password { tries_left }`: неверный PIN. Число попыток сообщают Kaztoken, удостоверение личности и AKey; один вызов тратит не больше одной попытки;
- `wrong_password { tries_left: None }`: PIN, который носитель не примет (не ASCII, а у удостоверения не 4 символа). Носителю при этом не отправляется ни одной команды;
- `blocked`: PIN заблокирован; `no_keys`: на носителе нет ключей с сертификатом; `failed`: ошибка носителя или службы.

Handle ключа токена хранит PIN-код в памяти ядра до `keys_release` или до конца экземпляра, после чего память обнуляется. Каждая подпись выполняется отдельным подключением к носителю с проверкой PIN, после которого карта сбрасывается. Если носитель отверг PIN, handle больше его не отправляет. Подпись носителя проверяется открытым ключом сертификата до того, как плагин её получит. Писать на токены (создавать ключи, записывать сертификаты) плагины не могут.

`keys_sign_cms_ex` собирает CMS по профилю плагина тем же кодом, что `keys_sign_cms`. Параметры:

- `content`: `data` (подписываются данные) или `digest` (готовый хеш идёт в messageDigest как есть и в CMS не вкладывается);
- `cosign`: `auto` (подписанный CMS с вложенным содержимым подписывается вторым подписантом, как `createCAdES`), `never` или `into` (новый подписант добавляется в данный CMS, подписывается `content`);
- `econtent_type`: OID типа содержимого и атрибута contentType;
- `digest`: допускается только хеш алгоритма подписи сертификата, другой даёт `invalid`, потому что получатели НУЦ проверяют только эту пару;
- `attrs`: флаги contentType, messageDigest, signingCertificateV2 (SHA-256 сертификата), `signing_time { at: now | unix_ms, form: auto | utc | generalized }` и `extra`, атрибуты плагина в виде OID и значений готовым DER. Значение, которое не разбирается как DER, и тип, который уже добавлен флагом, дают `invalid`. Атрибуты ложатся в DER SET в порядке сортировки. Без единого атрибута подписываются сами данные;
- `certificates`: `signer`, `chain` (цепочка `keys_chain`) или `extra` (сертификат подписанта и данные);
- `timestamp`: метка TSA на новом подписанте (как `tsp_stamp` с `replace`).

Метки времени, OCSP и CRL запрашивает ядро, а не плагин, и только у хостов PKI: `tsp.pki.gov.kz`, `ocsp.pki.gov.kz`, `crl.pki.gov.kz`, `pki.gov.kz`, `test.pki.gov.kz`, `crl.root.gov.kz`, `crl1.root.gov.kz` (на двух последних лежат CRL удостоверяющих центров НУЦ) и их поддоменов, по `http://` или `https://`. Адрес задаёт `PkiUrl`: `default` (`http://tsp.pki.gov.kz`, `http://ocsp.pki.gov.kz`), `fixed` (заданный адрес) или `from_cert` (адрес из сертификата: для OCSP из authorityInfoAccess, для TSA из time-stamping в subjectInfoAccess или authorityInfoAccess; если в сертификате адреса нет, результат `failed` с `other`). Адрес другого хоста, в том числе взятый из сертификата или точки распространения CRL, даёт `denied`. Таймаут задаётся от 1 мс до 60 с, повторов метки не больше 10, иначе `invalid`. `PkiMethod`: `get` (base64 запроса после `/` как есть), `get_url_encoded` (base64 в кодировке URL, как в NCALayer), `post { content_type }` (без типа используется тип протокола), `post_with_path` (POST тела на адрес GET), `get_under(n)` (GET, пока закодированный запрос короче `n`, иначе POST). `Nonce`: `none`, `random(n)` или `value(bytes)`.

Перенаправлениям ядро в этих запросах не следует (3xx считается ответом), так что запрос не уходит с хостов PKI, даже если ответ указывает на другой адрес. Каждый запрос ядра к хостам PKI, включая повтор метки, OCSP о каждом подписанте и скачивание каждого CRL, входит в лимит 64 HTTP-запросов за вызов (раздел [Лимиты](#лимиты)). Сверх лимита запрос не отправляется, а результатом становится сетевой сбой с `kind = other`.

`TsaChoice` бывает `basics` (Стрибог-512, политика 1.2.398.3.3.2.6.4), `kalkan` (SHA-256, политика 1.2.398.3.3.2.6.2), оба через GET с кодировкой URL на `tsp.pki.gov.kz`, или `custom(TsaSpec { url, method, hash, policy, nonce, cert_req, retries, timeout_ms, check_skew_ms, require_tsa_eku })`. Ответ TSA проверяется всегда: HTTP 200 с `application/timestamp-reply`, статус granted, подпись токена, nonce, отпечаток и политика запроса (без политики подходит любая). С `require_tsa_eku` проверяется назначение timeStamping у подписанта токена, с `check_skew_ms` проверяется, что genTime не дальше этого значения от часов ядра. `tsp_stamp` ставит метку на подписантов `signers`: `last`, `index(i)`, `all_unstamped` или `of_cert(сертификат)`, то есть на первого подписанта этого сертификата в том порядке, в каком его находит Kalkan. Метка заменяет прежнюю (`replace`) или добавляется к ней (`append`); в атрибут идёт токен (`token`) или весь `TimeStampResp` (`whole_response`). CMS, который не читается, даёт `invalid` с причиной `cms.*` и текстом ошибки ядра.

`ocsp_fetch` спрашивает о сертификате, издатель которого задан как `host_cas` (CA ядра), `given` или первый из `verifies_cert`, чей ключ проверяет подпись сертификата (если такого нет, результат `invalid`). `cert_id_hash` задаёт хеш CertID, `nonce` добавляет расширение nonce в запрос. Ответ возвращается таким, каким пришёл, с `BasicOCSPResponse` и статусом сертификата. С `check` ответ проверяется так же, как в проверках OCSP ядра: ответчик по цепочке CA ядра с OCSPSigning и nocheck, подпись, актуальность, CertID, эхо nonce. Найденная проблема попадает в `problem` (`responder_unverified`, `ocsp_stale`, `nonce_mismatch`, `malformed`), и статус тогда не сообщается.

`crl_fetch` скачивает полный CRL из точек распространения сертификата, а если у сертификата есть FreshestCRL, то и дельта-CRL (без полного он не используется). Статус по дельте применяется поверх полного; запись removeFromCRL означает, что сертификат не отозван.

Сетевой сбой не считается ошибкой host-функции и возвращается как `NetFailure { stage, kind, address, detail }`: `stage` принимает значения `tsp`, `ocsp`, `crl`; `kind` бывает `unknown_host`, `connect`, `timeout`, `tls`, `http(status)`, `invalid_response`, `rejected(status)`, `clock_skew`, `other`; `address` содержит хост; `detail` содержит текст ошибки ядра (у метки времени такой же, как в сообщениях commonUtils).

`cms_verify` проверяет каждого подписанта отдельно и по каждой проверке сообщает `ok`, `skipped` или `fail(problem)`:

- `signature`: подпись над подписанными атрибутами и messageDigest над содержимым. `data` передаёт содержимое открепленной подписи, без него результат `no_content`. Проблемы: `digest_mismatch`, `bad_signature`, `no_signer_cert` (в CMS нет сертификата подписанта), `malformed` (подписант не читается);
- `ess_cert_id`: signingCertificateV2 против сертификата (`ess_cert_id_mismatch`; без атрибута `skipped`);
- `validity`: срок действия сертификата (`expired`, `not_yet_valid`);
- `path`: путь через CA (`unknown_ca`, если издатель не найден, `path_invalid`, если путь не сходится);
- `revocation`: статус (`revoked { at_ms, reason }`, `status_unknown`, если ответчик не знает сертификат или ответ относится к другому, `responder_unverified`, `ocsp_stale`, `crl_invalid`, `malformed`, `net(NetFailure)`);
- `tsp`: метка времени подписанта, если она есть (`tsp_imprint_mismatch`, если метка от другой подписи, `tsp_invalid`, если она не проверяется или у сертификата TSA нет пути на её genTime).

Время проверки `at` бывает `now`, `signing_time` (атрибут signingTime) или `tsp_time` (genTime проверенной метки); если атрибута или метки нет, используется текущее время. Путь строится на это время, сдвинутое в срок действия сертификата (срок проверяется отдельно). `chain`: если не задан, используются CA ядра; `[]` отключает построение пути; список задаёт эти CA, и они же считаются доверенными для ответчиков OCSP. `revocation`:

- `none`;
- `embedded_ocsp`: только ответ OCSP из CMS (атрибут id-pkix-ocsp-basic `1.3.6.1.5.5.7.48.1.1` с `OCSPResponse` или `BasicOCSPResponse`, в OCTET STRING или без, подписанный или нет; либо id-ri-ocsp-response в `crls`), проверенный на время `at`;
- `live_ocsp`: ответ из CMS, если он есть, иначе ответчик сертификата (GET, CertID SHA-1);
- `live_ocsp_then_crl`: то же, плюс CRL, если ответчик не дал проверенного ответа.

Отзыв после времени проверки не учитывается, потому что подпись сделана раньше. Ответчики и точки распространения из сертификатов спрашиваются только на хостах PKI и без перенаправлений; другой хост даёт `net` с `kind: other`. `require_key_usage` выбирает из сертификатов, подходящих под идентификатор подписанта, первый, у которого есть все указанные биты keyUsage. `first_signer_only` ограничивает проверку первым подписантом.

#### Как `cms_verify` работает на самом деле

Решения принимает общий валидатор SDK (`validate_cms`), а `cms_verify` только переводит его результат в формат `VerifyReport`. Поэтому описание выше нужно читать с такими поправками:

1. `at` не используется. Поле и `VerifyAt` оставлены, чтобы не менять формат на проводе. Подписант проверяется на `genTime` проверенной метки времени с доверенным якорем, а без неё на текущее время, и никогда на собственный `signingTime`. В профиле совместимости с NCALayer (`live_ocsp`, `live_ocsp_then_crl`) метка фиксирует время, даже если статус её TSA получить нельзя.
2. `live_ocsp` тоже обращается к CRL.
3. Недоступный статус в режимах `live_*` даёт `fail(net{stage: ocsp, address: хост ответчика, kind: other})`, в режимах без сети `fail(status_unknown)`. Ответ «unknown» неотличим от отсутствия ответа.
4. У `revoked` нет `reason`: CRLReason всегда `none`.
5. `unknown_ca` не выдаётся, ошибка пути всегда `path_invalid`.
6. При `chain: []` нет якорей доверия, и `path` и `revocation` всегда `skipped`.
7. `tsp.check` остаётся `ok`, если валидатор только не может доказать статус TSA (`timestamp_unproven_ok`). Метка другой подписи или отозванный TSA, как и TSA без якоря, дают `fail`.

Из-за пункта 7 настольный хост мягче хоста ядра без интерфейса. Там неподтверждённая метка означает неизвестный статус, и вердикт `Valid` на этом основании невозможен, а плагин, который читает поля отчёта настольного хоста, увидит, что всё в порядке. Плагин `k2sign` передаёт `at = signing_time`, `chain: []`, `revocation: none`. Срок действия поэтому проверяется на текущее время, и подпись сертификатом, истёкшим после подписания, даёт `VALIDITY_EXPIRED`. Отзыв `k2sign` не проверяет. Тесты k2sign в `oncl-port-tests` проходят.

`keys_sign_xml_ex` подписывает XML так, как этого ждут получатели плагина. Незаданные поля дают алгоритмы, канонизацию и место подписи как у `keys_sign_xml`, но с переводами строк Santuario и байтами документа как есть; форма `keys_sign_xml` получается с `strip_whitespace` и `serialize { declaration: false, standalone_no: false, trim: true }`. Поля:

- `placement`: `document_element` (последним дочерним элементом корня), `first_child_of_document` (последним дочерним элементом первого узла документа; если это комментарий или PI, возникает ошибка, как у оригинала) или `parent` (в элемент по XPath `parent`, только вместе с ним);
- `namespaces` (префикс → URI) и `other_prefix_uri` (URI любого другого префикса) переводят XPath на сравнение по пространствам имён: имя без префикса означает отсутствие пространства имён, несвязанный префикс даёт ошибку. Без них имена сравниваются как написаны, а `SOAP-ENV:` считается пространством SOAP 1.1;
- `signature_method`: известный URI (RSA-SHA256 `xmldsig-more`, ГОСТ 2004 и 2015-512 Kalkan), подходящий ключу. Подписи RSA-SHA1 (`xmldsig`, `xmldsig-more`) не создаются, запрос получает отказ;
- `digest_method`: URI дайджеста, по умолчанию парный методу подписи;
- `signed_info_c14n`: канонизация SignedInfo;
- `transforms`: сначала `enveloped`, затем не больше одной канонизации; подпись всего документа возможна только с `enveloped`;
- `signature_id`: атрибут `Id` подписи;
- `signing_time_object`: `ds:Object/ds:SignatureProperties/ds:SignatureProperty Id="<property_id>" Target="#<signature_id>"` с неквалифицированным `<timestamp>`, а при `target_ref` ещё и вторая ссылка на него с теми же преобразованиями;
- `strip_whitespace`: без переводов строк между элементами подписи. Без этого флага после каждого элемента идёт перевод строки, как у Santuario;
- `base64_line_breaks`: base64 строками по 76 символов с `&#13;` (`true`) или одной строкой (`false`). По умолчанию поведение то же, что у Santuario с тем же переключателем: строками, если нет `strip_whitespace`;
- `output`: `as_is` (байты документа со вставленной подписью) или `serialize { declaration, standalone_no, trim }`, как при записи через JDK `Transformer`: собственное объявление XML (`<?xml version="1.0" encoding="UTF-8"?>`, с `standalone="no"`) вместо исходного, без пробелов до первого узла, а с `trim` и без пробелов по краям; остальное остаётся исходными байтами.

Ошибка подписи даёт `failed`.

`xml_verify` проверяет каждую подпись документа сертификатом из её `KeyInfo` так же, как это делает ядро при проверке подписей: более поздние подписи, дочерние для корня, не входят в то, что подписали более ранние. Подписи возвращаются в порядке документа; сертификат, который не читается, возвращается пустыми байтами. Если документ не разбирается, результат `invalid`.

`keys_sign_xades` создаёт подпись XAdES-BASELINE (XAdES 1.3.2) всего документа: enveloped `ds:Signature` последним дочерним элементом корня, с `Id` и `ds:Object` с `xades:QualifyingProperties`. `SignedProperties` содержит `SigningTime` (время ядра, UTC) и `SigningCertificateV2` (SHA-256 сертификата подписанта); их подписывает вторая ссылка с `Type="http://uri.etsi.org/01903#SignedProperties"` и Exclusive XML Canonicalization. Уровень `t` добавляет `SignatureTimeStamp` над элементом `ds:SignatureValue` в Exclusive XML Canonicalization (TSA из `tsa`, хеш тот, что использует эта TSA). Уровень `lt` добавляет ещё `CertificateValues` (сертификаты `chain` от издателя подписанта вверх) и `RevocationValues` о подписанте и о каждом сертификате `chain`, кроме самоподписанного корня; издатель берётся из `chain`, и если его там нет, результат `invalid`. Сведения об отзыве берутся из ответа OCSP от ответчика, указанного в AIA сертификата (`OCSPValues`), а у сертификата без адреса ответчика, как у промежуточных CA НУЦ, из CRL его точек распространения: полного и, если есть FreshestCRL, дельты (`CRLValues`). Если у сертификата нет ни ответчика, ни точки распространения, CRL недоступен или не проходит проверку, подпись не создаётся (`failed` со `stage = crl` или `invalid` с `crl_invalid`), так что пропусков в сведениях об отзыве не бывает. Сертификат, отозванный по OCSP или CRL, даёт `invalid` с `revoked`. Метка времени, OCSP и CRL запрашиваются только у хостов PKI, как в `tsp_*`, `ocsp_fetch` и `crl_fetch`. URI алгоритмов выбираются по сертификату, как у `keys_sign_xml` (ГОСТ 2015-512, ГОСТ 2004, RSA-SHA256), или берутся из `signature_method`/`digest_method`; подписи RSA-SHA1 не создаются. Подпись проходит `xml_verify`. Побайтного совпадения с другими реализациями XAdES эта функция не обещает.

#### Что на самом деле выдаёт `keys_sign_xades` в настольном хосте

Настольный хост подписывает через `oncl_xml::xades::sign`, старый API с форматом на проводе, а не через построитель ядра (`SignRequest::xades_legacy`, `prepare_spec_source`). Поэтому его выход не является полным XAdES-BASELINE: в нём нет обязательного `DataObjectFormat`, канонизация Inclusive C14N 1.0 (`REC-xml-c14n-20010315`) вместо Exclusive, другие `Id` подписи и ссылок. Подписи проверяются тем же сертификатом и содержат `SignedProperties`/`SigningCertificateV2`, но байты у хостов разные. Различие закреплено тестом `oncl-core/tests/batch.rs::guarded_xades_legacy_b_and_the_desktop_wire_shape_differ_exactly_as_documented`. Описание выше (BASELINE, Exclusive C14N) верно для построителя ядра, которым пользуется хост без интерфейса, а не для настольного.

Закрытый ключ остаётся в ядре, а плагин получает только handle, номер ключа в своём экземпляре. Номера растут и не повторяются, поэтому handle после `keys_release` не может указать на другой ключ. Handle действует до `keys_release` или до конца экземпляра. Handle другого экземпляра, освобождённый или неизвестный handle даёт `invalid`.

#### Потоки выбора ключа

`keys_flow_open` и `keys_flow_pick` разбивают окна выбора ключа ядра на шаги и поддерживают правила, которыми различались встроенные модули. Поток живёт до конца вызова `oncl_process`. За вызов открывается не больше 4 потоков, и отменённое окно хранилища тоже считается. Индикатор занятости показывается с момента ответа в окне хранилища до первого окна ключа потока или до конца вызова. Правила `FlowArgs`:

- `storages`: хранилища окна в этом порядке, повторы сохраняются. Пустой список означает окно без хранилищ (у `keys_choose` пустой список означает PKCS12 и JKS); неизвестное имя даёт `invalid`;
- `readers`: `live` берёт считыватели с носителем, найденные при открытии окна (при включённой поддержке токенов); `fixed([{ storage, reader }])` берёт перечисленные, первым первый, и каждый из них должен сейчас держать носитель своего хранилища, иначе `invalid`; `none` делает строки токенов неактивными. После ошибки токена окно открывается снова с тем же считывателем (у `live` только при ответе токеном), после ошибки файла с тем же путём;
- `start`: `recent` открывает последний открытый файл, `page(путь)` открывает путь страницы, если страница вправе его назвать (иначе окно открывается пустым, без ошибки; длина пути не ограничена), `empty` открывает пустое окно. С `remember` путь открытого файла становится последним (считыватель не запоминается);
- `detail`: строка для обоих окон до 1 КиБ; у плагина перед ней стоит его название;
- `non_empty_password` отвергает пустой пароль; `inner_password_policy` проверяет пароль ключей внутренних систем: 8–32 символа, латинские заглавная и строчная буквы, цифра и один из `#$^+=!*()@%&_-`; `same_storage` отвергает ответ не предложенным хранилищем ещё до чтения;
- `file`: `open` принимает любой файл, который открывает система; `chosen` принимает обычный файл на диске до 64 МиБ, в том числе на сетевом диске, но не устройство;
- `knca_types` оставляет в окне только ключи этих типов Kalkan (неизвестный тип даёт `invalid`); `none` показывает ошибку окна хранилища, когда ключей не осталось (`no_keys`, `no_signing_keys`, `no_auth_keys`); с `empty_is_none` её получает и пустое хранилище;
- `order`: `store`, `newest_first`, `oldest_first` (по notBefore); `checks`: `settled` (можно выбрать любой ключ) или `live { filter, more }` (условия `keys_select` и OCSP; окно ключа следит за проверками, которые начинаются при первом выборе);
- `skip_blocked_reader`: считыватель, носитель которого ответил «PIN заблокирован», в этом потоке больше не используется.

#### Выбор ключа в ручном окне

`Compiled::call_manual(backend, bindings, &dyn PluginInteraction, request)` (`oncl_plugin::manual`) исполняет плагин так же, как `call_headless`, но на выбор ключа отвечает ядро: пользователь уже привязал в окне один ключ (`BoundKey { handle, alias, certificate }`, без секрета и пути к хранилищу). `PluginInteraction` содержит только данные (ключ, часы, HTTP-транспорт и кэш OCSP для фильтра; готовая реализация называется `BoundInteraction`), интерфейс ему не нужен.

- `keys_select`, `keys_choose`, `keys_flow_open`, `keys_flow_pick`: фильтр плагина (`Filter`/`FilterMore`, `knca_types` потока) вычисляют функции `oncl-flows` по сертификату привязанного ключа. Если ключ подходит, плагин получает `Chosen { handle, alias, certificate }` (у потока один ключ в `FlowOpened`), если нет, `None`, и поток не открывается. Ответ всегда относится к одному и тому же ключу.
- `keys_terminals` возвращает `[]`, `tokens_scan` возвращает `enabled = false`, `reply_drop` разрешён и ничего не ломает.
- `keys_open` вызывает trap `Denied`; `dialog_*`, `file_*`, `keystore_*`, `core_open_window` вызывают trap `InteractionRequired`, как в `call_headless`. Плагин видит один и тот же trap и не может отличить ручное окно или пробный прогон от настоящего вызова.
- Остальные импорты уходят в `CapabilityBackend`. Сервер и CLI `call_manual` не вызывают, у них остаётся `call_headless`.
- Текст плагина на этом уровне не показывается.
- Каждый отличающийся фильтр вычисляется за вызов не больше одного раза (ключ и часы в вызове не меняются), и разных фильтров не больше `MAX_EVALUATIONS` = 16; сверх этого возвращается `limit`. `checkpoint()` вызывается до вычисления. Один выбор может ждать ответчика OCSP до 6 с. Аргументы, которые окно диалогов проверяет отдельно (имена хранилищ, длина `detail`/`initial_path`/`error`, считыватели), здесь не проверяются, потому что окон нет.
- Транспорт OCSP в `BoundInteraction` должен быть транспортом PKI хоста с той же политикой хостов, что у `ocsp_fetch` и `ca_*` (адрес берётся из AIA сертификата, а не от плагина). `BoundInteraction` строится заново на каждый вызов, и `now` не замораживается.
- Ответ `None` не лишает плагин ключа. Фильтр носит только совещательный характер, handle остаётся числом, а право на применение ключа даёт билет, одобрение и `before_use`, а не `keys_select`.

Хост при этом обязан выполнять следующее. `BoundKey` строится из той же привязки, которую держит backend; HTTP идёт через транспорт PKI хоста и общий `OcspCache`; `BoundInteraction` создаётся заново для каждого вызова. Каждый handle от плагина сверяется с единственным привязанным, а для прочих возвращается тот же `PermissionDenied`. `keys_release` привязанного handle ничего не делает и может вызываться повторно. `keys_describe` и `keys_chain` отвечают из единственной привязки. `max_uses = 1` обеспечивается билетом.

Билет применения ключа (`oncl-core`, раздел «Key-use ticket» в `docs/dev/sdk.md`). Для операции, объявленной в манифесте, ядро строит билет `PluginUse` из тех же декодированных `args`, которые уходят в движок: вид, SHA-256 фактического содержимого, `options_sha256` через `Profile::encode`, единственный привязанный ключ, `max_uses = 1`. Билет кладётся в `OperationContext`, а `sign_digest` переносит его в `KeyUseEvent::plugin()`. `PluginConsentGuard::before_use` разрешает применение ключа только по билету и неизрасходованному `PluginApproval`, иначе возвращает `PermissionDenied` до обращения к ключу. `cosign = Auto` принудительно меняется на `Never` до построения билета. Сервер (`DurableAuditGuard`) и CLI (`Authority`) пропускают применение ключа по билету только при гранте с `plugin_bytes = true` (`--plugin-bytes` в CLI), подробнее в [manual-plugins.md](manual-plugins.md). Операции плагинов без объявлений работают как прежде. Плагин, объявивший хотя бы одну операцию, вызывается через `plugin_call` только под объявленным именем, кем бы ни был вызывающий; иначе `PermissionDenied` возвращается до запуска модуля, а в `OperationContext::plugin_refusal` записывается `TicketRefusal::UndeclaredOperation`. Сервер пропускает такой грант с ошибкой в stderr, CLI отказывает. Отказы проверки пишутся в ограниченный журнал по `OperationId` (`refusals`/`take_refusals`).

Согласие и одобренный вызов (`oncl-core`, раздел «Manual window: consent summary, approval, approved call» в `docs/dev/sdk.md`):

1. `ConsentGuard` в `oncl-ui` отказывает любому событию, у которого `KeyUseEvent::is_plugin()`, и не тратит на него своё согласие. Метод доступен без дополнительных функций крейта, потому что `oncl-ui` не включает `oncl-core/plugins`; тест с билетом использует dev-функцию `testing`.
2. Движок ручного окна собирается через `EngineServices::with_plugin_keys(provider, Arc<PluginConsentGuard>)`, и это его единственная проверка. `Engine::plugin_call_approved` выдаёт одобрение проверке (`grant`) и отзывает его в `Drop` при успехе, ошибке, trap и панике. Одновременно идёт один одобренный вызов (`Busy`); движок без этой проверки отказывает с `NoGuard`.
3. `ApprovedUse` и `PluginApproval` строит только ядро. `Engine::plugin_prepare` вычисляет всё из объявленной операции, замороженных байтов параметра и привязанного ключа и возвращает `PluginPrepared` с доверенным `ConsentSummary` без текста плагина. `PluginPrepared::approve` принимает `UserConfirmation`, который создаёт единственная функция `UserConfirmation::after_user_confirmed(&ConsentSummary)`; он содержит SHA-256 показанной сводки, и подтверждение другой сводки одобрения не даёт. Хост вызывает эту функцию только из обработчика действия пользователя на кнопке подтверждения, после показа сводки; автоматического ответа и хранения согласия нет. Публичных конструкторов `PluginApproval` и `ApprovedUse` нет; для тестов проверки есть `for_tests` под функцией `testing`, которая в релиз не входит.
4. Для `cms_ex` с `content_form = "digest"` ядро само считает дайджест замороженного документа алгоритмом подписи ключа той же функцией `signature_algorithm`, что и подписант: ГОСТ 34.311, Стрибог или SHA-2 по сертификату и политике контекста.
5. Nonce занимает 16 байт из `getrandom`, срок жизни отсчитывается по монотонному `Instant`, по умолчанию `APPROVAL_TTL` = 120 с; его можно только уменьшить, ноль даёт отказ.

Перед запуском модуля `plugin_call_approved` заново выводит применение ключа из переданных параметров и сверяет его с одобрением. Если отличается документ, текст, ключ, handle, вызывающий, операция или вызов либо одобрение просрочено, возвращается отказ `NotApplied` до запуска модуля, так что модуль не получает неодобренный документ. Решающей проверкой остаётся `before_use`. Результат возвращается как `ApprovedCall`: ответ модуля, `applied()` (после trap модуля, когда ключ уже применён, это `Applied`) и типизированные `refusals()`. Содержимое `derived` не запускается.

Страница «Плагины» окна инструментов (`oncl-ui`, `crates/oncl-ui/src/workspace/plugins/`, `ui/manual_plugins.slint`) стоит в боковой панели рядом с Sign и Verify. Шаги: список, форма, ключ, подтверждение, выполнение, результат.

Список строится из операций `PluginService::manual_plugins()` по плагинам. Имя операции (проверенный идентификатор, который перепроверяется при отрисовке) выводится как текст хоста, а название плагина и `label` операции только в рамке «слова самого плагина» (`PluginFrame`, та же подпись, что в окне установки). Операция без применения ключа показана, но не открывается, потому что подтверждать нечего. Для каждого установленного плагина без операций для окна выводится одна строка: «нет операций для окна ручных инструментов, почему — OpenNCALayer не знает». Порты в коде не перечисляются, список строится из реестра. Плагин с нечитаемым пакетом показывается строкой без причины, причина пишется в журнал. Установленные плагины без операций для окна перечислены с причиной, которую хост вычисляет по манифесту и реестру (`WithoutReason`: `NoOperations`, `NoManualOperations`, `UnsupportedNetwork`, `NotRegistered`), без зашитых имён портов.

Форма строится из объявленных `[[operations.params]]`. Для document выбирается файл с пределом `max_bytes` из объявления; файл читается в память один раз и сравнивается с пределом по открытому файлу. У text предел задан в символах. У choice вариант по умолчанию не подставляется. Есть ещё flag и locale.

Ключ выбирается так же, как на странице Sign: файл хранилища, пароль, список сертификатов (`open_key_store`). `PluginKeyBinding` строится из той же копии хранилища, которой подписывает движок (`KeySelector::inline`), а отпечаток сертификата сверяется с выбранным до подготовки.

Подтверждение. `Engine::plugin_prepare` выполняется в рабочем потоке, и страница показывает `ConsentSummary`: операцию, id и версию плагина, SHA-256 пакета, вид применения ключа и профиль словами (строки `Operation::consent`/`ProfileFact`), сеть с адресами, имя файла с пометкой «выбран вами», размер и полный SHA-256 (только для чтения, текст можно выделить), ключ (имя, серийный номер, CN, отпечаток, срок). Введённые значения показываются отдельным блоком «не входит в то, что разрешается». Если сводка ядра и объявленная операция расходятся (имя, вид, введённый текст XPath), подтверждение не показывается. Кнопка называет действие («Подписать плагином {операция}») и становится доступной после подготовки и 600 мс без ввода. При открытии фокус стоит на «Отмена», кнопке по умолчанию; Enter без Tab ничего не подтверждает, Escape отменяет с любого шага, длинный текст прокручивается с клавиатуры (полоса прокрутки входит в порядок Tab). Единственный вызов `UserConfirmation::after_user_confirmed` в рабочем дереве находится в `consent::user_confirmed`, а её единственный вызов стоит в обработчике этой кнопки после решения контроллера; тест `the_users_confirmation_is_made_in_one_place_only` проверяет это по исходникам.

Выполнение. Затем вызываются `approve(…, ttl)` (120 с; согласие не хранится и для каждого вызова запрашивается заново) и `plugin_call_approved` в рабочем потоке. Предел исполнения составляет 300 с от подтверждения (`JobControl::set_deadline`). При отмене или закрытии окна до проверки перед применением ключа ключ не применялся, а после неё исход неизвестен и пишется в журнал. Окно с работающим плагином не закрывается, пока рабочий поток не ответит или не истечёт ожидание отмены (10 с). Пароль убирается из поля при отправке и хранится контроллером до выбора сертификата (страница ключа закрывается после 300 с простоя), затем переходит в рабочий поток и обнуляется при любом выходе. В журнал он не пишется.

Результат (`ApprovedCall`). Зелёным успехом показывается только `Applied` без отказов и ошибки, и даже тогда сказано, что подпись в ответе не проверялась. Если ключ применён, но плагин упал, это не успех. `Unknown` показывается как «неизвестно, считайте, что применён». Отказы ядра описываются словами через заменяемый слой `RefusalWords` (локальное сопоставление `TicketRefusal`). Ответ плагина показывается только в его рамке, без управляющих и bidi-символов и не длиннее 2000 символов (остаток подсчитывается). Ответ вызова, подтверждённого как применённый (`Applied` без отказа и ошибки, ответ есть), можно сохранить кнопкой «Сохранить ответ плагина (не проверен этой программой)». Она стоит после ответа и перед «К списку», не является основной, и Enter её не нажимает. Кнопка пишет весь ответ как получен, без извлечения, очистки и обрезки до 2000 символов, в один файл `.json`. Хост не знает, где в ответе подпись (у каждого порта своя форма), поэтому её не извлекает. Имя файла хост составляет из идентификатора операции и id плагина (`[a-z0-9._-]`, не длиннее 96 знаков, всегда `.json`, никогда не из ответа), а место выбирает пользователь в диалоге хоста. Запись атомарна: временный файл в той же папке, `sync_all`, жёсткая ссылка на цель. Там, где жёстких ссылок нет (FAT/exFAT и часть сетевых папок), файл создаётся эксклюзивно через `create_new`, а неполный файл при сбое удаляется. Существующий файл не заменяется (`save_exists`), сбой записи называется своей причиной, а ответ больше `max_transfer` отклоняется с указанием размера. Файлового вывода у ручного вызова нет: манифест не объявляет вывод, у `plugin_call_approved` нет `PluginOutputBinding`, и все 9 портов возвращают строку ответа. Поэтому сохраняется ответ, а не подпись. Копия ответа в состоянии страницы стирается при выходе.

Движок страницы отдельный (`plugin_offer`: `with_plugin_keys` с собственным `PluginConsentGuard`, документный `ConsentGuard` не используется). Его собирает `ManualPluginSource`, в приложении это `DesktopManualPlugins` на `PluginService`. Реестр читается заново при каждом открытии страницы и по кнопке «Обновить список». Строки ru/kk/en собраны в одной таблице (`texts.rs`) с тестом на все языки: поля, плейсхолдеры, письменность.

`PKI_ENDPOINTS` включает метод `GET` для OCSP и TSA НУЦ. Ядро до применения ключа проверяет сертификат подписанта онлайн запросом `GET` к адресу ответчика, и без этого метода запрос отклоняется, а вместе с ним и весь вызов (с `PermissionDenied` без типизированного отказа).

Текст до 16 КиБ, заголовок, кнопки и пункты до 1 КиБ; если что-то длиннее, результат `invalid`, и окно не показывается.

Пути сам плагин не называет, файл выбирает пользователь. Читается только обычный файл на диске (не канал и не устройство) размером до 64 МиБ. Выбранный сетевой путь (`file_choose`, `file_open_ex`) становится путём, который страница может называть дальше.

### `page_files`

| Функция | Аргумент | Результат |
|---|---|---|
| `page_file_read` | `PagePathArgs { path }` | `PageRead`: `ok(OpenedFile)`, `not_found`, `too_large`, `declined` |
| `page_file_write` | `PageWriteArgs { dir, name, data }` | `PageWrite`: `written(path)`, `invalid`, `declined` |

Путь, который назвала страница, проверяется по тем же правилам, что у встроенных модулей. Устройства (`\\.\`, `\\?\GLOBALROOT`) не допускаются никогда, сетевой путь допускается только выбранный ранее пользователем в окне ядра. Читается только обычный файл до 64 МиБ: каталог, канал и устройство дают `not_found`, файл больше лимита даёт `too_large`. До согласия файл не читается. Ядро спрашивает пользователя окном с сайтом, плагином и полным путём; согласие запоминается в экземпляре (сессии) для пары (сайт, канонический путь), отказ даёт `declined`.

`page_file_write` пишет в существующий каталог, который назвала страница. `name` должен быть именем без разделителей, `..`, управляющих и зарезервированных символов Windows, не начинаться с `.`, не заканчиваться `.` или пробелом и иметь расширение из `page_files_ext`; иначе результат `invalid` без вопроса пользователю. Окно согласия показывает полный путь файла, а согласие действует на каталог до конца сессии. Запись атомарная, существующий файл заменяется.

| Функция | Аргумент | Результат |
|---|---|---|
| `settings_get` | `()` | `BTreeMap<String, String>` — настройки; без файла или с повреждённым файлом — пустые (повреждение пишется в журнал) |
| `settings_put` | `BTreeMap<String, String>` | `()` — настройки заменяются целиком |

Настройки лежат в `<data>/plugins/settings/<id>.json` и пишутся атомарно. Допускается не больше 256 ключей и 64 КиБ JSON, иначе `limit`. Обновление плагина настройки сохраняет, удаление плагина их удаляет.

### `shared`

| Функция | Аргумент | Результат |
|---|---|---|
| `shared_get` | `SharedKey { key }` | `Option<Bytes>` — значение, если оно есть и не истекло |
| `shared_put` | `SharedPut { key, value, ttl_ms }` | `()`; `value = None` удаляет ключ |

Значения хранятся в памяти процесса и общие для всех экземпляров одного загруженного поколения плагина, то есть для всех сессий и сайтов. После перезагрузки или обновления плагина хранилище пустое. Допускается не больше 64 ключей и 64 КиБ ключей и значений вместе, иначе `limit`. Handle ключа через `shared` в другую сессию не переносится, потому что таблица ключей принадлежит экземпляру.

### `http`

| Функция | Аргумент | Результат |
|---|---|---|
| `http_request` | `HttpArgs { method, url, content_type, body }`, `method` — `get` или `post` | `HttpResponse { status, content_type, location, body }` |
| `http_request_ex` | `HttpExArgs { method, url, relative_to_origin, headers, content_type, body, timeout_ms }` | `HttpResponse` |

Адрес проверяется по префиксам манифеста (см. выше) и отправляется в проверенной форме; адрес вне префиксов даёт `denied`, и ничего не отправляется. Запрос идёт через прокси из настроек OpenNCALayer, только по HTTPS, с лимитами 32 МиБ и 60 с и без следования перенаправлениям: ответ 3xx возвращается плагину с `location`. У GET нет тела. За один вызов `oncl_process` уходит не больше 64 запросов, включая запросы ядра к хостам PKI; следующий запрос получает `limit` и не отправляется.

`http_request_ex` отправляет запрос, если выполнено одно из условий:

- адрес лежит под префиксом `http` (HTTPS, хост `*.` по границе метки);
- задан `relative_to_origin` (адрес разрешается от origin текущего вызова) или адрес абсолютный с тем же origin (схема, хост, порт), и этот origin подходит под шаблон `origins`. HTTP допускается, только если сам origin использует HTTP. Если origin нет или он не является адресом (`null`), результат `denied`;
- адрес лежит под префиксом `http_insecure` (HTTP, точный хост и порт).

Всё остальное, включая `file:`, `data:` и другие схемы, даёт `denied`. Разрешены только заголовки `Cookie`, `User-Agent`, `Accept`, `Accept-Language`, `X-Requested-With` без учёта регистра (другие дают `denied`), не больше 16 и не больше 8 КиБ вместе (иначе `limit`). CR, LF или NUL в заголовке или `content_type` дают `invalid`. POST без `content_type` уходит без `Content-Type`. `timeout_ms` задаётся от 1 до 60000. Перенаправлениям хост не следует, как и в `http_request`.

## SDK

Плагин на Rust пишется с крейтом `oncl-pdk`. Под `wasm32` он предоставляет:

- макрос `oncl_pdk::plugin!(handler)`. `handler: fn(&Request) -> String` получает запрос (`text`, `origin`, `locale`) и возвращает ответ странице. Макрос экспортирует `oncl_abi_version`, `oncl_alloc`, `oncl_free`, `oncl_process` и перед trap пишет панику плагина в журнал через `log`. Перед каждым вызовом `handler` макрос берёт 16 байт у `random` и засевает ими хеш, в котором `orgjson` хранит ключи запроса: своего источника случайности у модуля WebAssembly нет, а зная ключи хеша, страница могла бы подобрать ключи, которые все сталкиваются. Самому плагину вызывать `random` для этого не нужно;
- обёртки host-функций, возвращающие `HostResult`: `host::{log, now, random, cert_info, reply_drop}`, `keys::{choose, flow_open, Flow, Key}` (`Flow::{keys, pick}`; `Key::{sign_cms, sign_raw, sign_xml, sign_xml_ex, sign_xades, describe, alias, certificate, handle}`; при удалении `Key` вызывается `keys_release`), `tokens::scan`, `dialogs::{message, confirm, password, choice, reader}`, `files::{open, save, choose, choose_kind, open_ex, page_read, page_write}`, `pki::path`, `http::{get, post, request_ex}`, `settings::{get, put}`, `shared::{get, put}`, для встроенных модулей `core::{modules, bundles, install_bundle, open_window}` и `builtin::{dialog_csr, dialog_import, new_key, install_cert, change_password, id_card}`, а также `call_host` для вызова любой host-функции с типами ABI;
- `Request::add_info()` и реэкспорт `oncl_protocol::{invoker, orgjson}` и `serde_json`. Плагин, который отвечает в диалекте CommonInvoker (как `kz.gov.pki.knca.basics`), вызывает `invoker::invoke` (запрос читает `serde_json`, ключи объектов `body` идут в том порядке, в котором их положил метод) или `invoker::java::invoke_with` (см. ниже), через который отвечает и сам модуль basics;
- Java-диалекты оригинала для плагинов, которые должны отвечать как оригинал байт в байт (реэкспорт из `oncl-protocol`):
  - `orgjson::{parse, reserialize}`: разбор org.json 20211205 с его текстами ошибок и позицией (`Duplicate key "a" at 11 [character 12 line 1]`);
  - `orgjson::{JObject, JValue, quote}`: запись так, как пишет `JSONObject.toString()`, с порядком ключей `HashMap` (`JObject::hash_map()` для `new JSONObject()` и бинов, `JObject::from_map(n)` для `new JSONObject(map)`, `JObject::stringer()` для `JSONStringer`), числами без хвостовых нулей, `<\/` и `\u2028`;
  - читатели `orgjson::{opt_boolean, get_boolean, opt_int, get_int, get_object, get_array, array_get_string, …}` с текстами `JSONException`;
  - `javamap`: порядок `HashMap` для любого набора ключей;
  - `javab64::{decode_java, decode_kalkan, encode_mime}`;
  - `javaexc::Throwable`: тексты исключений Java;
  - `legacy::dispatch`: рефлексивный диспетчер `commonUtils` и его клонов. Он ищет метод по имени и числу аргументов, преобразует массивы, выдаёт тексты `NoSuchMethodException`/`IllegalAccessException`/`argument type mismatch`, обрабатывает `uuid` через org.json, а `null` без `uuid` превращает в обрыв соединения. Методы самого `commonUtils` `null` не возвращают: при отмене они отвечают `{"code":"500","message":"action.canceled"}` с `uuid` или без;
  - `invoker::java::invoke_with`: `CommonInvoker` оригинала с `details`, где указан класс исключения (`java.lang.IllegalArgumentException: Supported apiVersion is 2`), порядком `{"body":…,"status":true}` и `{"code":…,"details":…,"message":…,"status":false}`, таблицей методов с аннотациями и числом параметров, а для запроса, который не дошёл до `try` оригинала, с выбором `BadRequest::{Reply, Drop, CatchAll}`.

Модуль basics отвечает через `invoker::java::invoke_with` с `BadRequest::CatchAll`: на запрос без строкового `method` он отвечает `GENERAL_ERROR` с `org.json.JSONException` в `details`, как оригинал. `commonUtils` отвечает через `legacy::dispatch`.

Импортируются только те host-функции, которые плагин вызывает, поэтому плагину, который не работает с ключами, не нужно заявлять `keys`. `call_host` ссылается на все функции, и плагину с ним нужны все capabilities.

Пример лежит в `crates/oncl-pdk/example`: модуль `io.github.arynyklas.openncalayer.Example`, класс `Example` с методом на каждую возможность (`echo`, `count`, `origin`, `confirm`, `message`, `sign`, `signRaw`, `signXml`, `hold`, `release`, `rawSign`, `open`, `save`, `fetch`) и методами, которые нарочно ведут себя плохо (`spin`, `grow`, `panic`). Сборка:

```sh
cargo build --release --target wasm32-unknown-unknown --manifest-path crates/oncl-pdk/example/Cargo.toml
```

Модуль появляется в `crates/oncl-pdk/example/target/wasm32-unknown-unknown/release/oncl_plugin_example.wasm` и вместе с `plugin.toml` примера упаковывается в `.onclp`. Пример собирается как отдельный workspace со своим `Cargo.lock` и в релизы не входит. Тесты `oncl-plugin` собирают его сами в `target/plugin-example`.

## Жизненный цикл

Установленные плагины лежат в `<data>/plugins/`:

- `state.json`: установленные плагины (версия, sha256 пакета, источник, включён ли, отозван ли), версии, которые здесь не загрузились, случайный `install_id` для поэтапного выпуска и последний принятый `seq` каталога каждого канала;
- `packages/<id>-<version>.onclp`;
- `catalog/<канал>.json`. Подлинность каталога задают метаданные TUF общего клиента в `<data>/update/tuf/` ([`tuf.md`](tuf.md)).

Каждый файл заменяется атомарно. Состояние меняется под одной блокировкой и сохраняется раньше, чем изменение становится видно. Повреждённый `state.json` заменяется новым с записью в журнал, а другая ошибка чтения выключает плагины, и окно «Плагины» её показывает.

Каталог состоит из записей `plugins` индекса обновлений канала из настроек (`updates.channel`, по умолчанию канал версии OpenNCALayer). Подлинность индекса проверяет TUF, см. `docs/design/update-index.md`. Каталог скачивается через 10–60 с после старта, если действующего каталога нет, иначе через 2–10 минут; дальше раз в 6–24 часа, а после сбоя загрузки через 30 минут – 2 часа. Принятый каталог, у которого при загрузке проверены метаданные TUF, `seq` и канал, сохраняется на диск. При чтении с диска он проверяется заново без сети: подпись `targets` в сохранённом состоянии TUF проверяется от встроенного корня, байты каталога должны совпасть с длиной и sha256 из этих `targets`, ни они, ни корень не должны истечь (до этого срока каталог и действует), а `seq` не должен быть меньше принятого. Каталог в памяти проверяется только по этому сроку. Каталог, скачанный по запросу при включённых обновлениях, сразу применяется в фоне. При выключенных обновлениях (`updates.enabled = false`) плановых загрузок и автообновлений плагинов нет. Каталог тогда скачивается только по запросу: окно «Плагины», `installBundle`, «Проверить сейчас» в настройках и «Проверить обновления» в меню значка (проверка плагинов идёт в фоне по сохранённым настройкам). В сборке без зашитого корня доверия каталога нет: окно пишет «Каталог плагинов недоступен в этой сборке», и плагины ставятся только из файла.

При старте включённые и не отозванные плагины загружаются из своих пакетов, sha256 файла сверяется с записанным при установке. Плагин, который не загрузился (пакет изменён, нужен более новый OpenNCALayer, модуль занят), остаётся установленным в состоянии «ошибка» и не мешает остальным.

Установка из каталога запускается кнопкой «Установить…» или через `installBundle`. Пакет скачивается только по HTTPS, его размер и sha256 сверяются с индексом. Затем выполняются `Package::read`, сверка `id`, `version`, `modules` и `replaces` манифеста с записью индекса, проверка `min_core` и пробная компиляция с проверкой имён модулей (встроенный модуль или модуль другого плагина занимать нельзя). Пакет, не прошедший проверку, помечает версию плохой. Сбой сети версию плохой не делает: установку можно повторить, а обновление повторится при следующей проверке каталога. Не делает её плохой и модуль, который уже обслуживает другой установленный плагин, потому что это зависит от установки, а не от пакета. Обновление на такую версию не повторяется, пока плагины не изменятся (удаление, выключение, установка или обновление плагина), а установку можно повторить сразу. В этих случаях ничего не ставится, и значок сообщает об ошибке; если установка начата из окна «Плагины», окно ещё и объясняет причину на языке интерфейса. Затем окно «Установка плагина» показывает, кто просит (`origin` без управляющих символов, разделителей строк и символов направления текста, не длиннее 128 символов), имя, версию, что плагин заменяет и его capabilities. Кнопка «Установить» становится доступной через 1,5 с после появления окна, чтобы клик или Enter, предназначенные другому окну, не установили плагин. «Установить» загружает плагин, записывает пакет и состояние и сообщает «Плагин установлен»; «Отмена» или закрытие окна ничего не меняют.

Установка из файла («Установить из файла…», фильтр `*.onclp`) выполняет те же проверки пакета, `min_core` и модулей и показывает окно с предупреждением: «Этого плагина нет в каталоге OpenNCALayer, его не проверял мейнтейнер…». Если плагин с тем же `id` уже установлен, окно называет его версию и источник (каталог или локальный файл). Такой плагин помечается как «локальный», и каталог его не обновляет и не отзывает.

Обновление и отзыв. После каждого принятого каталога (плановая загрузка или «Проверить сейчас» при включённых обновлениях) для каждого плагина из каталога выбирается версия (`choose_plugin`). Обновление идёт поэтапно и только вверх; с отозванной версии плагин переходит на лучшую неотозванную, в том числе вниз и сразу для всех. Новая версия скачивается и проверяется так же, как при установке, загружается новым поколением и только после этого записывается. Если что-то не прошло, версия попадает в плохие, а старая продолжает работать. Обновление, которое не даёт плагину больше прав, чем у установленной версии, ставится без вопроса, и значок сообщает «Плагин обновлён». Если новая версия получает больше (новый флаг `keys`, `dialogs` или `files` или адрес `http`, не покрытый префиксами установленной версии), она скачивается и проверяется, но не ставится. Установленная версия продолжает работать, окно «Плагины» показывает у плагина, что сможет новая версия сверх установленной, и кнопку «Разрешить обновление», а значок один раз сообщает «Обновление плагина ждёт разрешения». Обновление ставится, когда пользователь его разрешит; если каталог за это время перестал его предлагать, ждать нечего. Отозванная версия без замены выгружается и помечается отозванной (уведомление показывается один раз) и не загружается, пока каталог её не вернёт.

Во время работы текущий вызов доигрывает на своём экземпляре, а следующий вызов той же сессии получает экземпляр нового поколения или `MODULE_NOT_FOUND`, если плагин выгружен. Сбой вызова закрывает только его экземпляр.

«Выключить» выгружает плагин, «Включить» загружает его снова (кроме отозванного). «Удалить» после вопроса выгружает плагин и удаляет его пакет и запись.

Запрос к модулю, который никто не обслуживает, получает `MODULE_NOT_FOUND`. Если действующий каталог (без скачивания) предлагает неустановленный плагин с таким модулем, значок сообщает «Сайту X нужен плагин «Y»» с кнопкой «Установить…», которая открывает окно «Плагины» (не чаще раза в 10 минут), а окно отмечает плагин «Нужен сайту X». Сообщение (и перечитывание открытого окна) появляется, только когда эта отметка меняется: плагин стал нужен или нужен другому сайту.

## installBundle

`installBundle` модуля `kz.gov.pki.ncalayerservices.accessory` проверяет запрос в том же порядке, что оригинал: на пустой `symname` отвечает `SYMNAME_PARAMETER_IS_EMPTY`, на запрос без заголовка `Origin` отвечает `org.json.JSONException: JSONObject["origin"] is not a string.`, а затем демон ищет в каталоге неустановленный плагин, у которого `replaces.symname` равен `symname`. Если действующего каталога нет, демон его скачивает, а если скачивание уже идёт, дожидается его. Всё это занимает не больше 10 с, после чего ответ даётся без каталога. Если скачать каталог не удалось (сеть, индекс не опубликован или отвергнут), запросы страниц ещё 5 минут обходятся без каталога и не скачивают его снова. «Обновить каталог», «Установить…» в окне «Плагины» и «Проверить сейчас» скачивают его сразу.

- Плагин найден: ответ `{"errorCode":"NONE"}` приходит сразу, а установка (скачивание, проверки, окно подтверждения) идёт в фоне. Как и у оригинала, ответ не ждёт пользователя. Пока установка идёт, в том числе ждёт ответа пользователя, повторный запрос получает тот же ответ и новую установку не начинает. О сбое установки, начатой страницей, значок сообщает не чаще раза в 10 минут для каждого плагина.
- Плагин не найден, уже установлен (в том числе выключен или отозван) или каталога нет (сборка без корня доверия обновлений, нет сети, метаданные TUF истекли, каталог не успел загрузиться за 10 с): ответ `BUNDLE_NOT_FOUND_OR_ALREADY_INSTALLED`, а значок сообщает «Сайт {origin} запросил модуль {symname}. Каталог OpenNCALayer не предлагает его установить: его там нет или он уже установлен» с кнопкой «Реестр плагинов» (не чаще раза в 10 минут). `origin` и `symname` показываются без управляющих символов, разделителей строк и символов направления письма, не длиннее 128 символов.

`uuid` запроса возвращается в ответе. `getBundles` добавляет к бандлам оригинала пары `replaces.symname → replaces.version` включённых загруженных плагинов, `getServices` добавляет модули плагинов. Оба списка строятся при каждом запросе и видят плагин сразу после установки. Версию бандла `getBundles` печатает так же, как `Bundle.getVersion().toString()` у оригинала: `major.minor.micro` и `.qualifier`, если он есть. `1.2` превращается в `1.2.0`, `2` в `2.0.0`, а `1.2.0` и `1.2.3.rc1` остаются как есть. Сам манифест не меняется, он сверяется с манифестом оригинала и `registry.toml`. Строка, которая не является версией OSGi (например, предварительная версия semver `1.0.0-beta.2`, которую оригинал не принимает и у своих бандлов не имеет), выводится как написана. `showBundleManager` открывает окно «Плагины».

Порядок записей намеренно отличается от оригинала: при установленных плагинах `getBundles` и `getServices` выводят модули плагинов после встроенных, по алфавиту. Порядок оригинала с плагинами зависит от его реестра OSGi и не воспроизводится.

## Порты

Порты сторонних плагинов оригинала лежат в `plugins/`: 35 каталогов `plugins/<short>`, по одному на плагин оригинала, и общие библиотеки в `plugins/common/`. Это отдельный workspace для `wasm32-unknown-unknown`, который не входит ни в workspace ядра, ни в его релизы. Отдельный порт собирается в пакет командой `cargo xtask plugin pack plugins/<short>`. Job `conformance` в `release.yml` собирает пакеты всех портов, но не публикует их (`docs/dev/release.md`).

В каталоге порта лежат:

- `plugin.toml`: манифест (раздел [«Манифест»](#манифест)) с `id` вида `io.github.arynyklas.openncalayer.port.<short>`, именами `module`, которые обслуживает порт, `replaces` (`symname` и версия бандла оригинала) и только теми capabilities, которые нужны порту;
- `registry.toml`: данные реестра. Здесь записаны бандл оригинала (`symname`, версия, поставщик), состояние порта (`full`: всё, что делает оригинал; `partial`: с оговорками; `needs-tokens`: всё, но часть проверяется только на токенах), способ сверки с оригиналом и отличия от оригинала (`[[differences]]`), которые реестр показывает пользователю;
- исходники крейта `oncl-port-<short>`.

Порты по группам:

| Группа | Семейство | Порты |
|---|---|---|
| 2 | ecc.kz | market, efactoring, nursign, k2sign |
| 3 | клоны commonUtils | rating1c, xdox, eot, ezsigner, uchet, arta, metadoc |
| 4 | CommonInvoker | idocs, fhs, doodocs, devart, thundercrypt |
| 5 | прочие средние | taxtech, energy, eproc, esf-osdkz, uchet-esf, qiwi, bas, eup, dogovor24, onaidocs, workspace, simourg, motiw |
| 6 | тяжёлые | buhta, acbank, knp, documentolog, qoltanba, skf |

Состояние `full` у портов buhta, acbank и doodocs, у остальных `partial`.

Общие библиотеки:

- `oncl-port-kit` (`common/kit`): то, что плагины оригинала делали средствами Java. Тела `multipart/form-data` байт в байт, `new URL(context, spec)` и origin, zip-архивы, `Properties.storeToXML`, шаблоны `SimpleDateFormat`, ответы семейства ecc.kz;
- `oncl-port-legacy` (`common/legacy`): общий код клонов commonUtils (рефлексивный диспетчер `oncl_pdk::legacy`). Бин `ResponseMessage`, проверки `StorageInfo`, типы ключей и выбор ключа, `KeyInfo`, Base64 Java, тексты сетевых исключений Java;
- `oncl-port-pki` (`common/pki`): работа с DER внутри модуля (RustCrypto `der`, `x509-cert`, `cms`; ключей и случайности нет, подписывает хост). Подписанные атрибуты и имена из строк DN, чтение CMS, атрибуты и запрос OCSP ЕСЭДО, доверенные сертификаты Java KeyStore, тексты сертификатов Java и Kalkan.

Диалекты JSON (org.json, порядок `HashMap` Java, диспетчеры) находятся в `oncl-pdk`. Тесты портов собраны в крейте `oncl-port-tests` (`crates/oncl-port-tests`). Он загружает собранный `.wasm` в настоящий хост плагинов с тестовой PKI и, где нужно, с эмулятором токенов.

Порядок `HashMap` у оригинала определяется бакетами `(h ^ h >>> 16) & (ёмкость − 1)` по порядку, а внутри бакета порядком вставки. Бакеты одинаковы на всех ОС, но порядок вставки свойств бина (например, `KeyInfo` в `getKeyInfo` commonUtils) выбирает JVM, и он разный. На Windows 11 это `pem, keyId, alias` в бакете 9 и `subjectDn, algorithm` в бакете 15, на Linux `pem, alias, keyId` и любой порядок второй пары (от запуска к запуску), на Windows 7 `keyId, alias, pem` и `algorithm, subjectDn`. Ядро и порты пишут порядок Windows 11 на всех ОС, так что на Linux и Windows 7 ключи одного бакета могут идти иначе, чем у оригинала на той же ОС.

Правила порта:

- Сохраняется всё, что видит страница: форма ответов, коды и тексты ошибок, порядок проверок, порядок полей (в том числе порядок `HashMap` Java), байты подписей и запросов к серверам.
- Исправляется то, что небезопасно или зависит от состояния вне песочницы. Подписи на SHA-1 (sha1RSA) не создаются. HTTPS используется только с проверкой сертификата и только по адресам из манифеста. Ключи и пароли не запоминаются между соединениями и не пишутся на диск; то, что порт сохраняет, например путь к хранилищу, идёт через capability `settings`. Файлы настроек и кэши оригинала не читаются. Пути к файлам от страницы заменяются окнами хоста. Каждое такое отличие записывается в `registry.toml`.
- Токены доступны только через экспериментальную поддержку ядра ([`tokens.md`](tokens.md)); пока она выключена, хранилища токенов пусты.

Ожидаемые ответы в тестах выведены из поведения оригинала и сверены с работающим оригиналом (см. «Сверка с оригиналом» ниже). Исключение составляет onaidocs, у него состояние `computed`.

Схему `registry.toml` читает только `xtask::registry::ports`. `cargo xtask registry build` отказывается собирать сайт, если хотя бы один порт её нарушает, и перечисляет все такие порты сразу.

| Поле | Правило |
|---|---|
| `id` | равен `id` из `plugin.toml`, а тот — `io.github.arynyklas.openncalayer.port.<short>`; `<short>` — `^[a-z0-9][a-z0-9-]{0,62}$` |
| `modules` | те же, что в `plugin.toml` |
| `[original]` `symname`, `version` | те же, что `[replaces]` в `plugin.toml`; `symname` — `^[A-Za-z0-9._-]{1,128}$` и не повторяется у двух портов |
| `[original]` `vendor` | 1–256 символов без управляющих |
| `[port]` `status` | `full`, `partial` или `needs-tokens` (всё, но часть проверяется только на токенах) |
| `[port]` `conformance` | `computed` или `confirmed` (раздел «Сверка с оригиналом» ниже); в канал `stable` `cargo xtask index add-plugin` пускает только `confirmed` |
| `[[differences]]` `ru` | до 64 отличий, каждое — 1–2048 символов без управляющих, кроме перевода строки; показываются как текст, на казахской и английской страницах — с пометкой «на русском» |

Лишние ключи считаются ошибкой. Каждый порт получает на сайте проекта страницу `/plugins/<short>/` (и `/kk/…`, `/en/…`) и строку каталога `/plugins/#<symname>`. Новый порт с `registry.toml` появляется на сайте при следующей сборке.

Чтобы добавить порт, нужны каталог `plugins/<short>` (имя не должно начинаться с `c`, так workspace отделяет порты от `common/`), `plugin.toml` и `registry.toml` и тесты в `oncl-port-tests`. При новых зависимостях нужно запустить `cargo xtask licenses --plugins`.

### Сверка с оригиналом

Поведение портов сверено с работающим оригиналом NCALayer 1.4 в изолированной лаборатории проекта. Одни и те же запросы страницы отправляются оригиналу и нашему ядру с портом, и ответы сравниваются поле за полем, включая порядок ключей, форму байтов подписей и тексты ошибок. Записи ответов оригинала приватные и в публичный репозиторий не попадают: тесты `oncl-port-tests` содержат ожидания, написанные вручную на синтетических значениях. `cargo xtask privacy` всегда ищет файлы и заголовки записей, пути с буквой диска и сертификаты, выпущенные тестовыми УЦ НУЦ (DER и base64). Серийные номера, DN тестовых ключей и имена лаборатории он ищет только по приватному списку (секрет `PRIVACY_DENYLIST`). Ссылки на лабораторию и её записи в тексте он не находит, их проверяют при ревью.

Каждое найденное расхождение получает одно из состояний:

- исправлено: изменён порт и добавлен тест, который закрепляет наблюдённое правило;
- принято как отличие: запись в `[[differences]]` порта с причиной (безопасность, состояние вне песочницы, порядок или предел, зависящие от ОС или ядра, либо осознанный выбор порта вместо поведения оригинала);
- недостижимо: у кода стоит комментарий `// Not observable:` с причиной, например для ветки нет ключа, устройства или сети, которыми её можно вызвать;
- открыто.

Место, где порт опирается на вывод из кода оригинала, ещё не проверенный на оригинале, помечается комментарием `// Unverified against the original:`. Сейчас таких мест в портах нет.

Поле `conformance` в `registry.toml` порта:

- `computed`: поведение выведено из кода оригинала (декомпиляцией бандла), а сверка с работающим оригиналом не закончена. Либо остались расхождения, не закрытые на оригинале, либо версия оригинала новее сверенной и сверена только по байткоду;
- `confirmed`: сверка закончена, и каждое расхождение исправлено, принято как отличие или недостижимо. Только такой порт команда `cargo xtask index add-plugin` пускает в канал `stable`, а порт с `computed` она отвергает (раздел 6 `docs/dev/release.md`). Для `beta` поле не проверяется.

Из 35 портов у 32 стоит `confirmed`, у simourg, ezsigner и onaidocs `computed`. У simourg и ezsigner новую версию оригинала порт принял по сравнению байткода бандлов, а на работающем оригинале сверка не повторена; после повтора им вернут `confirmed`.

- simourg 2.4: различаются три класса окон ключа и списка запомненных ключей, которые порт не воспроизводит (у него общие окна ядра). Классы, которые обрабатывают запросы и подписывают, совпадают побайтно. Сверка на работающем оригинале проведена на версии 2.2.
- ezsigner 1.2.2: различаются проверка локального пути (в 1.2.2 появилась ветка для macOS, которую порт не воспроизводит) и номер строки в одном классе. Остальные классы, включая `CMSSignUtil`, совпадают побайтно. Сверка на работающем оригинале проведена на версии 1.2.1.
- onaidocs 1.1.0: порт выведен из кода бандла (sha256 проверен, байткод разобран), но работающий оригинал в лаборатории не запускался. Не сверены ответы и тексты ошибок, состав CMS (только подписант или вся цепочка), параметры метки времени и окно ключа; список ведётся в `[[differences]]` порта. В канал `stable` порт не попадёт, пока не получит `confirmed`.

Необъяснённых расхождений при сверке не найдено. Правки портов, сделанные после последнего прогона на оригинале, закреплены тестами, но на оригинале ещё не повторены. Если поведение порта меняется, его версия получает следующий номер `1.0.0-beta.N`. `min_core` порта равен первой версии ядра, в которой есть всё поведение хоста, нужное порту; например, fhs и nursign требуют `0.1.0-alpha.6` ради текста разборщика JDK для текста перед первой разметкой. Начиная с `0.1.0-alpha.6` ядро отдаёт плагину (но не встроенному модулю) текст `SAXParseException` JDK и для текста перед первой разметкой (`Content is not allowed in prolog.`). Для такого документа изменились ответы портов, которые передают сообщение ядра (devart, eproc, клоны commonUtils, fhs V1, skf); более старое ядро даёт им прежний текст.

Ядро сверяется так же. На теге job `conformance` в `release.yml` собирает артефакт для лаборатории (`docs/dev/release.md`, раздел 7), агент сверяет сборку с оригиналом и ставит на коммит тега статус `conformance`. Без этого статуса новая версия ядра не попадёт в `stable`.
