# Индекс обновлений

Индекс канала перечисляет доступные версии OpenNCALayer и места, где лежат их файлы. Читает и проверяет его крейт `oncl-update`. Для TUF индекс является целью ([`tuf.md`](tuf.md)): его подлинность подтверждают метаданные TUF, а свежесть задают сроки ролей (разделы «Подпись» и «Проверка на клиенте»). Индекс готовят команды `cargo xtask index …`, метаданные TUF подписывают команды `cargo xtask tuf` ([`../dev/release.md`](../dev/release.md)).

## Где лежит

- Индекс: `updates/v1/<channel>.json`, где `<channel>` равен `stable` или `beta`. Он публикуется на GitHub Pages проекта байт в байт рядом со страницами сайта (`site/`). У сайта нет своего пути `updates`: `pages.yml` копирует каталог `updates/` в артефакт после сборки сайта и сверяет копию с репозиторием.
- Подтверждение подлинности: метаданные TUF в `tuf/v1/` (корни, `timestamp`, `snapshot`, `targets`). Клиент получает индекс как цель `indexes/<channel>.json` по пути `tuf/v1/targets/indexes/<sha256>.<channel>.json`; байты те же, что в `updates/v1/<channel>.json` (раскладка описана в [`tuf.md`](tuf.md)). Рядом лежат правила издателей `publishers.json` и роли издателей: из них каталог плагинов берёт выпуски сторонних издателей ([`publishers.md`](publishers.md)). В индекс владельца эти выпуски не попадают.
- Сами файлы (пакеты Velopack, расширение) лежат в неизменяемых GitHub Releases. Индекс ссылается на них по URL и sha256.

Метаданные и индекс клиент скачивает только по HTTPS, и перенаправления тоже должны вести на HTTPS: перенаправление на `http://` отвергается. Индекс больше 1 МиБ отвергается.

## Формат

```json
{
  "schema": 1,
  "channel": "beta",
  "seq": 42,
  "generated": "2026-10-01T00:00:00Z",
  "expires": "2026-10-31T00:00:00Z",
  "core": [
    {
      "version": "0.1.0-alpha.2",
      "flavors": {
        "win-x64": {
          "url": "https://github.com/arynyklas/OpenNCALayer/releases/download/v0.1.0-alpha.2/OpenNCALayer-0.1.0-alpha.2-win-x64-full.nupkg",
          "sha256": "<64 hex>",
          "size": 123,
          "contents_sha256": "<64 hex>",
          "delta_from": {
            "0.1.0-alpha.1": {"url": "https://…-delta.nupkg", "sha256": "<64 hex>", "size": 45}
          }
        }
      },
      "rollout": 100,
      "revoked": false,
      "notes_url": "https://github.com/arynyklas/OpenNCALayer/releases/tag/v0.1.0-alpha.2"
    }
  ],
  "extension": {
    "version": "0.1.0-alpha.2",
    "chromium_zip": {"url": "https://…", "sha256": "<64 hex>"},
    "firefox_xpi": {"url": "https://…", "sha256": "<64 hex>"}
  },
  "plugins": [
    {
      "id": "kz.example.echo",
      "version": "1.0.0",
      "url": "https://github.com/arynyklas/OpenNCALayer/releases/download/plugins-20261029/kz.example.echo-1.0.0.onclp",
      "sha256": "<64 hex>",
      "size": 12345,
      "min_core": "0.2.0",
      "modules": ["kz.example.Echo"],
      "replaces": {"symname": "kz.example.echo", "version": "1.2.1"},
      "name": {"ru": "…", "kk": "…", "en": "…"},
      "rollout": 100,
      "revoked": false
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `schema` | Версия формата, сейчас `1`. Индекс другой схемы клиент не читает. |
| `channel` | `stable` или `beta`. Должен совпадать с каналом клиента. |
| `seq` | Номер индекса канала, растёт с каждой публикацией. Клиент не принимает `seq` ниже последнего принятого. |
| `generated` | Время сборки индекса, RFC 3339. |
| `expires` | Срок индекса, RFC 3339. `cargo xtask index` ставит `generated` + 30 дней. Клиент по этому полю индекс не отвергает: свежесть задают `expires` ролей TUF, а поле остаётся частью формата. |
| `core` | Версии ядра. Каждая версия встречается один раз. |
| `core[].version` | Версия semver (тег `v<version>`). |
| `core[].flavors` | Пакеты по вариантам сборки: `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `osx`, `linux-x64`. Незнакомые ключи клиент пропускает, поэтому новые варианты не ломают старых клиентов. |
| `…flavors.<flavor>.url`, `sha256`, `size` | Полный пакет: URL, sha256 (64 строчные hex-цифры) и размер в байтах. |
| `…flavors.<flavor>.delta_from` | Необязательно. Дельта-пакеты; ключ равен версии, от которой применяется дельта. |
| `…flavors.<flavor>.contents_sha256` | Обязательно, если есть `delta_from`. sha256 списка файлов полного пакета: число записей zip, затем записи в порядке имён, каждая из длины имени (8 байт, little-endian), имени и sha256 распакованных данных (`oncl_update::contents_sha256`). Пакет, который Velopack собирает из дельты, представляет собой другой zip с теми же файлами (другой порядок и сжатие), и его sha256 с `sha256` не совпадает. Клиент проверяет его по этой сумме. |
| `core[].rollout` | Процент установок, которым предлагается версия, от 0 до 100. |
| `core[].revoked` | Необязательно, по умолчанию `false`. Отозванная версия больше не предлагается. Клиент читает только индекс своего канала, поэтому релиз, записанный и в `stable`, и в `beta`, отзывается в обоих. |
| `core[].notes_url` | Необязательно. Ссылка на описание релиза. |
| `extension` | Необязательно. Расширение браузера: версия совпадает с версией ядра, файлы для Chromium (`.zip`) и Firefox (`.xpi`). |
| `plugins` | Необязательно. Версии портов проекта (`docs/design/plugins.md`). Каждая пара `id` + `version` встречается один раз, каждое имя модуля и каждый заменяемый бандл (`replaces.symname`) принадлежат одному `id` во всём индексе. За ядром зарезервированы и отвергаются: `id` с префиксом `io.github.arynyklas.openncalayer.builtin.`, имена встроенных модулей (`crates/oncl-builtin-*/plugin.toml`) и `replaces.symname` тех бандлов оригинала, которые ядро реализует само (`oncl_builtin_accessory::CORE_BUNDLES`). Плагины сторонних издателей перечисляют их роли TUF, а не индекс; каталог клиента собирает записи из обоих мест по правилам старшинства из [`publishers.md`](publishers.md). |
| `plugins[].id`, `version` | Идентификатор плагина и semver его порта (не версия бандла оригинала). |
| `plugins[].url`, `sha256`, `size` | Пакет `.onclp`: URL, sha256 и размер в байтах. |
| `plugins[].min_core` | Самая старая версия ядра, на которой плагин работает. Более старое ядро эту версию не ставит. |
| `plugins[].modules` | Имена модулей протокола, которые обслуживает плагин: от 1 до 32, без повторов. |
| `plugins[].replaces` | Необязательно. Бандл оригинала, который заменяет плагин: `symname` и версия в формате оригинала. По нему работает `accessory.installBundle`, а `getBundles` показывает этот бандл, пока плагин установлен и включён. |
| `plugins[].name` | Название на русском, казахском и английском для менеджера плагинов и подсказок. |
| `plugins[].rollout` | Процент установок, которым предлагается версия. Бакет равен `sha256(install_id ‖ id ‖ 0x00 ‖ version)[0] * 100 / 256` и свой у каждого плагина и версии. |
| `plugins[].revoked` | Необязательно, по умолчанию `false`. Отозванная версия не предлагается. Установки на ней переходят на самую новую неотозванную версию (раскатка при этом не учитывается, возможен откат на старую), а если такой нет, плагин выключается. |

Все URL в индексе должны начинаться с `https://`. Незнакомые поля внутри схемы 1 клиент пропускает, поэтому поля можно добавлять без смены схемы.

## Подпись

Подлинность индекса подтверждает TUF ([`tuf.md`](tuf.md)). Корень доверия клиента лежит в `crates/oncl-update/keys/root.json` (версия 1); `build.rs` встраивает его в сборку и отдаёт через `oncl_update`. Если файла нет, обновления в сборке выключены, а повреждённый файл ломает сборку. Индекс записан в метаданных `targets` как цель `indexes/<channel>.json` с `length` и sha256. `targets`, `snapshot` и `timestamp` подписаны разными ключами Ed25519 ([`tuf.md`](tuf.md), «Роли, ключи, сроки»). `channel` и `seq` защищены тем, что sha256 цели проверяется; клиент дополнительно сверяет их с телом индекса.

`channel` индекса должен совпадать с каналом клиента, `seq` не уменьшается, URL и sha256 пакетов проверяются при скачивании. Свежесть задают сроки ролей (у timestamp 7 дней), а ключи меняются новым корнем без выпуска клиента.

## Подготовка индекса

Индексы хранятся в репозитории в `updates/v1/` и публикуются байт в байт: `.gitattributes` запрещает git менять в них концы строк, иначе sha256 цели TUF не сойдётся. Здесь описаны правила и команды, а порядок действий мейнтейнера от ключей TUF до выпуска приведён в [`../dev/release.md`](../dev/release.md).

Все файлы, на которые ссылается индекс, лежат в релизах проекта. URL каждой записи должен быть ровно `https://github.com/arynyklas/OpenNCALayer/releases/download/v<версия>/<файл>`, где `<версия>` совпадает с версией самой записи, а `<файл>` назван так:

- полный пакет: `OpenNCALayer-<версия>-<вариант>-full.nupkg`;
- дельта: `OpenNCALayer-<версия>-<вариант>-delta.nupkg`;
- расширение: `openncalayer-chromium-<версия>.zip` и `openncalayer-firefox-<версия>.xpi`;
- плагин: `<id>-<версия>.onclp` в релизе с тегом `plugins-ГГГГММДД[.N]` вместо `v<версия>`, то есть `https://github.com/arynyklas/OpenNCALayer/releases/download/plugins-ГГГГММДД[.N]/<id>-<версия>.onclp`. Предварительная версия плагина в `stable` не допускается.

Копии пакетов сторонних издателей лежат в выпусках `pub-<издатель>-<sha256>` того же репозитория. На них ссылаются роли издателей, а не индекс, и правило выше их не касается.

`notes_url` равен `https://github.com/arynyklas/OpenNCALayer/releases/tag/v<версия>`. Запросы (`?…`), фрагменты (`#…`) и незнакомые варианты не допускаются. Это правило проверяют `index add` и `index refresh` (и для индекса, который читают, и для того, который записывают), а также `index check`. Клиент его не проверяет, потому что публикуется только индекс, прошедший эту проверку.

- `cargo xtask index add --channel beta --tag v<версия> --release-assets <каталог>` дописывает версию в индекс по скачанным ассетам релиза:
  - полные пакеты по вариантам;
  - дельты; версия, от которой применяется дельта, определяется как самый новый полный пакет старше новой версии в `releases.<вариант>.json` Velopack из тех же ассетов;
  - расширение, только оба файла вместе.

  sha256 и размеры берутся из файлов. `seq` растёт на 1, `generated` ставится в текущее время, `expires` через 30 дней. `--rollout` задаёт процент раскатки, по умолчанию 100.
- `cargo xtask plugin pack <каталог крейта>` собирает плагин под `wasm32-unknown-unknown` и пишет `target/plugins/<id>-<версия>.onclp`. Версия в `plugin.toml` должна совпадать с версией крейта, модуль проходит ту же проверку ABI, что и в демоне. Пути машины сборки (домашний каталог, тулчейн, рабочее дерево) в модуль не попадают: сборка заменяет их на `/cargo`, `/rustc`, `/workspace` и `/plugin`. Архив детерминирован: одни и те же исходники одним тулчейном дают одни и те же байты.
- `cargo xtask index add-plugin --channel <channel> --tag plugins-ГГГГММДД[.N] --package <файл.onclp>…` дописывает версии плагинов в индекс. `id`, версия, `min_core`, модули, `replaces` и название берутся из манифеста пакета, sha256 и размер из файла. Повтор пары `id` + версия, модуль или бандл оригинала (`replaces.symname`), уже принадлежащий другому плагину, и предварительная версия в `stable` отвергаются. Индекс с новыми пакетами проходит проверку URL и владельцев до записи, так что при отказе файл не меняется. `seq`, `generated` и `expires` меняются как у `index add`, `--rollout` задаёт раскатку.
  - В `stable` попадает только порт, у которого `registry.toml` в каталоге портов (`--plugins`, по умолчанию `plugins/`) содержит `conformance = "confirmed"`, то есть совместимость проверена на работающем оригинале. Порт с `computed` или пакет, `id` которого нет ни у одного порта, команда в `stable` не добавит. Для `beta` каталог портов не читается.
- `cargo xtask index refresh --channel <channel>` продлевает индекс, не меняя содержимого: `seq` растёт на 1, `generated` ставится в текущее время, `expires` через 30 дней. Индекс нужно продлевать, пока с `generated` не прошло 30 дней.
- `cargo xtask index check updates/v1` проверяет индексы перед публикацией:
  - каждый индекс разбирается и соблюдает правила формата и срока (не больше 30 дней с `generated`), а его URL и владельцы модулей и бандлов соответствуют правилам выше;
  - относительно базовой ветки (`--base`, по умолчанию `origin/main`) у изменённого индекса `seq` больше, и ни один индекс не удалён;
  - без `--offline` каждый URL пакета ядра, расширения и плагина отвечает на `HEAD` кодом 200. Проверки статусов `vm-smoke` и `conformance` касаются только версий ядра;
  - с `--vm-smoke` на теге каждой новой версии должен стоять статус коммита `vm-smoke = success`: установщики прошли проверку на чистых системах лаборатории;
  - с `--conformance` на теге каждой новой версии в `stable` должен стоять статус коммита `conformance = success`: сборка тега сверена с оригиналом в лаборатории. В `beta` это требование не действует: релиз без суффикса проходит его в индексе `stable`, а предварительной версии достаточно `vm-smoke`.

  Оба статуса ставит агент лаборатории на коммит тега, сначала `vm-smoke`, затем для того же тега `conformance`. `index-check.yml` (его вызывает `ci.yml`) запускает проверку с `--vm-smoke --conformance` и читает статусы через API GitHub своим токеном (право `statuses: read`). Эти флаги несовместимы с `--offline`. Новой считается версия, которой нет в базе; без базы (`--no-base`) новой считается каждая версия индекса.

## Публикация

Тег `v<версия>` запускает `.github/workflows/release.yml`:

1. Для каждого варианта собираются архив, установщик и пакеты Velopack (`cargo xtask package windows|macos|linux`, внутри `vpk pack --packId OpenNCALayer --channel <вариант>`). Варианты: `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64` и `osx`. Дельта строится от полного пакета того же варианта из релиза с наибольшей версией ниже текущей: для релиза среди релизов, для предварительной версии среди версий любого вида. Этот пакет скачивается прямо из того релиза (`gh release download`; `vpk download github` видит только 10 последних релизов) и сверяется с его `SHA256SUMS`. Если такого релиза нет, дельты нет; любая другая ошибка останавливает сборку.

   В релиз попадают `OpenNCALayer-<версия>-<вариант>-full.nupkg`, `-delta.nupkg` (если есть предыдущий пакет), `releases.<вариант>.json` (фид Velopack: эта версия и полный пакет, от которого построена дельта), на Windows ещё `RELEASES-<вариант>`, а также установщики: `openncalayer-<версия>-<вариант>-setup.exe` для четырёх вариантов Windows, `openncalayer-<версия>-osx.pkg` и `openncalayer-<версия>-osx.zip`, `openncalayer-<версия>-linux-x64.AppImage`. Варианты `win7-*` собирает `cargo xtask win7` (с DLL рядом с exe). Исполняемые файлы их пакета, `Squirrel.exe`, заглушка Velopack и `Setup.exe` проходят проверку импортов Windows 7. Linux собирается в контейнере с glibc 2.28 (`cargo xtask package linux-build`).
2. Рядом кладутся расширение, SBOM `openncalayer-<версия>.cdx.json` (CycloneDX, `cargo cyclonedx`) и `SHA256SUMS`. На каждый файл релиза выпускается аттестация происхождения сборки (`actions/attest-build-provenance`), её проверяет `gh attestation verify <файл> --repo arynyklas/OpenNCALayer --signer-workflow arynyklas/OpenNCALayer/.github/workflows/release.yml` (для портов `--signer-workflow arynyklas/OpenNCALayer/.github/workflows/plugins.yml`). `--signer-workflow` обязателен: копии пакетов сторонних издателей в выпусках `pub-*` аттестует `publisher-pr.yml` того же репозитория (`docs/design/publishers.md`, «Копии пакетов в наших Releases»).
3. Код подписывается, только если заданы нужные секреты; иначе шаг пропускается с уведомлением в журнале. Authenticode через SignPath требует секрет `SIGNPATH_API_TOKEN` и переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`. Подписываются `openncalayer.exe` и `nmhost.exe` до упаковки и каждый `Setup.exe` после неё; DLL рядом с exe в сборках для Windows 7 не подписываются. Подпись и нотаризация Apple требуют секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`. `.app` (пакет обновления, `.zip` и содержимое `.pkg`) подписывает и нотаризует `vpk pack`. Сам `.pkg` подписывается и нотаризуется, только если задан ещё секрет `APPLE_INSTALL_IDENTITY` («Developer ID Installer»). Архив macOS остаётся неподписанным.
4. Когда задание `publish` создало черновик релиза, задание `index` скачивает его ассеты, выполняет `cargo xtask index add` для каждого канала версии и открывает PR в `main` с индексами. Хеши в индексе считаются по файлам черновика; после публикации GitHub их замораживает, и добавить к релизу ничего нельзя. Предварительная версия идёт только в `beta`, релиз без суффикса в `stable` и `beta`. У каждого индекса свой следующий `seq`, прежние записи сохраняются, индекс другого канала предварительная версия не трогает. Вариант `osx` добавляется вместе с остальными; универсальную сборку проверяет workflow `mac-smoke.yml` на Mac с Apple Silicon и с Intel.

На ветке PR мейнтейнер при необходимости меняет `rollout`, запускает `cargo xtask index check updates/v1 --base origin/main`, `cargo xtask tuf update` и `cargo xtask tuf check --no-timestamp --base origin/main`, коммитит индексы вместе с `tuf/v1` и пушит. PR, открытый workflow, сам проверки не запускает, поэтому `index-check.yml` из `ci.yml` (`cargo xtask index check updates/v1 --base origin/main --vm-smoke --conformance`) срабатывает на этот пуш. После слияния `pages.yml` ещё раз проверяет индексы и публикует `updates/` и `tuf/v1` на GitHub Pages под `/updates/` и `/tuf/v1/`. Весь сайт Pages собирается в один артефакт, и остальные страницы сайта лежат в нём рядом с `updates/`.

Настройки репозитория меняет только мейнтейнер:

- Pages: Settings → Pages → Source: GitHub Actions;
- PR от workflow: Settings → Actions → General → Allow GitHub Actions to create and approve pull requests;
- неизменяемые релизы: Settings → General → Releases → Enable release immutability.

## Проверка на клиенте

`oncl_update` принимает индекс, только если выполнены все условия:

1. Цепочка TUF проверена целиком: корни, `timestamp`, `snapshot`, `targets`, цель с длиной и sha256. Правила и причины отказа описаны в [`tuf.md`](tuf.md).
2. Индекс не больше 1 МиБ.
3. Индекс разобран и соблюдает правила формата: схема 1, URL только `https://`, `rollout` не больше 100, версии не повторяются.
4. `channel` индекса совпадает с каналом клиента.
5. `seq` не меньше последнего принятого для этого канала. Тот же `seq` означает тот же индекс, скачанный повторно: так клиент может повторить обновление, которое не скачалось. Каждый новый индекс канала получает новый `seq`.

Правило «меньше 30 дней с `generated`» клиент не применяет: он отвергает метаданные с истёкшим сроком роли, а не индекс по возрасту. Метаданные TUF общие для обоих каналов. Срок `targets` продлевает подпись владельца (не реже раза в 30 дней). Пока снимок офлайн, владелец так же продлевает `snapshot`; после перевода снимка в CI его, как и `timestamp`, подписывает каждая публикация Pages на 7 дней ([`tuf.md`](tuf.md)).

JSON индекса разбирается только после проверки подписи и sha256.

## Выбор версии

`oncl_update::choose` выбирает версию ядра для установки. Версия предлагается, если выполнены все условия:

- она не отозвана;
- она не помечена локально как плохая, то есть не провалила проверку работоспособности на этой установке;
- в ней есть пакет для варианта сборки установки;
- установка попала в раскатку: бакет `sha256(install_id ‖ version)[0] * 100 / 256` меньше `rollout`.

`install_id` состоит из 16 случайных байт установки, `version` равна строке версии. У каждой версии свой бакет, поэтому первыми обновляются не всегда одни и те же установки.

Из предложенных версий берётся самая новая. Если она новее текущей, это обновление, иначе ничего не делается.

Если индекс отзывает текущую версию, уйти с неё важнее, чем соблюсти поэтапную раскатку. Тогда `rollout` не учитывается: берётся самая новая версия, которая не отозвана, не помечена как плохая и имеет пакет для варианта. Так установка на отозванной версии получает исправление, даже если оно раскатано не на всех (в том числе при `rollout: 0`). Если эта версия новее текущей, это обновление, если старше, откат. Только в этом случае клиент переходит на более старую версию.

Если текущая версия ядра в индексе вообще не упомянута (локальная сборка или версия, убранная из индекса), клиент на старую версию не откатывается.

Скачанный пакет сверяется с `size` и `sha256` из индекса (`Package::check_file`). Несовпавший пакет не применяется.

## Состояние клиента

Файл `<данные>/update/state.json` записывается атомарно:

```json
{
  "last_seq": {"stable": 7, "beta": 42},
  "install_id": "<32 hex>",
  "bad": ["0.2.0-beta.1"],
  "pending_health": {"from": "0.1.0", "to": "0.2.0", "applied": "2026-10-27T10:00:00Z", "started": "2026-10-27T10:00:20Z"}
}
```

| Поле | Смысл |
|---|---|
| `last_seq` | Последний принятый `seq` по каналам. |
| `install_id` | Случайный идентификатор установки, нужен только для бакета раскатки. Никуда не отправляется. |
| `bad` | Версии, которые на этой установке не прошли проверку работоспособности. Они больше не предлагаются. |
| `pending_health` | Обновление применено, но новая версия ещё не подтвердила, что работает; поле есть только в это время. `started` отмечает начало текущего запуска новой версии и стирается при чистом завершении. `crashes` считает запуски подряд, которые упали или зависли. `rollback: true` означает откат с версии, не прошедшей проверку. `attempts` считает, сколько раз откат передавался Velopack. |

Если файл повреждён и не читается как состояние, демон записывает вместо него новый, с новым `install_id` и без `last_seq`; обновления от этого не останавливаются. Если файл не читается по другой причине (нет прав, его держит другая программа), демон его не трогает. В этом запуске он не проверяет работоспособность и не откатывает версию, проверку обновлений повторяет через 30–120 минут, а изменение, которое не удалось сохранить, не применяет. Все записи в файл идут под одной блокировкой, и каждая перечитывает файл и меняет только своё поле.

## Обновление в демоне

Сам себя обновляет только экземпляр, установленный через Velopack и собранный с корнем доверия `crates/oncl-update/keys/root.json`. Корень встраивается при сборке, если файл есть. Без него, а также в архиве из Releases или в собственной сборке обновления выключены, о чём пишется в журнал и в окно настроек.

Настройки хранятся в `settings.json`: `"updates": {"enabled": true, "channel": "stable"}`, канал `stable` или `beta`. Если канал не записан, сборка предварительной версии (`-alpha.1`, `-rc.1`) читает `beta`, а релиз `stable`, потому что предварительные версии попадают только в `beta`. Записанный канал не меняется. В окне настроек есть флажок «Обновлять автоматически», выбор канала и кнопка «Проверить сейчас», в меню значка есть пункт «Проверить обновления».

Порядок работы:

1. Первая проверка идёт через 2–10 минут после запуска, следующие раз в 6–24 часа. Время каждый раз выбирается случайно.
2. Метаданные TUF и индекс канала скачиваются с `https://arynyklas.github.io/OpenNCALayer/tuf/v1/` через прокси из настроек и проверяются, как описано выше. Затем `choose` выбирает версию.
3. Если индекс не скачался, следующая попытка будет через 30–120 минут. Если индекс отвергнут, следующая попытка в обычный срок. Уведомлений в обоих случаях нет, ошибку видно в журнале и в окне настроек. Индекса канала может ещё не быть: клиент не принял ни одного `timestamp`, а репозиторий отвечает на него 404, или в принятых `targets` нет записи канала, потому что в канал ничего не выпускали. Тогда в окне настроек пишется «В канале пока нет выпусков», уведомления нет, следующая проверка в обычный срок. Ответ 404 после первой принятой публикации считается ошибкой проверки, повтор через 30–120 минут.
4. О новой версии демон сообщает уведомлением «Доступна версия X», один раз на версию.
5. Velopack получает фид из одной выбранной версии: полный пакет и дельту от текущей версии, если она есть в индексе. Файлы скачиваются только по HTTPS и перед передачей Velopack сверяются с `size` и `sha256` из индекса. Полный пакет, который Velopack собрал из дельты или нашёл на диске, принимается, только если он совпадает с полным пакетом индекса по `sha256` и размеру или содержит те же файлы (`contents_sha256`). Проверка идёт до того, как пакет встаёт на место и из него извлекается `Update.exe`. Пакет с диска, не прошедший проверку, удаляется и скачивается заново, а собранный из дельты заменяется скачанным полным пакетом. Для этого Velopack собирается из нашего форка (см. `docs/dev/development.md`, «Форки сторонних крейтов»).
6. Демон ждёт, пока не останется открытых окон и запросов от страниц в работе, и ещё 30 секунд после последнего запроса. Затем индекс проверяется ещё раз: если версию за это время отозвали или обновления выключили, она не ставится. Новые запросы от страниц задерживаются до выхода демона.
7. В состояние записывается `pending_health`. Velopack ставит новую версию после выхода демона и запускает её с теми же аргументами.

Проверка работоспособности:

- Новая версия при каждом запуске записывает в `pending_health` время `started`. Проверка идёт в отдельном потоке и от цикла окон не зависит.
- Если серверы и цикл окон новой версии проработали 5 секунд подряд, она удаляет `pending_health` и показывает «Обновлено до X».
- Если этого не случилось за 60 секунд после запуска, версия считается плохой. Она попадает в `bad`, а демон, дождавшись простоя, ставит предыдущую версию из её полного пакета в индексе.
- Чистое завершение до подтверждения сбоем не считается. Чистое завершение означает «Выход» в меню значка, остановку демона для обновления или выход с кодом 2 или 3 (TLS не настроен, порт занят). При нём `started` стирается, а счётчик `crashes` обнуляется.
- Учёт запусков начинается сразу после проверки, что демон запущен в единственном экземпляре, ещё до проверки TLS и порта. Поэтому запуск, который упал при настройке или вышел с кодом 1, тоже считается сбоем.
- Обработчика завершения сеанса (выход из системы, выключение) нет. Если сеанс закончился, пока новая версия ещё не подтвердила работоспособность (обычно первые 5–7 секунд запуска), этот запуск считается сбоем. Два таких запуска подряд без подтверждённого запуска между ними откатят исправную версию и отметят её в `bad` на этой машине; следующие версии предлагаются как обычно.
- Если при запуске `started` ещё записан, прошлый запуск упал или завис, и `crashes` растёт на 1. После двух таких запусков подряд версия попадает в `bad`, и откат делается сразу, до запуска серверов и окон. Один сбой, после которого версия проработала нормально, к откату не ведёт.
- Предыдущая версия после запуска показывает «Обновление откачено».
- Если Velopack не применил откат и снова запустил плохую версию, откат повторяется, но не больше трёх раз. Если Velopack сразу отказался применять откат, повторов нет. В обоих случаях плохая версия остаётся в `bad` и продолжает работать, демон один раз сообщает «Версия X работает с ошибками», обычные проверки продолжаются.
- Если индекс не скачался, пакет не загрузился или скачанный пакет пропал до передачи Velopack (его может удалить очистка Velopack при другом запуске программы), откат повторяется через 30–120 минут, тоже не больше трёх раз. Этот счётчик действует в пределах одного запуска. Пока откат не отменён, следующий запуск плохой версии снова пробует его скачать до начала работы и только потом возвращается к этому расписанию. Если за запуск все три попытки не удались, откат отменяется так же, как при отказе Velopack: плохая версия остаётся в `bad`, демон один раз сообщает «Версия X работает с ошибками», и следующие запуски откат уже не скачивают. При запуске плохой версии на скачивание индекса и пакета отводится не больше 15 секунд. После этого демон запускается как обычно, а откат повторяется в фоне с обычным временем на загрузку.
- Неудавшийся цикл окон не считается чистым завершением, даже если демон выходит с кодом 2 или 3.
- Если в индексе нет пакета предыдущей версии, плохая версия остаётся в `bad`, а демон один раз сообщает об этом. Обычные проверки продолжаются, и исправленная версия установится, когда выйдет.
- Если предыдущая версия тоже в `bad`, отката нет.
