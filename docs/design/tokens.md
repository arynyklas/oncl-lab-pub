# Аппаратные токены и удостоверение личности

Поддержка экспериментальная и по умолчанию выключена. OpenNCALayer читает ключи и подписывает на PC/SC-носителях шести семейств, которые поддерживает Kalkan. Ни один драйвер не проверялся на настоящем носителе, каждый проверен только на программном эмуляторе своего семейства (крейт `oncl-token`, фича `emulator`). Байты команд повторяют документированные форматы семейств. Где формат ответа выведен, а не наблюдался, в коде стоит пометка `// Unverified on hardware: …`, а у каждого драйвера `HARDWARE_VERIFIED = false`.

Поддержка включается флажком «Токены и удостоверение личности (экспериментально)» в окне «Настройки…» (в `settings.json` ключ `"tokens": {"enabled": true}`). Флажок действует сразу, без перезапуска, для модулей `basics`, `commonUtils`, `Applet` и для плагинов. Ключи носителей, открытые к этому моменту (например, у плагина до `keys_release`), после выключения не подписывают и не подключаются к носителю.

## Семейства

| Хранилище | Носитель | Алгоритмы | ATR | Счётчик попыток PIN | Эмулятор | Железо |
|---|---|---|---|---|---|---|
| `AKKaztokenStore` | Kaztoken | ГОСТ 34.310-2004, ГОСТ 34.10-2015 512, RSA | 3 | да | да | нет |
| `AKKZIDCardStore` | удостоверение личности РК | ГОСТ 34.10-2015 512, RSA | 7 | да | да | нет |
| `AKEToken72KStore` | eToken PRO 72K | ГОСТ 34.310-2004, RSA | 1 | нет | да | нет |
| `AKEToken5110Store` | eToken 5110 | ГОСТ 34.310-2004, ГОСТ 34.10-2015 512, RSA | 2 | нет | да | нет |
| `AKJaCartaStore` | JaCarta | ГОСТ 34.310-2004, RSA (под T=0 без RSA) | 1 | нет | да | нет |
| `AKAKEYStore` | AKey | ГОСТ 34.310-2004, ГОСТ 34.10-2015 512, RSA | 4 | да | да | нет |

Семейство носителя определяется по точному совпадению ATR. PIN удостоверения состоит ровно из 4 ASCII-символов, PIN с не-ASCII символами отклоняется до первой команды носителю. Облачное хранилище `ABCloudServiceStore` не поддерживается.

## Что поддерживается

- Список подключённых носителей: `getActiveTokens` (commonUtils), `loadSlotList` (Applet), выбор считывателя в `browseKeyStore`, `keys_terminals` плагинов.
- Окно хранилища (`basics` `sign`, ключи плагинов `keys_choose`/`keys_select`, commonUtils, Applet `signXml`): строки токенов, выпадающий список считывателей с кнопкой «Обновить», поле PIN-кода. При неверном PIN выводится «Неверный PIN-код. Осталось попыток: N» (если носитель сообщает число), для заблокированного PIN есть отдельное сообщение.
- Данные удостоверения без PIN: `getPublicPartInfo` (Applet) возвращает `IIN<ИИН> <ФИО>`.
- Подпись CMS и CAdES, XMLDSig и «сырая» подпись плагинов в тех же форматах, что у ключей из файлов (ГОСТ как `r‖s` в порядке Kalkan, RSA как PKCS#1 v1.5). Подпись носителя проверяется открытым ключом сертификата, прежде чем уйти странице, поэтому неверная подпись превращается в ошибку и не попадает на сайт.
- `keys_open` плагинов с `terminal`: токен в указанном считывателе с PIN-кодом от плагина, без окна.

## Что не поддерживается

Запись на носитель: генерация ключей (`genKeyPairAndGetPKCS10`, `generateCsr`), запись сертификата (`setX509CertToKeyStore…`, `importCertificate`), удаление ключа (`deleteEntry`), форматирование (`resetStorage`), смена PIN (`changePassword`). Ошибка при записи на непроверенное железо необратима: можно перезаписать каталог ключей Kaztoken, занять запасной ключ удостоверения или отформатировать eToken. Поэтому при подключённом носителе этого семейства такие вызовы возвращают общий код ошибки оригинала (`GENKEY_COMMON`, `SETCERT_COMMON`, `COMMON`, `CHANGEPASS_COMMON`), не отправив носителю ни одной команды. Без носителя коды ответа не меняются.

## PC/SC по ОС

| ОС | Служба | Как подключается |
|---|---|---|
| Windows | «Смарт-карта» (SCardSvr) | `winscard.dll`: `SCardEstablishContext`, `SCardReleaseContext`, `SCardListReadersW`, `SCardGetStatusChangeW`, `SCardConnectW`, `SCardBeginTransaction`, `SCardEndTransaction`, `SCardTransmit`, `SCardDisconnect` — все есть в Windows 7 |
| macOS | системная | `PCSC.framework` |
| Linux | `pcscd` (пакеты `pcsc-lite` и `ccid` для USB-считывателей) | `libpcsclite.so.1` открывается во время работы (dlopen); бинарник от неё не зависит и запускается без неё |

Без службы (Linux без `libpcsclite.so.1` или без `pcscd`, остановленная служба Windows) демон работает как обычно: `getActiveTokens` возвращает `[]`, `loadSlotList` возвращает `EMPTY_SLOT`, окно хранилища пишет «Служба смарт-карт недоступна» с подсказкой для своей ОС. Считыватели опрашиваются только по запросу: при открытии окна, по кнопке «Обновить» и при каждом вызове API. Фонового опроса нет.

## PIN

- PIN хранится только в памяти демона (`Zeroizing`: память обнуляется при освобождении) и никогда не пишется в журнал.
- Каждая операция выполняется отдельной транзакцией: подключение, выбор апплета и сверка серийного номера носителя (если вставлена другая карта, будет ошибка), проверка PIN, команды, выход, отключение. Операция, которая отправила PIN, отключается со сбросом карты, иначе проверенный PIN оставался бы в силе для всех программ, пока карту не сбросят или не вынут. Так же отключается операция, открывшая сеанс AKey. Сеанс закрывается, даже если операция оборвалась до входа (вставлен другой носитель, ошибка чтения). Сброс ждёт, пока другое подключение закончит свою транзакцию. Операции без PIN (список носителей, `getPublicPartInfo`) карту не сбрасывают, чтобы не обрывать подключения других программ и параллельные операции. Если свежее подключение уже сброшено кем-то другим (до первой команды), операция один раз подключается заново.
- `getPublicPartInfo` сначала смотрит ATR карты в списке считывателей и подключается, только если это удостоверение личности. Другие носители он не трогает.
- Ключ, открытый в окне или через `keys_open`, держит PIN до конца операции (у плагинов до `keys_release` или конца экземпляра). Если носитель отверг PIN, ни один ключ, открытый тем же вызовом, больше его не отправляет, чтобы повторные подписи не тратили попытки. Один вызов тратит не больше одной попытки.

### PIN от страницы

PIN, который пользователь ввёл в окне хранилища, уходит носителю как есть. PIN от страницы (у плагина это `keys_open` с `terminal` и паролем `text`) отправляется носителю только с согласия пользователя, чтобы сайт не мог потратить попытки или заблокировать носитель без единого щелчка:

- окно ядра называет сайт, плагин, носитель и считыватель, а если носитель сообщает попытки (Kaztoken, удостоверение личности, AKey), то и число оставшихся. Попытки читаются до отправки PIN и не расходуются (Kaztoken и удостоверение отвечают на `VERIFY` без данных, AKey на запрос сведений о носителе);
- согласие даётся один раз для сайта и считывателя в экземпляре плагина, то есть в сессии. Когда осталось две попытки или меньше, окно появляется перед каждым таким PIN;
- после неверного PIN согласие для этого считывателя снимается, и следующий PIN снова требует окна. Сам демон PIN не повторяет;
- при отказе или закрытии окна возвращается `declined` (порты отвечают на него своей ошибкой или отменой), носителю ничего не отправляется. Для PIN без оставшихся попыток (`blocked`) и PIN, который носитель не примет, окно не открывается и ничего не отправляется;
- PIN, введённый пользователем в окне `dialog_password`, уходит без вопроса, но если носитель его отверг, повторная отправка того же пароля тоже требует согласия.

Applet не передаёт носителю пароль или PIN от страницы. Такие пароли получают только его методы записи на носитель, а они отклоняются без команд носителю. Встроенные модули basics и commonUtils спрашивают PIN только в своём окне.

## Что видят сайты без запроса

Как и оригинальный NCALayer, демон отвечает без окна на `getActiveTokens`, `loadSlotList` и `getPublicPartInfo`. Пока поддержка включена, любой сайт, открытый в браузере, может узнать, какие носители подключены, и прочитать **ИИН и ФИО** владельца вставленного удостоверения личности. В Linux имена считывателей из `loadSlotList` и `keys_terminals` (плагины) могут содержать серийный номер USB-носителя (его добавляет к имени `pcscd`), и по нему сайт может узнать конкретный носитель. Это одна из причин, почему поддержка выключена по умолчанию. Подписать что-либо сайт может только с PIN-кодом: встроенные модули спрашивают его в окне хранилища, а PIN, который плагин с возможностью `keys` получает от страницы, уходит носителю только после окна согласия ([«PIN от страницы»](#pin-от-страницы)).

## Эмулятор

Фича `emulator` крейта `oncl-token` (в демоне фича `token-emulator`) добавляет программные носители всех шести семейств: синтетические ключи из `fixtures/synthetic`, ответы ровно на те команды, которые шлют драйверы, счётчики попыток, извлечение карты посреди операции и режим «перепутанные половины подписи». Эти фичи не входят ни в одну релизную сборку.

Демон, собранный с `--features e2e-prompter,token-emulator`, при `ONCL_TOKEN_EMULATOR=<config.toml>` берёт носители из файла вместо службы смарт-карт и включает поддержку токенов. Формат файла (пути ключей указываются относительно каталога файла):

```toml
[[reader]]
name = "OpenNCALayer Emulated Kaztoken 0"
kind = "AKKaztokenStore"        # имя хранилища; без kind — пустой считыватель
pin = "123456"
tries = 10                      # необязательно
protocol = "T1"                 # необязательно: "T0" или "T1"
keys = [{ p12 = "fixtures/synthetic/user-gost2015-sign.p12", password = "Qwerty12" }]
# только для AKKZIDCardStore:
id_card = { iin = "123456789012", last_name = "ТЕСТОВ", first_name = "ТЕСТ", middle_name = "ТЕСТОВИЧ" }
```

Также необязательны `serial` (16 шестнадцатеричных цифр), `atr_index` и `fixed_k` (nonce ГОСТ в hex, чтобы подписи совпадали с программными). Пример лежит в `crates/openncalayer/tests/data/tokens.toml`.

Тесты commonUtils подписывают на эмулированном Kaztoken от начала до конца (`getActiveTokens`, `getKeyInfo`, неверный и верный PIN, CAdES с цепочкой до синтетического корня, метка времени, XML). Модулю там передаются синтетические корневые сертификаты (`with_cas`). Через сам демон по `wss` этот путь не проверяется: демон доверяет только CA НУЦ, подложить ему тестовые корни нельзя, а commonUtils отклоняет ключ с другой цепочкой, одинаково для носителя и для файла. По `wss` эмулятор проверяется на `getActiveTokens`, `loadSlotList`, `getPublicPartInfo` и подписи `basics`, которой цепочка НУЦ не нужна.

Настоящий PC/SC-бэкенд Linux проверяется в CI (job `tokens-vpcd`). Команда `cargo xtask token-emu --config <toml> [--vpcd host:port]` отдаёт эмулированную карту виртуальному считывателю `vpcd` из vsmartcard (это инструмент CI, он не линкуется и не поставляется), и `pcscd` видит её как настоящую.

## Трассировка для сообщений о проблемах

`ONCL_TOKEN_TRACE=1` в окружении демона пишет в журнал каждую команду носителю: заголовок, длину и данные команды, слово состояния и длину ответа. Данные команд проверки PIN и входа заменяются на `<redacted N bytes>`, данные ответов не пишутся, поэтому серийный номер носителя (он приходит в ответе) в трассировку не попадает. При этом в журнал попадают пути к файлам и имена объектов носителя (в командах выбора), а имя считывателя в Linux может содержать серийный номер USB-носителя. Поэтому журнал с трассировкой стоит просмотреть, прежде чем прикладывать к сообщению.

При запуске демон пишет в журнал одну строку о токенах: включена ли поддержка и доступна ли служба смарт-карт.
